> **सत्याचा अधिकृत स्रोत:** `src/lib/guardrails/`
> **शेवटचे अद्यतन:** 2026-08-29 — v3.8.51 (Video Bridge प्रतिलेखाचा उगम कॉलरद्वारे घोषित केला जातो,
> अद्याप सर्व्हरद्वारे सत्यापित केलेला नाही — #11661 नुसार स्पष्टीकरण दिले)

Guardrails, OmniRoute आणि अपस्ट्रीम प्रदात्यांच्या सीमेवर सुरक्षितता, धोरणे आणि आशय रूपांतरे लागू करतात. प्रत्येक guardrail विनंती payloads (`preCall`) आणि अपस्ट्रीम प्रतिसाद (`postCall`) तपासू शकतो (आणि पर्यायाने नाकारू, रूपांतरित करू किंवा त्यांवर भाष्य नोंदवू शकतो).

प्रणाली **fail-open** आहे: एखाद्या guardrail च्या अंमलबजावणीदरम्यान अपवाद निर्माण झाल्यास, विनंती अयशस्वी करण्याऐवजी registry त्रुटीची नोंद करून पुढील guardrail वर प्रक्रिया सुरू ठेवते. अवरोधित करणे हा नेहमी स्पष्ट निर्णय (`block: true`) असतो, अपघाताने ते कधीही होत नाही.

## अंगभूत सुरक्षात्मक उपाय

इम्पोर्ट केल्यावर रजिस्ट्री प्राधान्यक्रमानुसार सहा सुरक्षात्मक उपाय आपोआप लोड करते
(`registry.ts` → `registerDefaultGuardrails()` पाहा):

| प्राधान्यक्रम | नाव                 | टप्पा/टप्पे    | फाइल                  |
| ------------- | ------------------- | -------------- | --------------------- |
| `5`           | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`           | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`           | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`          | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`          | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`          | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

कमी प्राधान्यक्रमांक असलेले उपाय **प्रथम** चालतात.

### व्हिजन ब्रिज (`visionBridge.ts`) — मोडॅलिटी ब्रिज PR-1

**व्हिजनला समर्थन न देणाऱ्या मॉडेल्सना** उद्देशून केलेल्या आणि प्रतिमा असलेल्या विनंत्या अडवतो आणि एकतर
संपूर्ण विनंती व्हिजन-सक्षम मॉडेलकडे पुनर्मार्गित करतो किंवा
अपस्ट्रीम कॉलपूर्वी, कॉन्फिगर करता येणाऱ्या व्हिजन मॉडेलने तयार केलेल्या मजकूर वर्णनांनी प्रतिमेचे
भाग बदलतो. यामुळे केवळ-मजकूर प्रदाते मल्टिमोडल पेलोड्स पारदर्शकपणे हाताळू
शकतात.

प्रवाह:

1. लक्ष्य मॉडेल आधीच व्हिजनला समर्थन देत असल्यास वगळा (ते
   सक्तीच्या-ब्रिज सूची `isVisionBridgeForcedModel` मध्ये दिसत नसल्यास).
2. `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) द्वारे प्रतिमेचे भाग एक्स्ट्रॅक्ट करा; हे
   `open-sse/utils/mediaParts.ts` मधील **एकत्रित मीडिया
   डिटेक्टर** `detectMediaParts()` कडे काम सोपवते — कॉम्बो सुसंगतता फिल्टरसह
   सामायिक केलेला सत्याचा एकमेव स्रोत.
   एक्स्ट्रॅक्शन फक्त अशा उच्च-स्तरीय भागांच्या आकारांपुरते अनुमतीसूचीबद्ध आहे,
   जे `replaceImageParts` पुन्हा जोडू शकते (एक्स्ट्रॅक्ट↔रिप्लेस करार): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, आणि Responses API `input_image`. नेस्टेड जुळण्या आणि
   केवळ-सूचक आकार हे कॉम्बो-फिल्टरचे घटक आहेत आणि ते कधीही एक्स्ट्रॅक्ट केले जात नाहीत.
   काहीही सापडले नाही तर वगळा.
3. `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) द्वारे रनटाइम कॉन्फिग ठरवा: नवीन `modalityBridge*`
   सेटिंग्ज कीजना प्राधान्य मिळते; लेगसी `visionBridge*` कीज **एका-सायकलच्या
   फॉलबॅक** म्हणून कायम राहतात (रोलबॅक विंडो). ब्रिज अक्षम असल्यास कोणतेही मीडिया ट्रॅव्हर्सल करण्यापूर्वी वगळा.
4. मोड सिलेक्टर (`modalityBridgeVisionMode`, खालील तक्ता पाहा) पुनर्मार्गीकरण
   की वर्णन हे ठरवतो. पुनर्मार्गीकरण केवळ `model`
   बदललेला `modifiedPayload`, तसेच मेटा `{ rerouted, fromModel, toModel, imagesKept }` परत करते.
5. वर्णनाचा मार्ग: प्रतिमांची संख्या `maxImages` पर्यंत मर्यादित करा, कार्य-जागरूक प्रॉम्प्ट तयार करा,
   वर्णन कॅश तपासा, व्हिजन मॉडेलला **समांतरपणे**
   (`Promise.allSettled`) कॉल करा आणि त्यांच्या जागी `[Image N]: <description>` मजकूर भाग
   घाला. वर्णन अयशस्वी झाल्यास `null` मिळते आणि मूळ प्रतिमा भाग
   **जतन केला जातो** (#4012) — मात्र कॉम्बो वर्णन मार्गावर सर्व
   वर्णने अयशस्वी झाल्यास, पुष्टी झालेल्या व्हिजनला समर्थन न देणाऱ्या अपस्ट्रीमला त्याऐवजी
   `(unavailable — no vision-capable provider connected)` स्टब मिळतो (#8430).
6. `modifiedPayload` + मेटा (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) परत करा.

#### मोड सिलेक्टर (`modalityBridgeVisionMode`)

| मोड        | डीफॉल्ट | वर्तन                                                                                                                                                                                                                                                                                                                     |
| ---------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | लेगसी ह्युरिस्टिक, अपरिवर्तित (#6640/#7204): मूळ मॉडेलकडे आधीच वापरण्यायोग्य क्रेडेन्शियल्स नसल्यास नॉन-कॉम्बो/`auto/` मॉडेल्स सर्वोत्तम व्हिजन मॉडेलकडे पुनर्मार्गित होतात (अन्यथा वर्णन करतात); कॉम्बो लक्ष्ये नेहमी वर्णन करतात.                                                                                       |
| `describe` |         | नेहमी वर्णन करा — पुनर्मार्गीकरण ब्लॉक पूर्णपणे वगळला जातो; वापरकर्त्याने निवडलेले मॉडेल नेहमी उत्तर देते.                                                                                                                                                                                                                |
| `reroute`  |         | सक्तीने पुनर्मार्गीकरण करा: क्रेडेन्शियल्स असलेले मॉडेल कायम ठेवणारा गार्ड बायपास केला जातो. पुनर्मार्गीकरण-**लक्ष्यावरील** क्रेडेन्शियल गार्ड मात्र अजूनही लागू होतो — वापरण्यायोग्य व्हिजन लक्ष्य उपलब्ध नसल्यास, विनंती वर्णनाकडे जाते, जेणेकरून कच्च्या प्रतिमा केवळ-मजकूर बॅकएंडपर्यंत कधीही पोहोचणार नाहीत (#8430). |

सक्तीचे मोड `auto` ह्युरिस्टिक चालण्यापूर्वीच **शॉर्ट-सर्किट** होतात; `auto` चे वर्तन
PR-1 पूर्वीच्या सुरक्षात्मक उपायाशी बाइट-स्तरावर एकसारखे आहे.

#### API-कीची व्याप्ती (`visionBridgeKeyScope.ts`)

कॉलरची API की `allowedConnections`, कोटा पूल्स
(`allowedQuotas`) किंवा मॉडेल्स (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) मर्यादित करत असल्यास, ब्रिज फक्त
त्या कीला वापरण्याची परवानगी असलेली पुनर्मार्गीकरण आणि वर्णन मॉडेल्स, तसेच ती की वापरू शकणाऱ्या कनेक्शन्सवरील मॉडेल्स
निवडतो. त्यानंतर वर्णन कॉल नेहमी
`x-omniroute-self-loop-key-id` हेडरसह OmniRoute सेल्फ-लूपमधून जातो, त्यामुळे प्राप्त होणारी चॅट विनंती
त्या कीचे कनेक्शन आणि मॉडेल धोरण पुन्हा लागू करते. `enforceApiKeyPolicy()`
त्या हेडरचा आदर केवळ सेल्फ-लूप बेअररसहच करते, त्यामुळे तो फक्त
प्रवेश आणखी मर्यादित करू शकतो आणि रिझॉल्व्ह न होणारा आयडी नाकारला जातो.

कीसाठी कोणत्याही व्हिजन मॉडेलला परवानगी नसल्यास, वर्णनाचा मार्ग बाजूला होतो आणि
विनंती कोणताही बदल न करता पुढे जाते; हे अक्षम केलेल्या
सुरक्षात्मक उपायासारखेच फेल-ओपन वर्तन आहे (मेटा `{ skipped: true, reason: "no_permitted_vision_model" }`).
की नसलेल्या विनंत्या आणि हे निर्बंध नसलेल्या कीज पूर्वीप्रमाणेच
वागतात.

#### कार्य-जागरूक वर्णन प्रॉम्प्ट (`modalityBridgeVisionTaskAware`)

डीफॉल्ट **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) बेस
वर्णन प्रॉम्प्टला **शेवटच्या वापरकर्ता संदेशाचा** मजकूर (500 वर्णांपर्यंत संक्षिप्त केलेला)
जोडते, ज्यामुळे वर्णन वापरकर्त्याने प्रत्यक्षात काय विचारले त्यानुसार निर्देशित होते
(codex-vision-proxy नमुना) आणि व्हिजन मॉडेलला दृश्यमान मजकूर लिप्यंतरित करण्यास सांगितले
जाते. फ्लॅग बंद असल्यास — किंवा वापरकर्ता मजकूर नसल्यास — बेस प्रॉम्प्ट कोणत्याही बदलाशिवाय वापरला जातो.

वर्णन सेल्फ-लूपची स्वतःची OpenAI-सुसंगत विनंती (`callVisionModelSingle()`
`visionBridgeHelpers.ts` मध्ये) नेहमी `image_url.detail: "high"` ची विनंती करते —
कोणत्याही क्लायंट सिग्नलवर अवलंबून न राहता, प्रत्येक कॉलर/प्रदात्यासाठी बिनशर्त.
हा प्रॉम्प्ट ज्या मजकूर-लिप्यंतरण कार्याची मागणी करतो, त्यासाठी कमी-तपशील सॅम्पलिंगमुळे
OCR अचूकता कमी होते, म्हणून मूळ इनबाउंड विनंतीने कोणती तपशील पातळी वापरली याची पर्वा
न करता वर्णन कॉल स्वतः नेहमी उच्च तपशीलाची मागणी करतो. याचा परिणाम फक्त अंतर्गत
वर्णन विनंतीच्या बॉडीवर होतो; प्राथमिक विनंतीवर OmniRoute कॉलरचे स्वतःचे
`image_url.detail` कसे फॉरवर्ड करते, हे त्यामुळे बदलत नाही — तो डीफॉल्ट स्वतंत्रपणे
आणि फक्त शोधलेल्या OpenCode क्लायंटसाठी `defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`) मध्ये लागू केला जातो. वर्णन सेल्फ-लूपच्या
Anthropic वायर-फॉरमॅट शाखेत `detail` फील्ड नाही आणि ती या दोन्ही डीफॉल्टमुळे
प्रभावित होत नाही.

#### वर्णन आउटपुट मर्यादा (`modalityBridgeVisionMaxChars`)

| की                             | डीफॉल्ट | श्रेणी              |
| ------------------------------ | ------- | ------------------- |
| `modalityBridgeVisionMaxChars` | `0`     | `0` किंवा 100–50000 |

`0` (डीफॉल्ट) म्हणजे **कोणतीही मर्यादा नाही** — `callVisionModel()` ने परत केलेले
वर्णन कोणताही बदल न करता पुढे पाठवले जाते, ज्यामुळे विद्यमान वर्तन कायम राहते.
100–50000 श्रेणीतील कोणतेही मूल्य वर्णन पुन्हा
`[Image N]: <description>` म्हणून जोडण्यापूर्वी `…` प्रत्ययासह संक्षिप्त करते
(`src/lib/guardrails/visionBridge.ts` मधील `VisionBridgeGuardrail.preCall()`).
ज्या तपशील-केंद्रित OCR कार्यांसाठी डाउनस्ट्रीम मॉडेलला संपूर्ण लिप्यंतरण आवश्यक आहे,
त्यांच्यासाठी हे मूल्य वाढवा; अधिक मजकूर निर्माण करणाऱ्या व्हिजन मॉडेल्सचा टोकन वापर
मर्यादित करण्यासाठी ते कमी करा. डॅशबोर्ड फील्ड Vision टॅबच्या Advanced पॅनेलमध्ये
आहे (`ModalityBridgeVisionTab.tsx` मधील `modality-bridge-max-chars`) आणि स्पष्टपणे
दिलेल्या `0` ला न बदलता 1 ते 99 मधील कोणतेही मूल्य किमान 100 पर्यंत वाढवते —
`0` हे केवळ "सेट न केलेले" डीफॉल्ट नसून स्वतःच एक वैध Zod मूल्य आहे
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`).

#### वर्णन कॅशे (`modalityBridge/bridgeCache.ts`)

वर्णन आउटपुटसाठी इन-मेमरी LRU + TTL कॅशे, जी संपूर्ण प्रोसेसमध्ये सामायिक केली जाते.
की = `sha256(imageRef + composedPrompt + configuredBridgeModel)` आणि त्यासोबत
लांबी-उपसर्ग फ्रेमिंग (फील्ड-सीमा टक्कर नाही). मॉडेल घटक हे प्रत्यक्षात प्रतिसाद
देणारे मॉडेल नसून **कॉन्फिगर केलेले** ब्रिज मॉडेल आहे —
`callVisionModel` अंतर्गत फॉलबॅक करू शकते आणि प्रत्येक प्रयत्नानुसार की तयार केल्यास
कॅशेचे तुकडे होतील. अयशस्वी वर्णने कधीही कॅशे केली जात नाहीत. सेटिंग्ज:

| की                              | डीफॉल्ट | श्रेणी  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### रिमोट प्रतिमा सामान्यीकरण (सेल्फ-लूप वर्णन/base64 फेच)

ब्रिज जेव्हा स्वतः **रिमोट** प्रतिमा फेच करतो — Anthropic वर्णन सेल्फ-कॉल आणि
claude-वायर-फॉरमॅट base64 रूपांतरण (`ensureBase64ImagesForClaudeWire`), दोन्ही
`visionBridgeHelpers.ts` मधील `fetchRemoteImageAsDataUri()` द्वारे — तेव्हा परिणामी
डेटा URI व्हिजन-मॉडेल विनंतीमध्ये एम्बेड करण्यापूर्वी `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) मधून पाठवला जातो. अतिमोठ्या प्रतिमांची
**2048px दीर्घ कडा** इतकी आकार-कपात केली जाते (OpenAI/Anthropic आधीच सर्व्हर-साइड
लागू करत असलेल्या आकार-मर्यादेशी जुळणारी), ज्यामुळे व्हिजन मॉडेलला दिसणाऱ्या गोष्टीत
बदल न करता अपलोड बाइट्स/विलंब कमी होतो. आकार बदलण्यासाठी डायनॅमिक इम्पोर्टद्वारे
लोड केलेले `sharp` वापरले जाते: ज्या प्लॅटफॉर्मवर त्याची नेटिव्ह बायनरी लोड होण्यात
अपयशी ठरते, तेथे `normalizeDataUri()` **कधीही अपवाद फेकत नाही** — ते मूळ बाइट्स
जसेच्या तसे पुढे पाठवण्यावर फॉलबॅक करते, त्यामुळे वर्णन/base64-रूपांतरण मार्ग नेहमी
कार्यरत राहतो. प्रतिमा नसलेले बाइट्स (डिकोड करता येणारी प्रतिमा न परतवणारा फेच)
देखील कोणताही बदल न करता पुढे पाठवले जातात. हे सामान्यीकरण ब्रिजने स्वतःच्या
सेल्फ-कॉलसाठी फेच केलेल्या प्रतिमांपुरते मर्यादित आहे — ते कॉलरच्या रॉ पासथ्रू
पेलोडवर कधीही लागू केले जात नाही, जे केवळ स्पष्ट संमतीने बदल करण्याच्या तत्त्वाशी
(Hard Rule #20) सुसंगत आहे.

#### पारदर्शकता हेडर + आकडेवारी

वर्णन-रूपांतरित प्रतिसादांमध्ये
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
समाविष्ट असतो (`modalityBridge/bridgeStats.ts` मधील
`buildModalityBridgeHeader()` द्वारे तयार केलेला,
`src/sse/handlers/chatHelpers.ts` मधील `withModalityBridgeHeader()` द्वारे जोडलेला).
पुनर्मार्गित विनंत्यांना **कोणताही** हेडर मिळत नाही — पेलोड बदललेला नव्हता आणि
मॉडेलची अदलाबदल प्रतिसाद बॉडीच्या `model` फील्डमध्ये आधीच दिसते.

`GET /api/modality-bridge/stats` (व्यवस्थापन प्रमाणीकरण, `GET /api/settings` च्याच
स्तरावरील) `vision`, `audio`, आणि `video` साठी इन-मेमरी, प्रति-मोडॅलिटी काउंटर
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` परत करते.
`averageLatencyMs` त्याचा भाजक म्हणून सर्व प्रयत्नांऐवजी `latencySamples` वापरते;
वेळमापन नसलेले ऑपरेशन शून्य-मिलिसेकंदाचा कृत्रिम नमुना तयार करत नाही.
यशस्वी रूपांतरणांसाठी `bridged` हा मागील आवृत्त्यांशी सुसंगत उपनाम म्हणून कायम
राहतो; अयशस्वी प्रयत्नांमुळे त्यात वाढ होत नाही.
प्रक्रिया रीस्टार्ट झाल्यावर काउंटर डिझाइननुसार रीसेट होतात
(टेलिमेट्री, लेखांकन नव्हे).

#### डॅशबोर्ड कॉन्फिगरेशन

समर्पित डॅशबोर्ड पृष्ठ
`/dashboard/settings/modality-bridge` आहे. त्याचे URL-द्वारे वापरता येणारे `Vision`, `Audio`,
आणि `Video` टॅब `tab` मूल्य बदलताना क्वेरी पॅरामीटर्स जतन करतात.
Vision टॅब सक्षम करणे, मोड, मॉडेल निवड (स्वयंचलित
डीफॉल्टसह), कार्य-जागरूक प्रॉम्प्टिंग, प्रगत टाइमआउट/प्रतिमा/वर्णन-लांबी/कॅशे
मर्यादा, रनटाइम
काउंटर आणि संरक्षित नमुना विनंती उपलब्ध करून देतो. Audio टॅबदेखील सक्रिय आहे: तो
सक्षम करणे, Auto सह केवळ-STT मॉडेल निवडक, टाइमआउट/कमाल-क्लिप मर्यादा, ऑडिओ
काउंटर आणि `input_audio` नमुना चाचणी उपलब्ध करून देतो. Video टॅब कार्यरत आहे: तो
FFmpeg/ffprobe रनटाइम स्थिती नोंदवतो — चार स्पष्ट UI स्थितींपैकी एक (`unknown`,
प्रोब सुरू असताना किंवा पूर्ण होऊ शकला नसताना; नॉन-लूपबॅक
डॅशबोर्ड होस्टवर, जिथे क्लायंट-साइडवर प्रोब वगळला जातो, तेथे `restricted`;
प्रोब झाल्यानंतर अनुपलब्ध असल्याची पुष्टी झाल्यावर `unavailable`; किंवा
FFmpeg/ffprobe आवृत्त्यांसह `available`) — सक्षम/मॉडेल/फ्रेम/व्हिडिओ/टाइमआउट
मर्यादा कायमस्वरूपी जतन करतो, मॉडेल निवडकाला व्हिजन-सक्षम
मॉडेल्सपुरते फिल्टर करतो आणि व्हिडिओ काउंटर उपलब्ध करून देतो.

AI सेटिंग्जअंतर्गत असलेले पूर्वीचे Vision Bridge कार्ड आता नवीन पृष्ठाची
सुसंगतता लिंक आहे; ते यापुढे फॉर्मची दुसरी प्रत स्वतःकडे ठेवत नाही. Media Providers
देखील विद्यमान Speech-to-Text प्लेग्राउंड न काढता Image-to-Text आणि
Speech-to-Text कार्यप्रवाहांना संबंधित Modality Bridge टॅबशी जोडते.

**सेल्फ-लूप प्रवेश बायपास:** describe कॉल OmniRoute च्या स्वतःच्या
`/v1` सेल्फ-लूपमधून (नॉन-स्टँडर्ड प्रदाता मॉडेल) रूट केला जातो तेव्हा, उप-विनंती
`x-omniroute-admission-bypass: internal` पाठवते आणि निराकरण केलेल्या
सेल्फ-लूप क्रेडेन्शियलने प्रमाणीकृत केली जाते — स्थानिक मोडमध्ये स्थानिक
`sk_omniroute` सेंटिनेल, किंवा ऑपरेटरने कॉन्फिगर केलेली
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env की (#1350), जेणेकरून
`REQUIRE_API_KEY=true` डिप्लॉयमेंट्स अजूनही describe कॉल चालवू शकतील. बायपास
केवळ याच अचूक क्रेडेन्शियल्ससाठी मान्य केला जातो, त्यामुळे बाह्य क्लायंट
प्रवेश वगळण्यासाठी हा हेडर वापरू शकत नाहीत.

लेगसी डीफॉल्ट्स `src/shared/constants/visionBridgeDefaults.ts` मध्ये आहेत;
नवीन मोड/कार्य-जागरूक/कॅशे डीफॉल्ट्स आणि सेटिंग्ज रिझॉल्वर
`src/shared/constants/modalityBridgeDefaults.ts` मध्ये आहेत. गार्डरेल
`deps` कन्स्ट्रक्टर पर्याय उपलब्ध करून देते, ज्यामुळे चाचण्यांमध्ये बनावट
`getSettings` आणि `callVisionModel` अंमलबजावण्या इंजेक्ट करता येतात.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ऑडिओ इनपुट स्वीकारतो असे ज्ञात नसलेल्या लक्ष्यापर्यंत ऑडिओ असलेल्या चॅट
विनंत्या पोहोचण्यापूर्वी त्यांना इंटरसेप्ट करते. ते चॅट विनंतीचे रूटिंग कधीही
बदलत नाही: विद्यमान OpenAI-सुसंगत मल्टिपार्ट एंडपॉइंटद्वारे ऑडिओ भागांचे
लिप्यंतरण केले जाते आणि निवडलेले चॅट मॉडेल मजकूर लिप्यंतरणांसह पुढे सुरू राहते.

प्रवाह:

1. `getResolvedModelCapabilities()` द्वारे `supportsAudio` निराकरण करा. स्पष्ट
   प्रदाता-रजिस्ट्री मेटाडेटाला प्रथम प्राधान्य मिळते, त्यानंतर स्थिर मॉडेल मेटाडेटा,
   आणि नंतर सिंक केलेले `modalities_input`. `audio` नसलेली घोषित इनपुट यादी
   `false` असते; क्षमतेचा कोणताही पुरावा नसल्यास मूल्य `null` राहते. `false` आणि
   `null` दोन्ही पुराणमतवादी ब्रिज सक्रिय करतात, तर `true` त्याला बायपास करते.
2. `modalityBridgeAudio*` सेटिंग्ज निराकरण करा आणि सामायिक `detectMediaParts()`
   डिटेक्टरद्वारे प्रत्येक संदेशातून स्प्लाइस करता येण्याजोगे शीर्ष-स्तरीय
   ऑडिओ भाग एक्स्ट्रॅक्ट करा. समर्थित वायर स्वरूपे OpenAI `input_audio`,
   `audio_url`, आणि `source.media_type: "audio/*"` आहेत. नेस्टेड ऑडिओ रूटिंगसाठी
   शोधला जातो, परंतु स्प्लाइस पाथद्वारे काढला जात नाही. कामावर
   `modalityBridgeAudioMaxClips` ची मर्यादा असते; त्यानंतरचे भाग बदलले जात नाहीत.
3. कॉन्फिगर केलेल्या `provider/model` चा आदर करा, किंवा `selectAudioBridgeModel()`
   ला स्थिर कॅटलॉग क्रमाने `AUDIO_TRANSCRIPTION_PROVIDERS` मधून जाऊ द्या आणि
   वापरण्यायोग्य सक्रिय प्रदाता क्रेडेन्शियल असलेले पहिले मॉडेल निवडू द्या.
4. `callAudioTranscription()` base64/data-URI ऑडिओला मल्टिपार्ट `file` मध्ये
   रूपांतरित करते, किंवा DNS पिनिंग आणि 25 MB मर्यादेसह केवळ-सार्वजनिक
   आउटबाउंड गार्डद्वारे दूरस्थ `audio_url` डाउनलोड करते. त्यानंतर ते
   `resolveSelfLoopBearer()` सह प्रमाणीकृत स्थानिक `/v1/audio/transcriptions`
   सेल्फ-लूपवर फाइल आणि निवडलेले मॉडेल POST करते. विद्यमान ट्रान्सक्रिप्शन रूट
   सामान्य क्रेडेन्शियल शोध, कूलडाउन/रेट-मर्यादा हाताळणी आणि प्रदाता डिस्पॅच करते.
5. यशस्वी कॉल त्यांचे भाग `[Audio N]: <transcript>` ने बदलतात. कॉल
   `Promise.allSettled` सह चालतात: एखादे स्वतंत्र अपयश तो मूळ ऑडिओ भाग जतन करते
   (#4012 करार). प्रत्येक कॉल अयशस्वी झाला आणि लक्ष्य
   `supportsAudio === false` असल्याचे सिद्ध झाले, तर भाग
   `[Audio N]: (unavailable — no STT provider connected)` होतात (#8430 करार).
   अज्ञात लक्ष्यासाठी (`null`), सर्व कॉल अयशस्वी झाल्याचा परिणाम बदल न करता
   ठेवला जातो. वापरण्यायोग्य STT क्रेडेन्शियल नसलेल्या, मजकूर-मात्र असल्याचे
   सिद्ध झालेल्या लक्ष्याला नेटवर्क कॉल न करता तोच स्पष्ट स्टब मिळतो.

यशस्वी लिप्यंतरणे प्रक्रियाभर सामायिक Modality Bridge LRU/TTL कॅशे वापरतात.
कीमध्ये ऑडिओ संदर्भ, स्थिर `audio-transcription` ऑपरेशन लेबल आणि निवडलेले STT
मॉडेल एकत्र केले जाते; अपयशे कधीही कॅशे केली जात नाहीत. ऑडिओ प्रयत्न सामायिक
`bridged`, `cacheHits`, `failures`, आणि `lastUsedAt` काउंटर अपडेट करतात.
रूपांतरित प्रतिसादांमध्ये
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` असते;
बदल न केलेल्या विनंत्यांना Audio Bridge सेगमेंट मिळत नाही.

रनटाइम सेटिंग्ज DB-समर्थित आणि Zod-द्वारे प्रमाणित आहेत:

| की                            | डीफॉल्ट | श्रेणी                 |
| ----------------------------- | ------- | ---------------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                      |
| `modalityBridgeAudioModel`    | `""`    | स्वयंचलित किंवा STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000            |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10                   |

सामायिक कॅशेचे नियंत्रण `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` आणि `modalityBridgeCacheMaxEntries` यांच्याद्वारेच केले जाते.

### व्हिडिओ ब्रिज (`videoBridge.ts`, `videoBridgePipeline.ts`)

मूळ व्हिडिओ समर्थन असल्याचे ज्ञात नसलेल्या लक्ष्याला कॉल करण्यापूर्वी, Chat Completions
`messages` आणि Responses API `input` मधील उच्च-स्तरीय व्हिडिओ भागांना इंटरसेप्ट करते.
समर्थित स्वरूपे म्हणजे `input_video`, `video_url`, `video_source`, HTTPS URLs
आणि `data:video/*;base64,...` डेटा URIs. मजकुरातील साधी फाइलनावे व्हिडिओ
म्हणून हाताळली जात नाहीत.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) विनंतीचे ट्रॅव्हर्सल,
क्षमता/धोरण तपासणी, प्रत्येक विनंतीचे एकत्रीकरण आणि प्रतिसाद पेलोड हाताळते.
प्रत्येक व्हिडिओवरील काम — संपादन, संपूर्ण-निकाल कॅशे, फ्रेम
अनुक्रमाचे वर्णन करणे (ज्यात कॉलरने घोषित केलेले कोणतेही ऑडिओ ट्रान्सक्रिप्ट एकत्र केले जाते) आणि प्रत्येक प्रयत्नाची
मेट्रिक्स/रद्दीकरण/स्वच्छता — `videoBridgePipeline.ts` मधील
`processVideoPart` च्या मागे लपवलेले आहे, ज्याला `preCall` च्या लूपमध्ये प्रत्येक व्हिडिओ भागासाठी एकदा कॉल केले जाते.
ते मॉड्यूल स्पष्ट पोर्ट सीमा `VideoMediaBrokerPort`
(बाइट्स मिळवणे आणि नमुना फ्रेम्स काढणे), `VideoAudioTranscriptionPort`
(कॉलरने घोषित केलेले ऑडिओ ट्रान्सक्रिप्ट नमुना कॅप्शन्समध्ये एकत्र करणे) आणि
`VideoDrilldownPort` (फ्रेम ड्रिल-डाउन टिकाव सीमा; अद्याप
`processVideoPart` शी जोडलेली नाही — सध्या फक्त स्वतंत्र `/api/modality-bridge/video/drilldown`
रूट ड्रिल-डाउन नोंदी लिहितो) देखील परिभाषित करते.

सार्वजनिक `/v1` विनंती मार्ग कधीही सबप्रोसेस आयात किंवा सुरू करत नाही. दूरस्थ
व्हिडिओ 50 MiB मर्यादेत डाउनलोड केले जातात; इनलाइन base64 व्हिडिओंसाठी
प्रत्येक व्हिडिओवर डिकोड केलेल्या आकाराची 36 MiB ची पुराणमतवादी मर्यादा असते, जेणेकरून मॉडेल/संदेश/फ्रेमिंग एन्व्हलप
50 MiB च्या सार्वजनिक JSON विनंती-स्वीकृती मर्यादेत राहू शकेल. इनलाइन
लांबी आणि डिकोड केलेल्या आकाराचे अंदाज मेमरी वाटपापूर्वी तपासले जातात. प्रारंभिक दूरस्थ URL आणि प्रत्येक रीडायरेक्टसाठी HTTPS
आवश्यक आहे आणि त्यासाठी DNS पिनिंगसह विद्यमान
केवळ-सार्वजनिक आउटबाउंड गार्ड वापरला जातो. त्यानंतर बाइट्स अचूक अंतर्गत
`POST /api/modality-bridge/video/extract` ब्रोकर सीमा पार करतात. तो रूट
`LOCAL_ONLY` आणि `SPAWN_CAPABLE` दोन्ही आहे, प्रत्येक प्रोसेससाठी प्रमाणित,
विश्वसनीय-लूपबॅक विनंतीच स्वीकारतो आणि URL, फाइलसिस्टम पथ, एक्झिक्युटेबल
किंवा आर्ग्युमेंट सूची कधीही स्वीकारत नाही. API बॉडी-आकार पाइपलाइन आणि हँडलरचा वाढीव बॉडी
रीडर स्वतंत्रपणे 50 MiB ची ब्रोकर इनपुट मर्यादा लागू करतात. त्याची मर्यादित रांग
एका वेळी एक एक्स्ट्रॅक्शन चालवते, चार प्रलंबित जॉबना परवानगी देते आणि प्रलंबित इनपुटवर
100 MiB ची कमाल मर्यादा लागू करते.

ब्रोकरच्या आत, `ffprobe` एक खासगी स्थानिक फाइल वाचते; निश्चित फॉरमॅट
अनुमतिसूची प्लेलिस्ट आणि मॅनिफेस्ट फॉरमॅट वगळते. अनुमत MOV-कुटुंबातील
कंटेनर्ससाठी बाह्य MOV डेटा संदर्भ डीफॉल्टनुसार अक्षमच राहतात आणि
निश्चित कमांड त्यांना सक्षम करत नाही. `ffprobe` आणि `ffmpeg` दोन्ही
केवळ-`file` प्रोटोकॉल अनुमतिसूची, एक थ्रेड, निश्चित आर्ग्युमेंट अॅरे आणि कोणतेही शेल न वापरता
चालतात, तसेच एक्झिक्युटेबल्स `PATH` मधून शोधले जातात. संलग्न-चित्र कव्हर स्ट्रीम्स
प्ले करण्यायोग्य उमेदवार नसतात. प्ले करण्यायोग्य सर्व स्ट्रीम्सनी मर्यादांचे पालन केले पाहिजे आणि
नियतात्मक सर्वात-कमी-इंडेक्स फॉलबॅकपूर्वी स्पष्ट डीफॉल्ट स्ट्रीमला प्राधान्य दिले जाते.
व्हिडिओ 600 सेकंद, प्रत्येक परिमाणात 8,192 पिक्सेल आणि
33,554,432 स्रोत पिक्सेलपर्यंत मर्यादित असतात. FFmpeg मध्यबिंदूंवरील 1–16 JPEG फ्रेम्सचे नमुने घेते,
लहान इनपुट अपस्केल न करता लांब कडा कमाल 1,024 पिक्सेलपर्यंत कमी करते आणि
तिला कधीही URL दिला जात नाही. डीफॉल्टनुसार सॅम्पलिंग `uniform` असते. पर्यायी
`scene_aware` आणि प्रायोगिक `segment_aware` धोरणे आधीच प्रमाणित केलेल्या स्थानिक स्ट्रीमवर
एक अतिरिक्त निश्चित FFmpeg पास करतात, मर्यादित
`showinfo` दृश्य टाइमस्टॅम्प निवडतात आणि डिटेक्टर बिघाड, टाइमआउट, सदोष आउटपुट किंवा रिकामा
उमेदवार संच असल्यास त्याच समान मध्यबिंदूंवर नियतात्मक रीतीने फॉलबॅक करतात.
सेगमेंट-अवेयर मोड प्रमाणित दृश्य अंतरालांच्या प्रमाणात मध्यबिंदू नमुने वाटप करतो;
सेगमेंट-अवेयर पुरावे आणि फॉलबॅक वर्तनाचे तपशील खाली दिले आहेत. प्रत्येक धोरणात
निवडीनंतर 16-फ्रेमची कठोर मर्यादा
लागू केली जाते. सीन-अवेयर विनंतीमध्ये केवळ एका फ्रेमचे बजेट असल्यास,
ती सक्रिय पूर्ण-व्हिडिओ किंवा फोकस विंडोचा समान मध्यबिंदू वापरते आणि
`policyEffective: uniform` नोंदवते: निवडलेली एकच दृश्य फ्रेम कालखंडाची दोन्ही टोके
जतन करू शकत नाही. कॉलर पर्यायाने मर्यादित फोकस विंडो
(`start`/`end` सेकंद) देऊ शकतो; सीमा मीडियाच्या कालावधीपर्यंत मर्यादित केल्या जातात,
उलट किंवा अमर्यादित विंडो नाकारल्या जातात आणि सर्व सॅम्पलिंग
धोरणे केवळ सामान्यीकृत अंतरालातच राबवली जातात. परिणामी
विंडो सॅम्पलिंग मेटाडेटामध्ये आणि अविश्वसनीय वर्णन
उपसर्गामध्ये समाविष्ट केली जाते, जेणेकरून डाउनस्ट्रीम मॉडेल्स पूर्ण
टाइमलाइनपासून फोकस केलेला उतारा वेगळा ओळखू शकतील.

अर्थविषयक कॅप्शन फोकस ही स्वतंत्र आणि स्पष्ट सेटिंग आहे. डीफॉल्ट `full`
विश्लेषण मोड विद्यमान फ्रेम प्रॉम्प्ट जतन करतो आणि विनंतीतील मजकूर कॅप्शन मॉडेलकडे
कधीही पाठवत नाही. `focused` मोडमध्ये, ब्रिज त्याच Chat किंवा Responses
कंटेनरमधून केवळ वापरकर्त्याने लिहिलेला सर्वात अलीकडील रिक्त नसलेला `text`/`input_text` वाचतो,
तो NFC मध्ये सामान्यीकृत करतो, नियंत्रण वर्ण आणि व्हाइटस्पेस संक्षिप्त करतो
आणि त्याला 500 Unicode कोड पॉइंट्सपर्यंत मर्यादित करतो. रिकामा परिणाम मिळाल्यास अचूक
`full` प्रॉम्प्टवर फॉलबॅक केले जाते. वापरण्यायोग्य संकेत समर्पित
अविश्वसनीय-वापरकर्ता-संदर्भ ब्लॉकमध्ये JSON म्हणून सीरियलाइज केला जातो आणि तो फक्त निरीक्षण करण्यायोग्य तपशीलांना
प्राधान्य देऊ शकतो; तो मीडियामध्ये दृश्य किंवा श्राव्य सूचनांचे पालन न करण्याविषयीची
स्वतंत्र चेतावणी ओव्हरराइड करू शकत नाही. मजकूर-आधारित फोकस कधीही `start`/`end` चा अंदाज
लावत नाही किंवा कालाधारित सॅम्पलर बदलत नाही.

#### FU-07 संरचनात्मक सेगमेंट पुरावे

`segment_aware` आधीच प्रमाणित केलेल्या स्थानिक व्हिडिओ प्रवाहावर एकदाच मर्यादित पूर्व-विश्लेषण करते. निश्चित फिल्टर साखळी प्रथम रुंदी जास्तीत जास्त 320 पिक्सेलपर्यंत स्केल करते, दृश्यबदल आणि गोठलेले कालखंड शोधते, त्यानंतर अस्पष्टता, सरासरी ल्यूमा आणि स्थानिक/कालिक माहितीसाठी दर सेकंदाला 1 फ्रेमचा नमुना घेते. ही प्रक्रिया 600 संरचनात्मक नमुने, एक FFmpeg/फिल्टर थ्रेड, तेच केवळ-`file` प्रोटोकॉल आणि कंटेनर अनुमती-सूची, 1 MiB प्रक्रिया-आउटपुट मर्यादा आणि ब्रोकरच्या सामायिक रद्दीकरण/अंतिम-मुदतीच्या आत जास्तीत जास्त 30 सेकंदांपर्यंत मर्यादित आहे. ती विनंतीमधून आदेश, फिल्टर, पथ किंवा URL कधीही स्वीकारत नाही.

संरचनात्मक मूल्ये ही निर्धारक नमुना-आधारित प्रमाणे आहेत, व्हिडिओचे अर्थविषयक आकलन नाही. ती विषय, कृती, मथळे, भाषण किंवा वापरकर्त्याचा हेतू यांचा निष्कर्ष काढत नाहीत. दृश्य आणि गोठवण सीमांमधून खंड तयार होतात; गोठवण व्याप्ती, अस्पष्टता, एक्स्पोजर, स्थानिक तपशील आणि कालिक बदल केवळ विद्यमान 1–16 फ्रेम बजेटचे वाटप कसे केले जाते यावर प्रभाव टाकतात. पूर्णपणे गोठवलेला खंड एका फ्रेमपुरता मर्यादित केला जातो, तर न गोठलेले खंड उर्वरित बजेटसाठी स्पर्धा करतात. जेव्हा सीमांची संख्या फ्रेमपेक्षा जास्त असते, तेव्हा कालरेषेवरील एकसमान व्याप्ती कायम ठेवली जाते, जेणेकरून सुरुवातीचे जलद कट दीर्घ शेवटचा खंड लपवू शकणार नाहीत. गोठवण सीमेच्या 1-सेकंद विश्लेषण रिझोल्यूशनमधील दृश्य सीमा एकत्र केल्या जातात.

फिल्टर उपलब्ध नसणे, विकृत/रिकामे प्रमाण, डिटेक्टर त्रुटी किंवा मर्यादित पूर्व-विश्लेषण कालबाह्यता झाल्यास, तंतोतंत एकसमान मध्यबिंदू धोरणावर खुले अपयश होते. कॉलरचे रद्दीकरण किंवा ब्रोकरची अंतिम मुदत यांवर खुले अपयश होत नाही: ते सुरू असलेली उपप्रक्रिया समाप्त करते, त्यानंतरचे फ्रेम निष्कर्षण रोखते आणि खाजगी तात्पुरती निर्देशिका-संरचना `finally` मध्ये काढून टाकली जाते.

`scripts/perf/video-bridge-fu07-eval.ts` डीडुप्लिकेशननंतरच्या मथळा-कॉल बचती, सघन-गती बजेट वाटप, अस्पष्टता/एक्स्पोजर/SI-TI प्रमाण, दीर्घ शेवट असलेले जलद कट आणि क्रमिक-फेड खोटे सकारात्मक परिणाम यांसाठी निर्धारक वास्तविक FFmpeg फिक्स्चर्स निर्माण करते. ते पूर्व-विश्लेषणाचा प्रत्यक्ष कालावधी आणि `/usr/bin/time` उपलब्ध असल्यास चाइल्ड CPU व कमाल RSS नोंदवते. त्याच्या गुणवत्ता तपासण्या केवळ संरचनात्मक सत्याधार आहेत. वास्तविक मथळा-मॉडेलची गुणवत्ता `HOLD` स्थितीतच राहते, कारण या हार्नेसकडे अधिकृत एंडपॉइंट किंवा गोठवलेला परीक्षक नाही. `--caption-cost-per-call-usd` द्वारे प्रत्येक कॉलसाठी स्पष्ट सकारात्मक खर्च-अंदाज दिल्याशिवाय आर्थिक बचतही `HOLD` स्थितीतच राहते; स्क्रिप्ट यांपैकी कोणताही परिणाम बनावट तयार करत नाही.

प्रत्येक फ्रेम 4 MiB पर्यंत, सर्व रॉ फ्रेम्स मिळून 23 MiB पर्यंत आणि क्रमबद्ध केलेला ब्रोकर प्रतिसाद 32 MiB पर्यंत मर्यादित आहे. खाजगी तात्पुरती निर्देशिका `finally` मध्ये काढून टाकली जाते. OmniRoute मध्ये FFmpeg समाविष्ट केलेले नाही आणि ते सानुकूल एक्झिक्युटेबल पथ स्वीकारत नाही. मथळे तयार करण्यापूर्वी, ब्रिज एक सावध दृश्य डीडुप्लिकेशन प्रक्रिया लागू करतो: प्रत्येक JPEG ला 16×16 ग्रेस्केल बफरमध्ये कमी केले जाते आणि केवळ शेवटी राखून ठेवलेल्या फ्रेमशी त्याची तुलना केली जाते. एकापेक्षा अधिक फ्रेमच्या विनंती केलेल्या मथळा बजेटसाठी, निष्कर्षण त्या बजेटच्या जास्तीत जास्त दुप्पट आणि कधीही 16 फ्रेमपेक्षा अधिक नसलेला मर्यादित उमेदवार संच पुरवते. विनंती केलेली मर्यादा डीडुप्लिकेशननंतरच लागू केली जाते आणि बजेट किमान दोन असल्यास अंतिम विरळीकरणादरम्यान प्रथम व अंतिम निवडलेले उमेदवार राखून ठेवले जातात. आवृत्तीकृत
`grayscale-16x16-mean-cells-v2` धोरण सरासरी ल्यूमा फरक आणि ज्यांचा सामान्यीकृत फरक किमान 0.05 आहे अशा थंबनेल सेल्सचे प्रमाण यांपैकी मोठे मूल्य वापरते. डुप्लिकेट थ्रेशोल्ड हा स्थिरांक 0.04 आहे; तो रनटाइम सेटिंग म्हणून उपलब्ध करण्याऐवजी पूर्वानुमानक्षमतेसाठी निवडला आहे. हा दुय्यम
उच्च-कॉन्ट्रास्ट सिग्नल लहान हालचाली आणि दृश्यमान-मजकूरातील बदल जतन करतो, जे केवळ सरासरीवर आधारित तुलना लपवू शकते. तुलनाकर्ता किंवा डिकोडर त्रुटींवर खुले अपयश होते आणि व्याप्ती राखली जाते. आउटपुट मेटाडेटा निष्कर्षित उमेदवार, यशस्वीपणे वापरलेल्या फ्रेम्स आणि वगळलेले दृश्य डुप्लिकेट वेगळे दर्शवतो.

स्पष्टपणे चिन्हांकित केलेला व्हिडिओ भाग टाइमस्टॅम्प असलेल्या कॉन्टॅक्ट शीटची विनंती करू शकतो. ब्रिज जास्तीत जास्त 4-स्तंभांची, 16-फ्रेमची JPEG ग्रिड तयार करतो. प्रत्येक 512-पिक्सेल सेल त्याचा स्रोत टाइमस्टॅम्प उच्च-कॉन्ट्रास्ट तळाच्या पट्ट्यात कायमचा उमटवतो, तर त्याच टाइमस्टॅम्प्स पुढील टप्प्यातील संबद्धता आणि लेखापरीक्षणासाठी मजकूरात्मक मेटाडेटामध्येही राहतात. संपूर्ण JPEG ची मर्यादा 32 MiB कायम राहते. `sharp` ग्रिड डिकोड किंवा संयोजित करू शकत नसल्यास, ब्रिज स्वतंत्र JPEG फ्रेम्सवर परत जातो; क्लायंटचे रद्दीकरण तरीही शीट प्रक्रियेतून प्रसारित होते.

प्रमोशनचे प्रमाण कृत्रिम संयोजन मायक्रोबेंचमार्कपासून जाणीवपूर्वक वेगळे ठेवले आहे. `scripts/perf/video-bridge-contact-sheet-eval.ts` वास्तविक OpenAI-सुसंगत व्हिजन मॉडेल्ससाठी स्कीमा-आवृत्तीकृत A/B हार्नेस परिभाषित करते. ते प्रदात्याने नोंदवलेले टोकन्स, टोकापासून टोकापर्यंतचा प्रत्यक्ष विलंबकाल (शीट संयोजनासह), मॉडेल-कॉल संख्या आणि मॅनिफेस्टने परिभाषित केलेली तथ्य-धारणा मोजते. रॉ मॉडेल प्रतिसाद अहवालात लिहिले जात नाहीत; केवळ SHA-256 डायजेस्ट्स आणि जुळलेले तथ्य ID राखून ठेवले जातात. `--execute-real` दिलेले आणि `--model`, `OMNIROUTE_BASE_URL` व `OMNIROUTE_API_KEY` कॉन्फिगर केलेले नसल्यास हार्नेस कोणताही नेटवर्क किंवा सशुल्क मॉडेल कॉल करत नाही. अशा स्पष्ट वास्तविक रनशिवाय, त्याचा मशीन-वाचनीय निर्णय `HOLD` स्थितीत राहतो; केवळ कृत्रिम पेलोड/कॉल-संख्या मोजमाप हे प्रमोशनचे प्रमाण नाही.

कॉलर्सकडे आधीपासून संरेखित मजकूर असल्यास, ते समर्थित व्हिडिओ भागाला पर्यायी `transcript.cues` अॅरे जोडू शकतात. प्रत्येक क्यूमध्ये `text`, तपासलेल्या कालावधीतील मर्यादित `start`/`end` अंतराल आणि अनुमती-सूचीतील `source` (`client`, `embedded` किंवा `audio-bridge`) असणे आवश्यक आहे; `confidence` चे डीफॉल्ट मूल्य `1` आहे आणि ते `0` ते `1` दरम्यानच असले पाहिजे. तंतोतंत डुप्लिकेट क्यूज एकत्र केले जातात. **कच्ची व्हिडिओ फील्ड्स (#12430).** Bridge सक्षम असताना आणि native video समर्थन अज्ञात किंवा अनुपस्थित असताना, परिभाषित `transcript`/`audioTranscript` फील्ड्सदेखील `videoBridgeObserved` सक्रिय करतात, अगदी वर्णन अयशस्वी झाल्यानंतर किंवा `maxVideos` मर्यादा लागू झाल्यानंतरही. `null` आणि रिकाम्या strings मोजल्या जातात; अनुपस्थित फील्ड्स आणि non-video मेटाडेटा मोजले जात नाहीत. जतन केलेल्या प्रतींमध्ये ही फील्ड्स संपादित केली जातात किंवा विनंती वगळली जाते, आणि caches/Memory टाळले जातात.

त्या fallback मार्गांवर, वैध कॉलर cues हे अप्रमाणित provider fields ऐवजी
समर्थित `text`/`input_text` parts बनतात. विनंतीत दिलेले दोन्ही ट्रॅक
अविश्वसनीय `client` निरीक्षणे म्हणूनच राहतात आणि व्हिडिओचे वर्णन केले गेले
नाही व timestamps ची मीडियाशी पडताळणी झाली नाही, असा स्पष्ट इशारा दिला जातो.
विद्यमान 256-cue/64-KiB एकूण आणि प्रति-cue मर्यादा दोन्ही ट्रॅक्सवर एकत्रितपणे
लागू होतात; timestamps हे broker च्या 600-second कमाल मर्यादेत आणि पुरवलेल्या
कोणत्याही focus window मध्ये बसले पाहिजेत. अवैध ट्रॅक्स टाकून दिले जातात,
मनमाना मजकूर म्हणून पुढे पाठवले जात नाहीत; त्यांची एकत्रित मर्यादा ओलांडली
नसल्यास वैध sibling तरीही वापरला जाऊ शकतो. Null/रिकामी फील्ड्स कोणताही मजकूर
जोडत नाहीत. या fallback मुळे media fetch किंवा transcription जोडले जात नाही.
Transcript extension fields ही fallback video carrier आणि त्याच्या
`video_url`/`source` objects मधून काढून टाकली जातात. OpenAI wire allowlist
कठोरच राहते; unknown-native video carriers उपलब्ध राहतात आणि ज्ञात
text-only targets सुरक्षित markers ठेवतात. संरचित redaction shadows जोडलेल्या
ट्रान्सक्रिप्ट मजकुराचे संरक्षण करतात, तर कॉलरच्या मालकीची मूळ विनंती
अपरिवर्तित राहते. Native-supported targets आणि अक्षम bridges त्यांचे विद्यमान
bypass वर्तन कायम ठेवतात.

अतिरिक्त जतन केलेल्या प्रती समान observed-request signal वापरतात. कच्चा
pre-guardrail client-request snapshot, in-memory pending request, आणि
early rejected-request log हे video parts मधील transcript fields संरचनात्मकरीत्या
बदलतात; pipeline stages आणि context handoff यांनी तयार केलेले string prompts
persisted-request-body sink वर संपादित केले जातात. जतन केलेला
`video_content_removed` marker, हेतुपुरस्सर टाकून दिलेला मजकूर पुन्हा तयार
करण्याऐवजी `previous_response_id` continuation ला fail closed करतो. निरीक्षण
केलेल्या विनंतीने logging पूर्वी तिची per-part redaction shadow गमावल्यास,
किंवा नंतरच्या request mutations नंतर अनेक video shadows पैकी एकाचीही जुळणी
अयशस्वी झाल्यास, अंशतः संपादित ट्रान्सक्रिप्ट जतन करण्याऐवजी जतन केलेला request
body पूर्णपणे वगळला जातो.

निरीक्षण केलेल्या विनंतीसाठी, मॉडेलचा प्रतिसाद संरचित cue सीमा नसताना
ट्रान्सक्रिप्टचा कोणताही भाग उद्धृत करू शकतो. त्यामुळे त्याचा जतन केलेला
call-log `responseBody` omission marker ने बदलला जातो; तपशीलवार pipeline
artifact (ज्यामध्ये upstream/client bodies आणि stream chunks समाविष्ट असू
शकतात) जतन केला जात नाही. Semantic, idempotency, आणि reasoning-replay caches
त्या विनंतीसाठी reads आणि writes टाळतात. Provider request आणि client-visible
response अपरिवर्तित राहतात. तपशीलवार artifact वगळला जातो तेव्हा early
keepalive bytes तात्पुरत्या buffer मधून काढून टाकले जातात. Kiro ची malformed
EventStream warning फक्त payload byte count नोंदवते, त्यातील मजकूर किंवा JSON
parser ची raw error कधीही नोंदवत नाही.
यातून प्रत्येक असंबंधित provider/plugin diagnostic चे audit झाले आहे असा
दावा केला जात नाही; व्यापक retained-sink sweep चा मागोवा #11658 मध्ये घेतला
जातो.

अंतर्गत `/api/modality-bridge/video/drilldown` जीवनचक्र हा स्वतंत्र,
लूपबॅक/टोकन-प्रमाणित कॅशे अधःस्तर आहे. प्रत्येक ऑपरेशनसाठी एक
कॅनॉनिकल अपारदर्शक प्रिन्सिपल ID देखील आवश्यक आहे. उत्पादन कॉलर सक्षम करण्यापूर्वी, त्याने
प्रमाणित टेनंटवरून तो ID व्युत्पन्न केला पाहिजे आणि क्लायंटने निवडलेले मूल्य कधीही
फॉरवर्ड करू नये. कॅशे की त्या प्रिन्सिपलला कॅनॉनिकल सत्र आणि
व्हिडिओ-संदर्भ ID शी बांधतात, फक्त त्यांच्या SHA-256-व्युत्पन्न की संग्रहित करतात आणि वाचन
तसेच विलोपन दोन्ही त्याच प्रिन्सिपलपुरते मर्यादित करतात. कॅशे प्रत्येक नोंदीसाठी जास्तीत जास्त 16 व्युत्पन्न JPEG
फ्रेम संग्रहित करते, दहा मिनिटांनंतर त्या कालबाह्य करते आणि मर्यादित
`start`/`end` वाचन किंवा स्पष्ट सत्र विलोपनाला समर्थन देते.

प्रत्येक प्रिन्सिपल 16 नोंदी आणि 64 MiB कॅनॉनिकल JPEG डेटापुरता मर्यादित आहे. या
मर्यादा जागतिक 64-नोंदी/256 MiB कमाल मर्यादेपासून स्वतंत्र आहेत: प्रिन्सिपल कोट्यावरील
दबावामुळे जागतिक LRU निष्कासनाचा विचार करण्यापूर्वी फक्त त्या प्रिन्सिपलच्या सर्वांत कमी अलीकडे वापरलेल्या
नोंदी निष्कासित केल्या जातात. कॅशे क्रियाकलापाच्या वेळी कालबाह्य नोंदी प्रिन्सिपल आणि
जागतिक लेखांकन या दोन्हींमधून काढून टाकल्या जातात, तर रद्दीकरण आणि प्रमाणीकरणातील अपयश
अंशतः केलेली प्रतिस्थापना कमिट करत नाहीत.

कॅशे नॉन-कॅनॉनिकल Base64, अतिरिक्त पॅडिंग, JPEG नसलेले मीडिया, विकृत किंवा
अपूर्ण JPEG आणि मर्यादित पूर्ण-प्रतिमा `sharp`
डीकोडदरम्यान इशारा निर्माण करणारे JPEG नाकारते. ती प्रत्येक स्वीकारलेली प्रतिमा कॅनॉनिकल JPEG म्हणून पुन्हा एन्कोड करते,
कॉलरच्या फील्डवर विश्वास ठेवण्याऐवजी डीकोड केलेल्या बाइट्समधून रुंदी आणि उंची व्युत्पन्न करते
आणि शेवटी जोडलेले कोणतेही पॉलीग्लॉट बाइट्स जतन करण्याऐवजी टाकून देते. दोन्ही कोट्यांमध्ये फक्त
मर्यादित कॅनॉनिकल संकुचित बफरची गणना केली जाते. JSON वायर मर्यादेमध्ये 32 MiB
डीकोडेड-इनपुट कमाल मर्यादेसाठीचा Base64 ओव्हरहेड समाविष्ट आहे. प्रत्येक
संग्रहित व्युत्पत्ती तिचे प्रमाणित JPEG स्वरूप/रिझोल्यूशन, सॅम्पलिंग धोरण,
व्युत्पत्ती आवृत्ती, निर्मिती वेळ, सर्व्हरने संगणित केलेला कंटेंट हॅश आणि हॅश केलेला मूळ
संदर्भ तसेच विश्वसनीय कॉलरचा मूळ-कंटेंट हॅश नोंदवते. अणुस्वरूपी कॅशे कमिटपूर्वी
असिंक्रोनस डीकोड/हॅश टप्प्यांदरम्यान रद्दीकरण तपासले जाते.

हा टप्पा अद्याप उत्पादन प्रोड्युसरला रूटशी जोडत नाही आणि
बहु-रिझोल्यूशन व्हेरिएंट निवड प्रदान करत नाही. त्यामुळे पारदर्शक Video Bridge विनंती
मार्गावर कोणतेही अतिरिक्त काम होत नाही, तर टेनंट-बद्ध प्रिन्सिपल व्युत्पत्ती आणि
संपूर्ण FU-08 बहु-रिझोल्यूशन जीवनचक्र हे पूर्ण वर्तन म्हणून दस्तऐवजीकरण न करता
स्पष्ट पाठपुरावा काम म्हणून शिल्लक राहतात.

फ्रेमना कॉन्फिगर केलेल्या Video मॉडेलद्वारे क्रमाने कॅप्शन दिले जाते. रिक्त
Video ओव्हरराइडला Vision सेटिंग वारशाने मिळते; दोन्ही रिक्त असल्यास, Vision
ऑटो-राउटर प्रभावी दृष्टी-समर्थ मॉडेल निवडतो. यशस्वी कॅप्शन मूळ भागाच्या जागी
स्थिर `[Video description:` उपसर्ग वापरतात, जो मजकूराला अविश्वसनीय मीडिया-व्युत्पन्न
निरीक्षण म्हणूनही चिन्हांकित करतो आणि पुढील मॉडेलना मीडियामध्ये आढळलेल्या सूचनांचे
पालन न करण्यास सांगतो. फ्रेम-कॅप्शन कॅशे कीमध्ये JPEG बाइट्स, प्रॉम्प्ट, टाइमस्टॅम्प
आणि प्रभावी मॉडेल समाविष्ट असतात; फक्त यशस्वी कॅप्शन कॅशे केली जातात. कॅशे नोंदी
प्रत्यक्ष यशस्वी प्रोड्युसर मॉडेल जतन करतात, त्यात फॉलबॅक मॉडेलचाही समावेश असतो; वेगवेगळ्या
फ्रेम वेगवेगळ्या मॉडेलने तयार केल्या असल्यास ब्रिज `mixed` अहवाल देतो. कॅशे हिट
त्या प्रोड्युसरची ओळख विनंती केलेली रूटिंग योजना म्हणून पुन्हा लेबल करण्याऐवजी
पुन्हा वापरतो. संपूर्ण-व्हिडिओ परिणाम कॅशेची की आउटपुट बदलणाऱ्या प्रत्येक इनपुटवर आधारित असते —
प्रॉम्प्ट, प्रभावी मॉडेल, सॅम्पलिंग धोरण, फ्रेम संख्या, सिमॅंटिक विश्लेषण मोड,
सामान्यीकृत फोकस संकेताचा SHA-256 फिंगरप्रिंट, फोकस विंडो, `transcript`,
`audioTranscript` आणि कॉन्टॅक्ट-शीट फ्लॅग — त्यामुळे यांपैकी कोणतेही
परिमाण बदलल्यास तो कॅशे मिस असतो, जुन्या डेटाचा पुनर्वापर कधीही होत नाही. दृश्य डीडुप धोरणाची
आवृत्ती, थ्रेशोल्ड आणि मर्यादित उमेदवार-फ्रेम संख्या यांचाही परिणाम-कॅशे की आणि
मेटाडेटामध्ये स्पष्ट समावेश असतो; त्यामुळे धोरणातील बदल जुने संपूर्ण-व्हिडिओ
वर्णन पुन्हा वापरू शकत नाही. परिणाम-कॅशे v4 मेटाडेटा मोड आणि
फिंगरप्रिंट जतन करते, कच्चे वापरकर्ता कार्य कधीही नाही. गार्डरेल मेटाडेटा विनंती केलेला आणि
प्रभावी असे दोन्ही विश्लेषण मोड नोंदवतो; वापरण्यायोग्य वापरकर्ता मजकूर नसलेला विनंती केलेला `focused`
मोड प्रभावीपणे `full` म्हणून नोंदवला जातो.

गार्डरेल प्रत्येक समर्थित व्हिडिओ भाग निष्कर्षित करते, पण
`modalityBridgeVideoMaxVideos` पेक्षा अधिक भागांचे वर्णन करत नाही. ज्या लक्ष्याला
`supportsVideo === false` असल्याचे सिद्ध झाले आहे, त्यासाठी अयशस्वी आणि मर्यादेपेक्षा अधिक व्हिडिओ
स्पष्ट सुरक्षित मजकूर मार्करमध्ये रूपांतरित होतात, जेणेकरून कोणताही कच्चा व्हिडिओ शिल्लक राहत नाही.
क्षमता अज्ञात असताना, ते भाग त्यांचा व्हिडिओ वाहक कायम ठेवतात; कोणताही फॉलबॅक ट्रान्सक्रिप्ट
वरील मर्यादित मजकूर रूपांतरणाचे पालन करतो. `supportsVideo === true` असलेली लक्ष्ये
ब्रिजला बायपास करतात. क्लायंट विनंतीचा अबॉर्ट सिग्नल डाउनलोड, ब्रोकर क्यू,
सबप्रोसेस आणि कॅप्शन कॉलमधून प्रसारित होतो; अबॉर्ट व्हिडिओंच्या दरम्यान थांबतात आणि कच्च्या
मीडियासाठी कधीही फेल-ओपन होत नाहीत.

ब्रोकरच्या अंतिम मुदतीपर्यंत मर्यादित केली जातात; त्या मर्यादेपेक्षा जास्त मूल्ये असलेली नवीन सेटिंग्जची लेखने नाकारली जातात.
`GET /api/modality-bridge/video/runtime` ला प्रमाणीकरण किंवा रनटाइम तपासणीपूर्वी
विश्वसनीय स्टॅम्प केलेली लूपबॅक स्थानिकता आवश्यक असते आणि त्यानंतर व्यवस्थापन
प्रमाणीकरण आवश्यक असते. हे केवळ `available`, स्वच्छ केलेल्या FFmpeg/ffprobe आवृत्त्या आणि रनटाइम अनुपलब्ध असताना एक निश्चित
कारण परत करते. अंतर्गत एक्स्ट्रॅक्शन एंडपॉइंट हा
सार्वजनिक अपलोड API नाही: रांग पूर्ण भरल्यास `503` आणि `Retry-After` परत केले जाते, कॉलर
डिस्कनेक्ट झाल्यास `499` परत केले जाते आणि ब्रोकरची निश्चित अंतिम मुदत संपल्यास `504` परत केले जाते. रूपांतरित प्रतिसाद
Vision किंवा Audio विभाग न काढता मध्यवर्ती
`x-omniroute-modality-bridge` हेडरमध्ये `video->text;model=<visionModel>;parts=<videos>` जोडतात.

### PII मास्कर (`piiMasker.ts`)

**दोन्ही** टप्प्यांवर चालतो.

- **`preCall`** पेलोड क्लोन करतो, `system`, `messages`, `input` आणि
  `prompt` (साध्या स्ट्रिंग आयटमसह) यांमधून जातो आणि स्ट्रिंग `content`/`text` फील्डवर
  `processPII()` (`@/shared/utils/inputSanitizer` मधून) लागू करतो.
  `PII_REDACTION_ENABLED=true` असताना, आढळलेली PII आउटबाउंड
  पेलोडमध्ये संपादित केली जाते. हे `INPUT_SANITIZER_MODE` पासून स्वतंत्र आहे (जो केवळ
  प्रॉम्प्ट-इंजेक्शन धोरण नियंत्रित करतो). संपादन बंद असताना, कॉल आशयात बदल न करता
  शोध-संख्या नोंदवतो.
- **`postCall`** प्रतिसादाचा डीप क्लोन तयार करतो, `sanitizePIIResponse()` तसेच
  Responses-API-आकाराचा मास्कर (`maskResponsesOutput` — जो
  `output_text` आणि `output[].content[].text` व्यापतो) चालवतो. कोणतेही संपादन झाल्यास,
  सुधारित प्रतिसाद मूळ प्रतिसादाची जागा घेतो.

गार्डरेल कधीही ब्लॉक करत नाही; तो केवळ नोंद जोडतो (`meta.detections`,
`meta.redacted`) किंवा पुनर्लेखन करतो.

### प्रॉम्प्ट इंजेक्शन (`promptInjection.ts`)

वापरकर्त्याने पुरवलेल्या आशयातील प्रतिकूल संरचना शोधतो आणि
कॉन्फिगर केलेले धोरण लागू करतो. वर्तन पर्यावरण चल आणि कन्स्ट्रक्टर
पर्यायांद्वारे नियंत्रित केले जाते:

| सेटिंग          | पर्यावरण चल                                                                                           | डीफॉल्ट | परिणाम                                                                                                                                                                                                        |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| सक्षम           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | `false` असताना गार्डरेल तत्काळ समाप्त होतो.                                                                                                                                                                   |
| मोड             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | इंजेक्शन धोरण: `block`, `warn`, किंवा `log`. (मागास सुसंगततेसाठी `redact` स्वीकारले जाते, परंतु ते इंजेक्शन मजकूर **काढत नाही**; विनंतीतील PII पुनर्लेखन `PII_REDACTION_ENABLED` द्वारे नियंत्रित केले जाते.) |
| ब्लॉक थ्रेशोल्ड | `blockThreshold` पर्याय / `INPUT_SANITIZER_BLOCK_THRESHOLD` (उपनाव `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | ब्लॉक करण्यासाठी आवश्यक असलेली किमान तीव्रता. डीफॉल्टनुसार मध्यम तीव्रता केवळ निरीक्षणासाठी असते.                                                                                                             |

**मोड प्राधान्यक्रम** (`getMode`): कॉलर `options.mode` →
`INJECTION_GUARD_MODE` **DB फीचर-फ्लॅग ओव्हरराइड** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` पर्यावरण चल → `INPUT_SANITIZER_MODE` पर्यावरण चल →
`warn`. त्यामुळे डॅशबोर्ड ओव्हरराइडला पर्यावरण चलांपेक्षा प्राधान्य मिळते आणि Feature
Flags UI चालू असलेल्या गार्डला तत्काळ नियंत्रित करते (रीस्टार्टची आवश्यकता नाही). DB वाचन अपयश-सुरक्षित आहे:
त्यात त्रुटी आल्यास गार्ड पर्यावरण-आधारित वर्तनावर परत जातो आणि कोणतेही
ओव्हरराइड सेट नसताना वर्तन केवळ पर्यावरण चलांवर आधारित निराकरणासारखेच असते.

शोध स्रोत:

1. `@/shared/utils/inputSanitizer` मधील `sanitizeRequest()` (पाइपलाइनमध्ये
   इतरत्र वापरला जाणारा सामायिक डिटेक्टर संच).
2. अंगभूत `DEFAULT_GUARD_PATTERNS` (सध्या `system_override_inline` आणि
   `markdown_system_block`, दोन्हींची तीव्रता `high`).
3. कन्स्ट्रक्टर पर्यायांद्वारे दिलेले पर्यायी `customPatterns` (स्ट्रिंग, regex,
   किंवा `{ name, pattern, severity }` रेकॉर्ड).

जेव्हा `mode === "block"` **आणि** किमान एक शोध तीव्रतेच्या
उंबरठ्याची पूर्तता करतो, तेव्हा `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` परत करतो. `warn`/`log` मोडमध्ये guardrail नोंद करतो, परंतु
कॉलला अनुमती देतो. registry मधून न जाता prompts चे मूल्यमापन करण्याची आवश्यकता असलेल्या
callers साठी सामायिक helper `evaluatePromptInjection()` देखील export केला आहे.

**स्कॅन मर्यादा (v3.8.20):** detector जोडलेल्या prompt मजकुराच्या केवळ **पहिल्या 16 KB** ची
तपासणी करतो — `src/shared/utils/inputSanitizer.ts` मध्ये
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes). pattern loop चालवण्यापूर्वी
`detectInjection()` आणि `evaluatePromptInjection()` हे दोन्ही
`slice(0, MAX_INJECTION_SCAN_BYTES)` वापरतात. Injection directives इनपुटच्या सुरुवातीच्या
भागाजवळ असतात, त्यामुळे यामुळे detection कमकुवत न करता अनेकशे-KB payloads वरील regex
CPU/GC मर्यादित राहतो (पहा #3932, #4041).

### Credential Masker (`credentialMasker.ts`)

**दोन्ही** stages वर, default chain मध्ये शेवटी (priority `95`) चालतो. outbound payload मधील
(message content, tool-call arguments, tool results) **आणि** provider response मधील
सुप्रसिद्ध API-key / secret-token patterns लपवतो, जेणेकरून prompt मध्ये paste केलेले
credential (किंवा tool result द्वारे परत दिलेले) upstream provider किंवा client कडे
लीक होणार नाही.

- **केवळ opt-in**, PII redaction प्रमाणेच प्रथा (Hard Rule #20-संबंधित):
  `settings.credentialRedactionEnabled === true` **किंवा**
  `CREDENTIAL_REDACTION_ENABLED=true` असल्याशिवाय हे अक्षम असते. ते बंद असताना guardrail
  no-op असतो — तो कधीही block करत नाही आणि कधीही पुनर्लेखन करत नाही.
- `redactCredentials()` संपूर्ण payload/response tree मधून (`walkValue()`,
  prototype-pollution-सुरक्षित, `WeakSet` मुळे cycle-सुरक्षित) फिरतो आणि जुळणारे भाग
  `[REDACTED:<type>]` placeholder ने बदलतो; प्रत्यक्षात बदललेल्या branches चेच cloning
  करतो.
- `CREDENTIAL_PATTERNS` मध्ये LLM provider keys (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS tokens (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), payment keys (Stripe, Square), cloud
  keys (AWS access key, Twilio, SendGrid, Mailgun), private keys / JWTs,
  credentials असलेल्या connection strings (`mongodb://user:pass@...`, इत्यादी), आणि
  generic `Authorization`/`x-api-key`/`api-key`/`apikey` header-value
  pattern समाविष्ट आहेत. Header-सदृश keys (`authorization`, `x-api-key`, `api-key`,
  `apikey`) generic text regex द्वारे नव्हे, तर संरचनात्मकरीत्या लपवल्या जातात (केवळ
  value; `Bearer `/`Basic ` सारखा scheme prefix जतन केला जातो).
- guardrail कधीही block करत नाही; तो फक्त पुनर्लेखन (`modifiedPayload` /
  `modifiedResponse`) आणि annotation (`meta.credentialsRedacted`, `meta.count`) करतो.

Regression guard: `tests/unit/credential-masker-guardrail.test.ts`.

## मूलभूत करार (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true असल्यास साखळीचे पुढील कार्य तत्काळ थांबते
  message?: string; // अवरोधित करताना दर्शविला जाणारा संदेश
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // विनंती पुन्हा लिहिण्यासाठी preCall कडून परत केला जातो
  modifiedResponse?: TValue; // प्रतिसाद पुन्हा लिहिण्यासाठी postCall कडून परत केला जातो
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, किंवा `{ block: false }` यांपैकी काहीही परत करून guardrail "कोणताही बदल नाही" असे सूचित करते. `modifiedPayload`/`modifiedResponse` परत केल्यास, साखळीमधून पुढील guardrails कडे जाणारे मूल्य बदलले जाते.
`signal?: AbortSignal` कॉलरचे जीवनचक्र guardrails पर्यंत पोहोचवते. विनंती रद्द करणे हा मुद्दाम ठेवलेला fail-open अपवाद आहे: ज्याला raw media समर्थित नसल्याचे माहीत आहे अशा target मध्ये ते पुनर्स्थापित न करता, media bridges काम थांबवतात आणि cleanup करतात.

## रजिस्ट्री (`registry.ts`)

singleton `guardrailRegistry` पुढील गोष्टी उपलब्ध करून देते:

- `register(guardrail)` — guardrail जोडते (किंवा normalized name नुसार बदलते) आणि चढत्या `priority` क्रमाने पुन्हा क्रमवारी लावते.
- `clear()` / `list()` — प्रशासकीय सहाय्यक.
- `runPreCallHooks(payload, context)` — सक्रिय guardrails वर पुनरावृत्ती करते, `modifiedPayload` द्वारे payload पुढे पाठवते आणि पहिल्या `block: true` वर थांबते.
- `runPostCallHooks(response, context)` — प्रतिसादाच्या बाजूने समान प्रवाह.
- `resetGuardrailsForTests({ registerDefaults })` — स्वच्छ चाचणी विलगीकरणासाठी स्थिती साफ करते आणि पर्यायाने defaults पुन्हा नोंदवते.

दोन्ही runners `{ blocked, payload|response, results, guardrail?, message? }` परत करतात, ज्यामध्ये `results` हा `GuardrailExecutionResult` नोंदींचा array असतो. या नोंदींमध्ये प्रत्येक guardrail साठी `blocked`, `skipped`, `modified`, `error`, आणि `meta` fields समाविष्ट असतात आणि त्या tracing साठी उपयुक्त असतात.

### प्रत्येक विनंतीनुसार Guardrails अक्षम करणे

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` सध्याच्या विनंतीसाठी वगळल्या जाणाऱ्या guardrail names ची पुनरावृत्ती-विरहित यादी एकत्रित करते. स्रोत (सर्व पर्यायी, सर्व एकत्रित केले जातात):

- `apiKeyInfo.disabledGuardrails`
- विनंती body मधील `disabledGuardrails` (top-level)
- विनंती body मधील `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (किंवा जुना
  `x-disabled-guardrails`)

मूल्ये strings चे arrays किंवा स्वल्पविरामाने विभक्त केलेली string असू शकतात; names lowercase kebab-case मध्ये normalize केली जातात (`pii_masker` → `pii-masker`). परिणाम `context.disabledGuardrails` द्वारे registry कडे पाठवला जातो, जी जुळणारे guardrails वगळते (`results` मध्ये `skipped: true`).

## अंमलबजावणीचा क्रम

`src/sse/handlers/chat.ts` आणि
`open-sse/handlers/chatCore.ts` मधून जाणाऱ्या प्रत्येक विनंतीसाठी:

1. `resolveDisabledGuardrails(...)` API की, बॉडी आणि हेडर्सवरून वगळण्याची यादी तयार करते.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` चढत्या प्राधान्यक्रमाने गार्डरेल्स चालवते:
   - अक्षम केलेल्या गार्डरेल्सची `skipped` म्हणून नोंद केली जाते.
   - प्रत्येक गार्डरेलचे `preCall`, `modifiedPayload` द्वारे पेलोड पुन्हा लिहू शकते.
   - पहिले `block: true` आल्यावर साखळी त्वरित थांबते आणि हँडलर गार्डरेल नकार प्रतिसाद परत करतो.
3. (संभाव्यतः पुन्हा लिहिलेला) पेलोड कॉम्बो राउटिंग आणि अपस्ट्रीम डिस्पॅचकडे जातो.
4. प्रतिसाद तयार झाल्यानंतर, `guardrailRegistry.runPostCallHooks(...)` प्रतिसादावर तीच साखळी चालवते. येथे `block: true` असल्यास अपस्ट्रीम प्रतिसाद वगळला जातो.

अपवाद निर्माण करणाऱ्या गार्डरेल्सची `error: <message>` सह नोंद केली जाते आणि `logger.warn` द्वारे लॉग केले जाते, मात्र साखळी सुरूच राहते — रचनेनुसार फेल-ओपन.

| `PII_REDACTION_ENABLED`               | `pii-masker`               | `true` असताना, विनंतीमधील PII झाकले जाते (इंजेक्शन मोडपासून स्वतंत्र).                             |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (डाउनस्ट्रीम) | प्रतिसादाच्या बाजूच्या मास्करचे वर्तन नियंत्रित करते.                                              |

Modality Bridge गार्डरेल्स पर्यावरण चलांऐवजी DB-समर्थित सेटिंग्ज स्टोअरमधून (`getSettings()`) रनटाइम संरचना वाचतात. Vision च्या प्राथमिक की
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, आणि
`modalityBridgeCacheMaxEntries` आहेत. जुन्या
`visionBridge*` की केवळ दस्तऐवजीकृत एक-चक्र वाचन फॉलबॅक म्हणून स्वीकारल्या जातात; डॅशबोर्डमधून होणाऱ्या लेखनांसाठी प्राथमिक की वापरल्या जातात. डीफॉल्ट्स आणि फॉलबॅक रिझॉल्व्हर `src/shared/constants/modalityBridgeDefaults.ts` मध्ये आहेत, तर जुन्या कॉन्स्टंट्स `src/shared/constants/visionBridgeDefaults.ts` मध्ये कायम ठेवलेल्या आहेत.

Audio हे `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, आणि `modalityBridgeAudioMaxClips`, तसेच सामायिक
`modalityBridgeCache*` सेटिंग्ज वापरते. Audio साठी जुन्या कींचा फॉलबॅक नाही, कारण या की Modality Bridge स्कीमासोबत सादर करण्यात आल्या होत्या.

Video हे `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, आणि
`modalityBridgeVideoTimeout`, तसेच सामायिक `modalityBridgeCache*` सेटिंग्ज वापरते.
ते डीफॉल्टनुसार अक्षम असते, कारण FFmpeg/ffprobe या पर्यायी कार्यान्वयन अवलंबिता आहेत आणि फ्रेम कॅप्शनिंगमुळे विलंब व मॉडेल खर्च वाढतो.

## सानुकूल Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

पायऱ्या:

1. `BaseGuardrail` विस्तारित करणारी `src/lib/guardrails/myGuardrail.ts` तयार करा.
2. `preCall` आणि/किंवा `postCall` लागू करा.
3. एकतर आयात करताना नोंदणी करा (`registerDefaultGuardrails` मधून पुश करा) किंवा
   रनटाइममध्ये `guardrailRegistry.register(...)` कॉल करा — रजिस्ट्री समान सामान्यीकृत
   नाव असलेली कोणतीही आधीची guardrail बदलते.
4. `tests/unit/` अंतर्गत चाचण्या जोडा (विद्यमान उदाहरणे:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## चाचणी

ज्ञात स्थितीपासून सुरुवात करण्यासाठी चाचण्यांदरम्यान `resetGuardrailsForTests()` वापरा.
रिकाम्या रजिस्ट्रीपासून सुरुवात करण्यासाठी `{ registerDefaults: false }` पास करा आणि
फक्त चाचणीअंतर्गत असलेल्या guardrails नोंदवा. Vision Bridge अवलंबित्व
इंजेक्शन (`deps.getSettings`, `deps.callVisionModel`) स्वीकारते; Audio Bridge सेटिंग्ज,
क्षमता, STT मॉडेल निवड, क्रेडेन्शियल तपासण्या आणि ट्रान्सक्रिप्शनसाठी समतुल्य
इंजेक्शन बिंदू उपलब्ध करून देते. त्यामुळे चाचण्या DB किंवा नेटवर्क प्रवेशाशिवाय
दोन्ही प्रवाह तपासू शकतात.

## Injection-guard मार्ग कव्हरेज आणि रेड-टीम (टप्पा 8 · ब्लॉक D)

injection-guard (`createInjectionGuard` / `withInjectionGuard`) वापरकर्त्याचे प्रॉम्प्ट स्वीकारणारे सर्व मार्ग
व्यापते. ते `INJECTION_GUARD_MODE` चे पालन करते (डीफॉल्ट `warn` = फक्त लॉग;
`block` = HTTP 400 `SECURITY_001` परत करते).

| प्रकार           | मार्ग                                                                                                                                                | डीफॉल्ट मोड |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| मजकूर (विद्यमान) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| जनरेटिव्ह        | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| डेटा             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

मजकूर निष्कर्षण (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` व्यापते.

**रेड-टीम (दररोज रात्री, `nightly-llm-security.yml`):** promptfoo हे सत्यापित करते की प्रत्येक मार्ग
`INJECTION_GUARD_MODE=block` मध्ये OWASP-LLM कॉर्पस ब्लॉक करतो; garak प्रोब्स चालवते (secret नसल्यास वगळते).
सुसंगततेसाठी `moderations` समाविष्ट केले आहे — ब्लॉक-मोडमधील ऑपरेटर `resolveDisabledGuardrails` द्वारे
त्याला सूट देऊ शकतात.

रात्रीचे वर्कफ्लो (`.github/workflows/nightly-llm-security.yml`, cron + मॅन्युअल
डिस्पॅच) दोन जॉब्सचे आहे:

- **`promptfoo-guard` (ब्लॉकिंग)** — `INJECTION_GUARD_MODE=block` सह
  `promptfoo eval -c promptfooconfig.yaml` चालवते. प्रत्येक प्रतिकूल प्रकरण (उदा. "मागील सर्व
  सूचना दुर्लक्षित करा…", DAN-शैलीतील जेलब्रेक्स) प्रतिसादात
  `error.code === "SECURITY_001"` असल्याचे निश्चित करते, म्हणजेच guard ने विनंती प्रत्यक्षात नाकारली.
- **`garak` (सल्लात्मक)** — स्थानिक OmniRoute इन्स्टन्सवर (`http://localhost:20128/v1`)
  garak `--probes promptinject,dan,leakreplay` चालवते. हे provider secret
  (`PROMPTFOO_PROVIDER_KEY`) वर अवलंबून असते; secret नसल्यास व्यवस्थितपणे वगळते आणि त्याला
  `|| true` प्रत्यय जोडलेला असतो, त्यामुळे ते CI अयशस्वी न करता अहवाल देते.

guard helper (`createInjectionGuard` / `withInjectionGuard`) चे कव्हरेज
प्रॉम्प्ट असलेल्या प्रत्येक `/v1` मार्गावर पसरलेले आहे; प्रॉम्प्ट मजकूर
`src/shared/utils/inputSanitizer.ts` मधील `extractMessageContents()` द्वारे
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` मधून घेतला जातो.
