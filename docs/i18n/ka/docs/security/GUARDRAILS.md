> **ბოლოს განახლდა:** 2026-08-29 — v3.8.51 (ვიდეო ხიდის ტრანსკრიპტის წარმომავლობა დეკლარირებულია გამომძახებლის მიერ, ჯერ არ არის სერვერის მიერ დამოწმებული — განმარტებულია #11661-ის მიხედვით)

Guardrails უზრუნველყოფენ უსაფრთხოებას, პოლიტიკას და კონტენტის ტრანსფორმაციებს OmniRoute-სა და upstream პროვაიდერებს შორის საზღვარზე. თითოეულ guardrail-ს შეუძლია შეამოწმოს (და სურვილისამებრ უარყოს, გარდაქმნას ან ანოტირება გაუკეთოს) მოთხოვნის payload-ები (`preCall`) და upstream პასუხები (`postCall`).

სისტემა არის **fail-open**: თუ guardrail-ის შესრულებისას შეცდომა მოხდა, რეგისტრატორი აღრიცხავს შეცდომას და აგრძელებს შემდეგ guardrail-ზე, ნაცვლად მოთხოვნის შეწყვეტისა. დაბლოკვა არის მკაფიო გადაწყვეტილება (`block: true`), არასდროს შემთხვევითობა.

### ხედვის ხიდი (`visionBridge.ts`) — მოდალობის ხიდი PR-1

იჭერს სურათების შემცველ მოთხოვნებს, რომლებიც მიმართულია **ხედვის მხარდაჭერის არმქონე მოდელებისკენ**, და ან
მთელ მოთხოვნას გადაამისამართებს ხედვის მხარდაჭერის მქონე მოდელზე, ან upstream
გამოძახებამდე სურათის ნაწილებს ჩაანაცვლებს კონფიგურირებადი ხედვის მოდელის მიერ
შექმნილი ტექსტური აღწერებით. ეს მხოლოდ ტექსტზე მომუშავე პროვაიდერებს
მულტიმოდალური დატვირთვების გამჭვირვალედ დამუშავების საშუალებას აძლევს.

ნაკადი:

1. გამოტოვება, თუ სამიზნე მოდელს უკვე აქვს ხედვის მხარდაჭერა (თუ ის
   იძულებითი ხიდის სიაში `isVisionBridgeForcedModel` არ არის).
2. სურათის ნაწილების ამოღება `extractImageParts(messages)`-ის მეშვეობით
   (`visionBridgeHelpers.ts`), რომელიც დელეგირებას ახდენს **მედიის ერთიან
   დეტექტორზე** `detectMediaParts()` ფაილში `open-sse/utils/mediaParts.ts` — ეს არის
   ჭეშმარიტების ერთადერთი წყარო, რომელსაც კომბინაციის თავსებადობის ფილტრიც იყენებს.
   ამოღება ნებადართულია მხოლოდ იმ ფორმების ზედა დონის ნაწილებისთვის,
   რომელთა უკან ჩასმაც `replaceImageParts`-ს შეუძლია (ამოღება↔ჩანაცვლების კონტრაქტი): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` და Responses API `input_image`. ჩადგმული დამთხვევები და
   მხოლოდ ინდიკატორის შემცველი ფორმები კომბინაციის ფილტრის მასალაა და არასდროს ამოიღება.
   გამოტოვება, თუ არცერთი არ მოიძებნა.
3. შესრულების დროის კონფიგურაციის განსაზღვრა `resolveVisionBridgeRuntimeSettings()`-ის მეშვეობით
   (`src/shared/constants/modalityBridgeDefaults.ts`): ახალი `modalityBridge*`
   პარამეტრების გასაღებებს უპირატესობა ენიჭება; ძველი `visionBridge*` გასაღებები რჩება **ერთი ციკლის
   სარეზერვო ვარიანტად** (უკანდაბრუნების ფანჯარა). თუ ხიდი გამორთულია, გამოტოვება
   მედიის ნებისმიერ შემოვლამდე.
4. რეჟიმის ამომრჩევი (`modalityBridgeVisionMode`, იხილეთ ქვემოთ მოცემული ცხრილი) განსაზღვრავს
   გადამისამართებას ან აღწერას. გადამისამართება აბრუნებს `modifiedPayload`-ს მხოლოდ შეცვლილი `model`-ით,
   დამატებით მეტამონაცემებს `{ rerouted, fromModel, toModel, imagesKept }`.
5. აღწერის გზა: სურათების რაოდენობის შეზღუდვა `maxImages`-ით, ამოცანის შესაბამისი მოთხოვნის შედგენა,
   აღწერის კეშის შემოწმება, ხედვის მოდელის **პარალელურად** გამოძახება
   (`Promise.allSettled`) და მათ ადგილას `[Image N]: <description>` ტექსტური ნაწილების
   ჩასმა. წარუმატებელი აღწერა აბრუნებს `null`-ს და სურათის თავდაპირველი ნაწილი
   **შენარჩუნდება** (#4012) — გამონაკლისია კომბინირებული აღწერის გზა, როდესაც ყველა
   აღწერა წარუმატებელია; ამ შემთხვევაში დადასტურებულად ხედვის მხარდაჭერის არმქონე upstream იღებს
   `(unavailable — no vision-capable provider connected)` ჩამნაცვლებელს (#8430).
6. `modifiedPayload`-ისა და მეტამონაცემების დაბრუნება (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### API გასაღების მოქმედების სფერო (`visionBridgeKeyScope.ts`)

როდესაც გამომძახებლის API გასაღები ზღუდავს `allowedConnections`-ს, კვოტის აუზებს
(`allowedQuotas`) ან მოდელებს (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), ხიდი გადამისამართებისა და
აღწერისთვის ირჩევს მხოლოდ იმ მოდელებს, რომელთა გამოყენებაც გასაღებს შეუძლია, და მხოლოდ იმ კავშირებზე,
რომელთა გამოყენებაც გასაღებისთვის ნებადართულია. შემდეგ აღწერის გამოძახება ყოველთვის OmniRoute-ის თვითმარყუჟის გავლით
ხორციელდება `x-omniroute-self-loop-key-id` სათაურით, რათა მიმღებმა ჩატის მოთხოვნამ
კვლავ აღასრულოს ამ გასაღების კავშირებისა და მოდელების პოლიტიკა. `enforceApiKeyPolicy()`
ამ სათაურს ითვალისწინებს მხოლოდ თვითმარყუჟის bearer-თან ერთად, ამიტომ მას წვდომის მხოლოდ
შეზღუდვა შეუძლია, ხოლო იდენტიფიკატორი, რომლის ამოცნობაც ვერ ხერხდება, უარყოფილია.

თუ გასაღებისთვის ხედვის არცერთი მოდელი არ არის ნებადართული, აღწერის გზა განზე გადგება და
მოთხოვნა უცვლელად გაივლის, ზუსტად ისე, როგორც გამორთული დამცავი მექანიზმის fail-open ქცევისას
(მეტამონაცემები `{ skipped: true, reason: "no_permitted_vision_model" }`).
გასაღების გარეშე გაგზავნილი მოთხოვნები და გასაღებები, რომლებსაც ეს შეზღუდვები არ აქვთ, ზუსტად ისე
იქცევა, როგორც ადრე.

#### ამოცანის შესაბამისი აღწერის მოთხოვნა (`modalityBridgeVisionTaskAware`)

ნაგულისხმევად **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) საბაზისო
აღწერის მოთხოვნას უმატებს **მომხმარებლის ბოლო შეტყობინების** ტექსტს (შემოკლებულს
500 სიმბოლომდე), რათა აღწერა მიმართოს იმაზე, რაც მომხმარებელმა რეალურად მოითხოვა
(codex-vision-proxy-ის პატერნი), და ხედვის მოდელს სთხოვს ხილული ტექსტის
ტრანსკრიფციას. თუ ალამი გამორთულია — ან მომხმარებლის ტექსტი არ არსებობს —
საბაზისო მოთხოვნა უცვლელად გამოიყენება.

აღწერის თვითციკლის საკუთარი OpenAI-თან თავსებადი მოთხოვნა (`callVisionModelSingle()`
ფაილში `visionBridgeHelpers.ts`) ყოველთვის ითხოვს `image_url.detail: "high"` —
უპირობოდ, ყველა გამომძახებლისთვის/პროვაიდერისთვის და კლიენტის რომელიმე სიგნალზე
დამოკიდებულების გარეშე. დაბალი დეტალიზაციით შერჩევა OCR-ის სიზუსტეს აუარესებს
ზუსტად იმ ტექსტის ტრანსკრიფციის ამოცანისთვის, რომელსაც ეს მოთხოვნა ითხოვს,
ამიტომ აღწერის გამოძახება ყოველთვის ითხოვს მაღალ დეტალიზაციას, მიუხედავად
იმისა, დეტალიზაციის რომელი დონე გამოიყენა თავდაპირველმა შემომავალმა მოთხოვნამ.
ეს მხოლოდ შიდა აღწერის მოთხოვნის სხეულზე მოქმედებს; ის არ ცვლის, თუ როგორ
გადასცემს OmniRoute გამომძახებლის საკუთარ `image_url.detail`-ს ძირითად
მოთხოვნაში — ეს ნაგულისხმევი მნიშვნელობა ცალკე გამოიყენება და მხოლოდ აღმოჩენილი
OpenCode კლიენტებისთვის, `defaultImageDetail()`-ში
(`open-sse/handlers/chatCore/upstreamBody.ts`). აღწერის თვითციკლის Anthropic-ის
სადენო ფორმატის განშტოებას `detail` ველი არ აქვს და არცერთი ნაგულისხმევი
მნიშვნელობა მასზე არ მოქმედებს.

#### აღწერის გამომავალი მონაცემების ზღვარი (`modalityBridgeVisionMaxChars`)

| გასაღები                       | ნაგულისხმევი | დიაპაზონი        |
| ------------------------------ | ------------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` ან 100–50000 |

`0` (ნაგულისხმევი) ნიშნავს, რომ **ზღვარი არ არის** — `callVisionModel()`-ის მიერ
დაბრუნებული აღწერა უცვლელად გადაიცემა, რაც არსებულ ქცევას ინარჩუნებს.
100–50000 დიაპაზონში ნებისმიერი მნიშვნელობა აღწერას ამოკლებს `…` სუფიქსის
დართვით, სანამ ის `[Image N]: <description>` სახით კვლავ ჩაისმება
(`VisionBridgeGuardrail.preCall()` ფაილში `src/lib/guardrails/visionBridge.ts`).
გაზარდეთ ეს მნიშვნელობა დეტალებით დატვირთული OCR ამოცანებისთვის, სადაც შემდგომ
მოდელს სრული ტრანსკრიფცია სჭირდება; შეამცირეთ ის მრავალსიტყვიანი ხედვის
მოდელების მიერ ტოკენების გამოყენების შესაზღუდად. დაფის ველი მდებარეობს Vision
ჩანართის Advanced პანელში (`modality-bridge-max-chars` ფაილში
`ModalityBridgeVisionTab.tsx`) და 1-დან 99-ის ჩათვლით ნებისმიერ მნიშვნელობას
100-ის მინიმუმამდე ზრდის, ხოლო ცხადად მითითებულ `0`-ს უცვლელად ტოვებს —
`0` თავისთავად დასაშვები Zod მნიშვნელობაა
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) და არა მხოლოდ
„მიუთითებელი“ ნაგულისხმევი მნიშვნელობა.

#### აღწერის კეში (`modalityBridge/bridgeCache.ts`)

მეხსიერებაში არსებული LRU + TTL კეში აღწერის შედეგებისთვის, რომელიც მთელ
პროცესში საზიაროა. გასაღები = `sha256(imageRef + composedPrompt + configuredBridgeModel)`
სიგრძის პრეფიქსით ჩარჩოების გამოყენებით (ველების საზღვრების კოლიზიების გარეშე).
მოდელის კომპონენტია **კონფიგურირებული** ხიდის მოდელი და არა მოდელი, რომელმაც
რეალურად უპასუხა — `callVisionModel`-მა შეიძლება შიგნით სათადარიგო მოდელი
გამოიყენოს, ხოლო თითოეული მცდელობის მიხედვით გასაღების შექმნა კეშს
დაანაწევრებდა. წარუმატებელი აღწერები არასოდეს კეშირდება. პარამეტრები:

| გასაღები                        | ნაგულისხმევი | დიაპაზონი |
| ------------------------------- | ------------ | --------- |
| `modalityBridgeCacheEnabled`    | `true`       | —         |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440    |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000   |

#### დისტანციური გამოსახულების ნორმალიზაცია (თვითციკლის აღწერა/base64-ის მიღება)

როდესაც ხიდი თავად იღებს **დისტანციურ** გამოსახულებას — Anthropic-ის აღწერის
თვითგამოძახებისა და claude-ის სადენო ფორმატისთვის base64-ში გარდაქმნისას
(`ensureBase64ImagesForClaudeWire`), ორივე შემთხვევაში
`visionBridgeHelpers.ts`-ში არსებული `fetchRemoteImageAsDataUri()`-ის მეშვეობით
— მიღებული მონაცემთა URI ხედვის მოდელის მოთხოვნაში ჩასმამდე გადის
`normalizeDataUri()`-ში (`open-sse/utils/imageNormalize.ts`). ზედმეტად დიდი
გამოსახულებები მცირდება ისე, რომ **გრძელი გვერდი 2048px** გახდეს (რაც ემთხვევა
ზომის ზღვარს, რომელსაც OpenAI/Anthropic უკვე იყენებს სერვერის მხარეს), რაც
ამცირებს ასატვირთ ბაიტებს/დაყოვნებას ისე, რომ არ ცვლის იმას, რასაც ხედვის
მოდელი ხედავს. ზომის შეცვლა იყენებს `sharp`-ს, რომელიც დინამიკური იმპორტით
იტვირთება: პლატფორმაზე, სადაც მისი მშობლიური ორობითი ფაილი ვერ იტვირთება,
`normalizeDataUri()` **არასოდეს წარმოქმნის გამონაკლისს** — ის საწყისი ბაიტების
უცვლელად გადაცემაზე გადადის, ამიტომ აღწერის/base64-ში გარდაქმნის გზა ყოველთვის
აგრძელებს მუშაობას. არაგამოსახულებითი ბაიტებიც (როდესაც მიღების შედეგად
დეკოდირებადი გამოსახულება არ დაბრუნდა) უცვლელად გადაიცემა. ეს ნორმალიზაცია
ვრცელდება მხოლოდ იმ გამოსახულებებზე, რომლებსაც ხიდი საკუთარი თვითგამოძახებისთვის
იღებს — ის არასოდეს გამოიყენება გამომძახებლის უცვლელად გასატარებელ საწყის
დატვირთვაზე, მხოლოდ აშკარა თანხმობით ცვლილების პრინციპის შესაბამისად
(მკაცრი წესი #20).

ახალი `modalityBridge*` გასაღებები Zod-ით მოწმდება `updateSettingsSchema`-ში
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,

მიერ გამოყენებული `modalityBridgeAudio*` ჯგუფი. მიგრაცია
`141_modality_bridge_settings.sql` არსებულ მოძველებულ `visionBridge*`
მნიშვნელობებს შესაბამის ახალ გასაღებებში აკოპირებს (იდემპოტენტურად და
ოპერატორის მიერ დაყენებული `modalityBridge*` მნიშვნელობის გადაწერის გარეშე);
მოძველებული გასაღებები ერთი გამოშვების ციკლის განმავლობაში კვლავ მიიღება
წაკითხვის სათადარიგო ვარიანტად.

#### გამჭვირვალობის სათაური + სტატისტიკა

აღწერით გარდაქმნილ პასუხებს ახლავს
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(აგებულია `buildModalityBridgeHeader()`-ის მიერ ფაილში
`modalityBridge/bridgeStats.ts`, ემატება `withModalityBridgeHeader()`-ის მიერ
ფაილში `src/sse/handlers/chatHelpers.ts`). გადამისამართებული მოთხოვნები
სათაურს **არ** იღებს — დატვირთვა ხელუხლებელი დარჩა, ხოლო მოდელის ჩანაცვლება
უკვე ჩანს პასუხის სხეულის `model` ველში.

`GET /api/modality-bridge/stats` (მართვის ავტორიზაცია, იგივე დონე, რაც
`GET /api/settings`-ს აქვს) აბრუნებს მეხსიერებაში შენახულ, თითოეული მოდალობის
მრიცხველებს
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` `vision`-ისთვის, `audio`-სთვის და
`video`-სთვის. `averageLatencyMs` მნიშვნელის სახით იყენებს `latencySamples`-ს და
არა ყველა მცდელობას; დროის გაზომვის გარეშე შესრულებული ოპერაცია ხელოვნურად არ
ქმნის ნულმილიწამიან ნიმუშს. `bridged` წარმატებული გარდაქმნების უკუთავსებად
ფსევდონიმად რჩება; წარუმატებელი მცდელობები მას არ ზრდის.
მრიცხველები, დიზაინის შესაბამისად, პროცესის ხელახლა გაშვებისას ნულდება
(ტელემეტრია და არა აღრიცხვა).

#### დაფის კონფიგურაცია

დაფის სპეციალური გვერდია
`/dashboard/settings/modality-bridge`. მისი URL-ით მისამართვადი `Vision`, `Audio`
და `Video` ჩანართები `tab` მნიშვნელობის შეცვლისას მოთხოვნის პარამეტრებს
ინარჩუნებს. Vision ჩანართში ხელმისაწვდომია ჩართვა, რეჟიმი, მოდელის არჩევა
(ავტომატური ნაგულისხმევის ჩათვლით), ამოცანის გათვალისწინებით პრომპტის შედგენა,
დროის ამოწურვის/სურათის/აღწერის სიგრძის/ქეშის გაფართოებული ლიმიტები, შესრულების
გარემოს მრიცხველები და დაცული საცდელი მოთხოვნა. Audio ჩანართიც აქტიურია: მასში
ხელმისაწვდომია ჩართვა, მხოლოდ STT მოდელის ამრჩევი Auto ვარიანტით,
დროის ამოწურვის/კლიპის მაქსიმალური ხანგრძლივობის ლიმიტები, აუდიოს მრიცხველები
და `input_audio`-ს საცდელი ტესტი. Video ჩანართი ფუნქციურია: იგი აჩვენებს
FFmpeg/ffprobe-ის შესრულების გარემოს მდგომარეობას — მომხმარებლის ინტერფეისის
ოთხი მკაფიო მდგომარეობიდან ერთ-ერთს (`unknown`, სანამ შემოწმება მიმდინარეობს ან
ვერ დასრულდა; `restricted`, როდესაც დაფის ჰოსტი loopback არ არის და შემოწმება
კლიენტის მხარეს გამოტოვებულია; `unavailable`, როდესაც შემოწმებით დადასტურდა,
რომ ის არ არსებობს; ან `available`, FFmpeg/ffprobe-ის ვერსიებთან ერთად) —
ინახავს ჩართვის/მოდელის/კადრის/ვიდეოს/დროის ამოწურვის ლიმიტებს, მოდელის ამრჩევში

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

აუდიოს შემცველ ჩატის მოთხოვნებს მანამდე იჭერს, სანამ ისინი აუდიოშეყვანის
მიმღებად უცნობ სამიზნემდე მიაღწევს. იგი ჩატის მოთხოვნას არასდროს გადაამისამართებს:
აუდიოს ნაწილები ტრანსკრიბირდება არსებული OpenAI-თან თავსებადი multipart
ბოლო წერტილის მეშვეობით, ხოლო არჩეული ჩატის მოდელი მუშაობას ტექსტური
ტრანსკრიპტებით აგრძელებს.

ნაკადი:

1. განსაზღვრეთ `supportsAudio` `getResolvedModelCapabilities()`-ის მეშვეობით.
   პროვაიდერის რეესტრის მკაფიო მეტამონაცემებს აქვს უპირატესობა, შემდეგ მოდის
   მოდელის სტატიკური მეტამონაცემები, შემდეგ კი სინქრონიზებული
   `modalities_input`. გამოცხადებული შეყვანის სია, რომელიც `audio`-ს არ შეიცავს,
   არის `false`; შესაძლებლობის დამადასტურებელი მონაცემების არარსებობისას
   მნიშვნელობა `null` რჩება. როგორც `false`, ისე `null` ააქტიურებს კონსერვატიულ
   ხიდს, ხოლო `true` მას გვერდს უვლის.
2. განსაზღვრეთ `modalityBridgeAudio*` პარამეტრები და საზიარო
   `detectMediaParts()` დეტექტორის მეშვეობით თითოეული შეტყობინებიდან ამოიღეთ
   ჩასანაცვლებლად ვარგისი ზედა დონის აუდიონაწილები. მხარდაჭერილი სადენზე
   გადაცემის ფორმებია OpenAI-ის `input_audio`, `audio_url` და
   `source.media_type: "audio/*"`. ჩადგმული აუდიო მარშრუტიზაციისთვის
   გამოვლინდება, მაგრამ ჩანაცვლების გზით არ წაიშლება. სამუშაოს მოცულობა
   შეზღუდულია `modalityBridgeAudioMaxClips`-ით; მომდევნო ნაწილები უცვლელი რჩება.
3. გამოიყენეთ კონფიგურირებული `provider/model`, ან მიეცით
   `selectAudioBridgeModel()`-ს საშუალება, სტაბილური კატალოგის თანმიმდევრობით
   გაიაროს `AUDIO_TRANSCRIPTION_PROVIDERS` და შეარჩიოს პირველი მოდელი, რომელსაც
   აქტიური პროვაიდერის გამოყენებადი ავტორიზაციის მონაცემები აქვს.
4. `callAudioTranscription()` გარდაქმნის base64/data-URI აუდიოს multipart
   `file`-ად, ან ჩამოტვირთავს დისტანციურ `audio_url`-ს მხოლოდ საჯარო გამავალი
   კავშირების დამცავი მექანიზმის გავლით, DNS-ის ფიქსაციითა და 25 MB-იანი
   შეზღუდვით. შემდეგ იგი POST მოთხოვნით აგზავნის ფაილსა და არჩეულ მოდელს
   ლოკალურ `/v1/audio/transcriptions` საკუთარ ციკლში,
   `resolveSelfLoopBearer()`-ით ავტორიზაციის გავლით. ტრანსკრიფციის არსებული
   მარშრუტი ასრულებს ავტორიზაციის მონაცემების ჩვეულებრივ მოძიებას,
   შესვენების/სიხშირის ლიმიტის დამუშავებას და პროვაიდერთან გადამისამართებას.
5. წარმატებული გამოძახებები შესაბამის ნაწილებს `[Audio N]: <transcript>`-ით
   ანაცვლებს. გამოძახებები სრულდება `Promise.allSettled`-ით: ცალკეული
   წარუმატებლობისას თავდაპირველი აუდიონაწილი შენარჩუნდება (#4012 კონტრაქტი).
   თუ ყველა გამოძახება წარუმატებელია და სამიზნისთვის დადასტურებულია
   `supportsAudio === false`, ნაწილები გახდება
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 კონტრაქტი).
   უცნობი სამიზნის (`null`) შემთხვევაში, ყველა გამოძახების წარუმატებლობისას
   მოთხოვნა უცვლელი რჩება. დადასტურებულად მხოლოდ ტექსტურ სამიზნეს, რომელსაც
   STT-ის გამოყენებადი ავტორიზაციის მონაცემები არ აქვს, იგივე მკაფიო
   ჩამნაცვლებელი ტექსტი მიეწოდება ქსელური გამოძახების გარეშე.

წარმატებული ტრანსკრიპტები იყენებს მთელი პროცესისთვის საერთო Modality Bridge-ის
LRU/TTL ქეშს. გასაღები აერთიანებს აუდიოს მითითებას, სტაბილურ
`audio-transcription` ოპერაციის ჭდეს და არჩეულ STT მოდელს; წარუმატებლობები
არასდროს ქეშდება. აუდიოს მცდელობები აახლებს საზიარო `bridged`, `cacheHits`,
`failures` და `lastUsedAt` მრიცხველებს.
გარდაქმნილი პასუხები შეიცავს
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`-ს; უცვლელი
მოთხოვნები Audio Bridge-ის სეგმენტს არ იღებს.

შესრულების გარემოს პარამეტრები DB-ში ინახება და Zod-ით მოწმდება:

| გასაღები                      | ნაგულისხმევი | დიაპაზონი      |
| ----------------------------- | ------------ | -------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —              |
| `modalityBridgeAudioModel`    | `""`         | Auto ან STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10           |

გაზიარებული კეში კვლავ იმართება `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` და `modalityBridgeCacheMaxEntries` პარამეტრებით.

### ვიდეოხიდი (`videoBridge.ts`, `videoBridgePipeline.ts`)

ცნობილი ნატიური ვიდეომხარდაჭერის არმქონე სამიზნის გამოძახებამდე ახდენს ზედა დონის ვიდეონაწილების გადაჭერას Chat Completions-ის `messages`-ში და Responses
API-ის `input`-ში.
მხარდაჭერილი ფორმატებია `input_video`, `video_url`, `video_source`, HTTPS URL-ები
და `data:video/*;base64,...` მონაცემთა URI-ები. ტექსტში არსებული უბრალო ფაილის სახელები
ვიდეოდ არ განიხილება.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) პასუხისმგებელია მოთხოვნის შემოვლაზე,
შესაძლებლობის/პოლიტიკის შემოწმებაზე, თითოეული მოთხოვნის ფარგლებში აგრეგაციასა და პასუხის დატვირთვაზე.
თითოეულ ვიდეოზე შესასრულებელი სამუშაო — მიღება, სრული შედეგის კეში, კადრების
მიმდევრობის აღწერა (რომელიც აერთიანებს გამომძახებლის მიერ დეკლარირებულ აუდიოტრანსკრიპტს) და თითოეული მცდელობის
მეტრიკები/შეწყვეტა/გასუფთავება — დამალულია `processVideoPart`-ის მიღმა
`videoBridgePipeline.ts`-ში, რომელიც `preCall`-ის ციკლში თითოეული ვიდეონაწილისთვის ერთხელ გამოიძახება.
ეს მოდული ასევე განსაზღვრავს პორტების მკაფიო საზღვრებს: `VideoMediaBrokerPort`
(ბაიტების მიღება და შერჩეული კადრების ამოღება), `VideoAudioTranscriptionPort`
(გამომძახებლის მიერ დეკლარირებული აუდიოტრანსკრიპტის შერჩეული კადრების აღწერებთან გაერთიანება) და
`VideoDrilldownPort` (კადრების დეტალიზაციის შენახვის საზღვარი; ჯერ არ არის დაკავშირებული
`processVideoPart`-თან — ამჟამად დეტალიზაციის ჩანაწერებს მხოლოდ ცალკე `/api/modality-bridge/video/drilldown`
მარშრუტი წერს).

საჯარო `/v1` მოთხოვნის გზა არასოდეს ახდენს ქვეპროცესის იმპორტს ან გამოძახებას. დისტანციური
ვიდეოები იტვირთება 50 MiB შეზღუდვით; ჩაშენებულ base64 ვიდეოებს თითო ვიდეოზე
დეკოდირებული ზომის კონსერვატიული 36 MiB ლიმიტი აქვს, რათა მოდელის/შეტყობინებების/ჩარჩოების კონვერტი
საჯარო JSON მოთხოვნის მიღების 50 MiB ლიმიტის ფარგლებში დარჩეს. ჩაშენებული მონაცემების
სიგრძე და დეკოდირებული ზომის შეფასებები მეხსიერების გამოყოფამდე მოწმდება. საწყისი დისტანციური URL-ისა და
ყოველი გადამისამართებისთვის HTTPS სავალდებულოა; გამოიყენება არსებული, მხოლოდ საჯარო მისამართებზე გამავალი
წვდომის დამცავი DNS-ის მიბმით. შემდეგ ბაიტები კვეთს ზუსტად განსაზღვრულ შიდა
`POST /api/modality-bridge/video/extract` ბროკერის საზღვარს. ეს მარშრუტი არის როგორც
`LOCAL_ONLY`, ისე `SPAWN_CAPABLE`, იღებს მხოლოდ თითოეული პროცესისთვის ავთენტიფიცირებულ,
სანდო loopback მოთხოვნას და არასოდეს იღებს URL-ს, ფაილური სისტემის ბილიკს, შესრულებად ფაილს

### PII-ის შემნიღბველი (`piiMasker.ts`)

მუშაობს **ორივე** ეტაპზე.

- **`preCall`** ქმნის payload-ის ასლს, გაივლის `system`, `messages`, `input` და
  `prompt` ველებს (მათ შორის უბრალო სტრიქონის ელემენტებს) და სტრიქონულ `content`/`text`
  ველებზე იყენებს `processPII()`-ს (`@/shared/utils/inputSanitizer`-იდან). როდესაც
  `PII_REDACTION_ENABLED=true`, აღმოჩენილი PII გამავალი
  payload-იდან იფარება. ეს არ არის დამოკიდებული `INPUT_SANITIZER_MODE`-ზე (რომელიც მხოლოდ
  prompt injection-ის პოლიტიკას აკონტროლებს). როდესაც დაფარვა გამორთულია, გამოძახება აფიქსირებს აღმოჩენების
  რაოდენობას შიგთავსის გადაწერის გარეშე.
- **`postCall`** ქმნის პასუხის ღრმა ასლს, უშვებს `sanitizePIIResponse()`-ს და
  Responses-API-ის ფორმის შემნიღბველს (`maskResponsesOutput` — მოიცავს
  `output_text`-სა და `output[].content[].text`-ს). თუ რაიმე დაფარვა შესრულდა,
  შეცვლილი პასუხი ანაცვლებს თავდაპირველს.

დამცავი მექანიზმი არასოდეს ბლოკავს; ის მხოლოდ ანოტაციას ამატებს (`meta.detections`,
`meta.redacted`) ან გადაწერს.

### Prompt Injection (`promptInjection.ts`)

მომხმარებლის მიერ მოწოდებულ შიგთავსში აღმოაჩენს მტრულ სტრუქტურებს და აღასრულებს
კონფიგურირებულ პოლიტიკას. ქცევას გარემოს ცვლადები და კონსტრუქტორის
პარამეტრები განსაზღვრავს:

| პარამეტრი         | გარემოს ცვლადი                                                                                                | ნაგულისხმევი | ეფექტი                                                                                                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ჩართულია          | `INPUT_SANITIZER_ENABLED`                                                                                     | `true`       | როდესაც `false`-ია, დამცავი მექანიზმი დაუყოვნებლივ ასრულებს მუშაობას.                                                                                                                  |
| რეჟიმი            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                               | `warn`       | ინექციის პოლიტიკა: `block`, `warn` ან `log`. (`redact` თავსებადობისთვის მიიღება, მაგრამ ინექციის ტექსტს **არ** შლის; მოთხოვნაში PII-ის გადაწერას `PII_REDACTION_ENABLED` აკონტროლებს.) |
| ბლოკირების ზღვარი | `blockThreshold` პარამეტრი / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ფსევდონიმი `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | დაბლოკვისთვის საჭირო მინიმალური სიმძიმე. ნაგულისხმევად საშუალო დონე მხოლოდ დაკვირვებისთვისაა.                                                                                          |

**რეჟიმის პრიორიტეტულობა** (`getMode`): გამომძახებლის `options.mode` →
`INJECTION_GUARD_MODE`-ის **DB feature-flag override** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` გარემოს ცვლადი → `INPUT_SANITIZER_MODE` გარემოს ცვლადი →
`warn`. შესაბამისად, Dashboard-ის override გარემოს ცვლადებზე უპირატესია, ამიტომ Feature
Flags UI გაშვებულ დამცავ მექანიზმს რეალურ დროში აკონტროლებს (გადატვირთვის გარეშე). DB-დან წაკითხვა შეცდომისადმი უსაფრთხოა:
შეცდომის შემთხვევაში დამცავი მექანიზმი გარემოზე დაფუძნებულ ქცევას უბრუნდება, ხოლო როდესაც
override დაყენებული არ არის, ქცევა მხოლოდ გარემოს ცვლადებით განსაზღვრული გადაწყვეტის იდენტურია.

აღმოჩენის წყაროები:

1. `sanitizeRequest()` `@/shared/utils/inputSanitizer`-იდან (დეტექტორების საერთო
   ნაკრები, რომელიც pipeline-ის სხვა ადგილებშიც გამოიყენება).
2. ჩაშენებული `DEFAULT_GUARD_PATTERNS` (ამჟამად `system_override_inline` და
   `markdown_system_block`, ორივე `high` სიმძიმის).
3. კონსტრუქტორის პარამეტრების მეშვეობით გადაცემული არასავალდებულო `customPatterns` (სტრიქონები, regex
   ან `{ name, pattern, severity }` ჩანაწერები).

როდესაც `mode === "block"` **და** სულ მცირე ერთი აღმოჩენილი შემთხვევა აკმაყოფილებს სიმკაცრის
ზღვარს, `preCall` აბრუნებს `{ block: true, message: "Request rejected:
suspicious content detected" }`-ს. `warn`/`log` რეჟიმებში დამცავი მექანიზმი ჩანაწერს ჟურნალში ამატებს, თუმცა
გამოძახებას უშვებს. საზიარო დამხმარე ფუნქცია `evaluatePromptInjection()` ასევე ექსპორტირებულია
იმ გამომძახებლებისთვის, რომლებსაც მოთხოვნების შეფასება რეესტრის გამოყენების გარეშე სჭირდებათ.

**სკანირების ზღვარი (v3.8.20):** დეტექტორი გაერთიანებული მოთხოვნის ტექსტის მხოლოდ
**პირველ 16 KB**-ს ამოწმებს — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ბაიტი)
`src/shared/utils/inputSanitizer.ts`-ში. როგორც `detectInjection()`, ისე
`evaluatePromptInjection()` შაბლონების ციკლის გაშვებამდე იყენებს
`slice(0, MAX_INJECTION_SCAN_BYTES)`-ს. ინექციის დირექტივები, ჩვეულებრივ, შეყვანილი მონაცემების დასაწყისთან ახლოს მდებარეობს, ამიტომ ეს
ზღუდავს regex CPU/GC-ის დატვირთვას ასეულობით KB-ის მქონე payload-ებისთვის აღმოჩენის ეფექტიანობის შემცირების გარეშე (იხ.
#3932, #4041).

### ავტორიზაციის მონაცემების შემნიღბავი (`credentialMasker.ts`)

ეშვება **ორივე** ეტაპზე, ნაგულისხმევ ჯაჭვში ბოლოს (პრიორიტეტი `95`). გამავალ payload-ში (შეტყობინების
შიგთავსში, ხელსაწყოს გამოძახების არგუმენტებში, ხელსაწყოს შედეგებში) **და** პროვაიდერის პასუხში
ფარავს API-გასაღებების / საიდუმლო ტოკენების ცნობილ შაბლონებს, რათა მოთხოვნაში ჩასმული ავტორიზაციის მონაცემები
(ან ხელსაწყოს შედეგში გამეორებული მონაცემები) არც ზედა დონის პროვაიდერთან და არც კლიენტთან
არ გაჟონოს.

- **მხოლოდ ნებაყოფლობითი ჩართვა**, იგივე პრინციპით, როგორც PII-ის რედაქტირება (Hard Rule #20-თან დაკავშირებული):
  გამორთულია, თუ `settings.credentialRedactionEnabled === true` **ან**
  `CREDENTIAL_REDACTION_ENABLED=true` არ არის მითითებული. გამორთულ მდგომარეობაში დამცავი მექანიზმი არაფერს აკეთებს —
  ის არც ბლოკავს და არც ხელახლა წერს.
- `redactCredentials()` სრულად შემოივლის payload-ის/პასუხის ხეს (`walkValue()`,
  დაცულია prototype pollution-ისგან და ციკლებისგან `WeakSet`-ის მეშვეობით) და დამთხვევებს
  `[REDACTED:<type>]` ჩამნაცვლებლით ანაცვლებს; კლონირდება მხოლოდ რეალურად
  შეცვლილი განშტოებები.
- `CREDENTIAL_PATTERNS` მოიცავს LLM-პროვაიდერების გასაღებებს (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ტოკენებს (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), გადახდის გასაღებებს (Stripe, Square), ღრუბლოვანი
  სერვისების გასაღებებს (AWS-ის წვდომის გასაღები, Twilio, SendGrid, Mailgun), პირად გასაღებებს / JWT-ებს,
  ავტორიზაციის მონაცემების შემცველ კავშირის სტრიქონებს (`mongodb://user:pass@...` და სხვ.) და
  ზოგად `Authorization`/`x-api-key`/`api-key`/`apikey` სათაურის მნიშვნელობის
  შაბლონს. სათაურის ფორმის გასაღებები (`authorization`, `x-api-key`, `api-key`,
  `apikey`) რედაქტირდება სტრუქტურულად (მხოლოდ მნიშვნელობა; სქემის პრეფიქსი, როგორიცაა
  `Bearer `/`Basic `, შენარჩუნებულია) და არა ზოგადი ტექსტური regex-ის მეშვეობით.
- დამცავი მექანიზმი არასდროს ბლოკავს; ის მხოლოდ ხელახლა წერს (`modifiedPayload` /
  `modifiedResponse`) და ანოტაციას ამატებს (`meta.credentialsRedacted`, `meta.count`).

რეგრესიისგან დამცავი ტესტი: `tests/unit/credential-masker-guardrail.test.ts`.

## საბაზისო კონტრაქტი (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ჯაჭვის შესრულებას დაუყოვნებლივ წყვეტს
  message?: string; // ნაჩვენებია დაბლოკვისას
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // მოთხოვნის გადასაწერად აბრუნებს preCall
  modifiedResponse?: TValue; // პასუხის გადასაწერად აბრუნებს postCall
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

დამცავი მექანიზმი „ცვლილება არ არის“ მდგომარეობის შესახებ მიანიშნებს `void`-ის, `{}`-ის ან
`{ block: false }`-ის დაბრუნებით. `modifiedPayload`/`modifiedResponse`-ის დაბრუნება
ჩაანაცვლებს ჯაჭვში გამავალ მნიშვნელობას მომდევნო დამცავი მექანიზმებისთვის.
`signal?: AbortSignal` გამომძახებლის სასიცოცხლო ციკლს დამცავ მექანიზმებს გადასცემს. მოთხოვნის შეწყვეტა წინასწარგანზრახული fail-open გამონაკლისია: მედია-ხიდები წყვეტენ მუშაობას და ასუფთავებენ რესურსებს ისე, რომ დაუმუშავებელი მედია არ აღადგინონ სამიზნეზე, რომლის შესახებაც ცნობილია, რომ მას მხარს არ უჭერს.

## რეგისტრატორი (`registry.ts`)

სინგლტონი `guardrailRegistry` აჩვენებს:

- `register(guardrail)` — ამატებს (ან ცვლის ნორმალიზებული სახელით) გარდრეილს და
  ხელახლა ალაგებს ზრდადი `priority`-ის მიხედვით.
- `clear()` / `list()` — ადმინისტრაციული დამხმარეები.
- `runPreCallHooks(payload, context)` — ახდენს აქტიური გარდრეილების იტერაციას,
  გადასცემს `payload`-ს `modifiedPayload`-ის გავლით და ჩერდება პირველ `block: true`-ზე.
- `runPostCallHooks(response, context)` — იგივე ნაკადი პასუხის მხარეს.
- `resetGuardrailsForTests({ registerDefaults })` — ასუფთავებს მდგომარეობას და სურვილისამებრ
  ხელახლა არეგისტრირებს ნაგულისხმევ პარამეტრებს ტესტის სუფთა იზოლაციისთვის.

ორივე რანერი აბრუნებს `{ blocked, payload|response, results, guardrail?, message? }`-ს,
სადაც `results` არის `GuardrailExecutionResult` ჩანაწერების მასივი, რომელიც მოიცავს
თითოეული გარდრეილის `blocked`, `skipped`, `modified`, `error` და `meta` ველებს,
რაც სასარგებლოა ტრეისინგისთვის.

### გარდრეილების გამორთვა თითო მოთხოვნაზე

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` აგროვებს
გარდრეილების სახელების დედუპლიცირებულ სიას, რომლებიც უნდა გამოტოვებულ იქნას
მიმდინარე მოთხოვნისთვის. წყაროები (ყველა არასავალდებულო, ყველა გაერთიანებულია):

- `apiKeyInfo.disabledGuardrails`
- მოთხოვნის სხეული `disabledGuardrails` (ზედა დონის)
- მოთხოვნის სხეული `metadata.disabledGuardrails`
- ჰედერი `x-omniroute-disabled-guardrails` (ან მოძველებული
  `x-disabled-guardrails`)

მნიშვნელობები შეიძლება იყოს სტრიქონების მასივები ან მძიმით გამოყოფილი სტრიქონი;
სახელები ნორმალიზდება პატარა ასოებით kebab-case-ში (`pii_masker` → `pii-masker`).
შედეგი გადაეცემა `context.disabledGuardrails`-ის გავლით რეგისტრატორს,
რომელიც გამოტოვებს შესაბამის გარდრეილებს (`skipped: true` `results`-ში).

## შესრულების თანმიმდევრობა

ყოველი მოთხოვნისთვის, რომელიც გადის `src/sse/handlers/chat.ts`-სა და `open-sse/handlers/chatCore.ts`-ის გავლით:

1.  `resolveDisabledGuardrails(...)` აგებს გამოტოვების სიას API გასაღებიდან, სხეულიდან და სათაურებიდან.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` ასრულებს დამცავ მექანიზმებს პრიორიტეტის ზრდადი თანმიმდევრობით:
    - გამორთული დამცავი მექანიზმები აღირიცხება როგორც `skipped`.
    - თითოეული დამცავი მექანიზმის `preCall`-მა შეიძლება გადაწეროს მონაცემთა პაკეტი `modifiedPayload`-ის მეშვეობით.
    - პირველი `block: true` წყვეტს ჯაჭვს და დამმუშავებელი აბრუნებს დამცავი მექანიზმის უარყოფის პასუხს.
3.  (პოტენციურად გადაწერილი) მონაცემთა პაკეტი მიედინება კომბინირებულ მარშრუტიზაციასა და ზედა დინების გაგზავნაში.
4.  პასუხის აწყობის შემდეგ, `guardrailRegistry.runPostCallHooks(...)` აწარმოებს იმავე ჯაჭვს პასუხზე. `block: true` აქ აგდებს ზედა დინების პასუხს.

დამცავი მექანიზმები, რომლებიც შეცდომას აგდებენ, აღირიცხება `error: <message>`-ით და აღინიშნება `logger.warn`-ის მეშვეობით, მაგრამ ჯაჭვი გრძელდება — დიზაინით ღიაა წარუმატებლობისთვის.

## მორგებული Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ნაბიჯები:

1.  შექმენით `src/lib/guardrails/myGuardrail.ts`, რომელიც აფართოებს `BaseGuardrail`-ს.
2.  განახორციელეთ `preCall` და/ან `postCall`.
3.  ან დაარეგისტრირეთ იმპორტის დროს (`registerDefaultGuardrails`-დან დამატებით) ან გამოიძახეთ `guardrailRegistry.register(...)` გაშვების დროს — რეესტრი ჩაანაცვლებს ნებისმიერ წინა guardrail-ს იგივე ნორმალიზებული სახელით.
4.  დაამატეთ ტესტები `tests/unit/`-ში (არსებული მაგალითები: `tests/unit/guardrails-registry.test.ts`, `tests/unit/prompt-injection-guard.test.ts`, `tests/unit/guardrails/visionBridge.test.ts`).

## ტესტირება

გამოიყენეთ `resetGuardrailsForTests()` ტესტებს შორის, რათა დაიწყოთ ცნობილი მდგომარეობიდან. გადაეცით `{ registerDefaults: false }`, რათა დაიწყოთ ცარიელი რეესტრით და დაარეგისტრიროთ მხოლოდ ტესტირებადი guardrails. Vision Bridge იღებს დამოკიდებულების ინექციას (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge აჩვენებს ექვივალენტურ წერტილებს პარამეტრებისთვის, შესაძლებლობებისთვის, STT მოდელის არჩევისთვის, სერთიფიკატების შემოწმებისთვის და ტრანსკრიფციისთვის. ამიტომ, ტესტებს შეუძლიათ ორივე ნაკადის შემოწმება მონაცემთა ბაზის ან ქსელზე წვდომის გარეშე.

## ინექციისგან დამცავი მარშრუტების დაფარვა და წითელი გუნდი (ფაზა 8 · ბლოკი D)

ინექციისგან დამცავი მექანიზმი (`createInjectionGuard` / `withInjectionGuard`) მოიცავს ყველა მარშრუტს, რომელიც იღებს მომხმარებლის მოთხოვნებს. ის ითვალისწინებს `INJECTION_GUARD_MODE`-ს (ნაგულისხმევი `warn` = მხოლოდ ჟურნალი; `block` = აბრუნებს HTTP 400 `SECURITY_001`).

| ტიპი            | მარშრუტები                                                                                                                                           | ნაგულისხმევი რეჟიმი |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| Text (existing) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                |
| Generative      | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                |
| Data            | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                |

ტექსტის ამოღება (`extractMessageContents`) მოიცავს `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-ს.

**წითელი გუნდი (ღამის, `nightly-llm-security.yml`):** promptfoo ამოწმებს, რომ თითოეული მარშრუტი ბლოკავს OWASP-LLM კორპუსს `INJECTION_GUARD_MODE=block` რეჟიმში; garak აწარმოებს ზონდებს (გამოტოვებს საიდუმლოს გარეშე). `moderations` შედის თანმიმდევრულობისთვის — ოპერატორებს ბლოკირების რეჟიმში შეუძლიათ მისი გათავისუფლება `resolveDisabledGuardrails`-ის მეშვეობით.

ღამის სამუშაო პროცესი (`.github/workflows/nightly-llm-security.yml`, cron + ხელით გაშვება) მოიცავს ორ დავალებას:

- **`promptfoo-guard` (ბლოკირება)** — აწარმოებს `promptfoo eval -c promptfooconfig.yaml`-ს `INJECTION_GUARD_MODE=block`-ით. თითოეული მტრული შემთხვევა (მაგ. „უგულებელყავით ყველა წინა ინსტრუქცია…“, DAN-ის სტილის jailbreaks) ადასტურებს, რომ პასუხი შეიცავს `error.code === "SECURITY_001"`, ანუ guard-მა რეალურად უარყო მოთხოვნა.
- **`garak` (საკონსულტაციო)** — აწარმოებს garak `--probes promptinject,dan,leakreplay`-ს ლოკალური OmniRoute ინსტანციის წინააღმდეგ (`http://localhost:20128/v1`). დაცულია პროვაიდერის საიდუმლო გასაღებით (`PROMPTFOO_PROVIDER_KEY`); გამოტოვებს შეცდომის გარეშე და დამატებულია `|| true`, ასე რომ, ის აფიქსირებს CI-ის ჩავარდნის გარეშე.

guard დამხმარის (`createInjectionGuard` / `withInjectionGuard`) დაფარვა მოიცავს ყველა მოთხოვნის შემცველ `/v1` მარშრუტს; მოთხოვნის ტექსტი ამოღებულია `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-დან `extractMessageContents()` ფუნქციის მიერ `src/shared/utils/inputSanitizer.ts`-ში.
