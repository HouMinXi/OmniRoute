## Feature Flag ជាអ្វី

Feature flag គឺជាកុងតាក់ដែលមានឈ្មោះ (boolean ឬ enum) ដែលតម្លៃរបស់វាអាចត្រូវបានផ្លាស់ប្តូរ
នៅពេលដំណើរការ និងរក្សាទុកក្នុងមូលដ្ឋានទិន្នន័យ ដោយមិនតម្រូវឱ្យដាក់ process ឱ្យដំណើរការឡើងវិញ។ Flag
នីមួយៗត្រូវបានពិពណ៌នាដោយ `FeatureFlagDefinition` ដែលមាន `key`, `label`,
`description`, `category`, `defaultValue`, `type` និងព័ត៌មានណែនាំ `requiresRestart`។

### លំដាប់នៃការកំណត់តម្លៃ

**តម្លៃជាក់ស្តែង** របស់ flag ត្រូវបានកំណត់ដោយ
[`resolveFeatureFlag()`](../../src/shared/utils/featureFlags.ts) តាមលំដាប់អាទិភាពខាងក្រោម (អាទិភាពខ្ពស់ជាងគេមានប្រសិទ្ធភាព)៖

1. **ការកំណត់ជំនួសក្នុង DB** — តម្លៃដែលបានរក្សាទុកក្នុងតារាង `key_value` ក្រោម
   namespace `feature_flags` (កំណត់តាមរយៈផ្ទាំងគ្រប់គ្រង ឬ REST API)។
2. **អថេរបរិស្ថាន** — `process.env[<KEY>]` ប្រសិនបើត្រូវបានកំណត់ និងមិនមែនជាតម្លៃទទេ។
3. **តម្លៃលំនាំដើមនៃនិយមន័យ** — `defaultValue` ពី `featureFlagDefinitions.ts`។

Boolean flag ត្រូវបានចាត់ទុកថា **បានបើក** នៅពេលតម្លៃជាក់ស្តែងរបស់វាគឺ `"true"`,
`"1"` ឬ `"yes"` (សូមមើល `isFeatureFlagEnabled()`)។

> [!NOTE]
> Flag ភាគច្រើនក៏មានអថេរបរិស្ថានដែលត្រូវគ្នា និងមាន **ឈ្មោះដូចគ្នា**
> ដែលបានចងក្រងជាឯកសារនៅក្នុង [`ENVIRONMENT.md`](./ENVIRONMENT.md)។ ការកំណត់ជំនួសក្នុង DB របស់ flag
> មានអាទិភាពលើអថេរបរិស្ថាននោះ។ Flag ដែលមាន
> `requiresRestart: true` ត្រូវបានរក្សាទុកភ្លាមៗ ប៉ុន្តែត្រូវបានអានឡើងវិញតែនៅពេល
> process ចាប់ផ្តើមប៉ុណ្ណោះ — ការបិទបើកវានឹងបង្ហាញបដា **"ចាប់ផ្តើមម៉ាស៊ីនមេឡើងវិញ"** នៅក្នុងផ្ទាំងគ្រប់គ្រង។

#### `PUT /api/settings/feature-flags`

កំណត់ ឬលុបការបដិសេធតែមួយ។ តួ៖ `{ key: string; value?: string }`។
ការលុបចោល `value` នឹងលុបការបដិសេធ (ស្ដារ env / default)។

```bash
# Set a DB override
curl -X PUT http://localhost:20128/api/settings/feature-flags \
  -H "Content-Type: application/json" \
  -d '{"key":"REQUIRE_API_KEY","value":"true"}'

# Remove the override (no "value")
curl -X PUT http://localhost:20128/api/settings/feature-flags \
  -H "Content-Type: application/json" \
  -d '{"key":"REQUIRE_API_KEY"}'
```

ការឆ្លើយតបបង្ហាញពី `effectiveValue`/`source` ថ្មី, `previousValue`/
`previousSource` និង `requiresRestart`។ គន្លឹះដែលមិនស្គាល់ និងតម្លៃ enum ដែលហួសពីជួរត្រូវបានបដិសេធដោយ `400`។

#### `DELETE /api/settings/feature-flags`

ជម្រះការបដិសេធ DB **ទាំងអស់** ក្នុងពេលតែមួយ ដោយស្ដារទង់នីមួយៗទៅតម្លៃ env / default របស់វា។ ប្រគល់ `{ cleared: <count>, message: "..." }` មកវិញ។

> [!NOTE]
> ទង់ដែលមាន `requiresRestart: true` មានប្រសិទ្ធភាពតែបន្ទាប់ពីដំណើរការត្រូវបានផ្ទុកឡើងវិញ។
> លំហូរចាប់ផ្ដើមឡើងវិញរបស់ផ្ទាំងគ្រប់គ្រងហៅ `POST /api/restart` ហើយបន្ទាប់មកស្ទង់ `GET /api/health/ping` រហូតដល់ម៉ាស៊ីនមេដំណើរការឡើងវិញ។

## ជម្រើសបម្រុងថវិកាបន្ទាន់

`OMNIROUTE_EMERGENCY_FALLBACK` (ប្រភេទ `runtime`, លំនាំដើម `true`) គ្រប់គ្រងផ្លូវជម្រើសបម្រុងឥតគិតថ្លៃសម្រាប់ករណីបន្ទាន់នៅក្នុង
[`open-sse/services/emergencyFallback.ts`](../../open-sse/services/emergencyFallback.ts)។
នៅពេលបើកដំណើរការ សំណើដែលប្រើថវិការបស់ខ្លួនអស់នឹងត្រូវបានបញ្ជូនទៅកាន់អ្នកផ្តល់សេវា/ម៉ូដែលជម្រើសបម្រុងឥតគិតថ្លៃ ជំនួសឱ្យការបរាជ័យទាំងស្រុង។ កំណត់វាទៅជា `false` (ឬ `0`) — តាមរយៈប៊ូតុងបិទបើកលើផ្ទាំងគ្រប់គ្រង ការកំណត់ជាន់លើក្នុង DB ឬអថេរបរិស្ថាន `OMNIROUTE_EMERGENCY_FALLBACK` — ដើម្បីបិទឥរិយាបថនេះ ហើយអនុញ្ញាតឱ្យសំណើដែលប្រើថវិកាអស់បរាជ័យ។ (បង្ហាញជាប៊ូតុងបិទបើកលើផ្ទាំងគ្រប់គ្រងនៅក្នុង PRs #3741 / #3752។)

ការឆ្លើយតបដែលផ្តល់ដោយជម្រើសបម្រុងនេះមាន
`X-OmniRoute-Emergency-Fallback: from=<provider/model>; to=<provider/model>` ដូច្នេះកម្មវិធីភាគីអតិថិជនអាចដឹងថាវាត្រូវបានបញ្ជូនបន្តដោយមិនចាំបាច់ប្រៀបធៀប `X-OmniRoute-Provider` ជាមួយសំណើរបស់វា។ បឋមកថានេះមិនមាននៅក្នុងការឆ្លើយតបផ្សេងទៀតទាំងអស់ទេ។
