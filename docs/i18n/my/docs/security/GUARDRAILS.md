> **နောက်ဆုံးမွမ်းမံထားသည့်ရက်:** 2026-08-29 — v3.8.51 (Video Bridge transcript ၏ မူလရင်းမြစ်ကို ခေါ်ယူသူက ကြေညာသတ်မှတ်ထားခြင်းဖြစ်ပြီး၊
> server က အတည်ပြုစစ်ဆေးထားခြင်း မရှိသေးပါ — #11661 အရ ရှင်းလင်းထားသည်)

Guardrail များသည် OmniRoute နှင့် upstream provider များကြား နယ်နိမိတ်တွင်
ဘေးကင်းလုံခြုံမှု၊ မူဝါဒနှင့် အကြောင်းအရာပြောင်းလဲမှုများကို အတည်ပြုကျင့်သုံးစေသည်။ Guardrail တစ်ခုစီသည် request payload များကို (`preCall`) နှင့်
upstream response များကို (`postCall`) စစ်ဆေးနိုင်ပြီး (လိုအပ်ပါက
ငြင်းပယ်ခြင်း၊ ပြောင်းလဲခြင်း သို့မဟုတ် မှတ်ချက်ထည့်ခြင်းတို့ကို ပြုလုပ်နိုင်သည်)။

စနစ်သည် **fail-open** ဖြစ်သည်။ Guardrail တစ်ခုကို လုပ်ဆောင်နေစဉ် exception ဖြစ်ပေါ်ပါက registry သည်
error ကို မှတ်တမ်းတင်ပြီး request ကို ပျက်ကွက်စေမည့်အစား နောက် guardrail ဖြင့်
ဆက်လက်လုပ်ဆောင်သည်။ ပိတ်ဆို့ခြင်းသည် မတော်တဆဖြစ်ပေါ်ခြင်း မဟုတ်ဘဲ တိကျရှင်းလင်းသော ဆုံးဖြတ်ချက် (`block: true`) ဖြစ်သည်။

## အသင့်ပါ Guardrail များ

Registry ကို import လုပ်သည့်အခါ priority အစဉ်အတိုင်း guardrail ခြောက်ခုကို အလိုအလျောက် load လုပ်သည်
(`registry.ts` → `registerDefaultGuardrails()` ကိုကြည့်ပါ):

| Priority | အမည်                | Stage(s)       | ဖိုင်                 |
| -------- | ------------------- | -------------- | --------------------- |
| `5`      | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`      | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`      | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`     | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`     | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`     | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Priority နံပါတ်နိမ့်သောအရာများကို **ဦးစွာ** လုပ်ဆောင်သည်။

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

**Vision မပံ့ပိုးသော model များ** ဆီသို့ ပို့ထားသည့် image ပါဝင်သော request များကို ကြားဖြတ်ပြီး request တစ်ခုလုံးကို vision-capable model တစ်ခုသို့ reroute လုပ်သည် သို့မဟုတ် upstream call မတိုင်မီ image အပိုင်းများကို configure လုပ်နိုင်သော vision model တစ်ခုက ဖန်တီးပေးသည့် စာသားဖော်ပြချက်များဖြင့် အစားထိုးသည်။ ဤနည်းဖြင့် text-only provider များသည် multimodal payload များကို ပွင့်လင်းမြင်သာစွာ ကိုင်တွယ်နိုင်သည်။

လုပ်ဆောင်မှုစီးဆင်းပုံ:

1. Target model သည် vision ကို ပံ့ပိုးပြီးဖြစ်ပါက ကျော်သွားသည် (`isVisionBridgeForcedModel` forced-bridge စာရင်းတွင် ပါဝင်နေခြင်းမှလွဲ၍)။
2. `extractImageParts(messages)` မှတစ်ဆင့် image အပိုင်းများကို ထုတ်ယူသည်
   (`visionBridgeHelpers.ts`)။ ၎င်းသည် `open-sse/utils/mediaParts.ts` ရှိ **ပေါင်းစည်းထားသော media
   detector** `detectMediaParts()` သို့ တာဝန်လွှဲပေးပြီး၊ ၎င်းသည် combo compatibility filter နှင့် မျှဝေအသုံးပြုသော တစ်ခုတည်းသော ယုံကြည်ရသည့် အရင်းအမြစ်ဖြစ်သည်။
   Extraction ကို `replaceImageParts` က ပြန်လည်ထည့်သွင်းနိုင်သည့် အောက်ပါ top-level အပိုင်းပုံစံများသာ allowlist လုပ်ထားသည် (extract↔replace contract): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` နှင့် Responses API `input_image`။ Nested hit များနှင့် indicator-only ပုံစံများသည် combo-filter အတွက်သာဖြစ်ပြီး မည်သည့်အခါမျှ ထုတ်ယူခြင်းမပြုပါ။
   မတွေ့ရှိပါက ကျော်သွားသည်။
3. `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) မှတစ်ဆင့် runtime config ကို ဖြေရှင်းသည်။ `modalityBridge*`
   setting key အသစ်များကို ဦးစားပေးပြီး၊ အဟောင်း `visionBridge*` key များကို **cycle တစ်ခုစာ
   fallback** (rollback window) အဖြစ် ဆက်လက်ထားရှိသည်။ Bridge ကို ပိတ်ထားပါက မည်သည့် media traversal မပြုလုပ်မီ ကျော်သွားသည်။
4. Mode selector (`modalityBridgeVisionMode`, အောက်ပါဇယားကိုကြည့်ပါ) က
   reroute လုပ်မည် သို့မဟုတ် ဖော်ပြချက်ဖန်တီးမည်ကို ဆုံးဖြတ်သည်။ Reroute သည် `model` ကိုသာ
   ပြောင်းလဲထားသော `modifiedPayload` နှင့်အတူ meta `{ rerouted, fromModel, toModel, imagesKept }` ကို ပြန်ပေးသည်။
5. Describe လမ်းကြောင်းတွင် image အရေအတွက်ကို `maxImages` ဖြင့် ကန့်သတ်ခြင်း၊ task-aware prompt ကို စုစည်းခြင်း၊ describe cache ကို စစ်ဆေးခြင်း၊ vision model ကို **ပြိုင်တူ**
   ခေါ်ဆိုခြင်း (`Promise.allSettled`) နှင့် မူလနေရာများတွင် `[Image N]: <description>` စာသားအပိုင်းများ ထည့်သွင်းခြင်းတို့ ပြုလုပ်သည်။
   Describe မအောင်မြင်ပါက `null` ကို ရရှိပြီး မူလ image အပိုင်းကို
   **ဆက်လက်ထိန်းသိမ်းထားသည်** (#4012) — သို့သော် describe အားလုံး မအောင်မြင်သော combo describe လမ်းကြောင်းတွင် အတည်ပြုပြီးသား non-vision upstream အတွက်
   `(မရရှိနိုင်ပါ — vision-capable provider ချိတ်ဆက်ထားခြင်းမရှိပါ)` stub ကို အစားထိုးအသုံးပြုသည် (#8430)။
6. `modifiedPayload` နှင့် meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) ကို ပြန်ပေးသည်။

#### Mode selector (`modalityBridgeVisionMode`)

| Mode       | Default | လုပ်ဆောင်ပုံ                                                                                                                                                                                                                                                                                                                               |
| ---------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔       | အဟောင်း heuristic ကို မပြောင်းလဲဘဲ အသုံးပြုသည် (#6640/#7204): မူလ model တွင် အသုံးပြုနိုင်သော credential များရှိပြီးသားမဟုတ်ပါက non-combo/`auto/` model များကို အကောင်းဆုံး vision model သို့ reroute လုပ်သည် (credential များရှိပြီးသားဖြစ်ပါက describe လုပ်သည်)။ Combo target များကို အမြဲ describe လုပ်သည်။                             |
| `describe` |         | အမြဲ describe လုပ်သည် — reroute block တစ်ခုလုံးကို ကျော်သွားပြီး အသုံးပြုသူရွေးချယ်ထားသည့် model က အမြဲဖြေကြားသည်။                                                                                                                                                                                                                         |
| `reroute`  |         | Reroute ကို အတင်းအကျပ်လုပ်သည်။ Credential ရှိသော model ကို ဆက်လက်အသုံးပြုသည့် guard ကို ကျော်သွားသည်။ Reroute-**target** credential guard သည် ဆက်လက်သက်ရောက်ဆဲဖြစ်သည် — အသုံးပြုနိုင်သော vision target မရှိပါက request သည် describe သို့ ဆက်လက်ရောက်ရှိသွားသဖြင့် raw image များသည် text-only backend သို့ မည်သည့်အခါမျှ မရောက်ပါ (#8430)။ |

Forced mode များသည် auto heuristic မလုပ်ဆောင်မီ **ချက်ချင်းအဆုံးသတ်သည်**။ `auto` ၏ လုပ်ဆောင်ပုံသည်
PR-1 မတိုင်မီ guardrail နှင့် byte အဆင့်အထိ တစ်ထပ်တည်းဖြစ်သည်။

#### API-key scope (`visionBridgeKeyScope.ts`)

ခေါ်ဆိုသူ၏ API key က `allowedConnections`, quota pool များ
(`allowedQuotas`) သို့မဟုတ် model များ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) ကို ကန့်သတ်ထားသည့်အခါ bridge သည် ထို key က အသုံးပြုခွင့်ရှိသော connection များပေါ်ရှိ၊ ထို key က အသုံးပြုခွင့်ရှိသော model များကိုသာ reroute နှင့် describe အတွက် ရွေးချယ်သည်။ ထို့နောက် describe call သည်
`x-omniroute-self-loop-key-id` header ပါသော OmniRoute self-loop မှတစ်ဆင့် အမြဲဖြတ်သန်းသဖြင့် လက်ခံသည့် chat request က ထို key ၏ connection နှင့် model policy ကို ထပ်မံလိုက်နာစေသည်။ `enforceApiKeyPolicy()`
သည် ထို header ကို self-loop bearer နှင့် အတူပါရှိမှသာ လက်ခံသဖြင့် access ကို ကျဉ်းမြောင်းစေရုံသာ လုပ်နိုင်ပြီး ဖြေရှင်း၍မရသော id ကို ငြင်းပယ်သည်။

Key အတွက် ခွင့်ပြုထားသော vision model မရှိပါက describe လမ်းကြောင်းသည် ဖယ်ပေးပြီး request ကို မပြောင်းလဲဘဲ ဆက်လက်ဖြတ်သန်းစေသည်။ ၎င်းသည် ပိတ်ထားသော guardrail ကဲ့သို့ပင် fail-open လုပ်ဆောင်ပုံဖြစ်သည် (meta `{ skipped: true, reason: "no_permitted_vision_model" }`)။
Key မပါသော request များနှင့် ဤကန့်သတ်ချက်များမရှိသော key များသည် ယခင်အတိုင်း အတိအကျ လုပ်ဆောင်သည်။

#### Task-aware describe prompt (`modalityBridgeVisionTaskAware`)

မူလတန်ဖိုးမှာ **true** ဖြစ်သည်။ `composeVisionPrompt()` (`visionBridgeHelpers.ts`) သည် အခြေခံ describe prompt နောက်တွင် **နောက်ဆုံး user message** ၏ စာသားကို (စာလုံးရေ 500 အထိ ဖြတ်တောက်ထားပြီး) ထည့်ပေးသည်။ ထို့ကြောင့် ဖော်ပြချက်ကို အသုံးပြုသူ အမှန်တကယ် မေးမြန်းထားသည့်အရာဘက်သို့ ဦးတည်ပေးနိုင်ပြီး (codex-vision-proxy ပုံစံ) မြင်ရသော စာသားများကို ကူးရေးပေးရန် vision model အား တောင်းဆိုသည်။ Flag ကို ပိတ်ထားလျှင် — သို့မဟုတ် user စာသား မရှိလျှင် — အခြေခံ prompt ကို မပြောင်းလဲဘဲ အသုံးပြုသည်။

Describe self-loop ၏ ကိုယ်ပိုင် OpenAI-compatible request (`visionBridgeHelpers.ts` ထဲရှိ `callVisionModelSingle()`) သည် `image_url.detail: "high"` ကို အမြဲတောင်းဆိုသည် — caller/provider တိုင်းအတွက် ခြွင်းချက်မရှိဖြစ်ပြီး၊ client signal တစ်ခုခုအပေါ် မူတည်၍ ကန့်သတ်ထားခြင်း မရှိပါ။ Low-detail sampling သည် ဤ prompt က တောင်းဆိုထားသည့် စာသားကူးရေးခြင်းလုပ်ငန်းအတွက် OCR တိကျမှုကို လျော့ကျစေသောကြောင့်၊ မူလဝင်လာသော request က မည်သည့် detail level ကို အသုံးပြုထားသည်ဖြစ်စေ describe call ကိုယ်တိုင်က high detail ကို အမြဲတောင်းဆိုသည်။ ၎င်းသည် အတွင်းပိုင်း describe request body ကိုသာ သက်ရောက်သည်။ OmniRoute က caller ၏ ကိုယ်ပိုင် `image_url.detail` ကို အဓိက request တွင် မည်သို့ forward လုပ်သည်ကို မပြောင်းလဲပါ — ထို default ကို သီးခြားအသုံးချပြီး၊ `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) ထဲတွင် စစ်ဆေးတွေ့ရှိထားသော OpenCode clients များအတွက်သာ အသုံးချသည်။ Describe self-loop ၏ Anthropic wire-format branch တွင် `detail` field မရှိသဖြင့် default နှစ်မျိုးစလုံး၏ သက်ရောက်မှု မရှိပါ။

#### Describe output အများဆုံးကန့်သတ်ချက် (`modalityBridgeVisionMaxChars`)

| Key                            | မူလတန်ဖိုး | အပိုင်းအခြား            |
| ------------------------------ | ---------- | ----------------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` သို့မဟုတ် 100–50000 |

`0` (မူလတန်ဖိုး) သည် **ကန့်သတ်ချက်မရှိ** ဟု ဆိုလိုသည် — `callVisionModel()` မှ ပြန်ပေးသော ဖော်ပြချက်ကို ပြင်ဆင်ခြင်းမရှိဘဲ ဆက်လက်ပေးပို့သဖြင့် လက်ရှိအပြုအမူကို ထိန်းသိမ်းထားသည်။ 100–50000 အပိုင်းအခြားအတွင်းရှိ မည်သည့်တန်ဖိုးမဆို ဖော်ပြချက်ကို `[Image N]: <description>` အဖြစ် ပြန်လည်ပေါင်းထည့်ခြင်းမပြုမီ `…` နောက်ဆက်ဖြင့် ဖြတ်တောက်သည် (`src/lib/guardrails/visionBridge.ts` ထဲရှိ `VisionBridgeGuardrail.preCall()`)။ Downstream model က ကူးရေးထားသည့် စာသားအပြည့်အစုံကို လိုအပ်သော အသေးစိတ်များပြားသည့် OCR လုပ်ငန်းများအတွက် ဤတန်ဖိုးကို မြှင့်ပါ။ စကားများသော vision models များ၏ token အသုံးပြုမှုကို ကန့်သတ်ရန် လျှော့ပါ။ Dashboard field သည် Vision tab ၏ Advanced panel တွင်ရှိပြီး (`ModalityBridgeVisionTab.tsx` ထဲရှိ `modality-bridge-max-chars`) 1 မှ 99 အတွင်း မည်သည့်တန်ဖိုးကိုမဆို အနည်းဆုံး 100 အထိ မြှင့်ကန့်သတ်ပေးသော်လည်း အတိအလင်း သတ်မှတ်ထားသော `0` ကို မပြောင်းလဲဘဲ ထားသည် — `0` သည် "unset" မူလတန်ဖိုးတစ်ခုမျှသာ မဟုတ်ဘဲ ကိုယ်ပိုင်အခွင့်အရေးဖြင့် မှန်ကန်သော Zod value တစ်ခုဖြစ်သည် (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`)။

#### Describe cache (`modalityBridge/bridgeCache.ts`)

Describe outputs များအတွက် process တစ်ခုလုံးတွင် မျှဝေအသုံးပြုသော in-memory LRU + TTL cache ဖြစ်သည်။
Key = `sha256(imageRef + composedPrompt + configuredBridgeModel)` ဖြစ်ပြီး length-prefix framing ကို အသုံးပြုသည် (field-boundary တိုက်ဆိုင်မှုများ မရှိပါ)။ Model component သည် အမှန်တကယ် အဖြေပေးခဲ့သော model မဟုတ်ဘဲ **ပြင်ဆင်သတ်မှတ်ထားသော** bridge model ဖြစ်သည် — `callVisionModel` သည် အတွင်းပိုင်းတွင် fallback လုပ်နိုင်ပြီး attempt တစ်ခုချင်းစီအလိုက် key သတ်မှတ်ခြင်းက cache ကို အစိတ်စိတ်အမွှာမွှာ ဖြစ်စေမည်။ မအောင်မြင်သော describe များကို cache ထဲ လုံးဝမသိမ်းပါ။ Settings များမှာ-

| Key                             | မူလတန်ဖိုး | အပိုင်းအခြား |
| ------------------------------- | ---------- | ------------ |
| `modalityBridgeCacheEnabled`    | `true`     | —            |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440       |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000      |

#### Remote image normalization (self-loop describe/base64 fetch)

Bridge က **remote** image တစ်ခုကို ကိုယ်တိုင် fetch လုပ်သောအခါ — Anthropic describe self-call နှင့် claude-wire-format base64 conversion (`ensureBase64ImagesForClaudeWire`) နှစ်ခုစလုံးက `visionBridgeHelpers.ts` ထဲရှိ `fetchRemoteImageAsDataUri()` မှတစ်ဆင့် လုပ်ဆောင်သည် — ရရှိလာသော data URI ကို vision-model request ထဲ ထည့်သွင်းမီ `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) မှတစ်ဆင့် ဖြတ်သန်းစေသည်။ အရွယ်အစားကြီးလွန်းသော images များကို **2048px long edge** အထိ လျှော့ချသည် (OpenAI/Anthropic က server-side တွင် အသုံးပြုနှင့်ပြီးသော resize cap နှင့် ကိုက်ညီသည်)။ ၎င်းသည် vision model မြင်ရသည့်အရာကို မပြောင်းလဲစေဘဲ upload bytes/latency ကို လျှော့ချပေးသည်။ Resizing အတွက် dynamic import မှတစ်ဆင့် load လုပ်ထားသော `sharp` ကို အသုံးပြုသည်။ ၎င်း၏ native binary ကို load လုပ်ရန် မအောင်မြင်သော platform တွင် `normalizeDataUri()` သည် **လုံးဝ error မပစ်ပါ** — မူလ bytes များကို ပြောင်းလဲခြင်းမရှိဘဲ passthrough လုပ်သည့်ပုံစံသို့ fallback လုပ်သောကြောင့် describe/base64-conversion လမ်းကြောင်းသည် အမြဲ ဆက်လက်အလုပ်လုပ်နိုင်သည်။ Non-image bytes များ (decode လုပ်နိုင်သော image ကို ပြန်မပေးသည့် fetch တစ်ခု) ကိုလည်း မပြောင်းလဲဘဲ ဆက်လက်ပေးပို့သည်။ ဤ normalization ကို bridge က ၎င်း၏ ကိုယ်ပိုင် self-call အတွက် fetch လုပ်သော images များတွင်သာ ကန့်သတ်အသုံးပြုသည် — caller ၏ raw passthrough payload တွင် လုံးဝ အသုံးမပြုပါ။ ၎င်းသည် opt-in-only mutation မူဝါဒ (Hard Rule #20) နှင့် ကိုက်ညီသည်။

#### Settings schema + migration

`modalityBridge*` keys အသစ်များကို `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`) တွင် Zod ဖြင့် validate လုပ်ထားသည်- `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` သုံးခုနှင့် Audio Bridge က အသုံးပြုသော `modalityBridgeAudio*` အုပ်စုတို့ ဖြစ်သည်။ Migration `141_modality_bridge_settings.sql` သည် လက်ရှိ legacy `visionBridge*` တန်ဖိုးများကို ကိုက်ညီသော keys အသစ်များသို့ ကူးယူသည် (idempotent ဖြစ်ပြီး operator က သတ်မှတ်ထားသော `modalityBridge*` တန်ဖိုးကို လုံးဝ overwrite မလုပ်ပါ)။ Legacy keys များကို release cycle တစ်ခုအထိ read fallback အဖြစ် ဆက်လက်လက်ခံထားသည်။

လိုက်ဖက်ညီမှု link တစ်ခုဖြစ်ပြီး form ၏ ဒုတိယမိတ္တူကို မပိုင်ဆိုင်တော့ပါ။
Media Providers သည် လက်ရှိ Speech-to-Text playground ကို မဖယ်ရှားဘဲ
Image-to-Text နှင့် Speech-to-Text workflow များကို သက်ဆိုင်ရာ Modality Bridge
tab များသို့လည်း ချိတ်ဆက်ပေးထားသည်။

**Self-loop admission bypass:** describe call သည် OmniRoute ၏ ကိုယ်ပိုင် `/v1`
self-loop မှတစ်ဆင့် route လုပ်သည့်အခါ (စံမဟုတ်သော provider model) sub-request က
`x-omniroute-admission-bypass: internal` ကို ပေးပို့ပြီး ဖြေရှင်းသတ်မှတ်ထားသော
self-loop credential ဖြင့် authenticate လုပ်သည် — local mode တွင် local
`sk_omniroute` sentinel ကို အသုံးပြုသည်၊ သို့မဟုတ် operator က ဖွဲ့စည်းသတ်မှတ်ထားသော
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env key (#1350) ကို အသုံးပြုသဖြင့်
`REQUIRE_API_KEY=true` deployment များတွင်လည်း describe call ကို လုပ်ဆောင်နိုင်သည်။
bypass ကို ထို credential အတိအကျများအတွက်သာ လက်ခံသောကြောင့် external client များသည်
admission ကို ကျော်ရန် header ကို အသုံးမပြုနိုင်ပါ။

Legacy default များသည် `src/shared/constants/visionBridgeDefaults.ts` တွင်ရှိပြီး
mode/task-aware/cache default အသစ်များနှင့် settings resolver သည်
`src/shared/constants/modalityBridgeDefaults.ts` တွင်ရှိသည်။ Guardrail က
`deps` constructor option ကို ပေးထားသောကြောင့် test များသည် `getSettings` နှင့်
`callVisionModel` implementation အတုများကို inject လုပ်နိုင်သည်။

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Audio input ကို လက်ခံနိုင်သည်ဟု မသိရသော target တစ်ခုထံ audio ပါဝင်သည့် chat
request များ မရောက်မီ ကြားဖြတ်သည်။ Chat request ကို မည်သည့်အခါမျှ route ပြောင်းခြင်း
မပြုပါ။ Audio part များကို လက်ရှိ OpenAI-compatible multipart endpoint မှတစ်ဆင့်
စာသားအဖြစ် ပြောင်းလဲပြီး ရွေးချယ်ထားသော chat model သည် စာသား transcript များဖြင့်
ဆက်လက်လုပ်ဆောင်သည်။

လုပ်ငန်းစဉ်-

1. `getResolvedModelCapabilities()` မှတစ်ဆင့် `supportsAudio` ကို
   ဖြေရှင်းသတ်မှတ်သည်။ တိတိကျကျ သတ်မှတ်ထားသော provider-registry metadata ကို
   ပထမဦးစားပေးပြီး၊ ထို့နောက် static model metadata၊ ထို့နောက် sync လုပ်ထားသော
   `modalities_input` ကို အသုံးပြုသည်။ `audio` မပါဝင်သော ကြေညာထားသည့် input list
   တစ်ခုသည် `false` ဖြစ်ပြီး capability ဆိုင်ရာ အထောက်အထား လုံးဝမရှိပါက `null`
   အဖြစ် ကျန်ရှိသည်။ `false` နှင့် `null` နှစ်ခုစလုံးသည် ဘေးကင်းရေးဦးစားပေးသည့်
   bridge ကို activate လုပ်ပြီး `true` ဖြစ်ပါက ၎င်းကို bypass လုပ်သည်။
2. `modalityBridgeAudio*` setting များကို ဖြေရှင်းသတ်မှတ်ပြီး message တိုင်းမှ
   splice လုပ်နိုင်သော top-level audio part များကို မျှဝေသုံးစွဲသည့်
   `detectMediaParts()` detector ဖြင့် ထုတ်ယူသည်။ ပံ့ပိုးထားသော wire shape များမှာ
   OpenAI `input_audio`, `audio_url` နှင့် `source.media_type: "audio/*"` တို့ဖြစ်သည်။
   Nested audio ကို routing အတွက် ရှာဖွေတွေ့ရှိသော်လည်း splice path က ၎င်းကို
   မဖယ်ရှားပါ။ လုပ်ဆောင်မည့်ပမာဏကို `modalityBridgeAudioMaxClips` ဖြင့် ကန့်သတ်ထားပြီး
   နောက်ပိုင်း part များသည် မပြောင်းလဲဘဲ ကျန်ရှိသည်။
3. ဖွဲ့စည်းသတ်မှတ်ထားသော `provider/model` ကို လိုက်နာအသုံးပြုသည်၊ သို့မဟုတ်
   `selectAudioBridgeModel()` က `AUDIO_TRANSCRIPTION_PROVIDERS` ကို တည်ငြိမ်သော
   catalog အစဉ်အတိုင်း လိုက်လံစစ်ဆေးပြီး အသုံးပြုနိုင်သည့် active provider
   credential ရှိသော ပထမဆုံး model ကို ရွေးချယ်သည်။
4. `callAudioTranscription()` သည် base64/data-URI audio ကို multipart `file`
   အဖြစ် ပြောင်းလဲသည်၊ သို့မဟုတ် remote `audio_url` ကို DNS pinning နှင့် 25 MB
   အကန့်အသတ်ပါဝင်သော public-only outbound guard မှတစ်ဆင့် download လုပ်သည်။
   ထို့နောက် file နှင့် ရွေးချယ်ထားသော model ကို local
   `/v1/audio/transcriptions` self-loop သို့ POST လုပ်ပြီး
   `resolveSelfLoopBearer()` ဖြင့် authenticate လုပ်သည်။ လက်ရှိ transcription
   route သည် ပုံမှန် credential lookup၊ cooldown/rate-limit ကိုင်တွယ်မှုနှင့်
   provider dispatch တို့ကို လုပ်ဆောင်သည်။
5. အောင်မြင်သော call များသည် သက်ဆိုင်ရာ part များကို
   `[Audio N]: <transcript>` ဖြင့် အစားထိုးသည်။ Call များကို
   `Promise.allSettled` ဖြင့် လုပ်ဆောင်သည်။ Call တစ်ခုချင်းစီ မအောင်မြင်ပါက
   မူရင်း audio part ကို ထိန်းသိမ်းထားသည် (#4012 contract)။ Call အားလုံး
   မအောင်မြင်ပြီး target သည် `supportsAudio === false` ဖြစ်ကြောင်း သက်သေပြထားပါက
   part များသည် `[Audio N]: (မရရှိနိုင်ပါ — ချိတ်ဆက်ထားသော STT provider မရှိပါ)`
   ဖြစ်လာသည် (#8430 contract)။ အခြေအနေမသိရသည့် target (`null`) အတွက် အားလုံး
   မအောင်မြင်သော ရလဒ်သည် မပြောင်းလဲဘဲ ကျန်ရှိသည်။ အသုံးပြုနိုင်သည့် STT credential
   မရှိသော၊ text-only ဖြစ်ကြောင်း သက်သေပြထားသည့် target သည် network call
   မပြုလုပ်ဘဲ အလားတူ တိကျရှင်းလင်းသော stub ကို ရရှိသည်။

အောင်မြင်သော transcript များသည် process တစ်ခုလုံးအတွက် မျှဝေထားသော Modality Bridge
LRU/TTL cache ကို အသုံးပြုသည်။ Key သည် audio reference၊ တည်ငြိမ်သော
`audio-transcription` operation label နှင့် ရွေးချယ်ထားသော STT model တို့ကို
ပေါင်းစပ်ထားပြီး failure များကို မည်သည့်အခါမျှ cache မလုပ်ပါ။ Audio attempt များသည်
မျှဝေထားသော `bridged`, `cacheHits`, `failures` နှင့် `lastUsedAt` counter များကို
update လုပ်သည်။ ပြောင်းလဲပြီးသော response များတွင်
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ပါဝင်ပြီး
မပြောင်းလဲထားသော request များတွင် Audio Bridge segment မပါဝင်ပါ။

Runtime setting များသည် DB-backed ဖြစ်ပြီး Zod ဖြင့် validate လုပ်ထားသည်-

| ကီး                           | ပုံသေတန်ဖိုး | အတိုင်းအတာ                   |
| ----------------------------- | ------------ | ---------------------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —                            |
| `modalityBridgeAudioModel`    | `""`         | အလိုအလျောက် သို့မဟုတ် STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000                  |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10                         |

မျှဝေထားသော cache ကို `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` နှင့် `modalityBridgeCacheMaxEntries` တို့က ဆက်လက်ထိန်းချုပ်သည်။

### ဗီဒီယို Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

မူရင်းဗီဒီယိုပံ့ပိုးမှုရှိကြောင်း မသိရသေးသော ပစ်မှတ်တစ်ခုကို မခေါ်မီ Chat Completions `messages` နှင့် Responses
API `input` အတွင်းရှိ ထိပ်ဆုံးအဆင့် ဗီဒီယိုအပိုင်းများကို ကြားဖြတ်ရယူသည်။
ပံ့ပိုးထားသော ပုံစံများမှာ `input_video`, `video_url`, `video_source`, HTTPS URLs
နှင့် `data:video/*;base64,...` data URIs တို့ဖြစ်သည်။ စာသားထဲရှိ သာမန်ဖိုင်အမည်များကို
ဗီဒီယိုအဖြစ် မသတ်မှတ်ပါ။

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) က request တစ်လျှောက် ဖြတ်သန်းလုပ်ဆောင်ခြင်း၊
လုပ်ဆောင်နိုင်စွမ်း/မူဝါဒ စစ်ဆေးခြင်း၊ request တစ်ခုချင်းစီအလိုက် စုစည်းခြင်းနှင့် response payload တို့ကို
တာဝန်ယူသည်။ ဗီဒီယိုတစ်ခုချင်းစီဆိုင်ရာ အလုပ်များဖြစ်သည့် ရယူခြင်း၊ ရလဒ်တစ်ခုလုံး၏ cache၊
frame အစီအစဉ်တစ်ခုကို ဖော်ပြခြင်း (ခေါ်ဆိုသူက ကြေညာထားသော အသံ transcript တစ်ခုခုကို ပေါင်းစပ်ပေးသည်)
နှင့် ကြိုးပမ်းမှုတစ်ခုချင်းစီအလိုက် metrics/abort/cleanup တို့ကို
`videoBridgePipeline.ts` ရှိ `processVideoPart` နောက်ကွယ်တွင် ဖုံးကွယ်ထားပြီး `preCall` ၏ loop အတွင်း
ဗီဒီယိုအပိုင်းတစ်ခုလျှင် တစ်ကြိမ်ခေါ်သည်။ ထို module က ရှင်းလင်းစွာ သတ်မှတ်ထားသော port နယ်နိမိတ်များဖြစ်သည့်
`VideoMediaBrokerPort` (bytes ရယူခြင်းနှင့် နမူနာယူထားသော frames များကို ထုတ်ယူခြင်း)၊
`VideoAudioTranscriptionPort` (ခေါ်ဆိုသူက ကြေညာထားသော အသံ transcript ကို နမူနာယူထားသော captions များနှင့် ပေါင်းစပ်ခြင်း) နှင့်
`VideoDrilldownPort` (frame drill-down သိမ်းဆည်းမှု နယ်နိမိတ်ဖြစ်ပြီး `processVideoPart` နှင့် မချိတ်ဆက်ရသေးပါ —
လက်ရှိတွင် သီးခြား `/api/modality-bridge/video/drilldown`
route ကသာ drill-down entries များကို ရေးသားသည်) တို့ကိုလည်း သတ်မှတ်သည်။

အများသုံး `/v1` request လမ်းကြောင်းသည် subprocess တစ်ခုကို မည်သည့်အခါမျှ import သို့မဟုတ် invoke မလုပ်ပါ။ အဝေးရှိ
ဗီဒီယိုများကို 50 MiB ကန့်သတ်ချက်အောက်တွင် download လုပ်သည်။ inline base64 ဗီဒီယိုများအတွက်
model/messages/framing envelope သည် အများသုံး JSON request လက်ခံမှုကန့်သတ်ချက် 50 MiB အတွင်း
ဆက်လက်ရှိနေနိုင်ရန် ဗီဒီယိုတစ်ခုလျှင် decode လုပ်ပြီးသား အရွယ်အစားကို 36 MiB အထိ သတိထားကန့်သတ်ထားသည်။ Inline
အလျားနှင့် decode လုပ်ပြီးနောက် အရွယ်အစားခန့်မှန်းချက်များကို memory မခွဲဝေမီ စစ်ဆေးသည်။ ကနဦး အဝေး URL နှင့်
redirect တိုင်းတွင် HTTPS ကို မဖြစ်မနေသုံးရပြီး DNS pinning ပါဝင်သော လက်ရှိ
အများသုံးသာ outbound guard ကို အသုံးပြုသည်။ ထို့နောက် bytes များသည် တိကျစွာ သတ်မှတ်ထားသော အတွင်းပိုင်း
`POST /api/modality-bridge/video/extract` broker နယ်နိမိတ်ကို ဖြတ်သန်းသည်။ ထို route သည်
`LOCAL_ONLY` နှင့် `SPAWN_CAPABLE` နှစ်မျိုးလုံးဖြစ်ပြီး process တစ်ခုချင်းစီအလိုက် အထောက်အထားစစ်ဆေးထားသော
ယုံကြည်စိတ်ချရသည့် loopback request ကိုသာ လက်ခံကာ URL၊ filesystem path၊ executable
သို့မဟုတ် argument list ကို မည်သည့်အခါမျှ လက်မခံပါ။ API body-size pipeline နှင့် handler ၏ အဆင့်လိုက် body
reader တို့က 50 MiB broker input ကန့်သတ်ချက်ကို သီးခြားစီ အတည်ပြုကျင့်သုံးသည်။ ၎င်း၏ ကန့်သတ်ထားသော queue သည်

#### FU-07 ဖွဲ့စည်းပုံဆိုင်ရာ segment အထောက်အထား

`segment_aware` သည် အတည်ပြုပြီးသား local video stream ပေါ်တွင် ကန့်သတ်ထားသော pre-analysis pass တစ်ကြိမ်ကို အသုံးပြုသည်။ ပုံသေ filter chain သည် ပထမဦးစွာ အကျယ်ဆုံး 320 pixels အထိ scale လုပ်ပြီး scene ပြောင်းလဲမှုများနှင့် ရပ်တန့်နေသော interval များကို ရှာဖွေကာ ထို့နောက် blur၊ ပျမ်းမျှ luma နှင့် spatial/temporal information တို့အတွက် တစ်စက္ကန့်လျှင် frame 1 ခုနှုန်းဖြင့် sample ယူသည်။ အဆိုပါ pass ကို structural sample 600 ခု၊ FFmpeg/filter thread တစ်ခု၊ တူညီသော `file`-only protocol နှင့် container allowlist များ၊ 1 MiB process-output ကန့်သတ်ချက်နှင့် broker ၏ မျှဝေထားသော abort/deadline အတွင်း အများဆုံး 30 စက္ကန့်ဟူ၍ ကန့်သတ်ထားသည်။ ၎င်းသည် request မှ command၊ filter၊ path သို့မဟုတ် URL တစ်ခုခုကို မည်သည့်အခါမျှ လက်မခံပါ။

Structural value များသည် သတ်မှတ်ထားသည့်အတိုင်း ပြန်လည်ရရှိနိုင်သော sampling evidence များသာဖြစ်ပြီး semantic video understanding မဟုတ်ပါ။ ၎င်းတို့သည် subject များ၊ action များ၊ caption များ၊ speech သို့မဟုတ် user intent ကို ခန့်မှန်းကောက်ယူခြင်းမပြုပါ။ Scene နှင့် freeze boundary များက segment များကို ဖွဲ့စည်းပြီး freeze coverage၊ blur၊ exposure၊ spatial detail နှင့် temporal change တို့သည် ရှိပြီးသား frame 1–16 ခု budget ကို မည်သို့ခွဲဝေမည်ကိုသာ သက်ရောက်စေသည်။ လုံးဝရပ်တန့်နေသော segment တစ်ခုကို frame တစ်ခုသာ အများဆုံးထားပြီး မရပ်တန့်သော segment များသည် ကျန်ရှိသည့် budget အတွက် ယှဉ်ပြိုင်ကြသည်။ Boundary အရေအတွက်က frame အရေအတွက်ထက် များနေသည့်အခါ timeline တစ်လျှောက် ညီမျှသော coverage ကို ဆက်လက်ထိန်းသိမ်းထားသဖြင့် အစပိုင်းရှိ လျင်မြန်သော cut များက နောက်ဆုံးရှိ ရှည်လျားသော segment ကို ဖုံးကွယ်၍မရပါ။ Freeze boundary တစ်ခု၏ 1-second analysis resolution အတွင်းရှိ scene boundary များကို ပေါင်းစည်းသည်။

Filter မရှိခြင်း၊ evidence ပုံစံမမှန်ခြင်း/ဗလာဖြစ်ခြင်း၊ detector error ဖြစ်ခြင်း သို့မဟုတ် ကန့်သတ်ထားသော pre-analysis timeout ဖြစ်ခြင်းတို့တွင် အတိအကျ uniform midpoint policy သို့ fail open လုပ်သည်။ Caller abort သို့မဟုတ် broker deadline ဖြစ်ခြင်းတွင်မူ fail open မလုပ်ပါ။ ၎င်းသည် လုပ်ဆောင်ဆဲ subprocess ကို ရပ်ဆိုင်းပြီး နောက်ပိုင်း frame extraction ကို တားဆီးကာ private temporary tree ကို `finally` တွင် ဖယ်ရှားသည်။

`scripts/perf/video-bridge-fu07-eval.ts` သည် post-dedup caption-call ချွေတာမှု၊ dense-motion budget ခွဲဝေမှု၊ blur/exposure/SI-TI evidence၊ ရှည်လျားသော tail ပါသည့် လျင်မြန်သော cut များနှင့် gradual-fade false positive များအတွက် သတ်မှတ်ထားသည့်အတိုင်း ပြန်လည်ရရှိနိုင်သော FFmpeg fixture အစစ်များကို ဖန်တီးပေးသည်။ ၎င်းသည် pre-analysis wall time ကို မှတ်တမ်းတင်ပြီး `/usr/bin/time` ရရှိနိုင်သည့်နေရာတွင် child CPU နှင့် peak RSS ကိုလည်း မှတ်တမ်းတင်သည်။ ၎င်း၏ quality check များသည် structural oracle များသာဖြစ်သည်။ ဤ harness တွင် ခွင့်ပြုထားသော endpoint သို့မဟုတ် အတည်ပြုထားပြီး မပြောင်းလဲသည့် judge မရှိသောကြောင့် caption-model အစစ်၏ အရည်အသွေးသည် `HOLD` အဖြစ် ဆက်ရှိနေသည်။ `--caption-cost-per-call-usd` က call တစ်ကြိမ်လျှင် အတိအလင်း အပေါင်းတန်ဖိုးရှိသော ကုန်ကျစရိတ်ခန့်မှန်းချက်ကို ပေးမထားပါက ငွေကြေးချွေတာမှုသည်လည်း `HOLD` အဖြစ် ဆက်ရှိနေသည်။ Script သည် ရလဒ်နှစ်ခုစလုံးကို မည်သည့်အခါမျှ လုပ်ကြံဖန်တီးခြင်းမပြုပါ။

Frame တစ်ခုစီကို 4 MiB၊ raw frame အားလုံးပေါင်းကို 23 MiB နှင့် serialize လုပ်ထားသော broker response ကို 32 MiB အထိ ကန့်သတ်ထားသည်။ Private temporary directory ကို `finally` တွင် ဖယ်ရှားသည်။ OmniRoute တွင် FFmpeg ကို ထည့်သွင်းဖြန့်ဝေထားခြင်းမရှိသကဲ့သို့ custom executable path ကိုလည်း လက်မခံပါ။ Caption ရေးသားခြင်းမပြုမီ bridge သည် ထိန်းသိမ်းထားသော visual deduplication pass တစ်ခုကို အသုံးပြုသည်။ JPEG တစ်ခုစီကို 16×16 grayscale buffer အဖြစ် လျှော့ချပြီး နောက်ဆုံးထိန်းသိမ်းထားသော frame နှင့်သာ နှိုင်းယှဉ်သည်။ တောင်းဆိုထားသော caption budget သည် frame တစ်ခုထက်ပိုပါက extraction သည် ထို budget ၏ နှစ်ဆအထိရှိပြီး frame 16 ခုထက် မပိုသော ကန့်သတ်ထားသည့် candidate pool တစ်ခုကို ပေးသည်။ တောင်းဆိုထားသော cap ကို deduplication ပြီးမှသာ အသုံးချပြီး budget သည် အနည်းဆုံး နှစ်ခုရှိသည့်အခါ နောက်ဆုံး thinning ပြုလုပ်စဉ် ပထမဆုံးနှင့် နောက်ဆုံးရွေးချယ်ထားသော candidate များကို ထိန်းသိမ်းထားသည်။ Version သတ်မှတ်ထားသော `grayscale-16x16-mean-cells-v2` policy သည် ပျမ်းမျှ luma delta နှင့် normalized delta အနည်းဆုံး 0.05 ရှိသည့် thumbnail cell အချိုးတို့အနက် ပိုကြီးသောတန်ဖိုးကို အသုံးပြုသည်။ Duplicate threshold သည် ပုံသေကိန်းသေ 0.04 ဖြစ်ပြီး runtime setting အဖြစ် ဖော်ထုတ်ပေးမည့်အစား ကြိုတင်ခန့်မှန်းနိုင်မှုအတွက် ရွေးချယ်ထားခြင်းဖြစ်သည်။ ဤဒုတိယ high-contrast signal သည် mean-only comparison က ဖုံးကွယ်ထားနိုင်သည့် လှုပ်ရှားမှုငယ်များနှင့် မြင်နိုင်သောစာသားပြောင်းလဲမှုများကို ထိန်းသိမ်းပေးသည်။ Comparator သို့မဟုတ် decoder error များတွင် fail open လုပ်ပြီး coverage ကို ထိန်းသိမ်းထားသည်။ Output metadata သည် ထုတ်ယူထားသော candidate များ၊ အောင်မြင်စွာအသုံးပြုထားသော frame များနှင့် ဖယ်ရှားထားသော visual duplicate များကို သီးခြားခွဲပြထားသည်။

အတိအလင်း အမှတ်အသားပြုထားသော video part တစ်ခုသည် timestamp ပါသည့် contact sheet တစ်ခုကို တောင်းဆိုနိုင်သည်။ Bridge သည် column အများဆုံး 4 ခုနှင့် frame အများဆုံး 16 ခုပါဝင်သော JPEG grid တစ်ခုကို ဖန်တီးသည်။ 512-pixel cell တစ်ခုစီသည် ၎င်း၏ source timestamp ကို high-contrast အောက်ခြေ band တစ်ခုထဲတွင် ထည့်သွင်းရေးသားပြီး တူညီသော timestamp များကို downstream association နှင့် audit အတွက် textual metadata ထဲတွင်လည်း ဆက်လက်ထားရှိသည်။ JPEG အပြည့်အစုံကို 32 MiB အထိသာ ကန့်သတ်ထားသည်။ `sharp` က grid ကို decode သို့မဟုတ် compose မလုပ်နိုင်ပါက bridge သည် JPEG frame တစ်ခုချင်းစီကို အသုံးပြုသည့် fallback သို့ ပြောင်းသွားသည်။ Client abort သည် sheet operation တစ်လျှောက် ဆက်လက်သက်ရောက်သည်။

Promotion evidence ကို synthetic composition microbenchmark နှင့် ရည်ရွယ်ချက်ရှိရှိ သီးခြားခွဲထားသည်။ `scripts/perf/video-bridge-contact-sheet-eval.ts` သည် OpenAI-compatible vision model အစစ်များအတွက် schema-versioned A/B harness တစ်ခုကို သတ်မှတ်ပေးသည်။ ၎င်းသည် provider မှ အစီရင်ခံသော token များ၊ end-to-end wall latency (sheet composition အပါအဝင်)၊ model-call အရေအတွက်နှင့် manifest မှ သတ်မှတ်ထားသော fact retention တို့ကို တိုင်းတာသည်။ Raw model response များကို report ထဲသို့ မရေးဘဲ SHA-256 digest များနှင့် ကိုက်ညီသော fact ID များကိုသာ ထိန်းသိမ်းထားသည်။ `--execute-real` ကို ပေးထားပြီး `--model`၊ `OMNIROUTE_BASE_URL` နှင့် `OMNIROUTE_API_KEY` တို့ကို configure လုပ်ထားမှသာ harness သည် network သို့မဟုတ် paid model call ပြုလုပ်သည်။ ထိုသို့ အတိအလင်း real run မပြုလုပ်ပါက ၎င်း၏ machine-readable verdict သည် `HOLD` အဖြစ် ဆက်ရှိနေသည်။ Synthetic payload/call-count တိုင်းတာချက်များတစ်ခုတည်းသည် promotion evidence မဟုတ်ပါ။

အတွင်းပိုင်း `/api/modality-bridge/video/drilldown` lifecycle သည် သီးခြားဖြစ်ပြီး loopback/token ဖြင့် authentication ပြုလုပ်ထားသော cache substrate တစ်ခုဖြစ်သည်။ Operation တစ်ခုစီအတွက် canonical opaque principal ID တစ်ခုလည်း လိုအပ်သည်။ Production caller တစ်ခုကို ဖွင့်ပေးခြင်းမပြုမီ ၎င်းသည် authenticated tenant ထံမှ ထို ID ကို derive လုပ်ရမည်ဖြစ်ပြီး client က ရွေးချယ်ထားသော value ကို မည်သည့်အခါမျှ forward မလုပ်ရပါ။ Cache key များသည် ထို principal ကို canonical session နှင့် video-reference ID များဖြင့် ချိတ်ဆက်ထားပြီး ၎င်းတို့၏ SHA-256 ဖြင့် derive လုပ်ထားသော key များကိုသာ သိမ်းဆည်းကာ read နှင့် deletion နှစ်မျိုးစလုံးကို တူညီသော principal အတွင်းသာ scope သတ်မှတ်သည်။ Cache သည် entry တစ်ခုစီအတွက် derive လုပ်ထားသော JPEG frame 16 ခုအထိသာ သိမ်းဆည်းပြီး ဆယ်မိနစ်အကြာတွင် ၎င်းတို့ကို သက်တမ်းကုန်ဆုံးစေကာ ကန့်သတ်ထားသော `start`/`end` read များ သို့မဟုတ် session ကို အတိအလင်း ဖျက်ခြင်းအား ပံ့ပိုးသည်။

Cache သည် canonical မဟုတ်သော Base64၊ လွန်ကဲသော padding၊ JPEG မဟုတ်သည့် media၊ ပုံစံမမှန်သော သို့မဟုတ် အချက်အလက်မပြည့်စုံသော JPEG များနှင့် ကန့်သတ်ထားသော full-image `sharp` decode လုပ်စဉ် warning ထွက်ပေါ်စေသည့် JPEG များကို ငြင်းပယ်သည်။ လက်ခံထားသော image တစ်ခုစီကို canonical JPEG အဖြစ် ပြန်လည် encode လုပ်ပြီး caller field များကို ယုံကြည်မည့်အစား decoded byte များမှ width နှင့် height ကို derive လုပ်ကာ နောက်ဆက်တွဲ polyglot byte များကို ထိန်းသိမ်းမထားဘဲ စွန့်ပစ်သည်။ ကန့်သတ်ထားသော canonical compressed buffer ကိုသာ quota နှစ်ခုစလုံးတွင် ထည့်တွက်သည်။ JSON wire limit တွင် 32 MiB decoded-input အများဆုံးကန့်သတ်ချက်အတွက် Base64 overhead ပါဝင်သည်။ သိမ်းဆည်းထားသော derivation တစ်ခုစီသည် ၎င်း၏ အတည်ပြုပြီးသော JPEG format/resolution၊ sampling policy၊ derivation version၊ ဖန်တီးချိန်၊ server က တွက်ချက်ထားသော content hash၊ hash လုပ်ထားသော parent reference နှင့် trusted caller ၏ parent-content hash တို့ကို မှတ်တမ်းတင်ထားသည်။ Atomic cache commit မတိုင်မီ asynchronous decode/hash phase များကြားတွင် cancellation ရှိ၊ မရှိ စစ်ဆေးသည်။

ဤအဆင့်သည် production producer တစ်ခုကို route နှင့် မချိတ်ဆက်ရသေးသကဲ့သို့ multi-resolution variant ရွေးချယ်မှုကိုလည်း မပံ့ပိုးသေးပါ။ ထို့ကြောင့် transparent Video Bridge request path တွင် ထပ်ဆောင်းလုပ်ဆောင်မှု မရှိဘဲ tenant နှင့် ချိတ်ဆက်ထားသော principal derivation နှင့် FU-08 multi-resolution lifecycle အပြည့်အစုံတို့သည် ပြီးစီးပြီးသော လုပ်ဆောင်ချက်အဖြစ် မှတ်တမ်းတင်ထားခြင်းမဟုတ်ဘဲ အတိအလင်း ဆက်လက်လုပ်ဆောင်ရမည့် အလုပ်များအဖြစ် ကျန်ရှိနေသည်။

Frame များကို စီစဉ်သတ်မှတ်ထားသော Video model ဖြင့် အစဉ်လိုက် caption ရေးသည်။ အလွတ်ဖြစ်သော Video override သည် Vision setting ကို ဆက်ခံသည်။ နှစ်ခုစလုံး အလွတ်ဖြစ်ပါက Vision auto-router သည် အမှန်တကယ်အသုံးပြုမည့် vision-capable model ကို ရွေးချယ်သည်။ အောင်မြင်သော caption များသည် မူရင်း part ကို တည်ငြိမ်သော `[Video description:` prefix ဖြင့် အစားထိုးပြီး ထို prefix သည် text ကို ယုံကြည်စိတ်ချ၍မရသော media မှ derive လုပ်ထားသည့် observation အဖြစ်လည်း မှတ်သားကာ media အတွင်း တွေ့ရသော instruction များကို မလိုက်နာရန် downstream model များအား ညွှန်ကြားသည်။ Frame-caption cache key များတွင် JPEG byte များ၊ prompt၊ timestamp နှင့် အမှန်တကယ်အသုံးပြုသည့် model တို့ ပါဝင်ပြီး အောင်မြင်သော caption များကိုသာ cache လုပ်သည်။ Cache entry များသည် fallback model အပါအဝင် အမှန်တကယ် အောင်မြင်စွာ ထုတ်လုပ်ခဲ့သော producer model ကို ထိန်းသိမ်းထားပြီး မတူညီသော frame များကို မတူညီသော model များက ထုတ်လုပ်ထားပါက bridge သည် `mixed` ဟု report လုပ်သည်။ Cache hit တစ်ခုသည် ၎င်းကို တောင်းဆိုထားသော routing plan အဖြစ် label ပြန်တပ်မည့်အစား ထို producer identity ကို ပြန်လည်အသုံးပြုသည်။ Whole-video result cache ကို output ပြောင်းလဲစေသည့် input အားလုံး—prompt၊ အမှန်တကယ်အသုံးပြုသည့် model၊ sampling policy၊ frame count၊ semantic analysis mode၊ normalize လုပ်ထားသော focus hint ၏ SHA-256 fingerprint၊ focus window၊ `transcript`၊ `audioTranscript` နှင့် contact-sheet flag—ပေါ်အခြေခံ၍ key သတ်မှတ်ထားသဖြင့် ထို dimension များထဲမှ တစ်ခုခုကို ပြောင်းလဲပါက stale result ကို ပြန်လည်အသုံးပြုခြင်းမဟုတ်ဘဲ cache miss ဖြစ်သည်။ Visual dedup policy version၊ threshold နှင့် ကန့်သတ်ထားသော candidate-frame count တို့ကိုလည်း result-cache key နှင့် metadata တွင် အတိအလင်း ထည့်သွင်းထားသည်။ ထို့ကြောင့် policy ပြောင်းလဲပါက stale whole-video description ကို ပြန်လည်အသုံးမပြုနိုင်ပါ။ Result-cache v4 metadata သည် mode နှင့် fingerprint ကို ထိန်းသိမ်းထားသော်လည်း user task အကြမ်းကို မည်သည့်အခါမျှ မသိမ်းဆည်းပါ။ Guardrail metadata သည် တောင်းဆိုထားသော analysis mode နှင့် အမှန်တကယ်အသုံးပြုသည့် analysis mode နှစ်ခုစလုံးကို report လုပ်သည်။ အသုံးပြုနိုင်သော user text မရှိဘဲ `focused` mode ကို တောင်းဆိုထားပါက အမှန်တကယ်အသုံးပြုသည့် mode ကို `full` အဖြစ် report လုပ်သည်။

Guardrail သည် ပံ့ပိုးထားသော video part အားလုံးကို extract လုပ်သော်လည်း `modalityBridgeVideoMaxVideos` ထက် မပိုသော အရေအတွက်ကိုသာ ဖော်ပြသည်။ `supportsVideo === false` ဖြစ်ကြောင်း သက်သေပြထားသော target အတွက် မအောင်မြင်သော video များနှင့် ကန့်သတ်ချက်ကျော်လွန်သော video များကို အတိအလင်း safe text marker များအဖြစ် ပြောင်းလဲသဖြင့် raw video တစ်ခုမျှ မကျန်ရှိပါ။ Capability ကို မသိရသေးပါက ထို part များသည် ၎င်းတို့၏ video carrier ကို ဆက်လက်ထိန်းသိမ်းထားပြီး fallback transcript ရှိပါက အထက်ဖော်ပြပါ ကန့်သတ်ထားသော text conversion ကို လိုက်နာသည်။ `supportsVideo === true` ဖြစ်သော target များသည် bridge ကို ကျော်သွားသည်။ Client request abort signal သည် download၊ broker queue၊ subprocess များနှင့် caption call များတစ်လျှောက် ပို့ဆောင်သက်ရောက်သည်။ Abort များသည် video များကြားတွင် လုပ်ဆောင်မှုကို ရပ်တန့်စေပြီး raw media သို့ fail open မဖြစ်စေပါ။

### PII Masker (`piiMasker.ts`)

အဆင့် **နှစ်ခုစလုံး** တွင် လုပ်ဆောင်သည်။

- **`preCall`** သည် payload ကို clone လုပ်ပြီး `system`, `messages`, `input` နှင့်
  `prompt` (သာမန် string item များအပါအဝင်) တစ်လျှောက် စစ်ဆေးကာ string `content`/`text` field များတွင်
  (`@/shared/utils/inputSanitizer` မှ) `processPII()` ကို အသုံးပြုသည်။
  `PII_REDACTION_ENABLED=true` ဖြစ်သောအခါ တွေ့ရှိထားသည့် PII ကို အပြင်သို့ပို့မည့်
  payload တွင် ဖုံးကွယ်သည်။ ဤလုပ်ဆောင်ချက်သည် `INPUT_SANITIZER_MODE` နှင့် သီးခြားဖြစ်သည် (၎င်းက
  prompt-injection policy ကိုသာ ထိန်းချုပ်သည်)။ ဖုံးကွယ်မှုကို ပိတ်ထားသောအခါ call သည် content ကို
  ပြန်လည်မရေးသားဘဲ တွေ့ရှိမှုအရေအတွက်များကို မှတ်တမ်းတင်သည်။
- **`postCall`** သည် response ကို deep-clone လုပ်ပြီး `sanitizePIIResponse()` နှင့်အတူ
  Responses-API ပုံစံ masker (`maskResponsesOutput` — `output_text` နှင့်
  `output[].content[].text` ကို လွှမ်းခြုံသည်) ကို လုပ်ဆောင်သည်။ ဖုံးကွယ်မှုတစ်စုံတစ်ရာ ဖြစ်ပေါ်ပါက
  ပြင်ဆင်ထားသော response ဖြင့် မူလ response ကို အစားထိုးသည်။

ဤ guardrail သည် မည်သည့်အခါမျှ ပိတ်ဆို့ခြင်းမပြုဘဲ မှတ်ချက်အချက်အလက်သာ ထည့်သွင်းသည်
(`meta.detections`, `meta.redacted`) သို့မဟုတ် ပြန်လည်ရေးသားသည်။

| ဖွင့်ထားမှု                 | `INPUT_SANITIZER_ENABLED`                                                                             | `true`     | `false` ဖြစ်သောအခါ guardrail သည် လုပ်ငန်းစဉ်ကို ကျော်သွားသည်။                                                                                                                                                           |

| ပိတ်ဆို့မှုအဆင့်သတ်မှတ်ချက် | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`     | ပိတ်ဆို့ရန် လိုအပ်သော အနိမ့်ဆုံး severity ဖြစ်သည်။ မူလသတ်မှတ်ချက်အရ Medium သည် စောင့်ကြည့်ရန်သာ ဖြစ်သည်။                                                                                                                |

**Mode ဦးစားပေးအစီအစဉ်** (`getMode`): caller `options.mode` →
`INJECTION_GUARD_MODE` **DB feature-flag override** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`။ ထို့ကြောင့် dashboard override သည် env var များထက် ဦးစားပေးသဖြင့် Feature
Flags UI မှ လက်ရှိလုပ်ဆောင်နေသော guard ကို ချက်ချင်းထိန်းချုပ်နိုင်သည် (restart မလိုပါ)။ DB ဖတ်ရှုမှုသည် fail-safe ဖြစ်သည်။
error ဖြစ်ပါက guard သည် env အခြေပြုလုပ်ဆောင်ပုံသို့ ပြန်သွားပြီး
override မသတ်မှတ်ထားပါက လုပ်ဆောင်ပုံသည် env သီးသန့်ဖြေရှင်းပုံနှင့် တူညီသည်။

ရှာဖွေသိရှိမှု ရင်းမြစ်များ-

1. `@/shared/utils/inputSanitizer` မှ `sanitizeRequest()` (pipeline ၏ အခြားနေရာများတွင်
   အသုံးပြုသည့် မျှဝေထားသော detector အစု)။
2. ထည့်သွင်းပါရှိသော `DEFAULT_GUARD_PATTERNS` (လက်ရှိတွင် `system_override_inline` နှင့်
   `markdown_system_block` ဖြစ်ပြီး နှစ်ခုစလုံးမှာ `high` severity ဖြစ်သည်)။
3. Constructor option များမှတစ်ဆင့် ပေးပို့သော ရွေးချယ်နိုင်သည့် `customPatterns` (string၊ regex
   သို့မဟုတ် `{ name, pattern, severity }` record များ)။

`mode === "block"` ဖြစ်ပြီး **အနည်းဆုံး detection တစ်ခုက** severity
threshold ကို ပြည့်မီသောအခါ `preCall` သည် `{ block: true, message: "Request rejected:
suspicious content detected" }` ကို ပြန်ပေးသည်။ `warn`/`log` mode များတွင် guardrail က log မှတ်တမ်းတင်သော်လည်း
call ကို ခွင့်ပြုသည်။ Registry မှတစ်ဆင့် မသွားဘဲ prompt များကို အကဲဖြတ်ရန် လိုအပ်သော
caller များအတွက် မျှဝေထားသည့် helper `evaluatePromptInjection()` ကိုလည်း export လုပ်ထားသည်။

**စစ်ဆေးမှုကန့်သတ်ချက် (v3.8.20):** detector သည် ပေါင်းစပ်ထားသော prompt စာသား၏
**ပထမ 16 KB** ကိုသာ စစ်ဆေးသည် — `src/shared/utils/inputSanitizer.ts` ရှိ
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes) ဖြစ်သည်။
`detectInjection()` နှင့် `evaluatePromptInjection()` နှစ်ခုစလုံးသည် pattern loop ကို
မလုပ်ဆောင်မီ `slice(0, MAX_INJECTION_SCAN_BYTES)` ကို အသုံးပြုသည်။ Injection directive များသည်
input တစ်ခု၏ အပေါ်ပိုင်းအနီးတွင် ရှိတတ်သောကြောင့် detection ကို အားနည်းစေခြင်းမရှိဘဲ
ရာနှင့်ချီသော KB ရှိ payload များအတွက် regex CPU/GC ကို ဤနည်းဖြင့် ကန့်သတ်ပေးသည် (cf.
#3932, #4041)။

### Credential Masker (`credentialMasker.ts`)

Stage **နှစ်ခုစလုံး** တွင် လုပ်ဆောင်ပြီး default chain ၌ နောက်ဆုံးဖြစ်သည် (priority `95`)။ Outbound payload
(message content၊ tool-call argument များ၊ tool result များ) **နှင့်** provider response တို့မှ
လူသိများသော API-key / secret-token pattern များကို ဖုံးကွယ်ပေးသောကြောင့် prompt ထဲသို့
ကူးထည့်ထားသော credential (သို့မဟုတ် tool result တစ်ခုက ပြန်လည်ဖော်ပြသော credential) သည် upstream
provider သို့မဟုတ် client ထံသို့ ပြန်လည်ပေါက်ကြားမည်မဟုတ်ပါ။

- **Opt-in ဖြင့်သာ ဖွင့်နိုင်သည်**၊ PII redaction နှင့် တူညီသော သတ်မှတ်ချက်ဖြစ်သည် (Hard Rule #20 နှင့် ဆက်စပ်သည်) —
  `settings.credentialRedactionEnabled === true` **သို့မဟုတ်**
  `CREDENTIAL_REDACTION_ENABLED=true` မဟုတ်လျှင် ပိတ်ထားသည်။ ပိတ်ထားသည့်အခါ guardrail သည် no-op ဖြစ်ပြီး —
  မည်သည့်အခါမျှ block မလုပ်သလို rewrite လည်း မလုပ်ပါ။
- `redactCredentials()` သည် payload/response tree တစ်ခုလုံးကို ဖြတ်သန်းစစ်ဆေးပြီး (`walkValue()`၊
  prototype-pollution-safe ဖြစ်ကာ `WeakSet` မှတစ်ဆင့် cycle-safe ဖြစ်သည်) match ဖြစ်သောအရာများကို
  `[REDACTED:<type>]` placeholder ဖြင့် အစားထိုးကာ အမှန်တကယ် ပြောင်းလဲသွားသော branch များကိုသာ
  clone လုပ်သည်။
- `CREDENTIAL_PATTERNS` တွင် LLM provider key များ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate)၊ VCS/SaaS token များ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord)၊ payment key များ (Stripe, Square)၊ cloud
  key များ (AWS access key, Twilio, SendGrid, Mailgun)၊ private key / JWT များ၊
  credential ပါဝင်သော connection string များ (`mongodb://user:pass@...` စသည်) နှင့်
  ယေဘုယျ `Authorization`/`x-api-key`/`api-key`/`apikey` header-value
  pattern တို့ ပါဝင်သည်။ Header ပုံစံ key များ (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ကို ယေဘုယျ text regex ဖြင့် မဟုတ်ဘဲ ဖွဲ့စည်းပုံအလိုက် ဖုံးကွယ်သည် (value ကိုသာ ဖုံးကွယ်ပြီး
  `Bearer `/`Basic ` ကဲ့သို့သော scheme prefix ကို မူလအတိုင်း ထိန်းသိမ်းထားသည်)။
- Guardrail သည် မည်သည့်အခါမျှ block မလုပ်ပါ။ Rewrite (`modifiedPayload` /
  `modifiedResponse`) နှင့် annotation (`meta.credentialsRedacted`, `meta.count`) ကိုသာ လုပ်ဆောင်သည်။

Regression guard: `tests/unit/credential-masker-guardrail.test.ts`။

## အခြေခံ Contract (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ဖြစ်ပါက chain ကို ချက်ချင်းရပ်တန့်စေသည်
  message?: string; // ပိတ်ဆို့သည့်အခါ ဖော်ပြသည်
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // request ကို ပြန်လည်ရေးသားရန် preCall မှ ပြန်ပေးသည်
  modifiedResponse?: TValue; // response ကို ပြန်လည်ရေးသားရန် postCall မှ ပြန်ပေးသည်
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail တစ်ခုသည် `void`၊ `{}` သို့မဟုတ် `{ block: false }` တစ်ခုခုကို
ပြန်ပေးခြင်းဖြင့် "ပြောင်းလဲမှုမရှိ" ကြောင်း အချက်ပြသည်။ `modifiedPayload`/`modifiedResponse`
ကို ပြန်ပေးခြင်းသည် နောက်ဆက်တွဲ guardrail များသို့ chain တစ်လျှောက် စီးဆင်းနေသော
တန်ဖိုးကို အစားထိုးသည်။ `signal?: AbortSignal` သည် ခေါ်ဆိုသူ၏ lifecycle ကို
guardrail များသို့ သယ်ဆောင်ပေးသည်။ Request ကို ရပ်ဆိုင်းခြင်းသည် ရည်ရွယ်ထားသော
fail-open ခြွင်းချက်ဖြစ်သည်—media bridge များသည် အလုပ်လုပ်ခြင်းကို ရပ်တန့်ပြီး cleanup
ပြုလုပ်ကာ raw media ကို ပံ့ပိုးနိုင်ခြင်းမရှိကြောင်း သိထားသော target တစ်ခုသို့
ပြန်လည်မထည့်သွင်းပါ။

## Registry (`registry.ts`)

Singleton `guardrailRegistry` တွင် အောက်ပါတို့ ပါဝင်သည်-

- `register(guardrail)` — guardrail တစ်ခုကို ထည့်သွင်းပြီး (သို့မဟုတ် normalize လုပ်ထားသော
  name အလိုက် အစားထိုးပြီး) `priority` ငယ်ရာမှ ကြီးရာသို့ ပြန်လည်စီသည်။
- `clear()` / `list()` — စီမံခန့်ခွဲရေး အကူ method များ။
- `runPreCallHooks(payload, context)` — အသက်ဝင်နေသော guardrail များကို တစ်ခုပြီးတစ်ခု
  လုပ်ဆောင်ကာ payload ကို `modifiedPayload` မှတစ်ဆင့် လက်ဆင့်ကမ်းပြီး ပထမဆုံး
  `block: true` တွင် ရပ်တန့်သည်။
- `runPostCallHooks(response, context)` — response ဘက်တွင် အလားတူ flow ကို လုပ်ဆောင်သည်။
- `resetGuardrailsForTests({ registerDefaults })` — test တစ်ခုချင်းစီကို သီးခြားသန့်ရှင်းစွာ
  လုပ်ဆောင်နိုင်ရန် state ကို ရှင်းလင်းပြီး ရွေးချယ်မှုအလိုက် မူလ guardrail များကို
  ပြန်လည် register လုပ်သည်။

Runner နှစ်ခုစလုံးသည် `{ blocked, payload|response, results, guardrail?, message? }`
ကို ပြန်ပေးသည်။ ဤနေရာတွင် `results` သည် guardrail တစ်ခုချင်းစီ၏ `blocked`,
`skipped`, `modified`, `error` နှင့် `meta` field များ ပါဝင်သော
`GuardrailExecutionResult` record များ၏ array ဖြစ်ပြီး tracing အတွက် အသုံးဝင်သည်။

### Request တစ်ခုချင်းစီအလိုက် Guardrail များကို ပိတ်ခြင်း

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` သည် လက်ရှိ request အတွက်
ကျော်သွားသင့်သော guardrail name များကို ထပ်နေမှုမရှိအောင် စုစည်းပေးသည်။
ရင်းမြစ်များအားလုံးသည် မဖြစ်မနေ မဟုတ်ဘဲ ပေါင်းစည်းအသုံးပြုသည်-

- `apiKeyInfo.disabledGuardrails`
- Request body ၏ ထိပ်ဆုံးအဆင့်ရှိ `disabledGuardrails`
- Request body ၏ `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (သို့မဟုတ် အဟောင်းဖြစ်သော
  `x-disabled-guardrails`)

တန်ဖိုးများသည် string array များ သို့မဟုတ် ကော်မာဖြင့် ခွဲထားသော string တစ်ခု
ဖြစ်နိုင်သည်။ Name များကို စာလုံးအသေး kebab-case အဖြစ် normalize လုပ်သည်
(`pii_masker` → `pii-masker`)။ ရလဒ်ကို `context.disabledGuardrails` မှတစ်ဆင့်
registry သို့ ပေးပို့ပြီး ၎င်း registry က ကိုက်ညီသော guardrail များကို ကျော်သွားသည်
(`results` ထဲတွင် `skipped: true`)။

## လုပ်ဆောင်မှု အစီအစဉ်

`src/sse/handlers/chat.ts` နှင့်
`open-sse/handlers/chatCore.ts` တို့မှတစ်ဆင့် ဖြတ်သန်းသည့် request တစ်ခုစီအတွက်-

1. `resolveDisabledGuardrails(...)` သည် API key၊ body နှင့် headers တို့မှ skip list ကို တည်ဆောက်သည်။
2. `guardrailRegistry.runPreCallHooks(body, ctx)` သည် guardrails များကို priority ငယ်စဉ်ကြီးလိုက်ဖြင့် လုပ်ဆောင်သည်-
   - ပိတ်ထားသော guardrails များကို `skipped` အဖြစ် မှတ်တမ်းတင်သည်။
   - Guardrail တစ်ခုစီ၏ `preCall` သည် `modifiedPayload` မှတစ်ဆင့် payload ကို ပြန်လည်ရေးသားနိုင်သည်။
   - ပထမဆုံး `block: true` သည် chain ကို ချက်ချင်းရပ်တန့်စေပြီး handler က guardrail ငြင်းပယ်မှု response ကို ပြန်ပေးသည်။
3. (ပြန်လည်ရေးသားထားနိုင်သည့်) payload သည် combo routing နှင့် upstream dispatch ထဲသို့ စီးဆင်းသွားသည်။
4. Response ကို စုစည်းပြီးနောက် `guardrailRegistry.runPostCallHooks(...)` သည် response ပေါ်တွင် တူညီသော chain ကို လုပ်ဆောင်သည်။ ဤနေရာရှိ `block: true` သည် upstream response ကို စွန့်ပစ်သည်။

Exception ပစ်သော guardrails များကို `error: <message>` ဖြင့် မှတ်တမ်းတင်ပြီး
`logger.warn` မှတစ်ဆင့် log ရေးသော်လည်း chain သည် ဆက်လက်လုပ်ဆောင်သည် — ဒီဇိုင်းအရ fail-open ဖြစ်သည်။

## စိတ်ကြိုက် Guardrail များ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

အဆင့်များ-

1. `BaseGuardrail` ကို တိုးချဲ့ထားသော `src/lib/guardrails/myGuardrail.ts` ကို ဖန်တီးပါ။
2. `preCall` နှင့်/သို့မဟုတ် `postCall` ကို အကောင်အထည်ဖော်ပါ။
3. Import ပြုလုပ်ချိန်တွင် register လုပ်ပါ (`registerDefaultGuardrails` မှ push လုပ်ခြင်း) သို့မဟုတ်
   runtime တွင် `guardrailRegistry.register(...)` ကို ခေါ်ပါ — registry သည် normalized name တူညီသည့်
   ယခင် guardrail တစ်ခုခုကို အစားထိုးပါမည်။
4. `tests/unit/` အောက်တွင် test များ ထည့်ပါ (ရှိပြီးသား နမူနာများ-
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)။

## Injection-guard route လွှမ်းခြုံမှုနှင့် red-team (Phase 8 · Block D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) သည် user prompt များကို
လက်ခံသည့် route အားလုံးကို လွှမ်းခြုံသည်။ ၎င်းသည် `INJECTION_GUARD_MODE` ကို လိုက်နာသည် (မူလ `warn` = log သာရေးခြင်း၊
`block` = HTTP 400 `SECURITY_001` ကို ပြန်ပေးခြင်း)။

| အမျိုးအစား        | Route များ                                                                                                                                           | မူလ mode |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| Text (ရှိပြီးသား) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn     |
| Generative        | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn     |
| Data              | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn     |

စာသားထုတ်ယူမှု (`extractMessageContents`) သည် `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ကို လွှမ်းခြုံသည်။

**Red-team (ညစဉ်၊ `nightly-llm-security.yml`):** promptfoo သည် route တစ်ခုစီက
`INJECTION_GUARD_MODE=block` တွင် OWASP-LLM corpus ကို ပိတ်ဆို့ကြောင်း အတည်ပြုသည်။ garak သည် probe များကို လုပ်ဆောင်သည် (secret မရှိပါက ကျော်သွားသည်)။

`resolveDisabledGuardrails` မှတစ်ဆင့် ၎င်းကို ကင်းလွတ်ခွင့်ပေးနိုင်သည်။

ညစဉ် workflow (`.github/workflows/nightly-llm-security.yml`, cron + manual
dispatch) တွင် job နှစ်ခု ပါဝင်သည်-

- **`promptfoo-guard` (ပိတ်ဆို့နိုင်သော)** — `INJECTION_GUARD_MODE=block` ဖြင့်
