> **Джерело істини:** `src/lib/guardrails/`
> **Останнє оновлення:** 2026-08-29 — v3.8.51 (Походження стенограми Video Bridge оголошується абонентом,
> ще не перевірено сервером — уточнено згідно з #11661)

Захисні механізми забезпечують безпеку, політику та трансформації вмісту на межі між OmniRoute та вищестоящими провайдерами. Кожен захисний механізм може перевіряти (та за бажанням відхиляти, трансформувати або анотувати) корисні навантаження запитів (`preCall`) та відповіді вищестоящих систем (`postCall`).

Система є **відкритою при збої**: якщо захисний механізм видає помилку під час виконання, реєстр записує помилку та продовжує роботу з наступним захисним механізмом, замість того, щоб відхиляти запит. Блокування є явним рішенням (`block: true`), а не випадковістю.

Під час імпорту реєстр автоматично завантажує шість захисних механізмів у порядку пріоритету
(див. `registry.ts` → `registerDefaultGuardrails()`):

| Пріоритет | Назва               | Етап(и)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |

Менші значення пріоритету виконуються **першими**.

### Міст для зображень (`visionBridge.ts`) — Міст модальностей PR-1

Перехоплює запити із зображеннями, спрямовані до **моделей без підтримки зображень**, і або
переспрямовує весь запит до моделі з підтримкою зображень, або замінює частини із
зображеннями текстовими описами, створеними налаштовуваною моделлю для обробки
зображень, перш ніж виконати зовнішній виклик. Це дає змогу провайдерам, що підтримують
лише текст, прозоро обробляти мультимодальні корисні навантаження.

Послідовність:

1. Пропустити, якщо цільова модель уже підтримує зображення (якщо вона не входить до
   списку моделей із примусовим використанням мосту `isVisionBridgeForcedModel`).
2. Видобути частини із зображеннями за допомогою `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), яка делегує роботу **уніфікованому детектору
   медіаданих** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` — єдиному
   джерелу істини, спільному з фільтром сумісності комбінацій.
   Видобування обмежено дозволеним списком частин верхнього рівня тих форм,
   які `replaceImageParts` може вставити назад (контракт видобування↔заміни): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` та Responses API `input_image`. Вкладені збіги й
   форми, що містять лише індикатори, призначені для фільтра комбінацій і ніколи не видобуваються.
   Пропустити, якщо нічого не знайдено.
3. Визначити конфігурацію середовища виконання за допомогою `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань `modalityBridge*`
   мають пріоритет; застарілі ключі `visionBridge*` залишаються **резервним варіантом
   на один цикл** (вікно для відкочування). Пропустити до будь-якого обходу медіаданих, якщо
   міст вимкнено.
4. Селектор режиму (`modalityBridgeVisionMode`, див. таблицю нижче) визначає,
   чи виконувати переспрямування або опис. Переспрямування повертає `modifiedPayload`, у якому замінено
   лише `model`, а також метадані `{ rerouted, fromModel, toModel, imagesKept }`.
5. Шлях опису: обмежити кількість зображень значенням `maxImages`, сформувати запит з урахуванням завдання,
   перевірити кеш описів, викликати модель для обробки зображень **паралельно**
   (`Promise.allSettled`) і вставити замість зображень текстові частини
   `[Image N]: <description>`. Невдале створення опису повертає `null`, а вихідна частина із зображенням
   **зберігається** (#4012) — за винятком шляху опису для комбінації, коли всі
   спроби створити опис завершилися невдало: тоді для підтвердженого зовнішнього сервісу без підтримки зображень
   підставляється заглушка `(unavailable — no vision-capable provider connected)` (#8430).
6. Повернути `modifiedPayload` + метадані (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режиму (`modalityBridgeVisionMode`)

| Режим      | Типово | Поведінка                                                                                                                                                                                                                                                                                                                                                            |
| ---------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔      | Незмінена застаріла евристика (#6640/#7204): моделі, що не є комбінаціями, і моделі `auto/` переспрямовуються до найкращої моделі з підтримкою зображень, якщо вихідна модель уже не має придатних облікових даних (тоді створюється опис); цілі-комбінації завжди використовують опис.                                                                              |
| `describe` |        | Завжди створювати опис — блок переспрямування повністю пропускається; відповідь завжди надає вибрана користувачем модель.                                                                                                                                                                                                                                            |
| `reroute`  |        | Примусове переспрямування: перевірка збереження моделі з обліковими даними обходиться. Перевірка облікових даних **цілі** переспрямування все одно застосовується — якщо придатної цільової моделі з підтримкою зображень немає, запит переходить до створення опису, щоб необроблені зображення ніколи не потрапляли до сервісу, який підтримує лише текст (#8430). |

Примусові режими завершують вибір **до** запуску автоматичної евристики; поведінка `auto`
побайтово ідентична захисному механізму до PR-1.

#### Область дії API-ключа (`visionBridgeKeyScope.ts`)

Коли API-ключ виклику обмежує `allowedConnections`, пули квот
(`allowedQuotas`) або моделі (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), міст вибирає для
переспрямування й опису лише ті моделі, які дозволено використовувати цьому ключу, через з'єднання,
які дозволено використовувати цьому ключу. Потім виклик для створення опису завжди проходить через
самозациклення OmniRoute із заголовком `x-omniroute-self-loop-key-id`, щоб отриманий запит чату
повторно застосовував політику з'єднань і моделей цього ключа. `enforceApiKeyPolicy()`
враховує цей заголовок лише разом із токеном носія самозациклення, тож він може
тільки звузити доступ, а ідентифікатор, який не вдається розпізнати, відхиляється.

Якщо для ключа не дозволено жодної моделі з підтримкою зображень, шлях опису не втручається,
а запит передається без змін — це та сама відмовостійка відкрита поведінка, що й для вимкненого
захисного механізму (метадані `{ skipped: true, reason: "no_permitted_vision_model" }`).
Запити без ключа та ключі без цих обмежень поводяться так само,
як і раніше.

#### Запит для опису з урахуванням завдання (`modalityBridgeVisionTaskAware`)

За замовчуванням — **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає
текст **останнього повідомлення користувача** (обрізаний до 500 символів) до базового
запиту на опис, спрямовуючи опис на те, про що насправді запитував користувач
(патерн codex-vision-proxy), і просить модель зору транскрибувати видимий
текст. Якщо прапорець вимкнено або текст користувача відсутній, базовий запит
використовується без змін.

Власний OpenAI-сумісний запит циклу самоопису (`callVisionModelSingle()`
у `visionBridgeHelpers.ts`) завжди запитує `image_url.detail: "high"` —
безумовно, для кожного викликувача/провайдера, без залежності від будь-якого сигналу клієнта.
Вибір низького рівня деталізації погіршує точність OCR саме для завдання
транскрибування тексту, якого вимагає цей запит, тому сам виклик опису завжди
запитує високу деталізацію незалежно від рівня деталізації, використаного у
вихідному вхідному запиті. Це впливає лише на тіло внутрішнього запиту опису;
це не змінює того, як OmniRoute передає власне значення `image_url.detail`
викликувача в основному запиті — це значення за замовчуванням застосовується
окремо й лише для виявлених клієнтів OpenCode у `defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`). Гілка циклу самоопису у форматі
передавання Anthropic не має поля `detail`, тому жодне з цих значень за
замовчуванням на неї не впливає.

#### Обмеження вихідного опису (`modalityBridgeVisionMaxChars`)

| Ключ                           | Значення за замовчуванням | Діапазон          |
| ------------------------------ | ------------------------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`                       | `0` або 100–50000 |

`0` (значення за замовчуванням) означає **без обмеження** — опис, повернутий
`callVisionModel()`, передається без змін, зберігаючи наявну
поведінку. Будь-яке значення в діапазоні 100–50000 обрізає опис із
суфіксом `…`, перш ніж його буде вставлено назад як `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` у `src/lib/guardrails/visionBridge.ts`).
Збільшуйте це значення для насичених деталями завдань OCR, де наступній моделі
потрібна повна транскрипція; зменшуйте його, щоб обмежити використання токенів
багатослівними моделями зору. Поле на панелі керування розташоване на панелі
Advanced вкладки Vision (`modality-bridge-max-chars` у
`ModalityBridgeVisionTab.tsx`) і підвищує будь-яке значення від 1 до 99 до
мінімуму 100, залишаючи явно вказаний `0` без змін — `0` сам по собі є
допустимим значенням Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не лише
значенням за замовчуванням «не задано».

#### Кеш описів (`modalityBridge/bridgeCache.ts`)

Внутрішньопроцесний кеш LRU + TTL для результатів опису, спільний для всього
процесу. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` із
фреймінгом на основі префіксів довжини (без колізій меж полів). Компонент моделі —
це **налаштована** модель мосту, а не модель, яка фактично відповіла:
`callVisionModel` може внутрішньо перейти до резервного варіанта, а створення
ключів для кожної спроби фрагментувало б кеш. Невдалі описи ніколи не кешуються.
Налаштування:

| Ключ                            | Значення за замовчуванням | Діапазон |
| ------------------------------- | ------------------------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`                    | —        |
| `modalityBridgeCacheTtlMinutes` | `60`                      | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`                     | 10–5000  |

#### Нормалізація віддалених зображень (самоопис/отримання base64)

Коли міст самостійно отримує **віддалене** зображення — для внутрішнього виклику
опису Anthropic та перетворення у base64 у форматі передавання claude
(`ensureBase64ImagesForClaudeWire`), в обох випадках через
`fetchRemoteImageAsDataUri()` у `visionBridgeHelpers.ts` — отриманий URI даних
перед вбудовуванням у запит до моделі зору пропускається через
`normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`). Завеликі зображення зменшуються до
**2048px за довгою стороною** (відповідно до обмеження зміни розміру, яке
OpenAI/Anthropic уже застосовують на сервері), що зменшує обсяг передаваних
даних і затримку, не змінюючи того, що бачить модель зору. Для зміни розміру
використовується `sharp`, завантажений через динамічний імпорт: на платформі,
де не вдається завантажити його нативний бінарний файл, `normalizeDataUri()`
**ніколи не викидає виняток** — натомість він без змін передає вихідні байти,
тому шлях опису/перетворення у base64 завжди продовжує працювати. Дані, що не
є зображенням (отримані дані, які не вдалося декодувати як зображення), також
передаються без змін. Ця нормалізація застосовується лише до зображень, які
міст отримує для власного внутрішнього виклику, — вона ніколи не застосовується
до необробленого наскрізного корисного навантаження викликувача, що відповідає
принципу внесення змін лише за явною згодою (Жорстке правило #20).

#### Схема налаштувань + міграція

Нові ключі `modalityBridge*` перевіряються за допомогою Zod у
`updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, трійка `modalityBridgeCache*` і група
`modalityBridgeAudio*`, яку використовує Audio Bridge. Міграція
`141_modality_bridge_settings.sql` копіює наявні застарілі значення
`visionBridge*` до відповідних нових ключів (ідемпотентно, ніколи не
перезаписуючи значення `modalityBridge*`, установлене оператором); застарілі
ключі залишаються прийнятними як резервний варіант для читання протягом одного
циклу випуску.

#### Заголовок прозорості + статистика

Перетворені за допомогою опису відповіді містять
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(створюється `buildModalityBridgeHeader()` у `modalityBridge/bridgeStats.ts`,
додається `withModalityBridgeHeader()` у `src/sse/handlers/chatHelpers.ts`).
Перенаправлені запити **не** отримують заголовка — корисне навантаження не
змінювалося, а заміну моделі вже видно в полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (автентифікація керування, той самий рівень, що й
`GET /api/settings`) повертає збережені в пам’яті лічильники для кожної модальності
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` та
`video`. `averageLatencyMs` використовує `latencySamples`, а не всі спроби, як
знаменник; операція без вимірювання часу не створює штучний зразок із нульовою
кількістю мілісекунд. `bridged` залишається зворотно сумісним псевдонімом для успішних
перетворень; невдалі спроби не збільшують його.
Лічильники навмисно скидаються після перезапуску процесу
(телеметрія, а не облік).

#### Конфігурація панелі керування

Спеціальна сторінка панелі керування розташована за адресою
`/dashboard/settings/modality-bridge`. Її вкладки `Vision`, `Audio`
та `Video`, доступні через URL, зберігають параметри запиту під час перемикання значення `tab`.
Вкладка Vision надає налаштування ввімкнення, режиму, вибору моделі (включно з автоматичною
моделлю за замовчуванням), формування запитів з урахуванням завдання, розширених обмежень
часу очікування/зображення/довжини опису/кешу, лічильники
середовища виконання та захищений тестовий запит. Вкладка Audio також працює: вона надає
налаштування ввімкнення, засіб вибору моделі лише для STT з варіантом Auto, обмеження
часу очікування/максимальної тривалості кліпу, лічильники аудіо та тестовий запит `input_audio`.
Вкладка Video є функціональною: вона повідомляє стан FFmpeg/ffprobe у середовищі
виконання — один із чотирьох явних станів інтерфейсу (`unknown`, доки перевірка
виконується або не може завершитися, `restricted` на хості панелі керування, що не є
loopback-хостом, де перевірка пропускається на боці клієнта, `unavailable` після виконання
перевірки та підтвердження відсутності або `available` із версіями FFmpeg/ffprobe) — зберігає
обмеження ввімкнення/моделі/кадрів/відео/часу очікування, фільтрує засіб вибору моделей,
залишаючи моделі з підтримкою комп’ютерного зору, та відображає лічильники відео.

Колишня картка Vision Bridge у налаштуваннях ШІ тепер є посиланням для сумісності на
нову сторінку; вона більше не містить другу копію форми. Media Providers також
пов’язує робочі процеси Image-to-Text і Speech-to-Text із відповідними вкладками Modality
Bridge, не видаляючи наявний майданчик Speech-to-Text.

**Обхід контролю допуску для self-loop:** коли виклик опису маршрутизується через
власний `/v1` self-loop OmniRoute (нестандартна модель постачальника), підзапит надсилає
`x-omniroute-admission-bypass: internal` та автентифікується за допомогою визначених
облікових даних self-loop — локального маркера `sk_omniroute` у локальному режимі або
налаштованого оператором ключа середовища `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), щоб
розгортання з `REQUIRE_API_KEY=true` усе ще могли виконувати виклик опису. Обхід
дозволено лише для цих точних облікових даних, тому зовнішні клієнти не можуть використати
цей заголовок, щоб оминути контроль допуску.

Застарілі значення за замовчуванням містяться в `src/shared/constants/visionBridgeDefaults.ts`;
нові значення режиму/врахування завдання/кешу за замовчуванням і механізм визначення налаштувань містяться в
`src/shared/constants/modalityBridgeDefaults.ts`. Запобіжник надає параметр конструктора
`deps`, щоб тести могли підставляти фіктивні реалізації `getSettings` і
`callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює чат-запити, що містять аудіо, перш ніж вони досягнуть цільового об’єкта, про який
не відомо, чи приймає він аудіовхід. Він ніколи не змінює маршрут чат-запиту: аудіочастини
транскрибуються через наявну OpenAI-сумісну multipart-кінцеву точку, а
вибрана чат-модель продовжує роботу з текстовими транскриптами.

Послідовність:

1. Визначити `supportsAudio` через `getResolvedModelCapabilities()`. Явні
   метадані реєстру постачальників мають пріоритет, потім ідуть статичні метадані моделі, а далі —
   синхронізовані `modalities_input`. Оголошений список вхідних даних без `audio` означає `false`;
   за відсутності будь-яких даних про можливості значення залишається `null`. І `false`, і `null`
   активують консервативний міст, тоді як `true` обходить його.
2. Визначити налаштування `modalityBridgeAudio*` і витягти придатні для вставлення
   аудіочастини верхнього рівня з кожного повідомлення за допомогою спільного детектора
   `detectMediaParts()`. Підтримувані формати передачі: OpenAI `input_audio`, `audio_url` і
   `source.media_type: "audio/*"`. Вкладене аудіо виявляється для маршрутизації, але не
   видаляється шляхом вставлення. Обсяг роботи обмежено `modalityBridgeAudioMaxClips`;
   наступні частини залишаються без змін.
3. Використати налаштований `provider/model` або дозволити `selectAudioBridgeModel()`
   перебрати `AUDIO_TRANSCRIPTION_PROVIDERS` у стабільному порядку каталогу та вибрати першу
   модель із придатними активними обліковими даними постачальника.
4. `callAudioTranscription()` перетворює аудіо у форматі base64/data-URI на multipart-файл
   `file` або завантажує віддалений `audio_url` через захист вихідних з’єднань лише з
   публічними адресами, із закріпленням DNS та обмеженням у 25 МБ. Потім він надсилає файл
   і вибрану модель методом POST до локального self-loop `/v1/audio/transcriptions`,
   автентифікованого за допомогою `resolveSelfLoopBearer()`. Наявний маршрут транскрибування
   виконує звичайний пошук облікових даних, обробку періоду очікування/обмеження частоти та
   передавання постачальнику.
5. Успішні виклики замінюють відповідні частини на `[Audio N]: <transcript>`. Виклики
   виконуються через `Promise.allSettled`: окрема помилка зберігає початкову
   аудіочастину (контракт #4012). Якщо всі виклики завершилися невдало, а для цілі доведено
   `supportsAudio === false`, частини набувають вигляду
   `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для
   невідомої цілі (`null`) результат, у якому всі виклики завершилися невдало, залишається без змін. Ціль, для якої
   доведено підтримку лише тексту та немає придатних облікових даних STT, отримує ту саму явну
   заглушку без виконання мережевого виклику.

Успішні транскрипти використовують спільний для всього процесу кеш LRU/TTL Modality Bridge.
Ключ поєднує посилання на аудіо, стабільну мітку операції `audio-transcription`
та вибрану модель STT; помилки ніколи не кешуються. Спроби обробки аудіо оновлюють
спільні лічильники `bridged`, `cacheHits`, `failures` і `lastUsedAt`.
Перетворені відповіді містять
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; незмінені
запити не отримують сегмент Audio Bridge.

Налаштування середовища виконання зберігаються в БД і перевіряються за допомогою Zod:

| Ключ                          | Значення за замовчуванням | Діапазон        |
| ----------------------------- | ------------------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`                    | —               |
| `modalityBridgeAudioModel`    | `""`                      | Auto або ID STT |
| `modalityBridgeAudioTimeout`  | `60000`                   | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`                       | 1–10            |

Спільний кеш і надалі контролюється параметрами `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` і `modalityBridgeCacheMaxEntries`.

### Міст для відео (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює частини відео верхнього рівня в `messages` Chat Completions і `input`
Responses API перед викликом цільової моделі без відомої нативної підтримки відео.
Підтримувані формати: `input_video`, `video_url`, `video_source`, URL-адреси HTTPS
і URI даних `data:video/*;base64,...`. Звичайні імена файлів у тексті не
розглядаються як відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) відповідає за обхід запиту,
перевірку можливостей і політик, агрегацію на рівні запиту та корисне навантаження
відповіді. Обробку окремого відео — отримання, кешування всього результату,
опис послідовності кадрів (з об’єднанням будь-якої заявленої викликачем
транскрипції аудіо), а також метрики, переривання й очищення для кожної спроби —
приховано за `processVideoPart` у `videoBridgePipeline.ts`, який викликається
один раз для кожної частини відео в циклі `preCall`. Цей модуль також визначає
явні межі портів `VideoMediaBrokerPort` (отримання байтів і видобування
вибіркових кадрів), `VideoAudioTranscriptionPort` (об’єднання заявленої
викликачем транскрипції аудіо з підписами вибіркових кадрів) і
`VideoDrilldownPort` (межа збереження деталізації кадрів; ще не підключена до
`processVideoPart` — наразі записи деталізації створює лише окремий маршрут
`/api/modality-bridge/video/drilldown`).

Публічний шлях запиту `/v1` ніколи не імпортує й не запускає підпроцес.
Віддалені відео завантажуються з обмеженням у 50 МіБ; для вбудованих відео
base64 діє консервативне обмеження декодованого розміру в 36 МіБ на одне відео,
щоб оболонка моделі, повідомлень і фреймінгу залишалася в межах публічного
ліміту приймання JSON-запитів у 50 МіБ. Довжина вбудованих даних і оцінка
декодованого розміру перевіряються до виділення пам’яті. HTTPS є обов’язковим
для початкової віддаленої URL-адреси та кожного переспрямування; використовується
наявний захист вихідних з’єднань лише до загальнодоступних адрес із прив’язкою
DNS. Потім байти перетинають чітку внутрішню межу брокера
`POST /api/modality-bridge/video/extract`. Цей маршрут має одночасно позначки
`LOCAL_ONLY` і `SPAWN_CAPABLE`, приймає лише автентифікований на рівні процесу
запит із довіреного loopback-інтерфейсу й ніколи не приймає URL-адресу, шлях
файлової системи, виконуваний файл або список аргументів. Конвеєр обмеження
розміру тіла API та інкрементальний зчитувач тіла обробника незалежно
забезпечують ліміт вхідних даних брокера в 50 МіБ. Його обмежена черга виконує
по одному видобуванню за раз, допускає чотири завдання в очікуванні та обмежує
їхні сукупні вхідні дані до 100 МіБ.

Усередині брокера `ffprobe` читає приватний локальний файл; фіксований список
дозволених форматів виключає формати списків відтворення та маніфестів. Для
дозволених контейнерів сімейства MOV зовнішні посилання на дані MOV за
замовчуванням залишаються вимкненими, і фіксована команда не вмикає їх.
І `ffprobe`, і `ffmpeg` використовують список дозволених протоколів лише з
`file`, один потік, фіксовані масиви аргументів, не використовують оболонку,
а виконувані файли визначаються через `PATH`. Потоки обкладинок, позначені як
прикріплені зображення, не є кандидатами для відтворення. Усі відтворювані
потоки мають відповідати обмеженням, причому явному потоку за замовчуванням
надається перевага перед детермінованим резервним вибором потоку з найнижчим
індексом. Відео обмежені тривалістю 600 секунд, 8 192 пікселями на кожен вимір
і 33 554 432 пікселями джерела. FFmpeg вибирає 1–16 проміжних JPEG-кадрів,
зменшує довгу сторону щонайбільше до 1 024 пікселів без збільшення менших
вхідних даних і ніколи не отримує URL-адресу. За замовчуванням вибірка має
значення `uniform`. Необов’язкова політика `scene_aware` та експериментальна
політика `segment_aware` виконують один додатковий фіксований прохід FFmpeg
по вже перевіреному локальному потоку, вибирають обмежену кількість часових
позначок сцен `showinfo` і детерміновано повертаються до тих самих рівномірних
проміжних точок у разі збою детектора, перевищення часу очікування, некоректного
виведення або порожнього набору кандидатів. Режим з урахуванням сегментів
розподіляє вибірки проміжних точок пропорційно до перевірених інтервалів сцен;
свідчення для режиму з урахуванням сегментів і резервну поведінку докладно
описано нижче. Жорстке обмеження у 16 кадрів застосовується після відбору для
кожної політики. Якщо запит з урахуванням сцен має бюджет лише в один кадр,
використовується рівномірна проміжна точка активного повного відео або вікна
фокусування, а у звіті зазначається `policyEffective: uniform`: один вибраний
кадр сцени не може зберегти обидва часові краї. Викликач може за бажанням
надати скінченне вікно фокусування (`start`/`end` у секундах); межі
приводяться до тривалості медіафайлу, вікна зі зворотним порядком меж або
нескінченними значеннями відхиляються, а всі політики вибірки виконуються лише
в нормалізованому інтервалі. Отримане вікно включається до метаданих вибірки
та до префікса недовіреного опису, щоб наступні моделі могли відрізнити
сфокусований уривок від повної часової шкали.

Семантичне фокусування підписів є окремим явним налаштуванням. Режим аналізу
`full` за замовчуванням зберігає наявну підказку для кадрів і ніколи не передає
текст запиту моделі підписів. У режимі `focused` міст зчитує лише найновіший
непорожній створений користувачем `text`/`input_text` із того самого контейнера
Chat або Responses, нормалізує його до NFC, згортає керівні символи й пробіли
та обмежує до 500 кодових точок Unicode. Порожній результат спричиняє
повернення до точної підказки `full`. Придатна підказка серіалізується як JSON
у спеціальному блоці недовіреного користувацького контексту й може лише
визначати пріоритет спостережуваних деталей; вона не може перевизначити окреме
застереження щодо невиконання інструкцій, видимих або чутних у медіа.
Текстове фокусування ніколи не виводить `start`/`end` і не змінює часовий
семплер.

#### Структурні свідчення сегментів FU-07

`segment_aware` використовує один обмежений прохід попереднього аналізу вже перевіреного
локального відеопотоку. Фіксований ланцюжок фільтрів спочатку масштабує відео до ширини
не більше 320 пікселів, виявляє зміни сцен і завмерлі інтервали, а потім виконує вибірку
з частотою 1 кадр на секунду для оцінювання розмиття, середньої яскравості та
просторової/часової інформації. Прохід обмежено 600 структурними зразками, одним
потоком FFmpeg/фільтра, тими самими списками дозволених лише для протоколу `file`
і контейнерів, обсягом виводу процесу не більше 1 MiB та щонайбільше 30 секундами
в межах спільного переривання/граничного терміну брокера. Він ніколи не приймає
запити на команду, фільтр, шлях або URL.

Структурні значення є детермінованими даними вибірки, а не семантичним розумінням
відео. Вони не визначають суб’єктів, дії, субтитри, мовлення чи наміри користувача.
Межі сцен і завмирань формують сегменти; охоплення завмирання, розмиття,
експозиція, просторова деталізація та часові зміни впливають лише на розподіл
наявного бюджету в 1–16 кадрів. Повністю завмерлий сегмент обмежується одним кадром,
тоді як незавмерлі сегменти конкурують за решту бюджету. Коли кількість меж
перевищує кількість кадрів, зберігається рівномірне охоплення часової шкали, щоб
швидкі переходи на початку не могли приховати довгий кінцевий сегмент. Межі сцен
у межах 1-секундної роздільності аналізу від межі завмирання об’єднуються.

Відсутні фільтри, некоректні/порожні дані, помилка детектора або тайм-аут
обмеженого попереднього аналізу призводять до безпечного переходу до точної
політики рівномірних серединних точок. Переривання з боку викликувача або
граничний термін брокера не спричиняють такого переходу: вони завершують
поточний підпроцес, запобігають подальшому вилученню кадрів, а приватне
тимчасове дерево видаляється в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерує детерміновані реальні тестові
дані FFmpeg для оцінювання економії викликів створення описів після дедуплікації,
розподілу бюджету за інтенсивного руху, даних про розмиття/експозицію/SI-TI,
швидких переходів із довгим кінцевим сегментом і хибних спрацьовувань через
поступове згасання. Скрипт фіксує фактичний час попереднього аналізу, а за
наявності `/usr/bin/time` — процесорний час дочірнього процесу та піковий RSS.
Його перевірки якості є лише структурними оракулами. Якість реальної моделі
створення описів залишається `HOLD`, оскільки цей тестовий стенд не має
авторизованої кінцевої точки або зафіксованого оцінювача. Грошова економія також
залишається `HOLD`, якщо `--caption-cost-per-call-usd` не надає явну додатну
оцінку вартості одного виклику; скрипт ніколи не вигадує жоден із цих результатів.

Розмір кожного кадру обмежено 4 MiB, сукупний розмір усіх необроблених кадрів —
23 MiB, а розмір серіалізованої відповіді брокера — 32 MiB. Приватний тимчасовий
каталог видаляється в `finally`. OmniRoute не постачається з FFmpeg і не приймає
власний шлях до виконуваного файлу. Перед створенням описів міст застосовує
консервативний прохід візуальної дедуплікації: кожне зображення JPEG зменшується
до буфера відтінків сірого розміром 16×16 і порівнюється лише з останнім
збереженим кадром. Якщо запитаний бюджет описів перевищує один кадр, вилучення
надає обмежений пул кандидатів, що не перевищує подвоєного бюджету й ніколи не
містить більше 16 кадрів. Запитане обмеження застосовується лише після
дедуплікації, причому під час остаточного проріджування зберігаються перший і
останній вибрані кандидати, якщо бюджет становить щонайменше два кадри.
Версіонована політика
`grayscale-16x16-mean-cells-v2` використовує більше зі значень: середню зміну
яскравості або частку комірок мініатюри, нормалізована зміна яких становить
щонайменше 0.05. Порогове значення дублювання — константа 0.04, вибрана заради
передбачуваності, а не надана як параметр середовища виконання. Цей вторинний
сигнал високої контрастності зберігає невеликі рухи та зміни видимого тексту,
які може приховати порівняння лише за середнім значенням. Помилки засобу
порівняння або декодера призводять до безпечного збереження охоплення. Метадані
виводу окремо відображають вилучених кандидатів, успішно використані кадри та
відкинуті візуальні дублікати.

Явно позначена частина відео може запитувати контактний аркуш із часовими
позначками. Міст створює JPEG-сітку щонайбільше з 4 стовпців і 16 кадрів. У
нижню висококонтрастну смугу кожної 512-піксельної комірки вбудовується часова
позначка її джерела, а ті самі часові позначки залишаються в текстових метаданих
для подальшого зіставлення й аудиту. Розмір повного JPEG залишається обмеженим
32 MiB. Якщо `sharp` не може декодувати або скомпонувати сітку, міст повертається
до окремих кадрів JPEG; переривання клієнтом усе одно поширюється на операцію
створення аркуша.

Докази для просування навмисно відокремлено від синтетичного мікротесту
компонування. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає
версіонований за схемою стенд A/B-тестування для реальних моделей машинного зору,
сумісних з OpenAI. Він вимірює повідомлену постачальником кількість токенів,
наскрізну фактичну затримку (включно з компонуванням аркуша), кількість викликів
моделі та збереження фактів, визначених маніфестом. Необроблені відповіді моделі
не записуються у звіт; зберігаються лише дайджести SHA-256 та ідентифікатори
зіставлених фактів. Стенд не здійснює жодних мережевих або платних викликів
моделі, якщо не передано `--execute-real` і не налаштовано `--model`,
`OMNIROUTE_BASE_URL` та `OMNIROUTE_API_KEY`. Без такого явного реального запуску
його машинозчитуваний вердикт залишається `HOLD`; самі лише синтетичні вимірювання
корисного навантаження/кількості викликів не є доказами для просування.

Викликувачі можуть додати необов’язковий масив `transcript.cues` до підтримуваної
частини відео, якщо вони вже мають синхронізований текст. Кожна репліка повинна
містити `text`, скінченний інтервал `start`/`end` у межах визначеної тривалості
та значення `source` з білого списку (`client`, `embedded` або `audio-bridge`);
значення `confidence` за замовчуванням дорівнює `1` і має залишатися в межах
від `0` до `1`. Точні дублікати реплік згортаються. OmniRoute ніколи не запускає
транскрибування на основі цих метаданих: перевірені репліки копіюються до
описаного результату разом із джерелом, достовірністю та інтервалом і
відображаються як ненадійні спостереження поруч з описами кадрів. Некоректний
текст, текст поза допустимим діапазоном або текст без зазначеного походження
відхиляється, а не змішується з потоком описів. Обидва канали транскриптів у
тілі запиту нормалізують надане походження до `client`, включно із самостійно
заявленими мітками `embedded` або `audio-bridge`. Лише адаптер під керуванням
сервера може призначати ці довірені мітки через доступний лише з коду аргумент
`trustedSource`; поле JSON запиту не може передати значення цьому аргументу.
Текст транскрипту залишається ненадійним вмістом, отриманим із медіаданих,
незалежно від його походження, і ніколи не повинен визначати авторизацію.

Досвідчений викликач може надати доріжку `audioTranscript` для того самого відео;
вона розглядається як текст, наданий клієнтом, а не як доказ серверної транскрипції.
Механізм об’єднання виконує візуальні й аудіоспостереження в межах
єдиного кінцевого терміну та сигналу переривання, упорядковує їх на спільній часовій шкалі, згортає
точні дублікати й повідомляє про частковий результат, коли успішною є лише одна сторона.
Недійсний `audioTranscript` призводить до такого часткового результату — візуальний
опис зберігається, а аудіогілка записує санітизований код помилки —
замість відмови обробки всього відео. Доступність кожної гілки, прапорець часткового результату
та санітизовані коди помилок зберігаються в описаному результаті, у
метаданих захисного механізму (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), у метаданих кешу результатів і в лічильниках
об’єднання мосту. Стандартний шлях Video Bridge не викликає перетворення мовлення на текст
і не завантажує другу копію медіафайлу; без цієї явно наданої доріжки він залишається
лише відеорежимом.

**Зберігання транскриптів (#12150 P1).** Це застосовується автоматично щоразу, коли
Video Bridge (який сам потребує явного ввімкнення) відтворює репліку транскрипту — окремого
прапорця зберігання немає. Коли запит відтворює будь-яку репліку транскрипту (оголошений викликачем
`transcript` або об’єднаний `audioTranscript`), захисний механізм позначає його як
`videoBridgeObserved` і створює редаговану тінь опису відео —
ідентичне представлення, у якому довільний текстовий вміст кожної репліки замінено на
`[redacted-video-transcript]`; вона створюється шляхом підстановки структурованого поля репліки
до формування рядка (а не шляхом аналізу зведеного тексту, тому жоден вміст
репліки — зловмисний чи звичайний, зокрема вміст із символом `]`, як-от
`[inaudible]`/`[music]`, — не може зберегтися). У збереженому тілі запиту журналу викликів
кожна текстова частина, отримана з відео, замінюється на цю редаговану тінь, зіставлену за
рівністю вмісту; прив’язка `fullText` повторно зчитується із завершеного корисного навантаження
захисного механізму перед викликом, тому зіставлення залишається успішним після того, як наступні
захисні механізми в ланцюжку (маскувальники персональних даних і облікових даних із пріоритетами 10/95)
перезаписують текст опису на місці, а також після того, як ін’єкція системної підказки/передавання
керування/пам’яті змінює структуру масиву повідомлень. Тіло, надіслане моделі,
залишається незмінним. Спостережуваний запит також не заповнює довготривалу Memory
(вилучення даних як із запиту, так і з відповіді пропускається),
тож власна відповідь моделі не може відтворити текст транскрипту в Memory.

**Необроблені поля відео (#12430).** Коли міст увімкнено, а вбудована підтримка відео невідома або відсутня, визначені поля `transcript`/`audioTranscript` також активують `videoBridgeObserved`, навіть після помилки опису або досягнення обмеження `maxVideos`. `null` і порожні рядки враховуються; відсутні поля та метадані, не пов’язані з відео, — ні. У збережених копіях ці поля редагуються або запит не зберігається, а кеші/Memory обходяться.

На цих резервних шляхах коректні репліки, надані викликачем, перетворюються на підтримувані
частини `text`/`input_text`, а не на нестандартні поля постачальника. Обидві надані в запиті доріжки
залишаються ненадійними спостереженнями `client` із явним попередженням, що відео
не було описано, а часові позначки не було звірено з медіафайлом. Наявні
обмеження у 256 реплік/64 КіБ загалом і на кожну репліку застосовуються до обох доріжок разом;
часові позначки мають вкладатися в 600-секундну межу брокера та в будь-яке надане вікно
фокусування. Некоректні доріжки відкидаються, а не пересилаються як довільний текст; коректна
сусідня доріжка все ще може використовуватися, якщо їхній сукупний бюджет не перевищено. Поля зі
значенням null або порожні поля не додають тексту. Цей резервний механізм не додає отримання
медіафайлу чи транскрипції. Поля розширення транскрипту видаляються з резервного контейнера відео
та його об’єктів `video_url`/`source`. Суворий список дозволених полів OpenAI
залишається незмінним; контейнери відео з невідомою вбудованою підтримкою залишаються доступними,
а відомі цілі, що підтримують лише текст, зберігають безпечні маркери.
Структуровані редаговані тіні захищають доданий текст транскрипту, тоді як
оригінальний запит, що належить викликачу, залишається незмінним. Цілі з вбудованою підтримкою
та вимкнені мости зберігають наявну поведінку обходу.

Додатково збережені копії використовують той самий сигнал спостережуваного запиту. Необроблений
знімок клієнтського запиту до застосування захисного механізму, запит, що очікує в пам’яті, і журнал
рано відхиленого запиту структурно замінюють поля транскрипту у відеочастинах;
рядкові підказки, синтезовані етапами конвеєра та передаванням контексту, редагуються
в точці збереження тіла запиту. Збережений маркер `video_content_removed`
змушує продовження через `previous_response_id` завершуватися безпечною відмовою замість відновлення
тексту, який було навмисно видалено. Якщо спостережуваний запит втрачає свою
редаговану тінь для окремої частини до журналювання або якщо хоча б одна з кількох тіней відео
не збігається після подальших змін запиту, збережене тіло запиту
повністю пропускається замість збереження частково редагованого транскрипту.

Для спостережуваного запиту відповідь моделі може цитувати будь-яку частину
транскрипту без структурованої межі репліки. Тому її збережене в журналі викликів
`responseBody` замінюється маркером пропуску; докладний
артефакт конвеєра (який може містити тіла висхідних/клієнтських повідомлень і фрагменти потоку)
не зберігається. Семантичний кеш, кеш ідемпотентності та кеш повторного відтворення міркувань
не читаються й не записуються для цього запиту. Запит до постачальника та
видима клієнту відповідь залишаються незмінними. Ранні байти підтримання з’єднання видаляються
з тимчасового буфера, коли докладний артефакт пропускається. Попередження Kiro про некоректний EventStream
повідомляє лише кількість байтів корисного навантаження, але ніколи не його вміст або необроблену
помилку JSON-аналізатора.
Це не є твердженням, що кожну непов’язану діагностику постачальника/плагіна було
перевірено; ширше охоплення точок збереження відстежується в #11658.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремою
кеш-підсистемою зі зворотним підключенням і автентифікацією за токеном. Для кожної операції також потрібен
канонічний непрозорий ідентифікатор принципала. Перш ніж активувати клієнта у виробничому середовищі, він має
отримувати цей ідентифікатор з автентифікованого тенанта й ніколи не пересилати
значення, вибране клієнтом. Ключі кешу прив’язують цього принципала до канонічних ідентифікаторів сеансу та
посилання на відео, зберігають лише похідні від них ключі SHA-256 і обмежують як читання,
так і видалення тим самим принципалом. Кеш зберігає щонайбільше 16 похідних JPEG-кадрів
на запис, видаляє їх через десять хвилин і підтримує обмежені читання
`start`/`end` або явне видалення сеансу.

Для кожного принципала діє обмеження у 16 записів і 64 MiB канонічних JPEG-даних. Ці
обмеження не залежать від глобальної межі у 64 записи/256 MiB: тиск на квоту
принципала витісняє лише найдавніше використані записи цього принципала, перш ніж
розглядатиметься глобальне витіснення за LRU. Прострочені записи вилучаються як з обліку принципала,
так і з глобального обліку під час активності кешу, а скасування чи помилка валідації не
фіксують часткову заміну.

Кеш відхиляє неканонічний Base64, надлишкове доповнення, медіадані не у форматі JPEG, пошкоджені або
обрізані JPEG-файли, а також JPEG-файли, які спричиняють попередження під час обмеженого повного декодування зображення за допомогою `sharp`.
Кожне прийняте зображення повторно кодується як канонічний JPEG; ширина й висота визначаються
з декодованих байтів без довіри до полів клієнта, а будь-які кінцеві
поліглотні байти відкидаються, а не зберігаються. До обох квот зараховується лише обмежений канонічний
стиснений буфер. Обмеження передавання JSON враховує накладні витрати Base64 для максимальної межі
декодованих вхідних даних у 32 MiB. Для кожної
збереженої похідної версії записуються її валідований формат і роздільна здатність JPEG, політика семплювання,
версія формування похідної, час створення, обчислений сервером хеш вмісту та хешоване батьківське
посилання разом із хешем батьківського вмісту від довіреного клієнта. Скасування перевіряється
між асинхронними фазами декодування та хешування до атомарної фіксації в кеші.

Ця частина ще не підключає виробничого постачальника даних до маршруту й не
забезпечує вибір варіантів із різною роздільною здатністю. Тому прозорий шлях запиту Video Bridge
не створює додаткового навантаження, тоді як отримання прив’язаного до тенанта принципала та
повний життєвий цикл FU-08 із підтримкою кількох роздільних здатностей залишаються явними подальшими завданнями,
а не документуються як завершена поведінка.

Кадри послідовно описуються налаштованою моделлю Video. Порожнє перевизначення
Video успадковує налаштування Vision; якщо обидва значення порожні, автодиспетчер Vision
вибирає фактичну модель із підтримкою зору. Успішні описи
замінюють оригінальну частину стабільним префіксом `[Video description:`, який також
позначає текст як ненадійне спостереження, отримане з медіаданих, і вказує наступним
моделям не виконувати інструкції, знайдені в медіаданих. Ключі кешу описів кадрів
включають байти JPEG, запит, часову мітку та фактичну модель; кешуються лише успішні
описи. Записи кешу зберігають фактичну успішну модель-виробника,
включно з резервною моделлю; міст повідомляє `mixed`, коли різні кадри
було створено різними моделями. Влучання в кеш повторно використовує ідентичність цього виробника,
а не перепозначає її як запитаний план маршрутизації. Кеш результатів
усього відео індексується за кожним вхідним параметром, що змінює результат, — запитом, фактичною
моделлю, політикою семплювання, кількістю кадрів, режимом семантичного аналізу, відбитком SHA-256
нормалізованої підказки щодо фокуса, вікном фокуса, `transcript`,
`audioTranscript` і прапорцем контактного аркуша, — тому зміна будь-якого з цих
вимірів призводить до промаху кешу, а не до повторного використання застарілих даних. Версія політики
візуальної дедуплікації, порогове значення та обмежена кількість кадрів-кандидатів також явно зазначаються в
ключі й метаданих кешу результатів; отже, зміна політики не може повторно використати застарілий
опис усього відео. Метадані кешу результатів v4 зберігають режим і
відбиток, але ніколи не зберігають необроблене завдання користувача. Метадані захисного механізму повідомляють як
запитаний, так і фактичний режими аналізу; запитаний режим `focused` без
придатного користувацького тексту позначається як фактично `full`.

Захисний механізм видобуває всі підтримувані частини відео, але описує не більше ніж
`modalityBridgeVideoMaxVideos`. Для цільової моделі, щодо якої підтверджено
`supportsVideo === false`, невдалі відео та відео понад ліміт перетворюються на явні безпечні
текстові маркери, щоб необроблене відео не збереглося. Коли можливості невідомі, ці частини
зберігають свій відеоконтейнер; будь-яка резервна транскрипція проходить описане вище обмежене
перетворення на текст. Цільові моделі з `supportsVideo === true` обходять міст.
Сигнал переривання клієнтського запиту передається через завантаження, чергу брокера,
підпроцеси та виклики створення описів; переривання зупиняють обробку між відео й ніколи не допускають
відмовостійкого пропускання необроблених медіаданих.

Налаштування середовища виконання зберігаються в БД і перевіряються за допомогою Zod:

| Ключ                                | Значення за замовчуванням | Діапазон / поведінка                                                                                                      |
| ----------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`                   | Необов’язкове середовище виконання, що потребує явного ввімкнення                                                         |
| `modalityBridgeVideoAnalysisMode`   | `"full"`                  | `full` зберігає загальні описи; `focused` використовує обмежений недовірений контекст останнього повідомлення користувача |
| `modalityBridgeVideoModel`          | `""`                      | Успадковує модель Vision Bridge                                                                                           |
| `modalityBridgeVideoFrameCount`     | `8`                       | 1–16                                                                                                                      |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`               | `uniform`, `scene_aware` або пропорційний `segment_aware`; у разі збою детектора використовується `uniform`               |
| `modalityBridgeVideoMaxVideos`      | `1`                       | 1–4                                                                                                                       |
| `modalityBridgeVideoTimeout`        | `120000`                  | 1000–120000 мс                                                                                                            |

Збережені застарілі значення тайм-ауту відео, що перевищують 120 секунд, обмежуються
кінцевим терміном брокера; нові спроби записати налаштування понад цю межу відхиляються.
`GET /api/modality-bridge/video/runtime` перед автентифікацією або перевіркою середовища виконання
вимагає довіреної позначеної локальності loopback, а потім — управлінської
автентифікації. Він повертає лише `available`, очищені версії FFmpeg/ffprobe та фіксовану
причину, коли середовище виконання недоступне. Внутрішня кінцева точка видобування не є
публічним API завантаження: переповнення черги повертає `503` разом із `Retry-After`, від’єднання
викликувачем повертає `499`, а фіксований кінцевий термін брокера повертає `504`. Перетворені відповіді додають
`video->text;model=<visionModel>;parts=<videos>` до центрального
заголовка `x-omniroute-modality-bridge`, не видаляючи сегменти Vision або Audio.

### Маскувальник PII (`piiMasker.ts`)

Працює на **обох** етапах.

- **`preCall`** клонує корисне навантаження, обходить `system`, `messages`, `input` і
  `prompt` (включно з елементами у вигляді звичайних рядків) та застосовує `processPII()` (з
  `@/shared/utils/inputSanitizer`) до рядкових полів `content`/`text`. Коли
  `PII_REDACTION_ENABLED=true`, виявлені PII маскуються у вихідному
  корисному навантаженні. Це не залежить від `INPUT_SANITIZER_MODE` (який керує лише
  політикою щодо ін’єкцій у промпти). Коли маскування вимкнено, виклик записує кількість
  виявлень, не змінюючи вміст.
- **`postCall`** створює глибоку копію відповіді, запускає `sanitizePIIResponse()` разом із
  маскувальником форми Responses API (`maskResponsesOutput` — охоплює
  `output_text` і `output[].content[].text`). Якщо відбувається будь-яке маскування,
  змінена відповідь замінює оригінальну.

Захисний механізм ніколи не блокує; він лише додає анотації (`meta.detections`,
`meta.redacted`) або переписує вміст.

### Ін’єкція у промпт (`promptInjection.ts`)

Виявляє зловмисні структури у вмісті, наданому користувачем, і застосовує
налаштовану політику. Поведінка визначається змінними середовища та параметрами
конструктора:

| Налаштування     | Змінна середовища                                                                                           | За замовчуванням | Ефект                                                                                                                                                                                                    |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Увімкнено        | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`           | Коли `false`, захисний механізм негайно завершує роботу.                                                                                                                                                 |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`           | Політика щодо ін’єкцій: `block`, `warn` або `log`. (`redact` підтримується для зворотної сумісності, але **не** видаляє текст ін’єкції; переписування PII запиту контролюється `PII_REDACTION_ENABLED`.) |
| Поріг блокування | Параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдонім `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`           | Мінімальний рівень серйозності, необхідний для блокування. За замовчуванням середній рівень призначений лише для спостереження.                                                                          |

**Пріоритет режимів** (`getMode`): `options.mode` викликувача →
**перевизначення прапорцем функції в БД** для `INJECTION_GUARD_MODE` (Dashboard → Settings →
Feature Flags) → змінна середовища `INJECTION_GUARD_MODE` → змінна середовища `INPUT_SANITIZER_MODE` →
`warn`. Таким чином, перевизначення з панелі керування має пріоритет над змінними середовища, тому інтерфейс
Feature Flags керує активним захисним механізмом у реальному часі (без перезапуску). Читання з БД є відмовобезпечним:
у разі помилки захисний механізм повертається до поведінки на основі змінних середовища, а коли
перевизначення не задано, поведінка ідентична вирішенню лише за змінними середовища.

Джерела виявлення:

1. `sanitizeRequest()` з `@/shared/utils/inputSanitizer` (спільний набір детекторів,
   що використовується в інших частинах конвеєра).
2. Вбудовані `DEFAULT_GUARD_PATTERNS` (наразі `system_override_inline` і
   `markdown_system_block`, обидва з рівнем серйозності `high`).
3. Необов’язкові `customPatterns`, передані через параметри конструктора (рядки, регулярні вирази
   або записи `{ name, pattern, severity }`).

Коли `mode === "block"` **і** принаймні одне виявлення відповідає порогу
серйозності, `preCall` повертає `{ block: true, message: "Request rejected:
suspicious content detected" }`. У режимах `warn`/`log` захисний механізм реєструє
подію, але дозволяє виклик. Спільний допоміжний метод `evaluatePromptInjection()` також експортується
для викликачів, яким потрібно оцінювати промпти без використання реєстру.

**Межа сканування (v3.8.20):** детектор перевіряє лише **перші 16 КБ**
об’єднаного тексту промпту — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байти) у
`src/shared/utils/inputSanitizer.ts`. І `detectInjection()`, і
`evaluatePromptInjection()` виконують `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском
циклу перевірки шаблонів. Директиви ін’єкції розташовуються на початку вхідних даних, тому це
обмежує навантаження регулярних виразів на ЦП/GC для корисних навантажень розміром у сотні КБ без послаблення виявлення (пор.
#3932, #4041).

### Маскувальник облікових даних (`credentialMasker.ts`)

Виконується на **обох** етапах, останнім у стандартному ланцюжку (пріоритет `95`). Редагує
відомі шаблони API-ключів / секретних токенів у вихідному корисному навантаженні (вміст
повідомлень, аргументи викликів інструментів, результати інструментів) **і** у відповіді провайдера, щоб
облікові дані, вставлені в промпт (або повернуті результатом інструмента), не витікали
до зовнішнього провайдера або назад до клієнта.

- **Лише за явного ввімкнення**, за тією самою угодою, що й редагування PII (суміжно із жорстким правилом №20):
  вимкнено, якщо `settings.credentialRedactionEnabled === true` **або**
  `CREDENTIAL_REDACTION_ENABLED=true` не задано. Коли функцію вимкнено, захисний механізм нічого не робить —
  він ніколи не блокує й не переписує.
- `redactCredentials()` обходить усе дерево корисного навантаження/відповіді (`walkValue()`,
  безпечно щодо забруднення прототипу, безпечно щодо циклів завдяки `WeakSet`) і замінює збіги
  заповнювачем `[REDACTED:<type>]`, клонуючи лише ті гілки, які фактично
  змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі провайдерів LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платіжні ключі (Stripe, Square), хмарні
  ключі (ключ доступу AWS, Twilio, SendGrid, Mailgun), приватні ключі / JWT,
  рядки підключення, що містять облікові дані (`mongodb://user:pass@...` тощо), а також
  загальний шаблон значення заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключі у формі заголовків (`authorization`, `x-api-key`, `api-key`,
  `apikey`) редагуються структурно (лише значення, із збереженням префікса схеми на кшталт
  `Bearer `/`Basic `), а не за допомогою загального текстового регулярного виразу.
- Захисний механізм ніколи не блокує; він лише переписує (`modifiedPayload` /
  `modifiedResponse`) і додає анотації (`meta.credentialsRedacted`, `meta.count`).

Захист від регресій: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true перериває ланцюжок
  message?: string; // відображається під час блокування
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // повертається preCall для перезапису запиту
  modifiedResponse?: TValue; // повертається postCall для перезапису відповіді
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Захисний механізм сигналізує про «відсутність змін», повертаючи `void`, `{}` або
`{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює
значення, що передається ланцюжком до наступних захисних механізмів.
`signal?: AbortSignal` передає життєвий цикл виклику до захисних механізмів. Переривання запиту є навмисним винятком із принципу fail-open: медіамости припиняють роботу й виконують очищення, не відновлюючи необроблені медіадані для цільової системи, яка, як відомо, їх не підтримує.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає:

- `register(guardrail)` — додає (або замінює за нормалізованим ім'ям) захисний механізм та пересортовує за зростанням `priority`.
- `clear()` / `list()` — допоміжні функції адміністрування.
- `runPreCallHooks(payload, context)` — ітерує активні захисні механізми, пропускає `payload` через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — той самий потік на стороні відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищає стан та, за бажанням, повторно реєструє значення за замовчуванням для чистої ізоляції тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`, де `results` — це масив записів `GuardrailExecutionResult`, що містять поля `blocked`, `skipped`, `modified`, `error` та `meta` для кожного захисного механізму, корисні для трасування.

### Вимкнення захисних механізмів для кожного запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегує дедуплікований список імен захисних механізмів, які слід пропустити для поточного запиту. Джерела (всі необов'язкові, всі об'єднані):

- `apiKeyInfo.disabledGuardrails`
- Тіло запиту `disabledGuardrails` (верхнього рівня)
- Тіло запиту `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (або застарілий `x-disabled-guardrails`)

Значення можуть бути масивами рядків або рядком, розділеним комами; імена нормалізуються до нижнього регістру в kebab-case (`pii_masker` → `pii-masker`). Результат передається через `context.disabledGuardrails` до реєстру, який пропускає відповідні захисні механізми (`skipped: true` у `results`).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` та
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` створює список винятків з ключа API, тіла запиту
    та заголовків.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускає захисні механізми у порядку
    зростання пріоритету:
    - Вимкнені захисні механізми записуються як `skipped`.
    - `preCall` кожного захисного механізму може переписати корисне навантаження
      через `modifiedPayload`.
    - Перший `block: true` перериває ланцюжок, і обробник повертає
      відповідь про відхилення захисним механізмом.
3.  (Потенційно переписане) корисне навантаження надходить до комбінованої маршрутизації
    та вихідної диспетчеризації.
4.  Після формування відповіді `guardrailRegistry.runPostCallHooks(...)`
    запускає той самий ланцюжок на відповіді. `block: true` тут відкидає
    вихідну відповідь.

Захисні механізми, які викликають помилку, записуються з `error: <message>` та
реєструються через `logger.warn`, але ланцюжок продовжується — за задумом,
система працює за принципом "відмова-відкриття".

## Конфігурація

Змінні середовища, які читаються вбудованими захисними механізмами:

| Змінна                                | Використовується               | Ефект                                                                                                          |
| :------------------------------------ | :----------------------------- | :------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`             | Встановіть `false`, щоб повністю вимкнути виявлення.                                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`             | Політика ін'єкцій: `warn`, `block` або `log`. Застаріле значення `redact` не переписує текст ін'єкції.         |
| `INJECTION_GUARD_MODE`                | `prompt-injection`             | Режим для захисту від ін'єкцій; також прапорець функції БД, який **перевизначає** змінні середовища (БД > ЗМ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`             | Мінімальна серйозність, при якій `MODE=block` відхиляє: `high` (за замовчуванням), `medium` або `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`             | Застарілий псевдонім для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`                   | Якщо `true`, PII запиту редагується (незалежно від режиму ін'єкції).                                           |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (нижче за течією) | Контролює поведінку маскувальника на стороні відповіді.                                                        |

Захисні механізми Modality Bridge читають конфігурацію часу виконання зі сховища
налаштувань на основі БД (`getSettings()`), а не зі змінних середовища.
Основними ключами Vision є `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.
Застарілі ключі `visionBridge*` приймаються лише як задокументований
одноцикловий резервний варіант читання; записи на панелі керування
використовують основні ключі. Значення за замовчуванням та резервний
розв'язувач знаходяться в `src/shared/constants/modalityBridgeDefaults.ts`,
а застарілі константи зберігаються в
`src/shared/constants/visionBridgeDefaults.ts`.

Аудіо використовує `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` та `modalityBridgeAudioMaxClips`, а також спільні
налаштування `modalityBridgeCache*`. Аудіо не має резервного варіанту
застарілих ключів, оскільки ці ключі були введені зі схемою Modality Bridge.

Відео використовує `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`,
`modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` та
`modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`.
Він вимкнений за замовчуванням, оскільки FFmpeg/ffprobe є необов'язковими
операційними залежностями, а створення субтитрів кадрів додає затримку та
витрати на модель.

## Користувацькі обмежувачі (Guardrails)

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1.  Створіть `src/lib/guardrails/myGuardrail.ts`, розширюючи `BaseGuardrail`.
2.  Реалізуйте `preCall` та/або `postCall`.
3.  Зареєструйте під час імпорту (виштовхніть з `registerDefaultGuardrails`) або
    викличте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
    будь-який попередній обмежувач з тим самим нормалізованим ім'ям.
4.  Додайте тести до `tests/unit/` (існуючі приклади:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб почати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнього реєстру та
зареєструвати лише обмежувачі, що тестуються. Vision Bridge приймає впровадження
залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge надає
еквівалентні точки для налаштувань, можливостей, вибору моделі STT, перевірок
облікових даних та транскрипції. Таким чином, тести можуть перевіряти обидва
потоки без доступу до БД або мережі.

## Покриття маршрутів захисту від ін'єкцій та червона команда (Фаза 8 · Блок D)

Захист від ін'єкцій (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
які приймають підказки користувача. Він враховує `INJECTION_GUARD_MODE` (за замовчуванням `warn` = лише логування;
`block` = повертає HTTP 400 `SECURITY_001`).

| Тип              | Маршрути                                                                                                                                             | Режим за замовчуванням |
| :--------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------- |
| Текст (існуючий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                   |
| Генеративний     | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                   |
| Дані             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                   |

Вилучення тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Червона команда (нічна, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут блокує
корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає зонди (пропускає без секрету).
`moderations` включено для послідовності — оператори в режимі блокування можуть виключити його через
`resolveDisabledGuardrails`.

Нічний робочий процес (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокування)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен ворожий випадок (наприклад, "ігнорувати всі
  попередні інструкції...", "jailbreaks" у стилі DAN) стверджує, що відповідь містить
  `error.code === "SECURITY_001"`, тобто обмежувач фактично відхилив запит.
- **`garak` (консультативний)** — запускає garak `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Залежить від
  секрету провайдера (`PROMPTFOO_PROVIDER_KEY`); пропускається без помилок і має суфікс
  `|| true`, тому він звітує без збою CI.

Покриття допоміжного обмежувача (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що містить підказки; текст підказки витягується з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` за допомогою
`extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
