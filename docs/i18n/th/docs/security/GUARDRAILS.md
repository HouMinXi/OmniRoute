> **อัปเดตล่าสุด:** 2026-08-29 — v3.8.51 (ที่มาของทรานสคริปต์ Video Bridge ถูกประกาศโดยผู้เรียก
> และยังไม่ได้รับการตรวจสอบโดยเซิร์ฟเวอร์ — ชี้แจงตาม #11661)

Guardrails บังคับใช้มาตรการด้านความปลอดภัย นโยบาย และการแปลงเนื้อหาที่ขอบเขต
ระหว่าง OmniRoute กับผู้ให้บริการต้นทาง Guardrail แต่ละตัวสามารถตรวจสอบ (และ
เลือกที่จะปฏิเสธ แปลง หรือใส่คำอธิบายประกอบ) เพย์โหลดคำขอ (`preCall`) และ
การตอบกลับจากต้นทาง (`postCall`)

ระบบนี้เป็นแบบ **fail-open**: หาก Guardrail เกิดข้อผิดพลาดขณะทำงาน รีจิสทรี
จะบันทึกข้อผิดพลาดและดำเนินการต่อด้วย Guardrail ตัวถัดไป แทนที่จะทำให้
คำขอล้มเหลว การบล็อกต้องเกิดจากการตัดสินใจอย่างชัดเจน (`block: true`) ไม่ใช่เหตุบังเอิญ

### บริดจ์ด้านการมองเห็น (`visionBridge.ts`) — บริดจ์โมดาลิตี PR-1

ดักจับคำขอที่มีรูปภาพซึ่งส่งไปยัง **โมเดลที่ไม่รองรับการมองเห็น** แล้วเลือกว่าจะ
เปลี่ยนเส้นทางคำขอทั้งหมดไปยังโมเดลที่รองรับการมองเห็น หรือแทนที่ส่วนรูปภาพ
ด้วยคำอธิบายข้อความที่สร้างโดยโมเดลการมองเห็นซึ่งกำหนดค่าได้ก่อนเรียกบริการต้นทาง
วิธีนี้ช่วยให้ผู้ให้บริการแบบข้อความเท่านั้นสามารถจัดการเพย์โหลดแบบหลายโมดาลิตี
ได้อย่างโปร่งใส

ลำดับการทำงาน:

1. ข้ามหากโมเดลเป้าหมายรองรับการมองเห็นอยู่แล้ว (เว้นแต่โมเดลดังกล่าวจะอยู่ใน
   รายการบังคับใช้บริดจ์ `isVisionBridgeForcedModel`)
2. แยกส่วนรูปภาพผ่าน `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) ซึ่งมอบหมายให้ **ตัวตรวจจับสื่อแบบรวมศูนย์**
   `detectMediaParts()` ใน `open-sse/utils/mediaParts.ts` — แหล่งข้อมูลจริงเพียงแห่งเดียว
   ที่ใช้ร่วมกับตัวกรองความเข้ากันได้ของคอมโบ
   การแยกจำกัดด้วยรายการที่อนุญาตเฉพาะส่วนระดับบนสุดซึ่งมีรูปแบบที่
   `replaceImageParts` สามารถแทรกกลับได้ (สัญญาระหว่างการแยก↔การแทนที่): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` และ Responses API `input_image` รายการที่พบแบบซ้อน
   และรูปแบบที่เป็นเพียงตัวบ่งชี้เป็นข้อมูลสำหรับตัวกรองคอมโบ และจะไม่ถูกแยกออกมา
   ข้ามหากไม่พบรายการใด
3. แก้ไขค่ากำหนดรันไทม์ผ่าน `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): คีย์การตั้งค่า `modalityBridge*`
   แบบใหม่มีสิทธิ์เหนือกว่า ส่วนคีย์ `visionBridge*` แบบเก่ายังคงเป็น **ทางเลือกสำรองหนึ่งรอบ**
   (ช่วงเวลาสำหรับย้อนกลับ) ข้ามก่อนสำรวจสื่อใดๆ เมื่อปิดใช้งานบริดจ์
4. ตัวเลือกโหมด (`modalityBridgeVisionMode` ดูตารางด้านล่าง) จะตัดสินใจว่า
   จะเปลี่ยนเส้นทางหรืออธิบาย การเปลี่ยนเส้นทางจะคืนค่า `modifiedPayload` ที่สลับเฉพาะ
   `model` พร้อมเมตา `{ rerouted, fromModel, toModel, imagesKept }`
5. เส้นทางการอธิบาย: จำกัดจำนวนรูปภาพไว้ที่ `maxImages` สร้างพรอมต์ที่คำนึงถึงงาน
   ตรวจสอบแคชคำอธิบาย เรียกโมเดลการมองเห็น **แบบขนาน**
   (`Promise.allSettled`) และแทรกส่วนข้อความ `[Image N]: <description>` แทนที่
   รูปภาพเหล่านั้น การอธิบายที่ล้มเหลวจะให้ผลเป็น `null` และส่วนรูปภาพต้นฉบับจะถูก
   **เก็บไว้** (#4012) — ยกเว้นในเส้นทางการอธิบายของคอมโบเมื่อการอธิบายทั้งหมด
   ล้มเหลว ซึ่งบริการต้นทางที่ได้รับการยืนยันว่าไม่รองรับการมองเห็นจะได้รับข้อความแทน
   `(unavailable — no vision-capable provider connected)` (#8430)
6. คืนค่า `modifiedPayload` + เมตา (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)

#### ตัวเลือกโหมด (`modalityBridgeVisionMode`)

| โหมด       | ค่าเริ่มต้น | ลักษณะการทำงาน                                                                                                                                                                                                                                                                        |
| ---------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔           | ฮิวริสติกเดิมโดยไม่มีการเปลี่ยนแปลง (#6640/#7204): โมเดลที่ไม่ใช่คอมโบ/`auto/` จะเปลี่ยนเส้นทางไปยังโมเดลการมองเห็นที่ดีที่สุด เว้นแต่โมเดลเดิมจะมีข้อมูลรับรองที่ใช้งานได้อยู่แล้ว (จากนั้นจะอธิบาย) ส่วนเป้าหมายแบบคอมโบจะอธิบายเสมอ                                                |
| `describe` |             | อธิบายเสมอ — ข้ามบล็อกการเปลี่ยนเส้นทางทั้งหมด โมเดลที่ผู้ใช้เลือกจะเป็นผู้ตอบเสมอ                                                                                                                                                                                                    |
| `reroute`  |             | บังคับเปลี่ยนเส้นทาง: ข้ามกลไกป้องกันที่คงโมเดลซึ่งมีข้อมูลรับรองไว้ แต่กลไกป้องกันข้อมูลรับรองของ**เป้าหมาย**การเปลี่ยนเส้นทางยังคงมีผล — เมื่อไม่มีเป้าหมายที่รองรับการมองเห็นและใช้งานได้ คำขอจะเปลี่ยนไปใช้การอธิบาย เพื่อไม่ให้รูปภาพดิบไปถึงแบ็กเอนด์แบบข้อความเท่านั้น (#8430) |

โหมดบังคับจะลัดวงจร **ก่อน** ที่ฮิวริสติกอัตโนมัติจะทำงาน พฤติกรรมของ `auto`
เหมือนกับกลไกป้องกันก่อน PR-1 ทุกไบต์

#### ขอบเขตคีย์ API (`visionBridgeKeyScope.ts`)

เมื่อคีย์ API ของผู้เรียกจำกัด `allowedConnections` กลุ่มโควตา
(`allowedQuotas`) หรือโมเดล (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) บริดจ์จะเลือก
เฉพาะโมเดลสำหรับเปลี่ยนเส้นทางและอธิบายที่คีย์ดังกล่าวมีสิทธิ์ใช้ บนการเชื่อมต่อที่คีย์
ดังกล่าวมีสิทธิ์ใช้ จากนั้นการเรียกเพื่ออธิบายจะผ่านลูปย้อนกลับของ OmniRoute เสมอ
โดยมีส่วนหัว `x-omniroute-self-loop-key-id` เพื่อให้คำขอแชตที่รับเข้ามาบังคับใช้
นโยบายการเชื่อมต่อและโมเดลของคีย์นั้นอีกครั้ง `enforceApiKeyPolicy()`
จะยอมรับส่วนหัวดังกล่าวเมื่อใช้ร่วมกับ bearer ของลูปย้อนกลับเท่านั้น จึงทำได้เพียง
จำกัดสิทธิ์ให้แคบลง และรหัสที่ไม่สามารถแก้ไขได้จะถูกปฏิเสธ

หากไม่มีโมเดลการมองเห็นที่ได้รับอนุญาตสำหรับคีย์ เส้นทางการอธิบายจะไม่เข้ามาดำเนินการ
และคำขอจะผ่านไปโดยไม่มีการเปลี่ยนแปลง ซึ่งเป็นพฤติกรรมเปิดให้ผ่านเมื่อเกิดข้อผิดพลาด
เช่นเดียวกับกลไกป้องกันที่ถูกปิดใช้งาน (เมตา `{ skipped: true, reason: "no_permitted_vision_model" }`)
คำขอที่ไม่มีคีย์และคีย์ที่ไม่มีข้อจำกัดเหล่านี้จะทำงานเหมือนเดิมทุกประการ

#### พรอมต์การอธิบายที่คำนึงถึงงาน (`modalityBridgeVisionTaskAware`)

ค่าเริ่มต้นคือ **true** `composeVisionPrompt()` (`visionBridgeHelpers.ts`) จะต่อท้าย
พรอมป์พื้นฐานสำหรับการอธิบายด้วยข้อความจาก **ข้อความล่าสุดของผู้ใช้** (ตัดให้เหลือไม่เกิน 500 อักขระ)
เพื่อชี้นำคำอธิบายให้สอดคล้องกับสิ่งที่ผู้ใช้ถามจริง
(รูปแบบ codex-vision-proxy) และขอให้โมเดลวิชันถอดข้อความที่มองเห็น
เมื่อปิดแฟล็กนี้ — หรือไม่มีข้อความจากผู้ใช้ — ระบบจะใช้พรอมป์พื้นฐานโดยไม่มีการเปลี่ยนแปลง

คำขอที่เข้ากันได้กับ OpenAI ของ describe self-loop (`callVisionModelSingle()`
ใน `visionBridgeHelpers.ts`) จะร้องขอ `image_url.detail: "high"` เสมอ —
โดยไม่มีเงื่อนไข สำหรับผู้เรียก/ผู้ให้บริการทุกราย และไม่ขึ้นกับสัญญาณใดๆ จากไคลเอนต์
การสุ่มตัวอย่างแบบรายละเอียดต่ำลดความแม่นยำของ OCR สำหรับงานถอดข้อความ
ที่พรอมป์นี้ร้องขอโดยตรง ดังนั้นการเรียก describe จึงขอรายละเอียดสูงเสมอ
ไม่ว่าคำขอขาเข้าดั้งเดิมจะใช้ระดับรายละเอียดใดก็ตาม สิ่งนี้มีผลเฉพาะกับเนื้อหาคำขอ
describe ภายในเท่านั้น และไม่ได้เปลี่ยนวิธีที่ OmniRoute ส่งต่อ
`image_url.detail` ของผู้เรียกในคำขอหลัก — ค่าเริ่มต้นนั้นถูกนำไปใช้แยกต่างหาก
และเฉพาะกับไคลเอนต์ OpenCode ที่ตรวจพบเท่านั้น ใน `defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`) สาขารูปแบบ wire ของ Anthropic
ใน describe self-loop ไม่มีฟิลด์ `detail` และไม่ได้รับผลกระทบจากค่าเริ่มต้นทั้งสองรายการ

#### ขีดจำกัดเอาต์พุตของ Describe (`modalityBridgeVisionMaxChars`)

| คีย์                           | ค่าเริ่มต้น | ช่วง               |
| ------------------------------ | ----------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`         | `0` หรือ 100–50000 |

`0` (ค่าเริ่มต้น) หมายถึง **ไม่มีขีดจำกัด** — คำอธิบายที่ส่งคืนโดย
`callVisionModel()` จะถูกส่งต่อโดยไม่มีการแก้ไข เพื่อคงพฤติกรรมเดิมไว้
ค่าใดๆ ในช่วง 100–50000 จะตัดคำอธิบายและเติมส่วนต่อท้าย `…`
ก่อนนำไปแทรกกลับเป็น `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ใน `src/lib/guardrails/visionBridge.ts`)
เพิ่มค่านี้สำหรับงาน OCR ที่มีรายละเอียดมากและโมเดลปลายทางต้องใช้
ข้อความถอดเสียงฉบับเต็ม หรือลดค่านี้เพื่อจำกัดการใช้โทเค็นของโมเดลวิชัน
ที่สร้างคำอธิบายยืดยาว ฟิลด์บนแดชบอร์ดอยู่ในแผง Advanced ของแท็บ Vision
(`modality-bridge-max-chars` ใน `ModalityBridgeVisionTab.tsx`) และจะปรับ
ค่าใดๆ ระหว่าง 1 ถึง 99 ขึ้นเป็นค่าต่ำสุด 100 โดยปล่อยค่า `0` ที่ระบุอย่างชัดเจน
ไว้ตามเดิม — `0` เป็นค่า Zod ที่ถูกต้องโดยตัวมันเอง
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) ไม่ได้เป็นเพียง
ค่าเริ่มต้นที่หมายถึง "ไม่ได้ตั้งค่า"

#### แคช Describe (`modalityBridge/bridgeCache.ts`)

แคช LRU + TTL ในหน่วยความจำสำหรับเอาต์พุต describe ซึ่งใช้ร่วมกันทั้งโปรเซส
คีย์ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` พร้อม
การจัดเฟรมด้วยคำนำหน้าความยาว (ไม่มีการชนกันที่ขอบเขตฟิลด์) องค์ประกอบโมเดลคือ
โมเดลบริดจ์ที่ **กำหนดค่าไว้** ไม่ใช่โมเดลที่ตอบกลับจริง —
`callVisionModel` อาจสลับไปใช้โมเดลสำรองภายใน และการสร้างคีย์แยกตามแต่ละความพยายาม
จะทำให้แคชแตกกระจาย การ describe ที่ล้มเหลวจะไม่ถูกแคช การตั้งค่า:

| คีย์                            | ค่าเริ่มต้น | ช่วง    |
| ------------------------------- | ----------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`      | —       |
| `modalityBridgeCacheTtlMinutes` | `60`        | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`       | 10–5000 |

#### การทำให้อิมเมจระยะไกลเป็นมาตรฐาน (describe self-loop/การดึง base64)

เมื่อบริดจ์ดึงอิมเมจ **ระยะไกล** ด้วยตัวเอง — ทั้งการเรียก describe
ของ Anthropic กลับเข้าหาตัวเอง และการแปลง base64 สำหรับรูปแบบ wire ของ Claude
(`ensureBase64ImagesForClaudeWire`) ซึ่งทั้งคู่ทำผ่าน
`fetchRemoteImageAsDataUri()` ใน `visionBridgeHelpers.ts` — URI ข้อมูลที่ได้
จะถูกส่งผ่าน `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) ก่อนฝังลงในคำขอไปยังโมเดลวิชัน
อิมเมจขนาดใหญ่เกินไปจะถูกลดขนาดให้มี **ด้านยาว 2048px** (ตรงกับขีดจำกัด
การปรับขนาดที่ OpenAI/Anthropic ใช้ฝั่งเซิร์ฟเวอร์อยู่แล้ว) ซึ่งช่วยลดจำนวนไบต์
ในการอัปโหลด/เวลาแฝง โดยไม่เปลี่ยนสิ่งที่โมเดลวิชันมองเห็น การปรับขนาดใช้
`sharp` ซึ่งโหลดผ่าน dynamic import: บนแพลตฟอร์มที่ไม่สามารถโหลดไบนารีเนทีฟได้
`normalizeDataUri()` จะ **ไม่ throw โดยเด็ดขาด** — แต่จะเปลี่ยนไปส่งผ่าน
ไบต์ต้นฉบับแทน เพื่อให้เส้นทาง describe/การแปลง base64 ทำงานต่อไปได้เสมอ
ไบต์ที่ไม่ใช่อิมเมจ (การดึงข้อมูลที่ไม่ได้คืนอิมเมจซึ่งถอดรหัสได้) จะถูกส่งผ่าน
โดยไม่มีการเปลี่ยนแปลงเช่นกัน การทำให้เป็นมาตรฐานนี้จำกัดขอบเขตไว้เฉพาะอิมเมจ
ที่บริดจ์ดึงมาเพื่อการเรียกกลับเข้าหาตัวเองเท่านั้น — จะไม่นำไปใช้กับเพย์โหลดดิบ
ของผู้เรียกที่ส่งผ่านโดยตรง ซึ่งสอดคล้องกับหลักการแก้ไขเฉพาะเมื่อเลือกใช้เท่านั้น
(กฎตายตัว #20)

#### เฮดเดอร์ความโปร่งใส + สถิติ

การตอบกลับที่แปลงผ่าน describe จะมี
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(สร้างโดย `buildModalityBridgeHeader()` ใน `modalityBridge/bridgeStats.ts`
และประทับโดย `withModalityBridgeHeader()` ใน `src/sse/handlers/chatHelpers.ts`)
คำขอที่เปลี่ยนเส้นทางจะ **ไม่มี** เฮดเดอร์ — เพย์โหลดไม่ได้ถูกแก้ไข และการสลับโมเดล
มองเห็นได้อยู่แล้วในฟิลด์ `model` ของเนื้อหาการตอบกลับ

`GET /api/modality-bridge/stats` (การยืนยันตัวตนระดับการจัดการ ระดับเดียวกับ
`GET /api/settings`) ส่งคืนตัวนับในหน่วยความจำแยกตามโมดาลิตี
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` สำหรับ `vision`, `audio` และ

ความพยายามทั้งหมด การดำเนินการที่ไม่มีการจับเวลาจะไม่สร้างตัวอย่างเวลา
ศูนย์มิลลิวินาทีขึ้นมา ส่วน `bridged` ยังคงเป็นนามแฝงที่เข้ากันได้ย้อนหลัง
สำหรับการแปลงที่สำเร็จ และความพยายามที่ล้มเหลวจะไม่เพิ่มค่านี้
ตัวนับจะรีเซ็ตเมื่อโปรเซสรีสตาร์ตตามการออกแบบ
(ใช้เพื่อเทเลเมทรี ไม่ใช่การทำบัญชี)

พรอมป์ตามประเภทงาน ขีดจำกัดขั้นสูงสำหรับระยะหมดเวลา/รูปภาพ/ความยาวคำอธิบาย/แคช

ดำเนินการให้เสร็จได้, `restricted` เมื่อโฮสต์แดชบอร์ดไม่ใช่ลูปแบ็กและข้ามการ
ตรวจสอบที่ฝั่งไคลเอนต์, `unavailable` เมื่อตรวจสอบแล้วและยืนยันว่าไม่มี หรือ
`available` พร้อมเวอร์ชันของ FFmpeg/ffprobe) โดยจะบันทึกการตั้งค่าการเปิดใช้งาน/
โมเดล/เฟรม/วิดีโอ/ระยะหมดเวลา กรองตัวเลือกโมเดลให้เหลือเฉพาะโมเดลที่รองรับ
การมองเห็น และแสดงตัวนับวิดีโอ

การ์ด Vision Bridge เดิมภายใต้การตั้งค่า AI เป็นลิงก์เพื่อความเข้ากันได้ไปยัง
หน้าใหม่ และไม่ได้เป็นเจ้าของสำเนาฟอร์มชุดที่สองอีกต่อไป Media Providers ยัง
เชื่อมโยงเวิร์กโฟลว์ Image-to-Text และ Speech-to-Text ไปยังแท็บ Modality
Bridge ที่เกี่ยวข้อง โดยไม่ลบพื้นที่ทดลอง Speech-to-Text ที่มีอยู่

**การข้ามการตรวจสอบสิทธิ์สำหรับลูปกลับหาตนเอง:** เมื่อการเรียก describe
ถูกกำหนดเส้นทางผ่าน `/v1` แบบลูปกลับหาตนเองของ OmniRoute (โมเดลผู้ให้บริการ
ที่ไม่ใช่มาตรฐาน) คำขอย่อยจะส่ง
`x-omniroute-admission-bypass: internal` และยืนยันตัวตนด้วยข้อมูลรับรอง
ลูปกลับหาตนเองที่แก้ไขแล้ว ได้แก่ sentinel `sk_omniroute` ภายในเครื่อง
ในโหมด local หรือคีย์ env `OMNIROUTE_API_KEY` / `ROUTER_API_KEY`
ที่ผู้ปฏิบัติงานกำหนด (#1350) เพื่อให้การติดตั้งใช้งานที่ตั้งค่า
`REQUIRE_API_KEY=true` ยังคงเรียก describe ได้ การข้ามนี้จะได้รับการยอมรับ
เฉพาะเมื่อใช้ข้อมูลรับรองที่ตรงกันทุกประการเท่านั้น ดังนั้นไคลเอนต์ภายนอก
จึงไม่สามารถใช้ส่วนหัวนี้เพื่อข้ามการตรวจสอบสิทธิ์ได้

ค่าเริ่มต้นแบบเดิมอยู่ใน `src/shared/constants/visionBridgeDefaults.ts`
ส่วนค่าเริ่มต้นใหม่สำหรับโหมด/การรับรู้ประเภทงาน/แคช และตัวแก้ไขการตั้งค่า
อยู่ใน `src/shared/constants/modalityBridgeDefaults.ts` กลไกป้องกันมีตัวเลือก
คอนสตรักเตอร์ `deps` เพื่อให้การทดสอบสามารถฉีดอิมพลีเมนเทชันปลอมของ
`getSettings` และ `callVisionModel` ได้

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ดักจับคำขอแชตที่มีเสียงก่อนจะไปถึงเป้าหมายที่ไม่ทราบว่ารองรับอินพุตเสียง
โดยจะไม่กำหนดเส้นทางคำขอแชตใหม่ ส่วนเสียงจะถูกถอดเสียงผ่านเอนด์พอยต์
multipart ที่เข้ากันได้กับ OpenAI ซึ่งมีอยู่เดิม และโมเดลแชตที่เลือกจะทำงาน
ต่อด้วยข้อความถอดเสียง

ลำดับการทำงาน:

1. แก้ไขค่า `supportsAudio` ผ่าน `getResolvedModelCapabilities()` เมทาดาทา
   รีจิสทรีผู้ให้บริการที่ระบุชัดเจนมีลำดับความสำคัญสูงสุด ตามด้วยเมทาดาทา
   โมเดลแบบคงที่ แล้วจึงเป็น `modalities_input` ที่ซิงค์มา รายการอินพุตที่
   ประกาศไว้แต่ไม่มี `audio` จะเป็น `false` ส่วนกรณีที่ไม่มีหลักฐานด้าน
   ความสามารถจะยังคงเป็น `null` ทั้ง `false` และ `null` จะเปิดใช้บริดจ์แบบ
   ระมัดระวัง ขณะที่ `true` จะข้ามบริดจ์
2. แก้ไขการตั้งค่า `modalityBridgeAudio*` และแยกส่วนเสียงระดับบนสุดที่สามารถ
   แทรกแทนได้จากทุกข้อความผ่านตัวตรวจจับ `detectMediaParts()` ที่ใช้ร่วมกัน
   รูปแบบข้อมูลบนสายที่รองรับ ได้แก่ `input_audio` ของ OpenAI, `audio_url`
   และ `source.media_type: "audio/*"` ระบบตรวจพบเสียงที่ซ้อนอยู่เพื่อใช้
   กำหนดเส้นทาง แต่เส้นทางการแทรกแทนจะไม่ลบเสียงดังกล่าว ปริมาณงานถูกจำกัด
   ด้วย `modalityBridgeAudioMaxClips` ส่วนที่เกินมาจะยังคงไม่เปลี่ยนแปลง
3. ใช้ `provider/model` ที่กำหนดค่าไว้ หรือให้ `selectAudioBridgeModel()`
   ไล่ดู `AUDIO_TRANSCRIPTION_PROVIDERS` ตามลำดับแค็ตตาล็อกที่คงที่ และเลือก
   โมเดลแรกที่มีข้อมูลรับรองผู้ให้บริการที่เปิดใช้งานและใช้งานได้
4. `callAudioTranscription()` แปลงเสียงแบบ base64/data-URI เป็น `file`
   แบบ multipart หรือดาวน์โหลด `audio_url` ระยะไกลผ่านกลไกป้องกันขาออก
   ที่อนุญาตเฉพาะสาธารณะ พร้อมการตรึง DNS และขีดจำกัด 25 MB จากนั้นจะ POST
   ไฟล์และโมเดลที่เลือกไปยังลูปกลับหาตนเอง `/v1/audio/transcriptions`
   ภายในเครื่อง โดยยืนยันตัวตนด้วย `resolveSelfLoopBearer()` เส้นทางการ
   ถอดเสียงที่มีอยู่จะดำเนินการค้นหาข้อมูลรับรอง การจัดการช่วงพัก/การจำกัด
   อัตรา และการส่งต่อไปยังผู้ให้บริการตามปกติ
5. การเรียกที่สำเร็จจะแทนที่ส่วนเหล่านั้นด้วย `[Audio N]: <transcript>`
   การเรียกทำงานด้วย `Promise.allSettled`: ความล้มเหลวของแต่ละรายการจะคง
   ส่วนเสียงต้นฉบับนั้นไว้ (สัญญา #4012) หากการเรียกทั้งหมดล้มเหลวและพิสูจน์
   แล้วว่าเป้าหมายมี `supportsAudio === false` ส่วนต่าง ๆ จะกลายเป็น
   `[Audio N]: (unavailable — no STT provider connected)` (สัญญา #8430)
   สำหรับเป้าหมายที่ไม่ทราบสถานะ (`null`) ผลลัพธ์ที่ล้มเหลวทั้งหมดจะยังคง
   ไม่เปลี่ยนแปลง เป้าหมายที่พิสูจน์แล้วว่ารองรับเฉพาะข้อความและไม่มีข้อมูล
   รับรอง STT ที่ใช้งานได้จะได้รับข้อความแทนที่แบบชัดเจนเดียวกัน โดยไม่ส่ง
   คำขอเครือข่าย

ข้อความถอดเสียงที่สำเร็จจะใช้แคช LRU/TTL ของ Modality Bridge ที่ใช้ร่วมกัน
ทั้งโปรเซส คีย์ประกอบด้วยการอ้างอิงเสียง ป้ายกำกับการดำเนินการ
`audio-transcription` ที่คงที่ และโมเดล STT ที่เลือก โดยจะไม่แคชความล้มเหลว
ความพยายามด้านเสียงจะอัปเดตตัวนับ `bridged`, `cacheHits`, `failures`
และ `lastUsedAt` ที่ใช้ร่วมกัน การตอบกลับที่ผ่านการแปลงจะมี
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`
ส่วนคำขอที่ไม่ถูกเปลี่ยนแปลงจะไม่ได้รับเซกเมนต์ Audio Bridge

การตั้งค่ารันไทม์ได้รับการสนับสนุนโดย DB และตรวจสอบความถูกต้องด้วย Zod:

| คีย์                          | ค่าเริ่มต้น | ช่วงค่า              |
| ----------------------------- | ----------- | -------------------- |
| `modalityBridgeAudioEnabled`  | `true`      | —                    |
| `modalityBridgeAudioModel`    | `""`        | อัตโนมัติหรือ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`     | 1000–300000          |
| `modalityBridgeAudioMaxClips` | `3`         | 1–10                 |

แคชที่ใช้ร่วมกันยังคงควบคุมโดย `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` และ `modalityBridgeCacheMaxEntries`

### บริดจ์วิดีโอ (`videoBridge.ts`, `videoBridgePipeline.ts`)

สกัดกั้นส่วนวิดีโอระดับบนสุดใน `messages` ของ Chat Completions และ `input` ของ
Responses API ก่อนเรียกใช้ปลายทางที่ไม่ทราบว่ารองรับวิดีโอโดยตรง
รูปแบบที่รองรับ ได้แก่ `input_video`, `video_url`, `video_source`, URL แบบ HTTPS
และ URI ข้อมูล `data:video/*;base64,...` ส่วนชื่อไฟล์แบบธรรมดาในข้อความจะไม่ถูกถือว่า
เป็นวิดีโอ

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ทำหน้าที่จัดการการไล่สำรวจคำขอ
การตรวจสอบความสามารถ/นโยบาย การรวบรวมข้อมูลต่อคำขอ และเพย์โหลดการตอบกลับ
งานต่อวิดีโอแต่ละรายการ ได้แก่ การรับข้อมูล แคชผลลัพธ์ทั้งหมด การอธิบายลำดับเฟรม
(ซึ่งผสานทรานสคริปต์เสียงที่ผู้เรียกประกาศไว้ หากมี) ตลอดจนเมตริก/การยกเลิก/การล้างข้อมูล
ต่อความพยายาม จะถูกซ่อนไว้เบื้องหลัง `processVideoPart` ใน
`videoBridgePipeline.ts` ซึ่งถูกเรียกหนึ่งครั้งต่อส่วนวิดีโอภายในลูปของ `preCall`
โมดูลดังกล่าวยังกำหนดขอบเขตพอร์ตอย่างชัดเจน ได้แก่ `VideoMediaBrokerPort`
(รับไบต์และแยกเฟรมที่สุ่มตัวอย่าง), `VideoAudioTranscriptionPort`
(ผสานทรานสคริปต์เสียงที่ผู้เรียกประกาศไว้เข้ากับคำบรรยายของเฟรมที่สุ่มตัวอย่าง) และ
`VideoDrilldownPort` (ขอบเขตการจัดเก็บข้อมูลแบบเจาะลึกของเฟรม ซึ่งยังไม่ได้เชื่อมต่อ
เข้ากับ `processVideoPart` — ปัจจุบันมีเพียงเส้นทาง `/api/modality-bridge/video/drilldown`
ที่แยกต่างหากเท่านั้นที่เขียนรายการแบบเจาะลึก)

เส้นทางคำขอสาธารณะ `/v1` จะไม่นำเข้าหรือเรียกใช้โพรเซสย่อย
วิดีโอระยะไกลจะถูกดาวน์โหลดภายใต้ขีดจำกัด 50 MiB ส่วนวิดีโอ base64 แบบอินไลน์
มีขีดจำกัดขนาดหลังถอดรหัสต่อวิดีโอที่เผื่อไว้อย่างระมัดระวังที่ 36 MiB เพื่อให้เอนเวโลปของ
โมเดล/ข้อความ/การจัดเฟรมยังคงอยู่ภายในขีดจำกัดการรับคำขอ JSON สาธารณะที่ 50 MiB
ระบบจะตรวจสอบความยาวแบบอินไลน์และค่าประมาณขนาดหลังถอดรหัสก่อนการจัดสรรหน่วยความจำ
URL ระยะไกลเริ่มต้นและทุกการเปลี่ยนเส้นทางต้องใช้ HTTPS โดยใช้กลไกป้องกันขาออก
เฉพาะปลายทางสาธารณะที่มีอยู่ พร้อมการปักหมุด DNS จากนั้นไบต์จะข้ามขอบเขตโบรกเกอร์ภายใน
`POST /api/modality-bridge/video/extract` โดยตรง เส้นทางดังกล่าวเป็นทั้ง
`LOCAL_ONLY` และ `SPAWN_CAPABLE` โดยยอมรับเฉพาะคำขอลูปแบ็กที่เชื่อถือได้
และผ่านการตรวจสอบสิทธิ์ต่อโพรเซส และจะไม่ยอมรับ URL, พาธระบบไฟล์, ไฟล์ปฏิบัติการ
หรือรายการอาร์กิวเมนต์ ขั้นตอนประมวลผลขนาดเนื้อหาของ API และตัวอ่านเนื้อหาแบบเพิ่มทีละส่วน
ของตัวจัดการ ต่างบังคับใช้ขีดจำกัดอินพุตโบรกเกอร์ที่ 50 MiB อย่างเป็นอิสระต่อกัน
คิวแบบมีขอบเขตจะประมวลผลการแยกข้อมูลครั้งละหนึ่งงาน อนุญาตงานรอดำเนินการสี่งาน
และจำกัดอินพุตที่รอดำเนินการไว้ที่ 100 MiB

ภายในโบรกเกอร์ `ffprobe` จะอ่านไฟล์ภายในเครื่องแบบส่วนตัว โดยรายการรูปแบบที่อนุญาต
แบบตายตัวจะไม่รวมรูปแบบเพลย์ลิสต์และแมนิเฟสต์ สำหรับคอนเทนเนอร์ตระกูล MOV ที่อนุญาต
การอ้างอิงข้อมูล MOV ภายนอกจะยังคงถูกปิดใช้งานโดยค่าเริ่มต้น และคำสั่งแบบตายตัว
จะไม่เลือกเปิดใช้การอ้างอิงดังกล่าว ทั้ง `ffprobe` และ `ffmpeg` ใช้รายการอนุญาต
โปรโตคอลเฉพาะ `file` หนึ่งเธรด อาร์เรย์อาร์กิวเมนต์แบบตายตัว ไม่ใช้เชลล์
และใช้ไฟล์ปฏิบัติการที่ถูกค้นหาจาก `PATH` สตรีมภาพปกแบบ attached-picture
จะไม่ถูกพิจารณาเป็นตัวเลือกที่เล่นได้ สตรีมที่เล่นได้ทั้งหมดต้องผ่านข้อจำกัดต่าง ๆ
และระบบจะเลือกสตรีมเริ่มต้นที่ระบุอย่างชัดเจนก่อนใช้ตัวเลือกสำรองที่มีดัชนีต่ำสุด
แบบกำหนดแน่นอน วิดีโอถูกจำกัดไว้ที่ 600 วินาที, 8,192 พิกเซลต่อมิติ และ
33,554,432 พิกเซลต้นฉบับ FFmpeg จะสุ่มตัวอย่างเฟรม JPEG ที่จุดกึ่งกลางจำนวน 1–16 เฟรม
ย่อขอบด้านยาวให้เหลือไม่เกิน 1,024 พิกเซลโดยไม่ขยายอินพุตที่มีขนาดเล็กกว่า
และจะไม่ได้รับ URL เลย การสุ่มตัวอย่างใช้ `uniform` โดยค่าเริ่มต้น นโยบายเสริม
`scene_aware` และ `segment_aware` ซึ่งยังอยู่ในขั้นทดลอง จะดำเนินการ FFmpeg
แบบตายตัวเพิ่มเติมหนึ่งรอบกับสตรีมภายในเครื่องที่ผ่านการตรวจสอบแล้ว เลือกการประทับเวลา
ของฉากจาก `showinfo` ภายในขอบเขต และย้อนกลับไปใช้จุดกึ่งกลางแบบ uniform เดิม
อย่างกำหนดแน่นอนเมื่อเครื่องมือตรวจจับล้มเหลว หมดเวลา ส่งผลลัพธ์ผิดรูปแบบ
หรือไม่มีชุดตัวเลือก โหมด segment-aware จะจัดสรรตัวอย่างจุดกึ่งกลางตามสัดส่วน
ของช่วงฉากที่ผ่านการตรวจสอบ โดยมีรายละเอียดหลักฐานและพฤติกรรมสำรองของ segment-aware
อยู่ด้านล่าง ขีดจำกัดสูงสุด 16 เฟรมจะถูกนำไปใช้หลังการเลือกในทุกนโยบาย
เมื่อคำขอแบบ scene-aware มีงบประมาณเพียงหนึ่งเฟรม ระบบจะใช้จุดกึ่งกลางแบบ uniform
ของวิดีโอฉบับเต็มหรือหน้าต่างโฟกัสที่ใช้งานอยู่ และรายงาน `policyEffective: uniform`:
เฟรมฉากที่เลือกเพียงเฟรมเดียวไม่สามารถรักษาปลายทั้งสองด้านของช่วงเวลาไว้ได้
ผู้เรียกอาจระบุหน้าต่างโฟกัสแบบจำกัด (`start`/`end` เป็นวินาที) หรือไม่ก็ได้
โดยขอบเขตจะถูกจำกัดให้อยู่ภายในระยะเวลาของสื่อ หน้าต่างที่กลับด้านหรือมีค่าไม่เป็นจำนวนจำกัด
จะถูกปฏิเสธ และนโยบายการสุ่มตัวอย่างทั้งหมดจะทำงานเฉพาะภายในช่วงที่ปรับมาตรฐานแล้ว
หน้าต่างผลลัพธ์จะรวมอยู่ในเมตาดาตาการสุ่มตัวอย่างและคำนำหน้าคำอธิบายที่ไม่น่าเชื่อถือ
เพื่อให้โมเดลปลายทางสามารถแยกแยะข้อความตัดตอนที่โฟกัสจากไทม์ไลน์ฉบับเต็มได้

การโฟกัสเชิงความหมายสำหรับคำบรรยายเป็นการตั้งค่าที่แยกจากกันอย่างชัดเจน
โหมดวิเคราะห์ `full` ซึ่งเป็นค่าเริ่มต้นจะคงพรอมต์เฟรมเดิมไว้ และจะไม่ส่งต่อข้อความคำขอ
ไปยังโมเดลคำบรรยาย ในโหมด `focused` บริดจ์จะอ่านเฉพาะ `text`/`input_text`
ล่าสุดที่ไม่ว่างเปล่าและผู้ใช้เป็นผู้เขียน จากคอนเทนเนอร์ Chat หรือ Responses เดียวกัน
ปรับรูปแบบให้เป็น NFC ยุบอักขระควบคุมและช่องว่าง และจำกัดไว้ที่ 500 จุดรหัส Unicode
หากผลลัพธ์ว่างเปล่า ระบบจะย้อนกลับไปใช้พรอมต์ `full` เดิมทุกประการ
คำใบ้ที่ใช้งานได้จะถูกทำให้เป็นอนุกรมในรูปแบบ JSON ภายในบล็อกบริบทผู้ใช้ที่ไม่น่าเชื่อถือ
โดยเฉพาะ และทำได้เพียงจัดลำดับความสำคัญของรายละเอียดที่สังเกตเห็นได้เท่านั้น
คำใบ้ดังกล่าวไม่สามารถแทนที่คำเตือนแยกต่างหากที่ห้ามทำตามคำสั่งซึ่งมองเห็น
หรือได้ยินในสื่อ โฟกัสเชิงข้อความจะไม่อนุมาน `start`/`end`
หรือเปลี่ยนตัวสุ่มตัวอย่างเชิงเวลา

#### หลักฐานเซกเมนต์เชิงโครงสร้าง FU-07

`segment_aware` ใช้การวิเคราะห์ล่วงหน้าแบบมีขอบเขตหนึ่งรอบกับสตรีมวิดีโอภายในที่ผ่านการตรวจสอบแล้ว ชุดตัวกรองแบบคงที่จะปรับขนาดให้มีความกว้างไม่เกิน 320 พิกเซลก่อน จากนั้นตรวจจับการเปลี่ยนฉากและช่วงภาพค้าง แล้วจึงสุ่มตัวอย่างที่ 1 เฟรมต่อวินาทีเพื่อวัดความเบลอ ค่าลูมาเฉลี่ย และข้อมูลเชิงพื้นที่/เวลา รอบการวิเคราะห์นี้จำกัดไว้ที่ตัวอย่างเชิงโครงสร้าง 600 ตัวอย่าง ใช้เธรด FFmpeg/ตัวกรองหนึ่งเธรด ใช้รายการอนุญาตของโปรโตคอลเฉพาะ `file` และคอนเทนเนอร์ชุดเดียวกัน จำกัดเอาต์พุตของโปรเซสไว้ที่ 1 MiB และใช้เวลาได้ไม่เกิน 30 วินาทีภายในกลไกยกเลิก/เส้นตายที่ใช้ร่วมกันของโบรกเกอร์ ระบบจะไม่รับคำสั่ง ตัวกรอง พาธ หรือ URL จากคำขอโดยเด็ดขาด

ค่าเชิงโครงสร้างเป็นหลักฐานจากการสุ่มตัวอย่างที่ให้ผลแบบกำหนดแน่นอน ไม่ใช่ความเข้าใจเนื้อหาวิดีโอเชิงความหมาย ค่าเหล่านี้ไม่ได้อนุมานตัวแบบ การกระทำ คำบรรยาย เสียงพูด หรือเจตนาของผู้ใช้ ขอบเขตฉากและภาพค้างจะสร้างเซกเมนต์ ส่วนสัดส่วนภาพค้าง ความเบลอ การเปิดรับแสง รายละเอียดเชิงพื้นที่ และการเปลี่ยนแปลงเชิงเวลา มีผลเฉพาะต่อวิธีจัดสรรงบประมาณเดิมที่ 1–16 เฟรม เซกเมนต์ที่ค้างทั้งหมดจะถูกจำกัดไว้ที่หนึ่งเฟรม ขณะที่เซกเมนต์ที่ไม่ค้างจะแข่งขันกันเพื่อรับงบประมาณส่วนที่เหลือ เมื่อจำนวนขอบเขตมากกว่าจำนวนเฟรม ระบบจะยังคงกระจายการครอบคลุมอย่างสม่ำเสมอตลอดไทม์ไลน์ เพื่อไม่ให้การตัดฉากอย่างรวดเร็วในช่วงต้นบดบังเซกเมนต์ยาวในช่วงท้าย ขอบเขตฉากที่อยู่ภายในความละเอียดการวิเคราะห์ 1 วินาทีจากขอบเขตภาพค้างจะถูกรวมเข้าด้วยกัน

หากไม่มีตัวกรอง หลักฐานผิดรูปแบบ/ว่างเปล่า ตัวตรวจจับเกิดข้อผิดพลาด หรือการวิเคราะห์ล่วงหน้าแบบมีขอบเขตหมดเวลา ระบบจะเปิดทางให้ดำเนินการต่อโดยใช้นโยบายจุดกึ่งกลางแบบสม่ำเสมอที่ตรงกันทุกประการ การยกเลิกโดยผู้เรียกหรือการถึงเส้นตายของโบรกเกอร์จะไม่เปิดทางให้ดำเนินการต่อ แต่จะยุติโปรเซสย่อยที่กำลังทำงาน ป้องกันการแยกเฟรมในภายหลัง และลบโครงสร้างไดเรกทอรีชั่วคราวส่วนตัวใน `finally`

`scripts/perf/video-bridge-fu07-eval.ts` สร้างฟิกซ์เจอร์ FFmpeg จริงที่ให้ผลแบบกำหนดแน่นอน สำหรับประเมินการประหยัดจำนวนการเรียกสร้างคำบรรยายหลังการขจัดข้อมูลซ้ำ การจัดสรรงบประมาณสำหรับการเคลื่อนไหวหนาแน่น หลักฐานความเบลอ/การเปิดรับแสง/SI-TI การตัดฉากอย่างรวดเร็วที่มีช่วงท้ายยาว และผลบวกลวงจากการเฟดแบบค่อยเป็นค่อยไป สคริปต์จะบันทึกเวลาจริงที่ใช้ในการวิเคราะห์ล่วงหน้า และหากมี `/usr/bin/time` ก็จะบันทึกเวลา CPU ของโปรเซสลูกและค่า RSS สูงสุดด้วย การตรวจสอบคุณภาพของสคริปต์เป็นเพียงออราเคิลเชิงโครงสร้างเท่านั้น คุณภาพของโมเดลสร้างคำบรรยายจริงยังคงเป็น `HOLD` เนื่องจากชุดทดสอบนี้ไม่มีเอนด์พอยต์ที่ได้รับอนุญาตหรือผู้ตัดสินที่ตรึงไว้ การประหยัดค่าใช้จ่ายยังคงเป็น `HOLD` เช่นกัน เว้นแต่ `--caption-cost-per-call-usd` จะระบุค่าประมาณต้นทุนต่อการเรียกที่เป็นบวกอย่างชัดเจน สคริปต์จะไม่สร้างผลลัพธ์ทั้งสองแบบขึ้นมาเอง

แต่ละเฟรมถูกจำกัดไว้ที่ 4 MiB เฟรมดิบทั้งหมดรวมกันถูกจำกัดไว้ที่ 23 MiB และการตอบกลับแบบซีเรียลไลซ์ของโบรกเกอร์ถูกจำกัดไว้ที่ 32 MiB ไดเรกทอรีชั่วคราวส่วนตัวจะถูกลบใน `finally` OmniRoute ไม่ได้รวม FFmpeg มาให้ และไม่ยอมรับพาธไฟล์ปฏิบัติการแบบกำหนดเอง ก่อนสร้างคำบรรยาย บริดจ์จะใช้ขั้นตอนขจัดข้อมูลภาพซ้ำแบบระมัดระวัง โดยลดขนาด JPEG แต่ละภาพเป็นบัฟเฟอร์ระดับสีเทา 16×16 และเปรียบเทียบเฉพาะกับเฟรมล่าสุดที่เก็บไว้ สำหรับงบประมาณคำบรรยายที่ร้องขอมากกว่าหนึ่งเฟรม การแยกเฟรมจะจัดเตรียมพูลตัวเลือกแบบมีขอบเขตได้สูงสุดสองเท่าของงบประมาณดังกล่าว และไม่เกิน 16 เฟรม ระบบจะใช้ขีดจำกัดที่ร้องขอหลังจากขจัดข้อมูลซ้ำแล้วเท่านั้น โดยจะคงตัวเลือกแรกและตัวเลือกสุดท้ายที่เลือกไว้ระหว่างการลดจำนวนขั้นสุดท้าย เมื่องบประมาณมีอย่างน้อยสองเฟรม นโยบายที่มีเวอร์ชัน
`grayscale-16x16-mean-cells-v2` ใช้ค่าที่มากกว่าระหว่างเดลตาของลูมาเฉลี่ยกับอัตราส่วนของเซลล์ภาพขนาดย่อที่มีเดลตาแบบปรับมาตรฐานอย่างน้อย 0.05 เกณฑ์สำหรับข้อมูลซ้ำคือค่าคงที่ 0.04 ซึ่งเลือกเพื่อให้คาดการณ์ได้ แทนที่จะเปิดให้เป็นการตั้งค่าขณะรัน สัญญาณคอนทราสต์สูงรองนี้ช่วยรักษาการเคลื่อนไหวขนาดเล็กและการเปลี่ยนแปลงของข้อความที่มองเห็นได้ ซึ่งการเปรียบเทียบโดยใช้ค่าเฉลี่ยเพียงอย่างเดียวอาจบดบังไว้ ข้อผิดพลาดของตัวเปรียบเทียบหรือตัวถอดรหัสจะเปิดทางให้ดำเนินการต่อและรักษาความครอบคลุมไว้ เมทาดาทาเอาต์พุตจะแยกตัวเลือกที่แยกออกมา เฟรมที่ใช้งานสำเร็จ และข้อมูลภาพซ้ำที่ถูกตัดทิ้งออกจากกัน

ส่วนวิดีโอที่ทำเครื่องหมายไว้อย่างชัดเจนอาจร้องขอคอนแทคชีตที่มีการประทับเวลา บริดจ์จะสร้างตาราง JPEG ที่มีไม่เกิน 4 คอลัมน์และ 16 เฟรม แต่ละเซลล์ขนาด 512 พิกเซลจะฝังเวลาของแหล่งที่มาลงในแถบคอนทราสต์สูงด้านล่าง ขณะที่เวลาเดียวกันจะยังคงอยู่ในเมทาดาทาแบบข้อความเพื่อใช้เชื่อมโยงและตรวจสอบในขั้นตอนปลายทาง JPEG ฉบับสมบูรณ์ยังคงถูกจำกัดไว้ที่ 32 MiB หาก `sharp` ไม่สามารถถอดรหัสหรือประกอบตารางได้ บริดจ์จะย้อนกลับไปใช้เฟรม JPEG แต่ละเฟรม ส่วนการยกเลิกโดยไคลเอนต์จะยังคงส่งผ่านไปยังการดำเนินการกับชีต

หลักฐานสำหรับการเลื่อนสถานะแยกออกจากไมโครเบนช์มาร์กการประกอบแบบสังเคราะห์โดยเจตนา `scripts/perf/video-bridge-contact-sheet-eval.ts` กำหนดชุดทดสอบ A/B ที่มีการกำหนดเวอร์ชันสคีมาสำหรับโมเดลวิชันจริงที่เข้ากันได้กับ OpenAI โดยวัดจำนวนโทเค็นที่ผู้ให้บริการรายงาน เวลาแฝงตั้งแต่ต้นจนจบ (รวมการประกอบชีต) จำนวนการเรียกโมเดล และการคงอยู่ของข้อเท็จจริงตามที่กำหนดไว้ในแมนิเฟสต์ การตอบกลับดิบจากโมเดลจะไม่ถูกเขียนลงในรายงาน โดยจะเก็บไว้เฉพาะไดเจสต์ SHA-256 และ ID ของข้อเท็จจริงที่ตรงกัน ชุดทดสอบจะไม่เรียกใช้เครือข่ายหรือโมเดลแบบมีค่าใช้จ่าย เว้นแต่จะส่ง `--execute-real` และกำหนดค่า `--model`, `OMNIROUTE_BASE_URL` และ `OMNIROUTE_API_KEY` ไว้ หากไม่มีการรันจริงอย่างชัดเจนดังกล่าว คำตัดสินที่เครื่องอ่านได้จะยังคงเป็น `HOLD` การวัดเพย์โหลด/จำนวนการเรียกแบบสังเคราะห์เพียงอย่างเดียวไม่ถือเป็นหลักฐานสำหรับการเลื่อนสถานะ

ผู้เรียกสามารถแนบอาร์เรย์ `transcript.cues` แบบไม่บังคับเข้ากับส่วนวิดีโอที่รองรับได้ เมื่อมีข้อความที่จัดแนวไว้แล้ว แต่ละคิวต้องมี `text` ช่วงเวลา `start`/`end` ที่เป็นค่าจำกัดและอยู่ภายในระยะเวลาที่ตรวจสอบได้ และ `source` ที่อยู่ในรายการอนุญาต (`client`, `embedded` หรือ `audio-bridge`) โดย `confidence` มีค่าเริ่มต้นเป็น `1` และต้องอยู่ระหว่าง `0` ถึง `1` คิวที่ซ้ำกันทุกประการจะถูกรวมเข้าด้วยกัน OmniRoute จะไม่เริ่มการถอดเสียงจากเมทาดาทานี้ โดยคิวที่ผ่านการตรวจสอบจะถูกคัดลอกไปยังผลลัพธ์ที่อธิบายไว้ พร้อมแหล่งที่มา ค่าความเชื่อมั่น และช่วงเวลา และจะแสดงเป็นข้อสังเกตที่ไม่น่าเชื่อถือควบคู่กับคำบรรยายเฟรม ข้อความที่ไม่ถูกต้อง อยู่นอกช่วง หรือไม่มีที่มาจะถูกปฏิเสธ แทนที่จะนำไปปะปนในสตรีมคำบรรยาย ช่องทางทรานสคริปต์ทั้งสองช่องทางในเนื้อหาคำขอจะปรับที่มาที่ระบุให้เป็น `client` รวมถึงป้ายกำกับ `embedded` หรือ `audio-bridge` ที่ผู้เรียกอ้างเอง เฉพาะอะแดปเตอร์ที่เซิร์ฟเวอร์เป็นเจ้าของเท่านั้นที่สามารถกำหนดป้ายกำกับที่เชื่อถือได้เหล่านั้นผ่านอาร์กิวเมนต์เฉพาะโค้ด `trustedSource` ฟิลด์ JSON ในคำขอไม่สามารถเข้าถึงอาร์กิวเมนต์ดังกล่าวได้ ข้อความทรานสคริปต์ยังคงเป็นเนื้อหาที่ไม่น่าเชื่อถือซึ่งได้มาจากสื่อ ไม่ว่าจะมีที่มาอย่างไรก็ตาม และต้องไม่ถูกใช้เพื่อตัดสินการอนุญาตโดยเด็ดขาด

guardrail จะแยกทุกส่วนของวิดีโอที่รองรับ แต่จะอธิบายไม่เกิน `modalityBridgeVideoMaxVideos` สำหรับเป้าหมายที่พิสูจน์แล้วว่ามี `supportsVideo === false` วิดีโอที่ประมวลผลล้มเหลวและวิดีโอที่เกินขีดจำกัดจะถูกแทนด้วยตัวบ่งชี้ข้อความที่ปลอดภัยอย่างชัดเจน เพื่อไม่ให้มีวิดีโอดิบหลงเหลืออยู่ เมื่อไม่ทราบความสามารถ ส่วนเหล่านั้นจะยังคงมีตัวบรรจุวิดีโออยู่ ส่วน transcript สำรองใด ๆ จะผ่านการแปลงเป็นข้อความแบบมีขอบเขตข้างต้น เป้าหมายที่มี `supportsVideo === true` จะข้าม bridge สัญญาณยกเลิกคำขอจากไคลเอนต์จะแพร่ไปยังการดาวน์โหลด คิวของ broker, subprocess และการเรียกสร้างคำบรรยาย การยกเลิกจะหยุดการทำงานระหว่างวิดีโอ และจะไม่ปล่อยให้สื่อดิบผ่านไปเมื่อเกิดความล้มเหลว

### ตัวปกปิด PII (`piiMasker.ts`)

ทำงานใน **ทั้งสอง** ขั้นตอน

- **`preCall`** จะโคลน payload, ไล่ตรวจ `system`, `messages`, `input` และ
  `prompt` (รวมถึงรายการที่เป็นสตริงธรรมดา) และใช้ `processPII()` (จาก
  `@/shared/utils/inputSanitizer`) กับฟิลด์ `content`/`text` ที่เป็นสตริง เมื่อ
  `PII_REDACTION_ENABLED=true` ข้อมูล PII ที่ตรวจพบจะถูกปกปิดใน payload
  ขาออก การทำงานนี้ไม่ขึ้นกับ `INPUT_SANITIZER_MODE` (ซึ่งควบคุมเฉพาะ
  นโยบายการแทรกแซงพรอมป์เท่านั้น) เมื่อปิดการปกปิด การเรียกใช้งานจะบันทึกจำนวน
  ที่ตรวจพบโดยไม่เขียนเนื้อหาใหม่
- **`postCall`** จะทำ deep clone การตอบกลับ เรียกใช้ `sanitizePIIResponse()` พร้อมกับ
  ตัวปกปิดสำหรับโครงสร้าง Responses API (`maskResponsesOutput` — ครอบคลุม
  `output_text` และ `output[].content[].text`) หากมีการปกปิดเกิดขึ้น
  การตอบกลับที่แก้ไขแล้วจะแทนที่การตอบกลับเดิม

guardrail จะไม่บล็อก แต่จะเพียงเพิ่มคำอธิบายกำกับ (`meta.detections`,
`meta.redacted`) หรือเขียนข้อมูลใหม่

### การแทรกแซงพรอมป์ (`promptInjection.ts`)

ตรวจจับโครงสร้างเชิงโจมตีในเนื้อหาที่ผู้ใช้ระบุและบังคับใช้
นโยบายที่กำหนดค่าไว้ ลักษณะการทำงานถูกควบคุมโดยตัวแปรสภาพแวดล้อมและตัวเลือกของ
constructor:

| การตั้งค่า    | ตัวแปรสภาพแวดล้อม                                                                                        | ค่าเริ่มต้น | ผล                                                                                                                                                                                 |
| ------------- | -------------------------------------------------------------------------------------------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| เปิดใช้งาน    | `INPUT_SANITIZER_ENABLED`                                                                                | `true`      | เมื่อเป็น `false` guardrail จะหยุดการทำงานทันที                                                                                                                                    |
| โหมด          | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`      | นโยบายการแทรกแซง: `block`, `warn` หรือ `log` (`redact` รองรับเพื่อความเข้ากันได้ย้อนหลัง แต่จะ **ไม่** ลบข้อความแทรกแซง; การเขียน PII ในคำขอใหม่ควบคุมโดย `PII_REDACTION_ENABLED`) |
| เกณฑ์การบล็อก | ตัวเลือก `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (นามแฝง `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`      | ระดับความรุนแรงขั้นต่ำที่ต้องมีจึงจะบล็อก โดยค่าเริ่มต้น ระดับ Medium จะมีไว้เพื่อเฝ้าสังเกตเท่านั้น                                                                               |

**ลำดับความสำคัญของโหมด** (`getMode`): `options.mode` ของผู้เรียก →
การแทนที่ด้วย feature flag ใน DB สำหรับ `INJECTION_GUARD_MODE` (Dashboard → Settings →
Feature Flags) → env `INJECTION_GUARD_MODE` → env `INPUT_SANITIZER_MODE` →
`warn` ดังนั้นการแทนที่จาก dashboard จะมีลำดับความสำคัญเหนือ env vars ทำให้ UI ของ Feature
Flags สามารถควบคุม guard ที่กำลังทำงานอยู่ได้แบบสด ๆ (ไม่ต้องรีสตาร์ต) การอ่าน DB เป็นแบบปลอดภัยเมื่อเกิดข้อผิดพลาด:
หากเกิดข้อผิดพลาด guard จะย้อนกลับไปใช้ลักษณะการทำงานตาม env และเมื่อไม่มีการตั้งค่า
แทนที่ไว้ ลักษณะการทำงานจะเหมือนกับการพิจารณาจาก env เพียงอย่างเดียว

แหล่งที่มาของการตรวจจับ:

1. `sanitizeRequest()` จาก `@/shared/utils/inputSanitizer` (ชุดตัวตรวจจับร่วม
   ที่ใช้ในส่วนอื่นของ pipeline)
2. `DEFAULT_GUARD_PATTERNS` ที่มีมาให้ในตัว (ปัจจุบันคือ `system_override_inline` และ
   `markdown_system_block` ซึ่งทั้งคู่มีระดับความรุนแรง `high`)
3. `customPatterns` เสริมที่ส่งผ่านตัวเลือกของ constructor (สตริง, regex
   หรือระเบียน `{ name, pattern, severity }`)

เมื่อ `mode === "block"` **และ** มีการตรวจพบอย่างน้อยหนึ่งรายการที่ถึงเกณฑ์
ความรุนแรง `preCall` จะคืนค่า `{ block: true, message: "Request rejected:
suspicious content detected" }` ในโหมด `warn`/`log` การ์ดเรลจะบันทึกล็อก แต่
อนุญาตให้เรียกใช้งานได้ นอกจากนี้ยังส่งออกตัวช่วยที่ใช้ร่วมกัน `evaluatePromptInjection()`
สำหรับผู้เรียกที่ต้องการประเมินพรอมต์โดยไม่ผ่านรีจิสทรี

**ขอบเขตการสแกน (v3.8.20):** ตัวตรวจจับจะตรวจสอบเฉพาะ **16 KB แรก** ของ
ข้อความพรอมต์ที่นำมาต่อกัน — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ไบต์) ใน
`src/shared/utils/inputSanitizer.ts` ทั้ง `detectInjection()` และ
`evaluatePromptInjection()` จะเรียก `slice(0, MAX_INJECTION_SCAN_BYTES)` ก่อนดำเนินการ
วนลูปตรวจสอบรูปแบบ คำสั่งแทรกแซงมักอยู่ใกล้ส่วนต้นของอินพุต ดังนั้นวิธีนี้จึงจำกัดการใช้
CPU/GC ของ regex สำหรับเพย์โหลดขนาดหลายร้อย KB โดยไม่ลดทอนประสิทธิภาพการตรวจจับ (ดู
#3932, #4041)

### ตัวปกปิดข้อมูลรับรอง (`credentialMasker.ts`)

ทำงานใน **ทั้งสอง** ขั้นตอน โดยอยู่ลำดับสุดท้ายในเชนเริ่มต้น (ลำดับความสำคัญ `95`) ปกปิด

  คีย์ที่มีรูปแบบเหมือนเฮดเดอร์ (`authorization`, `x-api-key`, `api-key`,
  `apikey`) จะถูกปกปิดเชิงโครงสร้าง (เฉพาะค่า โดยคงคำนำหน้าสคีม เช่น
  `Bearer `/`Basic ` ไว้) แทนการใช้ regex ข้อความทั่วไป
- การ์ดเรลนี้จะไม่บล็อก แต่จะเขียนข้อมูลใหม่เท่านั้น (`modifiedPayload` /
  `modifiedResponse`) และเพิ่มคำอธิบายกำกับ (`meta.credentialsRedacted`, `meta.count`)

ตัวป้องกันการถดถอย: `tests/unit/credential-masker-guardrail.test.ts`

## สัญญาพื้นฐาน (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // ค่า true จะลัดวงจรของเชน
  message?: string; // แสดงเมื่อมีการบล็อก
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ส่งคืนโดย preCall เพื่อเขียนคำขอใหม่
  modifiedResponse?: TValue; // ส่งคืนโดย postCall เพื่อเขียนการตอบกลับใหม่
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

การ์ดเรลระบุว่า "ไม่มีการเปลี่ยนแปลง" ด้วยการส่งคืน `void`, `{}` หรือ
`{ block: false }` อย่างใดอย่างหนึ่ง การส่งคืน `modifiedPayload`/`modifiedResponse`
จะแทนที่ค่าที่ไหลผ่านเชนสำหรับการ์ดเรลลำดับถัดไป
`signal?: AbortSignal` ส่งต่อวงจรชีวิตของผู้เรียกไปยังการ์ดเรล การยกเลิกคำขอเป็นข้อยกเว้นแบบยอมให้ทำงานต่อโดยเจตนา: บริดจ์สื่อจะหยุดการทำงานและล้างทรัพยากร โดยไม่กู้คืนสื่อดิบไปยังปลายทางที่ทราบว่าไม่รองรับสื่อนั้น

## รีจิสทรี (`registry.ts`)

ซิงเกิลตัน `guardrailRegistry` เปิดเผยเมธอดต่อไปนี้:

- `register(guardrail)` — เพิ่มการ์ดเรล (หรือแทนที่ตามชื่อที่ผ่านการทำให้เป็นมาตรฐาน)
  และเรียงลำดับใหม่ตาม `priority` จากน้อยไปมาก
- `clear()` / `list()` — ตัวช่วยสำหรับการดูแลระบบ
- `runPreCallHooks(payload, context)` — วนซ้ำการ์ดเรลที่ทำงานอยู่ ส่งต่อ
  เพย์โหลดผ่าน `modifiedPayload` และหยุดเมื่อพบ `block: true` ครั้งแรก
- `runPostCallHooks(response, context)` — ใช้โฟลว์เดียวกันกับฝั่งการตอบกลับ
- `resetGuardrailsForTests({ registerDefaults })` — ล้างสถานะและเลือก
  ลงทะเบียนค่าเริ่มต้นใหม่เพื่อแยกการทดสอบอย่างสะอาด

รันเนอร์ทั้งสองส่งคืน `{ blocked, payload|response, results, guardrail?, message? }`
โดย `results` เป็นอาร์เรย์ของเรคคอร์ด `GuardrailExecutionResult` ซึ่งประกอบด้วย
ฟิลด์ `blocked`, `skipped`, `modified`, `error` และ `meta` ของแต่ละการ์ดเรล
ซึ่งมีประโยชน์สำหรับการติดตาม

### การปิดใช้งานการ์ดเรลสำหรับแต่ละคำขอ

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` รวบรวมรายการ
ชื่อการ์ดเรลที่ตัดรายการซ้ำแล้ว ซึ่งควรข้ามสำหรับคำขอปัจจุบัน
แหล่งที่มา (ทั้งหมดเป็นตัวเลือกและนำมารวมกันทั้งหมด):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` ในเนื้อหาคำขอ (ระดับบนสุด)
- `metadata.disabledGuardrails` ในเนื้อหาคำขอ
- เฮดเดอร์ `x-omniroute-disabled-guardrails` (หรือชื่อเดิม
  `x-disabled-guardrails`)

ค่าอาจเป็นอาร์เรย์ของสตริงหรือสตริงที่คั่นด้วยจุลภาค ชื่อจะถูก
ทำให้เป็นอักษรพิมพ์เล็กในรูปแบบ kebab-case (`pii_masker` → `pii-masker`) ผลลัพธ์
จะถูกส่งผ่าน `context.disabledGuardrails` ไปยังรีจิสทรี ซึ่งจะข้าม
การ์ดเรลที่ตรงกัน (`skipped: true` ใน `results`)

## ลำดับการดำเนินการ

สำหรับแต่ละคำขอที่ไหลผ่าน `src/sse/handlers/chat.ts` และ
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` สร้างรายการที่ต้องข้ามจาก API key, body
   และ headers
2. `guardrailRegistry.runPreCallHooks(body, ctx)` เรียกใช้ guardrails ตามลำดับ
   priority จากน้อยไปมาก:
   - Guardrails ที่ปิดใช้งานจะถูกบันทึกเป็น `skipped`
   - `preCall` ของแต่ละ guardrail อาจเขียน payload ใหม่ผ่าน `modifiedPayload`
   - รายการแรกที่มี `block: true` จะยุติลำดับการทำงานทันที และ handler จะส่งคืน
     การตอบกลับที่ระบุว่า guardrail ปฏิเสธคำขอ
3. Payload ที่อาจถูกเขียนใหม่จะถูกส่งต่อไปยัง combo routing และการส่งคำขอ
   ไปยัง upstream
4. หลังจากประกอบการตอบกลับแล้ว `guardrailRegistry.runPostCallHooks(...)`
   จะเรียกใช้ลำดับเดิมกับการตอบกลับ หากพบ `block: true` ในขั้นตอนนี้ การตอบกลับ
   จาก upstream จะถูกละทิ้ง

Guardrails ที่ throw ข้อผิดพลาดจะถูกบันทึกด้วย `error: <message>` และเขียน log ผ่าน
`logger.warn` แต่ลำดับการทำงานจะดำเนินต่อไป ซึ่งเป็นการออกแบบแบบ fail-open

## การกำหนดค่า

ตัวแปรสภาพแวดล้อมที่ guardrails ในตัวอ่าน:

| ตัวแปร                                | ใช้โดย                    | ผลกระทบ                                                                                                  |
| ------------------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | ตั้งค่าเป็น `false` เพื่อปิดใช้งานการตรวจจับทั้งหมด                                                      |

## การ์ดเรลแบบกำหนดเอง

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ขั้นตอน:

1. สร้าง `src/lib/guardrails/myGuardrail.ts` โดยสืบทอดจาก `BaseGuardrail`
2. อิมพลีเมนต์ `preCall` และ/หรือ `postCall`
3. ลงทะเบียนขณะนำเข้า (เพิ่มจาก `registerDefaultGuardrails`) หรือ
   เรียก `guardrailRegistry.register(...)` ขณะรันไทม์ — รีจิสทรีจะแทนที่
   การ์ดเรลก่อนหน้าที่มีชื่อหลังการปรับรูปแบบเหมือนกัน
4. เพิ่มการทดสอบภายใต้ `tests/unit/` (ตัวอย่างที่มีอยู่:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)

## การทดสอบ

ใช้ `resetGuardrailsForTests()` ระหว่างการทดสอบแต่ละรายการเพื่อเริ่มต้นจากสถานะที่ทราบแน่ชัด
ส่ง `{ registerDefaults: false }` เพื่อเริ่มต้นด้วยรีจิสทรีว่างและ
ลงทะเบียนเฉพาะการ์ดเรลที่กำลังทดสอบ Vision Bridge รองรับการฉีดการพึ่งพา
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge มีจุดเชื่อมต่อ
ที่เทียบเท่ากันสำหรับการตั้งค่า ความสามารถ การเลือกโมเดล STT การตรวจสอบข้อมูลรับรอง
และการถอดเสียง ดังนั้นการทดสอบจึงสามารถตรวจสอบโฟลว์ทั้งสองได้โดยไม่ต้องเข้าถึง DB
หรือเครือข่าย

## ความครอบคลุมของเส้นทางและการทดสอบแบบเรดทีมสำหรับการป้องกันการแทรกคำสั่ง (Phase 8 · Block D)

การป้องกันการแทรกคำสั่ง (`createInjectionGuard` / `withInjectionGuard`) ครอบคลุมทุกเส้นทาง
ที่รับพรอมต์จากผู้ใช้ โดยจะเคารพ `INJECTION_GUARD_MODE` (ค่าเริ่มต้น `warn` = บันทึกล็อกเท่านั้น;
`block` = ส่งคืน HTTP 400 `SECURITY_001`)

| ประเภท         | เส้นทาง                                                                                                                                              | โหมดเริ่มต้น |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| ข้อความ (เดิม) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn         |
| เชิงสร้างสรรค์ | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn         |
| ข้อมูล         | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn         |

การแยกข้อความ (`extractMessageContents`) ครอบคลุม `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`

**เรดทีม (ทุกคืน, `nightly-llm-security.yml`):** promptfoo ตรวจสอบว่าแต่ละเส้นทางบล็อก
คลัง OWASP-LLM ใน `INJECTION_GUARD_MODE=block`; garak เรียกใช้โพรบ (ข้ามหากไม่มีข้อมูลลับ)
`moderations` ถูกรวมไว้เพื่อความสอดคล้อง — ผู้ดูแลระบบที่ใช้โหมดบล็อกสามารถยกเว้นเส้นทางนี้ผ่าน
`resolveDisabledGuardrails`

เวิร์กโฟลว์รายคืน (`.github/workflows/nightly-llm-security.yml`, cron + การสั่งงาน
ด้วยตนเอง) มีสองงาน:

- **`promptfoo-guard` (บล็อกเมื่อไม่ผ่าน)** — เรียกใช้ `promptfoo eval -c promptfooconfig.yaml`
  โดยใช้ `INJECTION_GUARD_MODE=block` กรณีโจมตีแต่ละกรณี (เช่น "เพิกเฉยต่อ
  คำสั่งก่อนหน้าทั้งหมด…", การเจลเบรกแบบ DAN) จะยืนยันว่าการตอบกลับมี
  `error.code === "SECURITY_001"` กล่าวคือ การ์ดได้ปฏิเสธคำขอจริง
- **`garak` (ให้คำแนะนำ)** — เรียกใช้ garak `--probes promptinject,dan,leakreplay`
  กับอินสแตนซ์ OmniRoute ภายในเครื่อง (`http://localhost:20128/v1`) โดยขึ้นอยู่กับ
  ข้อมูลลับของผู้ให้บริการ (`PROMPTFOO_PROVIDER_KEY`); จะข้ามอย่างราบรื่นหากไม่มีข้อมูลดังกล่าว และต่อท้ายด้วย
  `|| true` จึงรายงานผลโดยไม่ทำให้ CI ล้มเหลว

ความครอบคลุมของตัวช่วยการ์ด (`createInjectionGuard` / `withInjectionGuard`)
ครอบคลุมทุกเส้นทาง `/v1` ที่มีพรอมต์; ข้อความพรอมต์จะถูกดึงจาก
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` โดย
`extractMessageContents()` ใน `src/shared/utils/inputSanitizer.ts`
