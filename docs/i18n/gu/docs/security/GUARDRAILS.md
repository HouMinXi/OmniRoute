> **સત્યનો અધિકૃત સ્રોત:** `src/lib/guardrails/`
> **છેલ્લે અપડેટ કરેલું:** 2026-08-29 — v3.8.51 (Video Bridge ટ્રાન્સક્રિપ્ટનું મૂળ કૉલર દ્વારા જાહેર કરવામાં આવે છે,
> હજી સર્વર દ્વારા ચકાસાયેલું નથી — #11661 અનુસાર સ્પષ્ટ કરવામાં આવ્યું)

Guardrails, OmniRoute અને અપસ્ટ્રીમ પ્રદાતાઓ વચ્ચેની સીમા પર સુરક્ષા, નીતિ અને કન્ટેન્ટ રૂપાંતરણો લાગુ કરે છે. દરેક guardrail વિનંતીના payloads (`preCall`) અને અપસ્ટ્રીમ પ્રતિસાદો (`postCall`)નું નિરીક્ષણ કરી શકે છે (અને વૈકલ્પિક રીતે તેમને નકારી, રૂપાંતરિત અથવા ઍનોટેટ કરી શકે છે).

સિસ્ટમ **fail-open** છે: જો કોઈ guardrail કાર્યરત હોય ત્યારે અપવાદ ફેંકે, તો registry ભૂલ નોંધે છે અને વિનંતીને નિષ્ફળ કરવાને બદલે આગામી guardrail સાથે ચાલુ રહે છે. બ્લૉક કરવું હંમેશાં સ્પષ્ટ નિર્ણય (`block: true`) હોય છે, ક્યારેય આકસ્મિક ઘટના નહીં.

## બિલ્ટ-ઇન ગાર્ડરેલ્સ

રજિસ્ટ્રી ઇમ્પોર્ટ કરતી વખતે પ્રાથમિકતાના ક્રમમાં છ ગાર્ડરેલ્સ આપમેળે લોડ કરે છે
(`registry.ts` → `registerDefaultGuardrails()` જુઓ):

| પ્રાથમિકતા | નામ                 | તબક્કો(ઓ)      | ફાઇલ                  |
| ---------- | ------------------- | -------------- | --------------------- |
| `5`        | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`        | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`       | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`       | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`       | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ઓછી પ્રાથમિકતા સંખ્યાઓ **પહેલા** ચાલે છે.

### વિઝન બ્રિજ (`visionBridge.ts`) — મોડેલિટી બ્રિજ PR-1

**નોન-વિઝન મોડલ્સ** માટેના ઇમેજ ધરાવતા અનુરોધોને ઇન્ટરસેપ્ટ કરે છે અને
સમગ્ર અનુરોધને વિઝન-સક્ષમ મોડલ તરફ ફરીથી રૂટ કરે છે અથવા અપસ્ટ્રીમ કૉલ પહેલાં
ઇમેજના ભાગોને રૂપરેખાંકિત કરી શકાય તેવા વિઝન મોડલ દ્વારા બનાવવામાં આવેલા
ટેક્સ્ટ વર્ણનોથી બદલે છે. આનાથી ફક્ત-ટેક્સ્ટ પ્રદાતાઓ મલ્ટિમોડલ પેલોડ્સને
પારદર્શક રીતે હેન્ડલ કરી શકે છે.

પ્રવાહ:

1. જો લક્ષ્ય મોડલ પહેલેથી જ વિઝનને સપોર્ટ કરતું હોય, તો તેને સ્કિપ કરો (સિવાય કે
   તે ફરજિયાત-બ્રિજ સૂચિ `isVisionBridgeForcedModel`માં હોય).
2. `extractImageParts(messages)` દ્વારા ઇમેજના ભાગો એક્સ્ટ્રેક્ટ કરો
   (`visionBridgeHelpers.ts`), જે `open-sse/utils/mediaParts.ts`માંના
   **એકીકૃત મીડિયા ડિટેક્ટર** `detectMediaParts()`ને કાર્ય સોંપે છે — આ
   કૉમ્બો સુસંગતતા ફિલ્ટર સાથે વહેંચાયેલ સત્યનો એકમાત્ર સ્રોત છે.
   એક્સ્ટ્રેક્શન ફક્ત એવા ટોચના-સ્તરના ભાગોના આકારો સુધી મંજૂર છે જેને
   `replaceImageParts` ફરીથી જોડી શકે છે (એક્સ્ટ્રેક્ટ↔રિપ્લેસ કરાર): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, અને Responses API `input_image`. નેસ્ટેડ મેળ અને
   ફક્ત-સૂચક આકારો કૉમ્બો-ફિલ્ટર માટેની સામગ્રી છે અને ક્યારેય એક્સ્ટ્રેક્ટ
   થતા નથી. કંઈ ન મળે તો સ્કિપ કરો.
3. `resolveVisionBridgeRuntimeSettings()` દ્વારા રનટાઇમ કૉન્ફિગનું નિરાકરણ કરો
   (`src/shared/constants/modalityBridgeDefaults.ts`): નવી `modalityBridge*`
   સેટિંગ્સ કીઝને પ્રાધાન્ય મળે છે; લેગસી `visionBridge*` કીઝ
   **એક-ચક્રના ફૉલબૅક** (રોલબૅક વિન્ડો) તરીકે ઉપલબ્ધ રહે છે. બ્રિજ
   નિષ્ક્રિય હોય ત્યારે કોઈપણ મીડિયા ટ્રાવર્સલ પહેલાં સ્કિપ કરો.
4. મોડ સિલેક્ટર (`modalityBridgeVisionMode`, નીચેનું કોષ્ટક જુઓ) રીરુટ કે
   વર્ણન કરવું તે નક્કી કરે છે. રીરુટ ફક્ત `model` બદલેલા `modifiedPayload`
   સાથે મેટા `{ rerouted, fromModel, toModel, imagesKept }` પરત કરે છે.
5. વર્ણન પાથ: ઇમેજની સંખ્યા `maxImages` સુધી મર્યાદિત કરો, કાર્ય-જાગૃત
   પ્રોમ્પ્ટ તૈયાર કરો, વર્ણન કૅશ તપાસો, વિઝન મોડલને **સમાંતરમાં**
   (`Promise.allSettled`) કૉલ કરો અને તેમની જગ્યાએ
   `[Image N]: <description>` ટેક્સ્ટ ભાગો દાખલ કરો. નિષ્ફળ વર્ણન `null`
   આપે છે અને મૂળ ઇમેજ ભાગ **જાળવી રાખવામાં આવે છે** (#4012) — પરંતુ કૉમ્બો
   વર્ણન પાથ પર જ્યારે દરેક વર્ણન નિષ્ફળ ગયું હોય ત્યારે અપવાદરૂપે, પુષ્ટિ
   થયેલા નોન-વિઝન અપસ્ટ્રીમને તેના બદલે
   `(અનુપલબ્ધ — કોઈ વિઝન-સક્ષમ પ્રદાતા કનેક્ટ થયેલ નથી)` સ્ટબ મળે છે (#8430).
6. `modifiedPayload` + મેટા (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) પરત કરો.

#### મોડ સિલેક્ટર (`modalityBridgeVisionMode`)

| મોડ        | ડિફૉલ્ટ | વર્તન                                                                                                                                                                                                                                                                                                  |
| ---------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔       | લેગસી હ્યુરિસ્ટિક, અપરિવર્તિત (#6640/#7204): નોન-કૉમ્બો/`auto/` મોડલ્સ શ્રેષ્ઠ વિઝન મોડલ તરફ રીરુટ થાય છે, સિવાય કે મૂળ મોડલ પાસે પહેલેથી ઉપયોગ કરી શકાય તેવા ક્રેડેન્શિયલ્સ હોય (ત્યારે વર્ણન કરવામાં આવે છે); કૉમ્બો લક્ષ્યો હંમેશાં વર્ણન કરે છે.                                                   |
| `describe` |         | હંમેશાં વર્ણન કરો — રીરુટ બ્લૉક સંપૂર્ણપણે સ્કિપ થાય છે; વપરાશકર્તાએ પસંદ કરેલું મોડલ હંમેશાં જવાબ આપે છે.                                                                                                                                                                                             |
| `reroute`  |         | ફરજિયાત રીરુટ: ક્રેડેન્શિયલ ધરાવતા મોડલને જાળવી રાખતો ગાર્ડ બાયપાસ થાય છે. રીરુટ-**લક્ષ્ય** ક્રેડેન્શિયલ ગાર્ડ હજુ પણ લાગુ પડે છે — જ્યારે ઉપયોગ કરી શકાય તેવું કોઈ વિઝન લક્ષ્ય અસ્તિત્વમાં ન હોય ત્યારે અનુરોધ વર્ણન તરફ આગળ વધે છે, જેથી રૉ ઇમેજ ક્યારેય ફક્ત-ટેક્સ્ટ બૅકએન્ડ સુધી ન પહોંચે (#8430). |

ફરજિયાત મોડ્સ `auto` હ્યુરિસ્ટિક ચાલે તે **પહેલાં** શૉર્ટ-સર્કિટ થાય છે;
`auto`નું વર્તન PR-1 પહેલાના ગાર્ડરેલ સાથે બાઇટ-દર-બાઇટ સમાન છે.

#### API-કીનો વ્યાપ (`visionBridgeKeyScope.ts`)

જ્યારે કૉલરની API કી `allowedConnections`, ક્વોટા પૂલ્સ
(`allowedQuotas`) અથવા મોડલ્સ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) પર પ્રતિબંધ મૂકે છે,
ત્યારે બ્રિજ ફક્ત એવા રીરુટ અને વર્ણન મોડલ્સ પસંદ કરે છે જેનો ઉપયોગ કી કરી શકે,
અને એવા કનેક્શન્સ પર જેનો ઉપયોગ કી કરી શકે. ત્યારબાદ વર્ણન કૉલ હંમેશાં
`x-omniroute-self-loop-key-id` હેડર સાથે OmniRoute સેલ્ફ-લૂપ મારફતે જાય છે,
જેથી પ્રાપ્ત થતો ચેટ અનુરોધ તે કીની કનેક્શન અને મોડલ નીતિને ફરીથી લાગુ કરે છે.
`enforceApiKeyPolicy()` એ હેડરને માત્ર સેલ્ફ-લૂપ બેરર સાથે જ માન્ય રાખે છે,
તેથી તે ફક્ત ઍક્સેસને વધુ મર્યાદિત કરી શકે છે, અને જે idનું નિરાકરણ ન થાય
તેને નકારવામાં આવે છે.

જો કી માટે કોઈ વિઝન મોડલની પરવાનગી ન હોય, તો વર્ણન પાથ બાજુએ ખસી જાય છે અને
અનુરોધ કોઈ ફેરફાર વિના પસાર થાય છે, જે નિષ્ક્રિય ગાર્ડરેલ જેવું જ ફેલ-ઓપન
વર્તન છે (મેટા `{ skipped: true, reason: "no_permitted_vision_model" }`).
કી વિનાના અનુરોધો અને આ પ્રતિબંધો વિનાની કીઝનું વર્તન પહેલાની જેમ જ રહે છે.

#### કાર્ય-જાગૃત વર્ણન પ્રોમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફૉલ્ટ **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) બેઝ
વર્ણન પ્રોમ્પ્ટમાં **છેલ્લા વપરાશકર્તા સંદેશા**નું લખાણ (500 અક્ષરો સુધી મર્યાદિત)
ઉમેરે છે, જેથી વર્ણન વપરાશકર્તાએ ખરેખર જે પૂછ્યું હોય તેની દિશામાં કેન્દ્રિત થાય
(codex-vision-proxy પેટર્ન) અને વિઝન મોડલને દૃશ્યમાન લખાણનું ટ્રાન્સક્રિપ્શન કરવા કહે.
ફ્લૅગ બંધ હોય — અથવા વપરાશકર્તાનું કોઈ લખાણ ન હોય — ત્યારે બેઝ પ્રોમ્પ્ટ કોઈ ફેરફાર
વિના વપરાય છે.

વર્ણન સેલ્ફ-લૂપની પોતાની OpenAI-સુસંગત વિનંતી (`callVisionModelSingle()`
in `visionBridgeHelpers.ts`) હંમેશાં `image_url.detail: "high"`ની વિનંતી કરે છે —
દરેક કૉલર/પ્રોવાઇડર માટે બિનશરતી રીતે, કોઈપણ ક્લાયન્ટ સંકેત પર આધારિત નહીં.
લો-ડિટેઇલ સૅમ્પલિંગ આ પ્રોમ્પ્ટમાં માગવામાં આવેલા ચોક્કસ ટેક્સ્ટ-ટ્રાન્સક્રિપ્શન
કાર્ય માટે OCRની ચોકસાઈ ઘટાડે છે, તેથી મૂળ ઇનબાઉન્ડ વિનંતીમાં કયું ડિટેઇલ સ્તર
વપરાયું હતું તે ધ્યાનમાં લીધા વિના, વર્ણન કૉલ પોતે હંમેશાં હાઇ ડિટેઇલ માગે છે.
આ ફક્ત આંતરિક વર્ણન વિનંતીની બૉડીને અસર કરે છે; પ્રાથમિક વિનંતી પર OmniRoute
કૉલરનું પોતાનું `image_url.detail` કેવી રીતે ફૉર્વર્ડ કરે છે તે આ બદલતું નથી —
તે ડિફૉલ્ટ અલગથી લાગુ થાય છે, અને ફક્ત શોધી કાઢેલા OpenCode ક્લાયન્ટ્સ માટે,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`)માં.
વર્ણન સેલ્ફ-લૂપની Anthropic વાયર-ફૉર્મેટ બ્રાન્ચમાં કોઈ `detail` ફીલ્ડ નથી અને
તે બંનેમાંથી કોઈપણ ડિફૉલ્ટથી પ્રભાવિત થતી નથી.

#### વર્ણન આઉટપુટ મર્યાદા (`modalityBridgeVisionMaxChars`)

| કી                             | ડિફૉલ્ટ | શ્રેણી             |
| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

`0` (ડિફૉલ્ટ)નો અર્થ **કોઈ મર્યાદા નહીં** — `callVisionModel()` દ્વારા પરત કરાયેલું
વર્ણન કોઈ ફેરફાર વિના પસાર કરવામાં આવે છે, જેથી હાલનું વર્તન જળવાઈ રહે.
100–50000ની શ્રેણીનું કોઈપણ મૂલ્ય વર્ણનને `[Image N]: <description>` તરીકે પાછું
ઉમેરવામાં આવે તે પહેલાં `…` પ્રત્યય સાથે ટૂંકાવે છે
(`VisionBridgeGuardrail.preCall()` in `src/lib/guardrails/visionBridge.ts`).
વિગતોથી ભરપૂર OCR કાર્યોમાં, જ્યાં ડાઉનસ્ટ્રીમ મોડલને સંપૂર્ણ ટ્રાન્સક્રિપ્શનની
જરૂર હોય, ત્યાં આ મૂલ્ય વધારો; વધુ બોલકાં વિઝન મોડલ્સ માટે ટોકન વપરાશ મર્યાદિત
રાખવા તેને ઘટાડો. ડૅશબોર્ડ ફીલ્ડ Vision ટૅબની Advanced પૅનલમાં છે
(`modality-bridge-max-chars` in `ModalityBridgeVisionTab.tsx`) અને સ્પષ્ટ `0`ને
અસ્પર્શિત રાખતાં 1 અને 99 વચ્ચેના કોઈપણ મૂલ્યને ન્યૂનતમ 100 સુધી વધારી દે છે —
`0` માત્ર "સેટ ન કરેલું" ડિફૉલ્ટ નથી, પરંતુ પોતાની રીતે માન્ય Zod મૂલ્ય છે
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`).

#### વર્ણન કૅશ (`modalityBridge/bridgeCache.ts`)

વર્ણન આઉટપુટ માટે ઇન-મેમરી LRU + TTL કૅશ, જે સમગ્ર પ્રોસેસમાં શેર થાય છે.
કી = `sha256(imageRef + composedPrompt + configuredBridgeModel)`, લેન્થ-પ્રિફિક્સ
ફ્રેમિંગ સાથે (ફીલ્ડની સીમાઓ વચ્ચે કોઈ અથડામણ નહીં). મોડલ ઘટક
**કૉન્ફિગર કરેલું** બ્રિજ મોડલ છે, વાસ્તવમાં જવાબ આપનાર મોડલ નહીં —
`callVisionModel` આંતરિક રીતે ફૉલબૅક કરી શકે છે, અને દરેક પ્રયાસ પ્રમાણે કી
બનાવવાથી કૅશ વિખંડિત થઈ જાય. નિષ્ફળ વર્ણનો ક્યારેય કૅશ થતા નથી. સેટિંગ્સ:

| કી                              | ડિફૉલ્ટ | શ્રેણી  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રિમોટ ઇમેજ નોર્મલાઇઝેશન (સેલ્ફ-લૂપ વર્ણન/base64 ફેચ)

જ્યારે બ્રિજ પોતે કોઈ **રિમોટ** ઇમેજ ફેચ કરે છે — Anthropic વર્ણન સેલ્ફ-કૉલ અને
claude-wire-format base64 રૂપાંતરણ (`ensureBase64ImagesForClaudeWire`), બંને
`visionBridgeHelpers.ts`માં `fetchRemoteImageAsDataUri()` મારફતે — ત્યારે
પરિણામી data URIને વિઝન-મોડલ વિનંતીમાં એમ્બેડ કરતાં પહેલાં
`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`)માંથી પસાર કરવામાં આવે
છે. અતિમોટી ઇમેજોને **2048px લાંબી ધાર** સુધી ડાઉનસ્કેલ કરવામાં આવે છે
(OpenAI/Anthropic પહેલેથી સર્વર-સાઇડ પર લાગુ કરે છે તે રીસાઇઝ મર્યાદા સાથે
સુસંગત), જે વિઝન મોડલ શું જુએ છે તેમાં ફેરફાર કર્યા વિના અપલોડ બાઇટ્સ/લેટન્સી
ઘટાડે છે. રીસાઇઝિંગ `sharp`નો ઉપયોગ કરે છે, જે ડાયનેમિક ઇમ્પોર્ટ મારફતે લોડ થાય
છે: જે પ્લૅટફૉર્મ પર તેનું નેટિવ બાઇનરી લોડ થવામાં નિષ્ફળ જાય, ત્યાં
`normalizeDataUri()` **ક્યારેય અપવાદ ફેંકતું નથી** — તે મૂળ બાઇટ્સને જેમનાં તેમ
પસાર કરવાની રીત પર ફૉલબૅક કરે છે, જેથી વર્ણન/base64-રૂપાંતરણ પાથ હંમેશાં કાર્યરત
રહે. ઇમેજ ન હોય તેવા બાઇટ્સ (એવો ફેચ જે ડીકોડ કરી શકાય તેવી ઇમેજ પરત ન કરે) પણ
અસ્પર્શિત રીતે પસાર થાય છે. આ નોર્મલાઇઝેશન ફક્ત બ્રિજ તેના પોતાના સેલ્ફ-કૉલ માટે
ફેચ કરે તેવી ઇમેજો પૂરતું મર્યાદિત છે — કૉલરના રૉ પાસથ્રૂ પેલોડ પર તે ક્યારેય
લાગુ થતું નથી, જે ફક્ત ઑપ્ટ-ઇન મ્યુટેશનના સિદ્ધાંત (Hard Rule #20) સાથે સુસંગત છે.

(`src/shared/validation/settingsSchemas.ts`)માં Zod દ્વારા માન્ય કરાય છે:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCache*` ત્રિપુટી, અને Audio Bridge દ્વારા વપરાતું
`modalityBridgeAudio*` જૂથ. માઇગ્રેશન `141_modality_bridge_settings.sql`
હાલનાં લેગસી `visionBridge*` મૂલ્યોને અનુરૂપ નવી કીઓમાં કૉપી કરે છે
(આઇડેમ્પોટન્ટ, ઑપરેટર દ્વારા સેટ કરાયેલા `modalityBridge*` મૂલ્યને ક્યારેય
ઓવરરાઇટ કરતું નથી); એક રિલીઝ ચક્ર માટે લેગસી કીઓ રીડ ફૉલબૅક તરીકે સ્વીકારાતી
રહે છે.

#### પારદર્શિતા હેડર + આંકડા

વર્ણન દ્વારા રૂપાંતરિત પ્રતિસાદોમાં
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
હોય છે (`modalityBridge/bridgeStats.ts`માં `buildModalityBridgeHeader()` દ્વારા
બનાવેલું, `src/sse/handlers/chatHelpers.ts`માં `withModalityBridgeHeader()`
દ્વારા સ્ટૅમ્પ કરેલું). ફરી રૂટ કરાયેલી વિનંતીઓને **કોઈ** હેડર મળતું નથી —
પેલોડ અસ્પર્શિત હતો અને મોડલમાં થયેલો ફેરફાર પ્રતિસાદ બૉડીના `model` ફીલ્ડમાં
પહેલેથી જ દેખાય છે.

`GET /api/modality-bridge/stats` (મેનેજમેન્ટ ઑથ, `GET /api/settings` જેવું જ સ્તર)
`vision`, `audio`, અને `video` માટે ઇન-મેમરી પ્રતિ-મોડાલિટી કાઉન્ટર્સ
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` પરત કરે છે. `averageLatencyMs` તેના
છેદ તરીકે બધા પ્રયાસોને નહીં, પરંતુ `latencySamples` ને વાપરે છે; સમય માપ્યા વિનાનું
ઑપરેશન શૂન્ય-મિલિસેકન્ડનો બનાવટી નમૂનો ઉમેરતું નથી. `bridged` સફળ
રૂપાંતરણો માટે બૅકવર્ડ-કમ્પેટિબલ ઉપનામ તરીકે યથાવત્ રહે છે;
નિષ્ફળ પ્રયાસો તેને વધારતા નથી.
ડિઝાઇન મુજબ પ્રોસેસ રીસ્ટાર્ટ થતાં કાઉન્ટર્સ રીસેટ થાય છે
(ટેલિમેટ્રી, એકાઉન્ટિંગ નહીં).

#### ડૅશબોર્ડ કૉન્ફિગરેશન

સમર્પિત ડૅશબોર્ડ પેજ
`/dashboard/settings/modality-bridge` છે. તેની URL દ્વારા ઍક્સેસ કરી શકાય તેવી `Vision`, `Audio`,
અને `Video` ટૅબ્સ `tab` મૂલ્ય બદલતી વખતે ક્વેરી પેરામીટર્સ જાળવી રાખે છે.
Vision ટૅબ સક્ષમતા, મોડ, મોડલ પસંદગી (ઑટોમેટિક
ડિફૉલ્ટ સહિત), ટાસ્ક-અવેર પ્રૉમ્પ્ટિંગ, અદ્યતન ટાઇમઆઉટ/ઇમેજ/વર્ણન-લંબાઈ/કૅશ
મર્યાદાઓ, રનટાઇમ
કાઉન્ટર્સ અને સુરક્ષિત નમૂના વિનંતી ઉપલબ્ધ કરાવે છે. Audio ટૅબ પણ કાર્યરત છે: તે
સક્ષમતા, Auto સાથેનું માત્ર-STT મોડલ પિકર, ટાઇમઆઉટ/મહત્તમ-ક્લિપ મર્યાદાઓ, ઑડિયો
કાઉન્ટર્સ અને `input_audio` નમૂના પરીક્ષણ ઉપલબ્ધ કરાવે છે. Video ટૅબ કાર્યક્ષમ છે: તે
FFmpeg/ffprobe રનટાઇમ સ્થિતિ દર્શાવે છે — ચાર સ્પષ્ટ UI સ્થિતિઓમાંથી એક (`unknown` જ્યારે
પ્રોબ ચાલુ હોય અથવા પૂર્ણ ન થઈ શક્યો હોય, લૂપબૅક ન હોય તેવા
ડૅશબોર્ડ હોસ્ટ પર જ્યાં ક્લાયન્ટ-સાઇડ પ્રોબ ટાળવામાં આવે ત્યાં `restricted`, પ્રોબ થયા પછી
ગેરહાજરીની પુષ્ટિ થાય ત્યારે `unavailable`, અથવા FFmpeg/ffprobe વર્ઝન સાથે `available`) — સક્ષમતા/મોડલ/ફ્રેમ/વિડિયો/ટાઇમઆઉટ મર્યાદાઓ
સાચવે છે, મોડલ પિકરને વિઝન-ક્ષમ
મોડલ્સ સુધી ફિલ્ટર કરે છે અને વિડિયો કાઉન્ટર્સ ઉપલબ્ધ કરાવે છે.

AI સેટિંગ્સ હેઠળનું અગાઉનું Vision Bridge કાર્ડ હવે નવા પેજની
કમ્પેટિબિલિટી લિંક છે; હવે તે ફોર્મની બીજી નકલ ધરાવતું નથી. Media Providers પણ
હાલનું Speech-to-Text પ્લેગ્રાઉન્ડ દૂર કર્યા વિના Image-to-Text અને Speech-to-Text વર્કફ્લોને સંબંધિત Modality
Bridge ટૅબ્સ સાથે લિંક કરે છે.

**સેલ્ફ-લૂપ ઍડમિશન બાયપાસ:** જ્યારે વર્ણન કૉલ OmniRoute ના

સેલ્ફ-લૂપ ક્રેડેન્શિયલથી પ્રમાણિત થાય છે — લોકલ મોડમાં સ્થાનિક `sk_omniroute` સેન્ટિનલ અથવા
ઑપરેટર દ્વારા કૉન્ફિગર કરેલી `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env કી (#1350), જેથી
`REQUIRE_API_KEY=true` ડિપ્લોયમેન્ટ્સ હજુ પણ વર્ણન કૉલ ચલાવી શકે. બાયપાસને
માત્ર એ ચોક્કસ ક્રેડેન્શિયલ્સ માટે જ માન્ય રાખવામાં આવે છે, તેથી બાહ્ય ક્લાયન્ટ્સ
ઍડમિશન ટાળવા માટે આ હેડરનો ઉપયોગ કરી શકતા નથી.

લેગસી ડિફૉલ્ટ્સ `src/shared/constants/visionBridgeDefaults.ts` માં છે;
નવા મોડ/ટાસ્ક-અવેર/કૅશ ડિફૉલ્ટ્સ અને સેટિંગ્સ રિઝૉલ્વર
`src/shared/constants/modalityBridgeDefaults.ts` માં છે. ગાર્ડરેલ
`deps` કન્સ્ટ્રક્ટર વિકલ્પ ઉપલબ્ધ કરાવે છે, જેથી પરીક્ષણો બનાવટી `getSettings` અને
`callVisionModel` અમલીકરણો ઇન્જેક્ટ કરી શકે.

### ઑડિયો બ્રિજ (`audioBridge.ts`) — મોડાલિટી બ્રિજ PR-3

ઑડિયો સ્વીકારતું હોવાનું જાણીતું ન હોય તેવા લક્ષ્ય સુધી ઑડિયો ધરાવતી ચૅટ વિનંતીઓ પહોંચે તે પહેલાં તેમને ઇન્ટરસેપ્ટ કરે છે.
તે ચૅટ વિનંતીને ક્યારેય ફરી રૂટ કરતું નથી: ઑડિયો ભાગોનું હાલના OpenAI-કમ્પેટિબલ મલ્ટિપાર્ટ એન્ડપૉઇન્ટ દ્વારા
ટ્રાન્સક્રિપ્શન થાય છે અને પસંદ કરેલું ચૅટ મોડલ ટેક્સ્ટ ટ્રાન્સક્રિપ્ટ્સ સાથે આગળ વધે છે.

પ્રવાહ:

1. `getResolvedModelCapabilities()` દ્વારા `supportsAudio` ઉકેલો. સ્પષ્ટ
   પ્રોવાઇડર-રજિસ્ટ્રી મેટાડેટાને પ્રથમ પ્રાધાન્ય મળે છે, ત્યારબાદ સ્ટેટિક મોડલ મેટાડેટા અને પછી સિંક કરેલું
   `modalities_input`. `audio` વિનાની જાહેર કરેલી ઇનપુટ સૂચિ `false` છે; ક્ષમતાનો કોઈ
   પુરાવો ન હોય તો `null` રહે છે. `false` અને `null` બંને
   સંરક્ષણાત્મક બ્રિજને સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સ ઉકેલો અને શેર કરેલા `detectMediaParts()`
   ડિટેક્ટર દ્વારા દરેક સંદેશમાંથી સ્પ્લાઇસ કરી શકાય તેવા ટોચના-સ્તરના
   ઑડિયો ભાગો બહાર કાઢો. સમર્થિત વાયર આકારો OpenAI `input_audio`, `audio_url`, અને
   `source.media_type: "audio/*"` છે. નેસ્ટેડ ઑડિયો રૂટિંગ માટે શોધાય છે, પરંતુ
   સ્પ્લાઇસ પાથ દ્વારા દૂર થતો નથી. કાર્ય `modalityBridgeAudioMaxClips` દ્વારા મર્યાદિત છે;
   ત્યાર પછીના ભાગો અસ્પર્શિત રહે છે.
3. કૉન્ફિગર કરેલા `provider/model` ને માન આપો, અથવા `selectAudioBridgeModel()` ને
   સ્થિર કૅટલૉગ ક્રમમાં `AUDIO_TRANSCRIPTION_PROVIDERS`માંથી પસાર થઈને ઉપયોગ કરી શકાય તેવું
   સક્રિય પ્રોવાઇડર ક્રેડેન્શિયલ ધરાવતું પ્રથમ મોડલ પસંદ કરવા દો.
4. `callAudioTranscription()` base64/data-URI ઑડિયોને મલ્ટિપાર્ટ
   `file` માં રૂપાંતરિત કરે છે અથવા DNS પિનિંગ અને 25 MB મર્યાદા સાથેના માત્ર-જાહેર આઉટબાઉન્ડ
   ગાર્ડ દ્વારા રિમોટ `audio_url` ડાઉનલોડ કરે છે. ત્યારબાદ તે ફાઇલ અને પસંદ કરેલા
   મોડલને સ્થાનિક `/v1/audio/transcriptions` સેલ્ફ-લૂપ પર POST કરે છે, જેનું પ્રમાણીકરણ
   `resolveSelfLoopBearer()` વડે થાય છે. હાલનો ટ્રાન્સક્રિપ્શન રૂટ સામાન્ય
   ક્રેડેન્શિયલ લુકઅપ, કૂલડાઉન/રેટ-લિમિટ હેન્ડલિંગ અને પ્રોવાઇડર ડિસ્પૅચ કરે છે.
5. સફળ કૉલ્સ તેમના ભાગોને `[Audio N]: <transcript>` થી બદલે છે. કૉલ્સ
   `Promise.allSettled` સાથે ચાલે છે: વ્યક્તિગત નિષ્ફળતા મૂળ
   ઑડિયો ભાગને જાળવી રાખે છે (#4012 કરાર). જો દરેક કૉલ નિષ્ફળ જાય અને લક્ષ્ય
   `supportsAudio === false` હોવાનું સાબિત થયેલું હોય, તો ભાગો
   `[Audio N]: (unavailable — no STT provider connected)` બને છે (#8430 કરાર). અજ્ઞાત
   લક્ષ્ય (`null`) માટે, બધું નિષ્ફળ ગયેલું પરિણામ અસ્પર્શિત રહે છે. ઉપયોગ કરી શકાય તેવું
   STT ક્રેડેન્શિયલ ન ધરાવતા સાબિત ટેક્સ્ટ-માત્ર લક્ષ્યને નેટવર્ક કૉલ કર્યા વિના
   એ જ સ્પષ્ટ સ્ટબ મળે છે.

સફળ ટ્રાન્સક્રિપ્ટ્સ પ્રોસેસ-વ્યાપી Modality Bridge LRU/TTL કૅશનો ઉપયોગ કરે છે.
કી ઑડિયો સંદર્ભ, સ્થિર `audio-transcription` ઑપરેશન
લેબલ અને પસંદ કરેલા STT મોડલને જોડે છે; નિષ્ફળતાઓ ક્યારેય કૅશ થતી નથી. ઑડિયો પ્રયાસો
શેર કરેલા `bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર્સ અપડેટ કરે છે.
રૂપાંતરિત પ્રતિસાદો
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ધરાવે છે; અસ્પર્શિત
વિનંતીઓને Audio Bridge સેગમેન્ટ મળતું નથી.

રનટાઇમ સેટિંગ્સ DB-બૅક્ડ અને Zod દ્વારા માન્ય કરેલાં છે:

| કી                            | ડિફૉલ્ટ | શ્રેણી          |
| ----------------------------- | ------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —               |
| `modalityBridgeAudioModel`    | `""`    | ઑટો અથવા STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10            |

શેર કરેલી કૅશનું નિયંત્રણ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, અને `modalityBridgeCacheMaxEntries` દ્વારા જ થાય છે.

### વીડિયો બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

જાણીતી મૂળ વીડિયો સપોર્ટ ક્ષમતા ન ધરાવતા લક્ષ્યને કૉલ કરવામાં આવે તે પહેલાં Chat Completionsના `messages` અને Responses
APIના `input`માં ટોચના-સ્તરના વીડિયો ભાગોને ઇન્ટરસેપ્ટ કરે છે.
સમર્થિત સ્વરૂપો `input_video`, `video_url`, `video_source`, HTTPS URLs,
અને `data:video/*;base64,...` ડેટા URIs છે. ટેક્સ્ટમાં સાદા ફાઇલનામોને વીડિયો તરીકે ગણવામાં આવતાં નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતી ટ્રાવર્સલ,
ક્ષમતા/નીતિ ચકાસણી, પ્રતિ-વિનંતી એકત્રીકરણ અને પ્રતિસાદ પેલોડનું સંચાલન કરે છે.
પ્રતિ-વીડિયો કાર્ય — પ્રાપ્તિ, સંપૂર્ણ-પરિણામ કૅશ, ફ્રેમ
ક્રમનું વર્ણન કરવું (જે કૉલર દ્વારા જાહેર કરાયેલા કોઈપણ ઑડિયો ટ્રાન્સક્રિપ્ટને સંમિશ્રિત કરે છે), અને પ્રતિ-પ્રયાસ
મેટ્રિક્સ/અબૉર્ટ/ક્લીનઅપ — `videoBridgePipeline.ts`માં
`processVideoPart` પાછળ છુપાયેલું છે, જેને `preCall`ના લૂપની અંદર દરેક વીડિયો ભાગ દીઠ એક વાર કૉલ કરવામાં આવે છે.
તે મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓ `VideoMediaBrokerPort`
(બાઇટ્સ મેળવવા અને સૅમ્પલ કરેલી ફ્રેમ્સ કાઢવા), `VideoAudioTranscriptionPort`
(કૉલર દ્વારા જાહેર કરાયેલા ઑડિયો ટ્રાન્સક્રિપ્ટને સૅમ્પલ કરેલા કૅપ્શન્સ સાથે સંમિશ્રિત કરવા), અને
`VideoDrilldownPort` (ફ્રેમ ડ્રિલ-ડાઉન સ્થાયિત્વ સીમા; હજી સુધી
`processVideoPart` સાથે જોડાયેલ નથી — હાલમાં ફક્ત અલગ `/api/modality-bridge/video/drilldown`
રૂટ જ ડ્રિલ-ડાઉન એન્ટ્રીઓ લખે છે) પણ વ્યાખ્યાયિત કરે છે.

જાહેર `/v1` વિનંતી પાથ ક્યારેય સબપ્રોસેસને ઇમ્પોર્ટ કરતો કે શરૂ કરતો નથી. રિમોટ

#### FU-07 માળખાકીય સેગમેન્ટ પુરાવા

`segment_aware` પહેલેથી માન્ય કરાયેલા સ્થાનિક વિડિયો સ્ટ્રીમ પર એક મર્યાદિત પૂર્વ-વિશ્લેષણ પાસનો ઉપયોગ કરે છે. નિશ્ચિત ફિલ્ટર ચેઇન પહેલાં પહોળાઈને વધુમાં વધુ 320 પિક્સેલ સુધી સ્કેલ કરે છે, દૃશ્ય પરિવર્તનો અને સ્થિર અંતરાલો શોધે છે, અને પછી ધૂંધળાશ, સરેરાશ લ્યુમા તથા અવકાશી/કાલિક માહિતી માટે પ્રતિ સેકન્ડ 1 ફ્રેમનું નમૂનીકરણ કરે છે. આ પાસ 600 સંરચનાત્મક નમૂનાઓ, એક FFmpeg/ફિલ્ટર થ્રેડ, સમાન માત્ર-`file` પ્રોટોકૉલ અને કન્ટેનર અનુમતિ-સૂચિઓ, 1 MiB પ્રક્રિયા-આઉટપુટ મર્યાદા તથા બ્રોકરના વહેંચાયેલા રદકરણ/સમયમર્યાદાની અંદર વધુમાં વધુ 30 સેકન્ડ સુધી મર્યાદિત છે. તે વિનંતીમાંથી ક્યારેય કમાન્ડ, ફિલ્ટર, પાથ અથવા URL સ્વીકારતું નથી.

સંરચનાત્મક મૂલ્યો નિર્ધારિત નમૂનીકરણ પુરાવા છે, વિડિયોની અર્થસૂચક સમજ નહીં. તેઓ વિષયો, ક્રિયાઓ, કૅપ્શનો, વાણી અથવા વપરાશકર્તાનો આશય તારવતા નથી. દૃશ્ય અને સ્થિરતા સીમાઓ સેગમેન્ટ બનાવે છે; સ્થિરતા આવરણ, ધૂંધળાશ, એક્સપોઝર, અવકાશી વિગતો અને કાલિક પરિવર્તન ફક્ત હાલના 1–16 ફ્રેમના બજેટની ફાળવણીને પ્રભાવિત કરે છે. સંપૂર્ણપણે સ્થિર સેગમેન્ટ વધુમાં વધુ એક ફ્રેમ સુધી મર્યાદિત હોય છે, જ્યારે બિન-સ્થિર સેગમેન્ટ બાકીના બજેટ માટે સ્પર્ધા કરે છે. જ્યારે સીમાઓની સંખ્યા ફ્રેમ કરતાં વધી જાય છે, ત્યારે સમયરેખાનું સમાન આવરણ જાળવવામાં આવે છે, જેથી શરૂઆતના ઝડપી કટ લાંબા અંતિમ સેગમેન્ટને છુપાવી ન શકે. સ્થિરતા સીમાની 1-સેકન્ડ વિશ્લેષણ રિઝોલ્યુશનની અંદરની દૃશ્ય સીમાઓને એકત્રિત કરવામાં આવે છે.

પ્રમોશન પુરાવાને કૃત્રિમ કમ્પોઝિશન માઇક્રોબેન્ચમાર્કથી ઇરાદાપૂર્વક અલગ રાખવામાં આવે છે. `scripts/perf/video-bridge-contact-sheet-eval.ts` વાસ્તવિક OpenAI-સુસંગત વિઝન મોડેલો માટે સ્કીમા-વર્ઝન ધરાવતું A/B હાર્નેસ વ્યાખ્યાયિત કરે છે. તે પ્રદાતા દ્વારા જણાવાયેલા ટોકન, શરૂઆતથી અંત સુધીની વાસ્તવિક વિલંબતા (શીટ કમ્પોઝિશન સહિત), મોડેલ-કૉલની સંખ્યા અને મેનિફેસ્ટમાં વ્યાખ્યાયિત તથ્ય જાળવણી માપે છે. કાચા મોડેલ પ્રતિસાદ રિપોર્ટમાં લખવામાં આવતા નથી; ફક્ત SHA-256 ડાઇજેસ્ટ અને મેળ ખાતા તથ્ય ID જાળવવામાં આવે છે. જ્યાં સુધી `--execute-real` પસાર કરવામાં ન આવે અને `--model`, `OMNIROUTE_BASE_URL` તથા `OMNIROUTE_API_KEY` કૉન્ફિગર ન કરવામાં આવે, ત્યાં સુધી હાર્નેસ કોઈ નેટવર્ક અથવા સશુલ્ક મોડેલ કૉલ કરતું નથી. આવા સ્પષ્ટ વાસ્તવિક રન વિના, તેનો મશીન-વાચ્ય નિર્ણય `HOLD` જ રહે છે; માત્ર કૃત્રિમ પેલોડ/કૉલ-સંખ્યા માપનો પ્રમોશન પુરાવો નથી.

જો કૉલર પાસે પહેલેથી જ સંરેખિત ટેક્સ્ટ હોય, તો તેઓ સમર્થિત વિડિયો ભાગ સાથે વૈકલ્પિક `transcript.cues` ઍરે જોડી શકે છે. દરેક ક્યૂમાં `text`, તપાસેલી અવધિની અંદરનો સીમિત `start`/`end` અંતરાલ અને અનુમતિ-સૂચિમાં રહેલું `source` (`client`, `embedded` અથવા `audio-bridge`) હોવું આવશ્યક છે; `confidence`નું ડિફૉલ્ટ મૂલ્ય `1` છે અને તે `0`થી `1` વચ્ચે જ હોવું જોઈએ. બરાબર સમાન ડુપ્લિકેટ ક્યૂને એકમાં સંકુચિત કરવામાં આવે છે. OmniRoute આ મેટાડેટામાંથી ક્યારેય ટ્રાન્સક્રિપ્શન શરૂ કરતું નથી: માન્ય કરાયેલા ક્યૂને સ્રોત, વિશ્વસનીયતા અને અંતરાલ સાથે વર્ણવેલા પરિણામમાં કૉપિ કરવામાં આવે છે અને ફ્રેમ કૅપ્શનોની સાથે અવિશ્વસનીય અવલોકનો તરીકે રેન્ડર કરવામાં આવે છે. અમાન્ય, મર્યાદાની બહારના અથવા ઉદ્ભવ-માહિતી વિનાના ટેક્સ્ટને કૅપ્શન સ્ટ્રીમમાં ભેળવવાને બદલે નકારવામાં આવે છે. બંને વિનંતી-બોડી ટ્રાન્સક્રિપ્ટ ચૅનલ પૂરા પાડવામાં આવેલા ઉદ્ભવને `client` તરીકે નોર્મલાઇઝ કરે છે, જેમાં સ્વયં-દાવો કરાયેલા `embedded` અથવા `audio-bridge` લેબલ પણ સામેલ છે. ફક્ત સર્વરની માલિકીનું ઍડેપ્ટર કોડ-માત્ર `trustedSource` આર્ગ્યુમેન્ટ દ્વારા એ વિશ્વસનીય લેબલ અસાઇન કરી શકે છે; વિનંતીના JSONનું કોઈ ફીલ્ડ એ આર્ગ્યુમેન્ટ સુધી પહોંચી શકતું નથી. ટ્રાન્સક્રિપ્ટ ટેક્સ્ટ તેના ઉદ્ભવને ધ્યાનમાં લીધા વિના અવિશ્વસનીય મીડિયા-વ્યુત્પન્ન સામગ્રી જ રહે છે અને તે ક્યારેય અધિકૃતતા નક્કી કરતું હોવું જોઈએ નહીં.

એક અદ્યતન કૉલર એ જ વિડિયો માટે `audioTranscript` ટ્રૅક પ્રદાન કરી શકે છે;
તેને ક્લાયન્ટ દ્વારા પ્રદાન કરાયેલ ટેક્સ્ટ તરીકે ગણવામાં આવે છે, સર્વર ટ્રાન્સક્રિપ્શનના પુરાવા તરીકે નહીં.
ફ્યુઝન સીમ એક જ સમયમર્યાદા અને અબોર્ટ સિગ્નલ હેઠળ વિઝ્યુઅલ અને ઑડિયો અવલોકનો ચલાવે છે,
તેમને એક સામાન્ય સમયરેખા પર ક્રમબદ્ધ કરે છે, એકદમ સમાન નકલોને સંકોચે છે,
અને જ્યારે માત્ર એક બાજુ સફળ થાય ત્યારે આંશિક પરિણામની જાણ કરે છે.
અમાન્ય `audioTranscript` ને કારણે પરિણામ એ આંશિક પરિણામ સુધી ઘટે છે — વિઝ્યુઅલ
વર્ણન જાળવવામાં આવે છે અને ઑડિયો શાખા સેનિટાઇઝ કરેલો નિષ્ફળતા કોડ નોંધે છે —
સમગ્ર વિડિયોને નિષ્ફળ કરવાને બદલે. દરેક શાખાની ઉપલબ્ધતા, આંશિક ફ્લૅગ,
અને સેનિટાઇઝ કરેલા નિષ્ફળતા કોડ વર્ણવેલા પરિણામમાં, ગાર્ડરેલ મેટાડેટામાં
(`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), પરિણામ-કૅશ મેટાડેટામાં અને બ્રિજ
ફ્યુઝન કાઉન્ટર્સમાં જાળવવામાં આવે છે. ડિફૉલ્ટ Video Bridge પાથ સ્પીચ-ટુ-ટેક્સ્ટ

તે માત્ર-વિડિયો જ રહે છે.

કૅશની કી આઉટપુટ બદલતા દરેક ઇનપુટ પર આધારિત છે — પ્રોમ્પ્ટ, અસરકારક
મોડલ, સૅમ્પલિંગ પૉલિસી, ફ્રેમ કાઉન્ટ, સિમેન્ટિક એનાલિસિસ મોડ, નોર્મલાઇઝ કરેલા ફોકસ હિન્ટની SHA-256
ફિંગરપ્રિન્ટ, ફોકસ વિન્ડો, `transcript`,
`audioTranscript` અને કૉન્ટેક્ટ-શીટ ફ્લૅગ — તેથી આ પૈકી કોઈપણ
પરિમાણ બદલવાથી કૅશ મિસ થાય છે, જૂના પરિણામનો ફરી ઉપયોગ ક્યારેય થતો નથી. વિઝ્યુઅલ ડિડુપ પૉલિસી
વર્ઝન, થ્રેશોલ્ડ અને મર્યાદિત કૅન્ડિડેટ-ફ્રેમ કાઉન્ટ પણ
રિઝલ્ટ-કૅશ કી અને મેટાડેટામાં સ્પષ્ટ છે; તેથી પૉલિસીમાં ફેરફાર જૂના
આખા-વિડિયો વર્ણનનો ફરી ઉપયોગ કરી શકતો નથી. રિઝલ્ટ-કૅશ v4 મેટાડેટા મોડ અને
ફિંગરપ્રિન્ટ રાખે છે, કાચું યુઝર ટાસ્ક ક્યારેય નહીં. ગાર્ડરેલ મેટાડેટા માગવામાં આવેલા અને અસરકારક—બંને
એનાલિસિસ મોડ રિપોર્ટ કરે છે; ઉપયોગી યુઝર ટેક્સ્ટ વિનાનો માગવામાં આવેલ `focused` મોડ
અસરકારક રીતે `full` તરીકે રિપોર્ટ થાય છે.

ગાર્ડરેલ દરેક સપોર્ટેડ વિડિયો પાર્ટ કાઢે છે, પરંતુ
`modalityBridgeVideoMaxVideos` કરતાં વધુનું વર્ણન કરતી નથી. જે ટાર્ગેટમાં
`supportsVideo === false` હોવાનું સાબિત થયું હોય, તેના માટે નિષ્ફળ અને મર્યાદાથી વધુ વિડિયો સ્પષ્ટ સુરક્ષિત
ટેક્સ્ટ માર્કરમાં પરિવર્તિત થાય છે, જેથી કોઈ કાચો વિડિયો બાકી ન રહે. જ્યારે ક્ષમતા અજ્ઞાત હોય, ત્યારે તે પાર્ટ
તેમનો વિડિયો કૅરિયર જાળવી રાખે છે; કોઈપણ ફૉલબૅક ટ્રાન્સક્રિપ્ટ ઉપરોક્ત મર્યાદિત ટેક્સ્ટ
કન્વર્ઝનનું પાલન કરે છે. `supportsVideo === true` ધરાવતા ટાર્ગેટ બ્રિજને બાયપાસ કરે છે.
ક્લાયન્ટ રિક્વેસ્ટનું અબૉર્ટ સિગ્નલ ડાઉનલોડ, બ્રોકર ક્યૂ,
સબપ્રોસેસ અને કૅપ્શન કૉલમાં આગળ પ્રસરે છે; અબૉર્ટ વિડિયો વચ્ચે પ્રક્રિયા અટકાવે છે અને કાચા મીડિયા તરફ ક્યારેય ફેઇલ-ઓપન
થતું નથી.

રનટાઇમ સેટિંગ્સ DB-બૅક્ડ અને Zod-વૅલિડેટેડ છે:

| કી                                  | ડિફૉલ્ટ     | શ્રેણી / વર્તન                                                                                            |
| ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | વૈકલ્પિક રનટાઇમ, પસંદગીથી સક્ષમ કરવાનું                                                                   |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` સામાન્ય કૅપ્શન્સ જાળવે છે; `focused` મર્યાદિત, અવિશ્વસનીય નવીનતમ-વપરાશકર્તા સંદર્ભનો ઉપયોગ કરે છે  |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge મોડેલ વારસામાં મેળવે છે                                                                     |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                      |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, અથવા પ્રમાણસર `segment_aware`; ડિટેક્ટર નિષ્ફળ જાય તો `uniform` પર પાછું ફરે છે |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                       |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                            |

120 સેકન્ડથી વધુના લેગસી સંગ્રહિત Video timeout મૂલ્યોને
બ્રોકરની સમયમર્યાદા સુધી મર્યાદિત કરવામાં આવે છે; તે મર્યાદાથી ઉપરના નવા સેટિંગ્સના લખાણો નકારવામાં આવે છે.
`GET /api/modality-bridge/video/runtime` ને પ્રમાણીકરણ અથવા રનટાઇમ પ્રોબિંગ પહેલાં વિશ્વસનીય રીતે સ્ટૅમ્પ કરેલી લૂપબૅક
લોકાલિટીની જરૂર પડે છે અને ત્યારબાદ મેનેજમેન્ટ
પ્રમાણીકરણની જરૂર પડે છે. તે માત્ર `available`, શુદ્ધ કરેલાં FFmpeg/ffprobe વર્ઝન્સ અને રનટાઇમ અનુપલબ્ધ હોય ત્યારે એક નિશ્ચિત
કારણ પરત કરે છે. આંતરિક એક્સ્ટ્રેક્શન એન્ડપૉઇન્ટ
જાહેર અપલોડ API નથી: ક્યૂ સંતૃપ્તિ `503` સાથે `Retry-After` પરત કરે છે, કૉલરનું
ડિસ્કનેક્ટ થવું `499` પરત કરે છે અને બ્રોકરની નિશ્ચિત સમયમર્યાદા `504` પરત કરે છે. રૂપાંતરિત પ્રતિસાદો Vision અથવા Audio સેગમેન્ટ્સ દૂર કર્યા વિના કેન્દ્રીય
`x-omniroute-modality-bridge` હેડરમાં
`video->text;model=<visionModel>;parts=<videos>` ઉમેરે છે.

### PII Masker (`piiMasker.ts`)

**બંને** તબક્કાઓ પર ચાલે છે.

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input` અને
  `prompt` (સાદી સ્ટ્રિંગ આઇટમ્સ સહિત)માંથી પસાર થાય છે અને સ્ટ્રિંગ `content`/`text` ફીલ્ડ્સ પર
  `processPII()` (`@/shared/utils/inputSanitizer`માંથી) લાગુ કરે છે. જ્યારે
  `PII_REDACTION_ENABLED=true` હોય, ત્યારે શોધાયેલ PII ને આઉટબાઉન્ડ
  પેલોડમાં ઢાંકવામાં આવે છે. આ `INPUT_SANITIZER_MODE`થી સ્વતંત્ર છે (જે માત્ર
  પ્રૉમ્પ્ટ-ઇન્જેક્શન નીતિને નિયંત્રિત કરે છે). જ્યારે ઢાંકવાનું બંધ હોય, ત્યારે કૉલ સામગ્રીને ફરી લખ્યા વિના
  શોધની સંખ્યાઓ નોંધે છે.
- **`postCall`** પ્રતિસાદને ડીપ-ક્લોન કરે છે અને
  Responses-API-આકારના માસ્કર (`maskResponsesOutput` — જે
  `output_text` અને `output[].content[].text`ને આવરી લે છે) સાથે `sanitizePIIResponse()` ચલાવે છે. જો કોઈ ઢાંકવાનું થાય, તો
  સંશોધિત પ્રતિસાદ મૂળ પ્રતિસાદને બદલે છે.

આ ગાર્ડરેલ ક્યારેય બ્લૉક કરતું નથી; તે માત્ર એનોટેટ (`meta.detections`,
`meta.redacted`) કરે છે અથવા ફરી લખે છે.

### Prompt Injection (`promptInjection.ts`)

વપરાશકર્તા દ્વારા પૂરી પાડવામાં આવેલી સામગ્રીમાં વિરોધાત્મક સંરચનાઓ શોધે છે અને ગોઠવેલી
નીતિ લાગુ કરે છે. વર્તન environment variables અને constructor
options દ્વારા સંચાલિત થાય છે:

| સેટિંગ          | Env var                                                                                               | ડિફૉલ્ટ | અસર                                                                                                                                                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| સક્ષમ           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | `false` હોય ત્યારે, ગાર્ડરેલ શૉર્ટ-સર્કિટ થાય છે.                                                                                                                                                                              |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (`redact` બૅકવર્ડ કમ્પેટિબિલિટી માટે સ્વીકારવામાં આવે છે, પરંતુ ઇન્જેક્શન ટેક્સ્ટ દૂર કરતું **નથી**; રિક્વેસ્ટ PIIનું પુનર્લેખન `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત થાય છે.) |
| બ્લૉક થ્રેશોલ્ડ | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | બ્લૉક કરવા માટે આવશ્યક લઘુત્તમ ગંભીરતા. ડિફૉલ્ટ રૂપે Medium માત્ર અવલોકન માટે છે.                                                                                                                                              |

**મોડની અગ્રતા** (`getMode`): કૉલર `options.mode` →
`INJECTION_GUARD_MODE` **DB ફીચર-ફ્લૅગ ઓવરરાઇડ** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. તેથી ડૅશબોર્ડ ઓવરરાઇડ env vars પર પ્રાધાન્ય મેળવે છે, જેથી Feature
Flags UI ચાલતા ગાર્ડને લાઇવ નિયંત્રિત કરે છે (પુનઃપ્રારંભ વગર). DB રીડ નિષ્ફળતા-સુરક્ષિત છે:
જો તેમાં ભૂલ થાય, તો ગાર્ડ env-આધારિત વર્તન પર પાછું ફરે છે અને જ્યારે કોઈ
ઓવરરાઇડ સેટ ન હોય ત્યારે વર્તન માત્ર-env રિઝોલ્યુશન જેવું જ રહે છે.

શોધના સ્રોતો:

1. `@/shared/utils/inputSanitizer`માંથી `sanitizeRequest()` (પાઇપલાઇનમાં
   અન્યત્ર વપરાતો શેર કરેલ ડિટેક્ટર સેટ).
2. બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને
   `markdown_system_block`, બંને `high` ગંભીરતાવાળા).
3. constructor options દ્વારા પાસ કરાયેલા વૈકલ્પિક `customPatterns` (સ્ટ્રિંગ્સ, regex,
   અથવા `{ name, pattern, severity }` રેકોર્ડ્સ).

જ્યારે `mode === "block"` હોય **અને** ઓછામાં ઓછી એક શોધ ગંભીરતાની
થ્રેશોલ્ડને પૂર્ણ કરતી હોય, ત્યારે `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` પરત કરે છે. `warn`/`log` મોડમાં ગાર્ડરેલ લૉગ કરે છે પરંતુ
કૉલને મંજૂરી આપે છે. શેર કરેલ સહાયક `evaluatePromptInjection()` પણ એવા
કૉલર્સ માટે એક્સપોર્ટ કરવામાં આવે છે જેમને રજિસ્ટ્રીમાંથી પસાર થયા વિના પ્રોમ્પ્ટ્સનું મૂલ્યાંકન કરવું હોય.

**સ્કૅન મર્યાદા (v3.8.20):** ડિટેક્ટર જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટના માત્ર **પ્રથમ 16 KB**નું
નિરીક્ષણ કરે છે — `src/shared/utils/inputSanitizer.ts`માં
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ્સ). પેટર્ન લૂપ ચલાવતા પહેલાં
`detectInjection()` અને `evaluatePromptInjection()` બંને
`slice(0, MAX_INJECTION_SCAN_BYTES)` કરે છે. ઇન્જેક્શન નિર્દેશો ઇનપુટની શરૂઆતની નજીક હોય છે, તેથી આ
શોધને નબળી પાડ્યા વિના અનેક-સો-KB પેલોડ્સ પર regex CPU/GCને મર્યાદિત કરે છે (જુઓ
#3932, #4041).

### ક્રેડેન્શિયલ માસ્કર (`credentialMasker.ts`)

ડિફૉલ્ટ ચેઇનમાં છેલ્લે (પ્રાથમિકતા `95`) રહીને **બંને** તબક્કાઓ પર ચાલે છે. આઉટબાઉન્ડ પેલોડમાંથી (મેસેજ
સામગ્રી, ટૂલ-કૉલ આર્ગ્યુમેન્ટ્સ, ટૂલ પરિણામો) **અને** પ્રોવાઇડરના પ્રતિસાદમાંથી
જાણીતી API-key / secret-token પેટર્ન્સને રીડેક્ટ કરે છે, જેથી પ્રોમ્પ્ટમાં પેસ્ટ કરેલું
ક્રેડેન્શિયલ (અથવા ટૂલ પરિણામ દ્વારા પાછું ઇકો થયેલું) અપસ્ટ્રીમ પ્રોવાઇડર અથવા
ક્લાયન્ટ સુધી લીક ન થાય.

- **માત્ર ઑપ્ટ-ઇન**, PII રીડેક્શન જેવી જ પરંપરા (હાર્ડ રૂલ #20ની નજીક):
  જ્યાં સુધી `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` ન હોય ત્યાં સુધી અક્ષમ રહે છે. તે બંધ હોય ત્યારે ગાર્ડરેલ કોઈ કાર્યવાહી કરતું નથી —
  તે ક્યારેય બ્લૉક કરતું નથી અને ક્યારેય ફરી લખતું નથી.
- `redactCredentials()` સંપૂર્ણ પેલોડ/પ્રતિસાદ ટ્રીમાં ટ્રાવર્સ કરે છે (`walkValue()`,
  પ્રોટોટાઇપ-પોલ્યુશનથી સુરક્ષિત, `WeakSet` દ્વારા સાઇકલથી સુરક્ષિત) અને મેળ ખાતી સામગ્રીને
  `[REDACTED:<type>]` પ્લેસહોલ્ડરથી બદલે છે, તેમજ ફક્ત ખરેખર બદલાયેલી શાખાઓને જ
  ક્લોન કરે છે.
- `CREDENTIAL_PATTERNS` LLM પ્રોવાઇડર કીઝ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ટોકન્સ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), પેમેન્ટ કીઝ (Stripe, Square), ક્લાઉડ
  કીઝ (AWS access key, Twilio, SendGrid, Mailgun), પ્રાઇવેટ કીઝ / JWTs,
  ક્રેડેન્શિયલ ધરાવતી કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને
  સામાન્ય `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-વેલ્યુ
  પેટર્નને આવરી લે છે. હેડર જેવા આકારની કીઝ (`authorization`, `x-api-key`, `api-key`,
  `apikey`)ને સામાન્ય ટેક્સ્ટ regex દ્વારા નહીં પરંતુ માળખાકીય રીતે રીડેક્ટ કરવામાં આવે છે (ફક્ત વેલ્યુ,
  `Bearer `/`Basic ` જેવા સ્કીમ પ્રિફિક્સ જાળવી રાખવામાં આવે છે).
- ગાર્ડરેલ ક્યારેય બ્લૉક કરતું નથી; તે ફક્ત ફરી લખે છે (`modifiedPayload` /
  `modifiedResponse`) અને ઍનોટેટ કરે છે (`meta.credentialsRedacted`, `meta.count`).

રિગ્રેશન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## મૂળભૂત કરાર (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને તરત જ અટકાવે છે
  message?: string; // અવરોધિત કરતી વખતે દર્શાવવામાં આવે છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિસાદને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં"નો સંકેત આપે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ચેઇનમાં આગળના ગાર્ડરેલ્સ તરફ વહેતું મૂલ્ય બદલાઈ જાય છે.
`signal?: AbortSignal` કૉલરની લાઇફસાઇકલને ગાર્ડરેલ્સ સુધી લઈ જાય છે. વિનંતી રદ થવી એ ઇરાદાપૂર્વકનો fail-open અપવાદ છે: મીડિયા બ્રિજ કામ અટકાવે છે અને જે લક્ષ્ય તેને સપોર્ટ કરતું નથી તે જાણીતું હોવા છતાં તેમાં મૂળ મીડિયા પુનઃસ્થાપિત કર્યા વિના ક્લીનઅપ કરે છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` નીચેની સુવિધાઓ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેલ ઉમેરે છે (અથવા સામાન્યકૃત નામ દ્વારા બદલે છે) અને
  ચઢતા `priority` મુજબ ફરીથી ગોઠવે છે.
- `clear()` / `list()` — વહીવટી સહાયકો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેલ્સ પર ક્રમશઃ ફરે છે, પેલોડને
  `modifiedPayload` મારફતે આગળ ધપાવે છે અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિસાદની બાજુએ સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્વચ્છ ટેસ્ટ અલગીકરણ માટે સ્ટેટ સાફ કરે છે અને વૈકલ્પિક રીતે
  ડિફૉલ્ટ્સને ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }`
પરત કરે છે, જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સની એરે છે, જેમાં
દરેક ગાર્ડરેલ માટેના `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સમાવિષ્ટ હોય છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### દરેક વિનંતી માટે ગાર્ડરેલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન
વિનંતી માટે છોડવામાં આવનાર ગાર્ડરેલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
સ્ત્રોતો (બધા વૈકલ્પિક, બધા મર્જ કરવામાં આવે છે):

- `apiKeyInfo.disabledGuardrails`
- વિનંતી બોડીનું `disabledGuardrails` (ટોચના સ્તરે)
- વિનંતી બોડીનું `metadata.disabledGuardrails`
- હેડર `x-omniroute-disabled-guardrails` (અથવા જૂનું
  `x-disabled-guardrails`)

મૂલ્યો સ્ટ્રિંગ્સની એરે અથવા કૉમાથી અલગ કરેલી સ્ટ્રિંગ હોઈ શકે છે; નામોને
લોઅરકેસ kebab-caseમાં સામાન્યકૃત કરવામાં આવે છે (`pii_masker` → `pii-masker`). પરિણામ
`context.disabledGuardrails` મારફતે રજિસ્ટ્રીને આપવામાં આવે છે, જે
મેળ ખાતા ગાર્ડરેલ્સને છોડી દે છે (`results`માં `skipped: true`).

## અમલીકરણ ક્રમ

`src/sse/handlers/chat.ts` અને
`open-sse/handlers/chatCore.ts`માંથી પસાર થતી દરેક વિનંતી માટે:

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ સૂચિ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ચડતા પ્રાથમિકતા ક્રમમાં ગાર્ડરેલ્સ ચલાવે છે:
   - અક્ષમ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall`, `modifiedPayload` મારફતે પેલોડને ફરી લખી શકે છે.
   - પ્રથમ `block: true` ચેઇનને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર
     ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવિત રીતે ફરી લખાયેલો) પેલોડ કોમ્બો રાઉટિંગ અને અપસ્ટ્રીમ
   ડિસ્પેચમાં જાય છે.
4. પ્રતિસાદ તૈયાર થયા પછી, `guardrailRegistry.runPostCallHooks(...)`
   પ્રતિસાદ પર એ જ ચેઇન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ
   પ્રતિસાદને કાઢી નાખે છે.

જે ગાર્ડરેલ્સ અપવાદ ફેંકે છે તે `error: <message>` સાથે નોંધાય છે અને
`logger.warn` મારફતે લૉગ થાય છે, પરંતુ ચેઇન ચાલુ રહે છે — ડિઝાઇન મુજબ ફેઇલ-ઓપન.

## રૂપરેખાંકન

બિલ્ટ-ઇન ગાર્ડરેલ્સ દ્વારા વાંચવામાં આવતા એન્વાયર્નમેન્ટ વેરિએબલ્સ:

| વેરિએબલ                               | આના દ્વારા વપરાય છે        | અસર                                                                                                             |
| ------------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | શોધને સંપૂર્ણપણે અક્ષમ કરવા માટે `false` સેટ કરો.                                                               |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | ઇન્જેક્શન નીતિ: `warn`, `block`, અથવા `log`. લેગસી મૂલ્ય `redact` ઇન્જેક્શન ટેક્સ્ટને ફરીથી લખતું નથી.          |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | ઇન્જેક્શન ગાર્ડ માટેનો મોડ; આ DB ફીચર ફ્લેગ પણ છે, જે એન્વાયર્નમેન્ટ વેરિએબલ્સને **ઓવરરાઇડ** કરે છે (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` દ્વારા અસ્વીકાર થવા માટેની ન્યૂનતમ ગંભીરતા: `high` (ડિફૉલ્ટ), `medium`, અથવા `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` માટેનો લેગસી ઉપનામ.                                                           |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | જ્યારે `true` હોય, ત્યારે વિનંતીમાં રહેલી PII રિડેક્ટ થાય છે (ઇન્જેક્શન મોડથી સ્વતંત્ર).                        |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ડાઉનસ્ટ્રીમ) | પ્રતિસાદ-બાજુના માસ્કરની વર્તણૂકને નિયંત્રિત કરે છે.                                                            |

`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, અને

`modalityBridgeVideoMaxVideos`, અને
`modalityBridgeVideoTimeout`, તેમજ શેર કરેલ `modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે.
તે ડિફૉલ્ટ રૂપે અક્ષમ છે કારણ કે FFmpeg/ffprobe વૈકલ્પિક ઓપરેશનલ
ડિપેન્ડન્સીઝ છે અને ફ્રેમ કૅપ્શનિંગ લેટન્સી અને મોડેલ ખર્ચ વધારે છે.

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail`ને વિસ્તૃત કરતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે નોંધણી કરો (`registerDefaultGuardrails`માંથી પુશ કરો) અથવા
   રનટાઇમ પર `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન સામાન્યકૃત
   નામ ધરાવતા કોઈપણ અગાઉના ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ પરીક્ષણો ઉમેરો (હાલનાં ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

જાણીતી સ્થિતિથી શરૂઆત કરવા માટે પરીક્ષણો વચ્ચે `resetGuardrailsForTests()`નો ઉપયોગ કરો.
ખાલી રજિસ્ટ્રીથી શરૂઆત કરવા માટે `{ registerDefaults: false }` પાસ કરો અને
માત્ર પરીક્ષણ હેઠળના ગાર્ડરેલ્સની નોંધણી કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન (`deps.getSettings`, `deps.callVisionModel`) સ્વીકારે છે; Audio Bridge
સેટિંગ્સ, ક્ષમતાઓ, STT મોડેલ પસંદગી, ક્રેડેન્શિયલ તપાસો અને ટ્રાન્સક્રિપ્શન માટે
સમકક્ષ સીમ્સ ઉપલબ્ધ કરાવે છે. તેથી પરીક્ષણો DB અથવા નેટવર્ક ઍક્સેસ વિના બંને
પ્રવાહોને ચકાસી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લૉક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) વપરાશકર્તા પ્રોમ્પ્ટ્સ
સ્વીકારતા તમામ રૂટ્સને આવરી લે છે. તે `INJECTION_GUARD_MODE`નું પાલન કરે છે (ડિફૉલ્ટ
`warn` = ફક્ત લૉગ; `block` = HTTP 400 `SECURITY_001` પરત કરે છે).

| પ્રકાર           | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલનું) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ          | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ નિષ્કર્ષણ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ને આવરી લે છે.

**રેડ-ટીમ (દરરોજ રાત્રે, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે દરેક રૂટ
`INJECTION_GUARD_MODE=block`માં OWASP-LLM કોર્પસને બ્લૉક કરે છે; garak પ્રોબ્સ ચલાવે છે
(સિક્રેટ વિના સ્કિપ કરે છે). સુસંગતતા માટે `moderations`નો સમાવેશ કરવામાં આવ્યો છે —
બ્લૉક-મોડમાં ઑપરેટર્સ `resolveDisabledGuardrails` મારફતે તેને મુક્તિ આપી શકે છે.

રાત્રિકાલીન વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ)માં બે જૉબ્સ છે:

- **`promptfoo-guard` (બ્લૉકિંગ)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ (દા.ત. "અગાઉની
  તમામ સૂચનાઓ અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે પ્રતિસાદમાં
  `error.code === "SECURITY_001"` હોય, એટલે કે ગાર્ડે વિનંતીને ખરેખર નકારી હતી.
- **`garak` (સલાહકારી)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ
  (`http://localhost:20128/v1`) સામે garak `--probes promptinject,dan,leakreplay`
  ચલાવે છે. તે પ્રોવાઇડર સિક્રેટ (`PROMPTFOO_PROVIDER_KEY`) પર આધારિત છે; સિક્રેટ
  ન હોય તો સરળતાથી સ્કિપ કરે છે અને તેની પાછળ `|| true` જોડાયેલું છે, તેથી તે CIને
  નિષ્ફળ કર્યા વિના રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`)નું કવરેજ પ્રોમ્પ્ટ ધરાવતા
દરેક `/v1` રૂટ સુધી વિસ્તરે છે; પ્રોમ્પ્ટ ટેક્સ્ટને
`src/shared/utils/inputSanitizer.ts`માંના `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`માંથી
લેવામાં આવે છે.
