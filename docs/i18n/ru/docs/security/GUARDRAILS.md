> **Источник истины:** `src/lib/guardrails/`
> **Последнее обновление:** 2026-08-29 — v3.8.51 (Происхождение стенограммы Video Bridge объявляется вызывающей стороной,
> еще не проверено сервером — уточнено согласно #11661)

Защитные механизмы (guardrails) обеспечивают безопасность, соблюдение политик и преобразования контента на границе между OmniRoute и вышестоящими провайдерами. Каждый защитный механизм может проверять (и опционально отклонять, преобразовывать или аннотировать) полезные данные запросов (`preCall`) и ответы вышестоящих систем (`postCall`).

Система является **открытой при сбое (fail-open)**: если защитный механизм выдает ошибку во время выполнения, реестр записывает ошибку и продолжает работу со следующим защитным механизмом, вместо того чтобы отклонять запрос. Блокировка — это явное решение (`block: true`), а не случайность.

## Встроенные защитные механизмы

При импорте реестр автоматически загружает шесть защитных механизмов в порядке приоритета
(см. `registry.ts` → `registerDefaultGuardrails()`):

| Приоритет | Имя                 | Этап(ы)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Меньшие значения приоритета выполняются **первыми**.

### Мост компьютерного зрения (`visionBridge.ts`) — мост модальностей PR-1

Перехватывает запросы с изображениями, направленные к **моделям без поддержки компьютерного зрения**, и либо
перенаправляет весь запрос к модели с поддержкой компьютерного зрения, либо заменяет части
с изображениями текстовыми описаниями, созданными настраиваемой моделью компьютерного зрения, до
вызова вышестоящего сервиса. Благодаря этому провайдеры, работающие только с текстом, могут прозрачно обрабатывать
мультимодальные полезные нагрузки.

Последовательность:

1. Пропустить обработку, если целевая модель уже поддерживает компьютерное зрение (если только она не входит в
   список принудительного применения моста `isVisionBridgeForcedModel`).
2. Извлечь части с изображениями через `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), которая делегирует работу **унифицированному детектору
   медиаданных** `detectMediaParts()` в `open-sse/utils/mediaParts.ts` — единственному
   источнику истины, совместно используемому с фильтром совместимости combo.
   Извлечение ограничено разрешённым списком частей верхнего уровня тех форм,
   которые `replaceImageParts` может вставить обратно (контракт извлечения↔замены): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` и Responses API `input_image`. Вложенные совпадения и
   формы, содержащие только индикаторы, относятся к материалу combo-фильтра и никогда не извлекаются.
   Пропустить обработку, если ничего не найдено.
3. Определить конфигурацию среды выполнения через `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): новые ключи настроек `modalityBridge*`
   имеют приоритет; устаревшие ключи `visionBridge*` остаются в качестве **резервного варианта на
   один цикл** (окно отката). Если мост отключён, пропустить обработку до любого обхода медиаданных.
4. Селектор режима (`modalityBridgeVisionMode`, см. таблицу ниже) выбирает
   перенаправление или описание. При перенаправлении возвращается `modifiedPayload`, в котором заменено только
   поле `model`, а также метаданные `{ rerouted, fromModel, toModel, imagesKept }`.
5. Путь описания: ограничить количество изображений значением `maxImages`, составить учитывающую задачу подсказку,
   проверить кэш описаний, вызвать модель компьютерного зрения **параллельно**
   (`Promise.allSettled`) и вставить вместо изображений текстовые части `[Изображение N]: <описание>`.
   Если создание описания завершилось ошибкой, возвращается `null`, а исходная часть с изображением
   **сохраняется** (#4012) — кроме пути описания combo, когда не удалось создать ни одного
   описания: в этом случае для подтверждённо не поддерживающего компьютерное зрение вышестоящего сервиса используется
   заглушка `(недоступно — не подключён ни один провайдер с поддержкой компьютерного зрения)` (#8430).
6. Вернуть `modifiedPayload` + метаданные (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режима (`modalityBridgeVisionMode`)

| Режим      | По умолчанию | Поведение                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔            | Устаревшая эвристика без изменений (#6640/#7204): модели, не относящиеся к combo, и модели `auto/` перенаправляются к лучшей модели компьютерного зрения, если у исходной модели нет пригодных учётных данных (если есть — создаётся описание); для целей combo всегда создаётся описание.                                                                                                        |
| `describe` |              | Всегда создавать описание — блок перенаправления полностью пропускается; ответ всегда даёт выбранная пользователем модель.                                                                                                                                                                                                                                                                        |
| `reroute`  |              | Принудительное перенаправление: проверка сохранения модели с учётными данными обходится. Проверка учётных данных **целевой модели** перенаправления по-прежнему применяется — если подходящая целевая модель компьютерного зрения отсутствует, запрос переходит к созданию описания, чтобы необработанные изображения никогда не попадали в серверную часть, работающую только с текстом (#8430). |

Принудительные режимы завершают выбор **до** запуска автоматической эвристики; поведение `auto`
побайтово идентично защитному механизму до PR-1.

#### Область действия API-ключа (`visionBridgeKeyScope.ts`)

Когда API-ключ вызывающей стороны ограничивает `allowedConnections`, пулы квот
(`allowedQuotas`) или модели (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), мост выбирает только
доступные этому ключу модели перенаправления и описания в доступных этому ключу
подключениях. Затем вызов описания всегда проходит через внутренний цикл OmniRoute с
заголовком `x-omniroute-self-loop-key-id`, чтобы принимающий чат-запрос
повторно применил политику подключений и моделей этого ключа. `enforceApiKeyPolicy()`
учитывает этот заголовок только вместе с bearer-токеном внутреннего цикла, поэтому он может лишь
сужать доступ, а идентификатор, который невозможно разрешить, отклоняется.

Если ключу не разрешена ни одна модель компьютерного зрения, путь описания не вмешивается,
и запрос проходит без изменений — такое же отказоустойчивое поведение, как у отключённого
защитного механизма (метаданные `{ skipped: true, reason: "no_permitted_vision_model" }`).
Запросы без ключа и ключи без этих ограничений работают точно так же,
как и раньше.

#### Учитывающая задачу подсказка для описания (`modalityBridgeVisionTaskAware`)

По умолчанию **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) добавляет
текст **последнего сообщения пользователя** (обрезанный до 500 символов) к базовому
промпту описания, направляя описание на то, о чём на самом деле спросил пользователь
(паттерн codex-vision-proxy), и просит визуальную модель транскрибировать видимый
текст. Если флаг отключён или пользовательский текст отсутствует, базовый промпт
используется без изменений.

Собственный OpenAI-совместимый запрос цикла самоописания (`callVisionModelSingle()`
в `visionBridgeHelpers.ts`) всегда запрашивает `image_url.detail: "high"` —
безусловно, для каждого вызывающего кода/провайдера и независимо от любых сигналов
клиента. Выборка с низкой детализацией ухудшает точность OCR именно для задачи
транскрибирования текста, которую задаёт этот промпт, поэтому сам вызов описания
всегда запрашивает высокую детализацию независимо от того, какой уровень детализации
использовался в исходном входящем запросе. Это влияет только на тело внутреннего
запроса описания; способ, которым OmniRoute передаёт собственное значение
`image_url.detail` вызывающей стороны в основном запросе, не изменяется — значение
по умолчанию применяется отдельно и только для обнаруженных клиентов OpenCode в
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Ветвь цикла
самоописания с форматом обмена Anthropic не имеет поля `detail` и не затрагивается
ни одним из этих значений по умолчанию.

#### Ограничение вывода описания (`modalityBridgeVisionMaxChars`)

| Ключ                           | По умолчанию | Диапазон          |
| ------------------------------ | ------------ | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` или 100–50000 |

`0` (по умолчанию) означает **без ограничения** — описание, возвращаемое
`callVisionModel()`, передаётся без изменений, сохраняя существующее
поведение. Любое значение в диапазоне 100–50000 обрезает описание с добавлением
суффикса `…` перед его вставкой обратно в виде `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`).
Увеличивайте это значение для насыщенных деталями задач OCR, в которых последующей
модели нужна полная транскрипция; уменьшайте его, чтобы ограничить расход токенов
разговорчивыми визуальными моделями. Поле панели управления находится в разделе
Advanced вкладки Vision (`modality-bridge-max-chars` в
`ModalityBridgeVisionTab.tsx`) и повышает любое значение от 1 до 99 до минимального
порога 100, оставляя явно заданный `0` без изменений — `0` сам по себе является
допустимым значением Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто
значением по умолчанию для состояния «не задано».

#### Кэш описаний (`modalityBridge/bridgeCache.ts`)

Внутрипроцессный кэш LRU + TTL для результатов описания, общий для всего процесса.
Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` с
префиксами длины (без коллизий на границах полей). Компонент модели — это
**настроенная** модель моста, а не модель, которая фактически ответила:
`callVisionModel` может внутренне переключиться на резервный вариант, а создание
ключа для каждой попытки фрагментировало бы кэш. Неудачные описания никогда не
кэшируются. Настройки:

| Ключ                            | По умолчанию | Диапазон |
| ------------------------------- | ------------ | -------- |
| `modalityBridgeCacheEnabled`    | `true`       | —        |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000  |

#### Нормализация удалённых изображений (самоописание/получение base64)

Когда мост самостоятельно получает **удалённое** изображение — при самовызове
описания Anthropic и преобразовании в base64 для формата обмена Claude
(`ensureBase64ImagesForClaudeWire`), в обоих случаях через
`fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts`, — полученный URI данных
перед встраиванием в запрос к визуальной модели пропускается через
`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`). Слишком большие
изображения уменьшаются до **2048px по длинной стороне** (что соответствует
ограничению изменения размера, уже применяемому OpenAI/Anthropic на стороне
сервера), сокращая объём загружаемых данных и задержку без изменения того, что
видит визуальная модель. Для изменения размера используется `sharp`, загружаемый
через динамический импорт: на платформе, где не удаётся загрузить его нативный
бинарный файл, `normalizeDataUri()` **никогда не выбрасывает исключение** — вместо
этого он без изменений пропускает исходные байты, поэтому путь
описания/преобразования в base64 продолжает работать. Байты, не являющиеся
изображением (если запрос не вернул декодируемое изображение), также передаются
без изменений. Эта нормализация применяется только к изображениям, которые мост
получает для собственного самовызова, и никогда не применяется к необработанной
полезной нагрузке вызывающей стороны, что соответствует принципу внесения
изменений только при явном согласии (жёсткое правило №20).

#### Схема настроек + миграция

Новые ключи `modalityBridge*` проверяются Zod в `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, тройка `modalityBridgeCache*` и группа
`modalityBridgeAudio*`, используемая Audio Bridge. Миграция
`141_modality_bridge_settings.sql` копирует существующие устаревшие значения
`visionBridge*` в соответствующие новые ключи (идемпотентно, никогда не
перезаписывая значение `modalityBridge*`, заданное оператором); устаревшие ключи
продолжают приниматься как резервный вариант чтения в течение одного цикла
выпуска.

#### Заголовок прозрачности + статистика

Преобразованные посредством описания ответы содержат
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(формируется `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`,
добавляется `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`).
Перенаправленные запросы **не** получают заголовок — полезная нагрузка не
изменялась, а замена модели уже видна в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (управленческая аутентификация, тот же уровень, что и у
`GET /api/settings`) возвращает хранящиеся в памяти счётчики для каждой модальности
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` и
`video`. В качестве знаменателя `averageLatencyMs` использует `latencySamples`,
а не общее количество попыток; операция без замера времени не создаёт
фиктивный образец с нулевой задержкой. `bridged` остаётся обратно совместимым
псевдонимом для успешных преобразований; неудачные попытки не увеличивают его.
Счётчики намеренно сбрасываются при перезапуске процесса
(это телеметрия, а не учёт).

#### Конфигурация панели управления

Отдельная страница панели управления доступна по адресу
`/dashboard/settings/modality-bridge`. Её адресуемые через URL вкладки `Vision`, `Audio`
и `Video` сохраняют параметры запроса при изменении значения `tab`.
Вкладка Vision позволяет включать функцию, выбирать режим и модель (включая
автоматически выбираемую модель по умолчанию), настраивать подсказки с учётом задачи,
расширенные ограничения на тайм-аут, изображение, длину описания и кеш,
просматривать счётчики времени выполнения и выполнять защищённый тестовый запрос.
Вкладка Audio также работает: она позволяет включать функцию, выбирать только STT-модели,
включая Auto, задавать ограничения на тайм-аут и максимальную длительность клипа,
просматривать счётчики аудио и выполнять тест с `input_audio`. Вкладка Video
функциональна: она сообщает о состоянии среды выполнения FFmpeg/ffprobe — одном из
четырёх явных состояний интерфейса (`unknown`, пока проверка выполняется или если её
не удалось завершить; `restricted`, если панель управления открыта не на loopback-хосте
и проверка пропущена на стороне клиента; `unavailable`, если проверка завершена
и подтвердила отсутствие инструментов; либо `available` с версиями FFmpeg/ffprobe),
сохраняет настройки включения, модели, кадров, видео и тайм-аута, ограничивает
список моделей моделями с поддержкой зрения и отображает счётчики видео.

Прежняя карточка Vision Bridge в настройках ИИ теперь служит ссылкой совместимости
на новую страницу; она больше не содержит вторую копию формы. Раздел Media Providers
также связывает рабочие процессы Image-to-Text и Speech-to-Text с соответствующими
вкладками Modality Bridge, не удаляя существующую тестовую площадку Speech-to-Text.

**Обход контроля допуска для self-loop:** когда вызов описания направляется через
собственный `/v1` self-loop OmniRoute (модель нестандартного провайдера), подзапрос
отправляет `x-omniroute-admission-bypass: internal` и проходит аутентификацию с
использованием разрешённых учётных данных self-loop — локального маркера
`sk_omniroute` в локальном режиме либо настроенного оператором ключа окружения
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), чтобы развёртывания с
`REQUIRE_API_KEY=true` по-прежнему могли выполнять вызов описания. Обход
разрешается только для этих точных учётных данных, поэтому внешние клиенты не могут
использовать заголовок для пропуска контроля допуска.

Устаревшие значения по умолчанию находятся в `src/shared/constants/visionBridgeDefaults.ts`;
новые значения по умолчанию для режима, учёта задачи и кеша, а также средство разрешения
настроек находятся в `src/shared/constants/modalityBridgeDefaults.ts`. Защитный механизм
предоставляет параметр конструктора `deps`, чтобы тесты могли внедрять фиктивные
реализации `getSettings` и `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает содержащие аудио запросы чата до того, как они достигнут целевого
объекта, который не поддерживает аудиоввод согласно имеющимся данным. Запрос чата
никогда не перенаправляется: аудиочасти транскрибируются через существующую
OpenAI-совместимую multipart-конечную точку, после чего выбранная модель чата
продолжает работу с текстовыми транскрипциями.

Порядок работы:

1. Разрешить `supportsAudio` через `getResolvedModelCapabilities()`. Явные
   метаданные реестра провайдеров имеют приоритет, за ними следуют статические
   метаданные модели, а затем синхронизированные `modalities_input`. Объявленный
   список входных данных без `audio` даёт `false`; при полном отсутствии сведений
   о возможностях остаётся `null`. И `false`, и `null` активируют консервативный
   мост, тогда как `true` обходит его.
2. Разрешить настройки `modalityBridgeAudio*` и извлечь из каждого сообщения
   допускающие замену аудиочасти верхнего уровня с помощью общего детектора
   `detectMediaParts()`. Поддерживаемые форматы передачи: OpenAI `input_audio`,
   `audio_url` и `source.media_type: "audio/*"`. Вложенное аудио обнаруживается
   для маршрутизации, но не удаляется путём замены. Объём работы ограничивается
   значением `modalityBridgeAudioMaxClips`; последующие части остаются без изменений.
3. Использовать настроенное значение `provider/model` или позволить
   `selectAudioBridgeModel()` последовательно перебрать `AUDIO_TRANSCRIPTION_PROVIDERS`
   в стабильном порядке каталога и выбрать первую модель с пригодными активными
   учётными данными провайдера.
4. `callAudioTranscription()` преобразует аудио в формате base64/data-URI в
   multipart-файл `file` либо загружает удалённый `audio_url` через защитный механизм
   исходящих подключений, разрешающий только публичные адреса, с фиксацией DNS
   и ограничением в 25 МБ. Затем он отправляет POST-запрос с файлом и выбранной
   моделью в локальный self-loop `/v1/audio/transcriptions`, аутентифицированный
   с помощью `resolveSelfLoopBearer()`. Существующий маршрут транскрибирования
   выполняет обычный поиск учётных данных, обработку периода ожидания и ограничения
   частоты запросов, а также перенаправление провайдеру.
5. При успешных вызовах соответствующие части заменяются на
   `[Audio N]: <transcript>`. Вызовы выполняются через `Promise.allSettled`:
   отдельный сбой сохраняет исходную аудиочасть (контракт #4012). Если все вызовы
   завершаются сбоем и для целевого объекта доказано `supportsAudio === false`,
   части заменяются на
   `[Audio N]: (недоступно — не подключён ни один STT-провайдер)` (контракт #8430).
   Для неизвестного целевого объекта (`null`) при сбое всех вызовов содержимое
   остаётся без изменений. Целевой объект, для которого доказано, что он поддерживает
   только текст, при отсутствии пригодных учётных данных STT получает ту же явную
   заглушку без выполнения сетевого вызова.

Успешные транскрипции используют общий для процесса LRU/TTL-кеш Modality Bridge.
Ключ объединяет ссылку на аудио, стабильную метку операции `audio-transcription`
и выбранную STT-модель; ошибки никогда не кешируются. Попытки обработки аудио
обновляют общие счётчики `bridged`, `cacheHits`, `failures` и `lastUsedAt`.
Преобразованные ответы содержат
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; запросы,
оставленные без изменений, не получают сегмент Audio Bridge.

Настройки времени выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                          | По умолчанию | Диапазон        |
| ----------------------------- | ------------ | --------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —               |
| `modalityBridgeAudioModel`    | `""`         | Авто или ID STT |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10            |

Общий кеш по-прежнему управляется параметрами `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`.

### Мост для видео (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает видеочасти верхнего уровня в `messages` API Chat Completions и
`input` API Responses перед вызовом целевой модели, для которой не заявлена
встроенная поддержка видео. Поддерживаются форматы `input_video`, `video_url`,
`video_source`, URL-адреса HTTPS и URI данных `data:video/*;base64,...`.
Простые имена файлов в тексте не считаются видео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за обход запроса,
проверку возможностей и политик, агрегацию в рамках запроса и полезную нагрузку
ответа. Работа с каждым видео — получение данных, кеширование всего результата,
описание последовательности кадров (с объединением с указанной вызывающей
стороной расшифровкой аудио), а также метрики, прерывание и очистка для каждой
попытки — скрыта за `processVideoPart` в `videoBridgePipeline.ts`, которая
вызывается один раз для каждой видеочасти в цикле `preCall`. Этот модуль также
определяет явные границы портов `VideoMediaBrokerPort` (получение байтов и
извлечение выбранных кадров), `VideoAudioTranscriptionPort` (объединение
указанной вызывающей стороной расшифровки аудио с подписями выбранных кадров) и
`VideoDrilldownPort` (граница сохранения данных детального анализа кадров; пока
не подключена к `processVideoPart` — в настоящее время записи детального анализа
создаёт только отдельный маршрут `/api/modality-bridge/video/drilldown`).

Публичный путь запросов `/v1` никогда не импортирует и не запускает подпроцесс.
Удалённые видео загружаются с ограничением в 50 МиБ; для встроенных видео в
формате base64 установлен консервативный лимит декодированного размера в 36 МиБ
на одно видео, чтобы оболочка модели, сообщений и фрейминга не превышала
публичный лимит приёма JSON-запросов в 50 МиБ. Длина встроенных данных и оценки
размера после декодирования проверяются до выделения памяти. HTTPS обязателен как
для исходного удалённого URL-адреса, так и для каждого перенаправления; при этом
используется существующее ограничение исходящих подключений только к публичным
адресам с фиксацией DNS. Затем байты передаются через строго определённую
внутреннюю границу брокера `POST /api/modality-bridge/video/extract`. Этот маршрут
одновременно имеет характеристики `LOCAL_ONLY` и `SPAWN_CAPABLE`, принимает
только аутентифицированный на уровне процесса запрос через доверенный loopback-
интерфейс и никогда не принимает URL-адрес, путь файловой системы, исполняемый
файл или список аргументов. Конвейер ограничения размера тела API и инкрементный
считыватель тела обработчика независимо друг от друга обеспечивают соблюдение
лимита входных данных брокера в 50 МиБ. Его ограниченная очередь выполняет одно
извлечение за раз, допускает четыре ожидающих задания и ограничивает общий объём
ожидающих входных данных значением 100 МиБ.

Внутри брокера `ffprobe` читает закрытый локальный файл; фиксированный список
разрешённых форматов исключает форматы плейлистов и манифестов. Для разрешённых
контейнеров семейства MOV внешние ссылки на данные MOV по умолчанию остаются
отключёнными, и фиксированная команда не включает их использование. Как
`ffprobe`, так и `ffmpeg` используют список разрешённых протоколов, содержащий
только `file`, один поток, фиксированные массивы аргументов, работают без
оболочки, а исполняемые файлы разрешаются через `PATH`. Потоки обложек,
представленные прикреплёнными изображениями, не считаются воспроизводимыми
кандидатами. Все воспроизводимые потоки должны соответствовать ограничениям;
явно заданный поток по умолчанию имеет приоритет перед детерминированным выбором
потока с наименьшим индексом. Продолжительность видео ограничена 600 секундами,
размер каждого измерения — 8 192 пикселями, а исходное количество пикселей —
33 554 432. FFmpeg выбирает 1–16 промежуточных JPEG-кадров, уменьшает длинную
сторону максимум до 1 024 пикселей без увеличения меньших исходных изображений и
никогда не получает URL-адрес. По умолчанию используется стратегия выборки
`uniform`. Необязательная стратегия `scene_aware` и экспериментальная стратегия
`segment_aware` выполняют один дополнительный фиксированный проход FFmpeg по уже
проверенному локальному потоку, выбирают ограниченный набор временных меток сцен
`showinfo` и детерминированно возвращаются к тем же равномерно распределённым
промежуточным точкам в случае сбоя или тайм-аута детектора, некорректного вывода
либо пустого набора кандидатов. В режиме с учётом сегментов промежуточные выборки
распределяются пропорционально длительности проверенных интервалов сцен;
свидетельства для режима с учётом сегментов и поведение при откате подробно
описаны ниже. Жёсткое ограничение в 16 кадров применяется после отбора при любой
стратегии. Если для запроса с учётом сцен предусмотрен бюджет только в один кадр,
используется равномерная промежуточная точка активного окна полного видео или
окна фокусировки, а в отчёте указывается `policyEffective: uniform`: один
выбранный кадр сцены не позволяет сохранить оба временных края. Вызывающая
сторона может при необходимости указать конечное окно фокусировки (`start`/`end`
в секундах); границы ограничиваются продолжительностью медиаданных, окна с
обратным порядком границ или неконечными значениями отклоняются, а все стратегии
выборки применяются только внутри нормализованного интервала. Полученное окно
включается в метаданные выборки и в префикс недоверенного описания, чтобы
последующие модели могли отличить выбранный фрагмент от полной временной шкалы.

Семантическая фокусировка подписей — отдельная явная настройка. Режим анализа
`full`, используемый по умолчанию, сохраняет существующую подсказку для кадров и
никогда не передаёт текст запроса модели создания подписей. В режиме `focused`
мост считывает только последний непустой пользовательский `text`/`input_text` из
того же контейнера Chat или Responses, нормализует его в NFC, заменяет
управляющие символы и последовательности пробельных символов и ограничивает
длину 500 кодовыми точками Unicode. Пустой результат приводит к возврату к
точной подсказке `full`. Пригодная подсказка сериализуется в формате JSON в
отдельном блоке недоверенного пользовательского контекста и может только
определять приоритет наблюдаемых деталей; она не может отменить отдельное
предупреждение о запрете следовать инструкциям, видимым или слышимым в
медиаданных. Текстовая фокусировка никогда не выводит значения `start`/`end` и не
изменяет временную выборку.

#### FU-07 — структурные свидетельства сегментов

`segment_aware` использует один ограниченный проход предварительного анализа уже проверенного локального видеопотока. Фиксированная цепочка фильтров сначала масштабирует видео до ширины не более 320 пикселей, обнаруживает смены сцен и интервалы с замершим изображением, а затем выполняет выборку с частотой 1 кадр в секунду для оценки размытия, средней яркости и пространственной/временной информации. Проход ограничен 600 структурными образцами, одним потоком FFmpeg/фильтра, теми же списками разрешённых протоколов только для `file` и контейнеров, ограничением вывода процесса в 1 МиБ и не более чем 30 секундами в пределах общего прерывания/крайнего срока брокера. Он никогда не принимает из запроса команды, фильтры, пути или URL-адреса.

Структурные значения являются детерминированными данными выборки, а не результатом семантического понимания видео. По ним не определяются объекты, действия, субтитры, речь или намерения пользователя. Границы сцен и замерших интервалов формируют сегменты; доля замерших кадров, размытие, экспозиция, пространственная детализация и временные изменения влияют только на распределение существующего бюджета в 1–16 кадров. Полностью замерший сегмент ограничивается одним кадром, тогда как незамершие сегменты конкурируют за оставшийся бюджет. Когда границ больше, чем кадров, сохраняется равномерное покрытие временной шкалы, чтобы частая смена сцен в начале не могла скрыть длинный заключительный сегмент. Границы сцен, находящиеся в пределах 1-секундного разрешения анализа от границы замершего интервала, объединяются.

Отсутствующие фильтры, некорректные/пустые данные, ошибка детектора или истечение времени ограниченного предварительного анализа приводят к безопасному продолжению работы с точным применением политики равномерно распределённых средних точек. Прерывание вызывающей стороной или истечение крайнего срока брокера не приводят к такому продолжению: выполняющийся подпроцесс завершается, последующее извлечение кадров предотвращается, а приватное временное дерево удаляется в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` создаёт детерминированные реальные тестовые данные FFmpeg для оценки сокращения количества вызовов создания описаний после дедупликации, распределения бюджета при интенсивном движении, данных о размытии/экспозиции/SI-TI, частой смены сцен с длинным заключительным сегментом и ложных срабатываний при постепенном затухании. Скрипт регистрирует фактическое время предварительного анализа, а при наличии `/usr/bin/time` — процессорное время дочернего процесса и пиковый RSS. Его проверки качества представляют собой только структурные оракулы. Качество реальной модели создания описаний остаётся в состоянии `HOLD`, поскольку у этого тестового стенда нет авторизованной конечной точки или зафиксированного оценщика. Денежная экономия также остаётся в состоянии `HOLD`, если параметр `--caption-cost-per-call-usd` не задаёт явную положительную оценку стоимости одного вызова; скрипт никогда не фабрикует ни один из этих результатов.

Размер каждого кадра ограничен 4 МиБ, общий размер всех необработанных кадров — 23 МиБ, а размер сериализованного ответа брокера — 32 МиБ. Приватный временный каталог удаляется в `finally`. OmniRoute не включает FFmpeg в комплект поставки и не принимает пользовательский путь к исполняемому файлу. Перед созданием описаний мост применяет консервативный проход визуальной дедупликации: каждое изображение JPEG преобразуется в буфер оттенков серого размером 16×16 и сравнивается только с последним сохранённым кадром. Если запрошенный бюджет описаний превышает один кадр, извлечение предоставляет ограниченный пул кандидатов, размер которого не превышает удвоенный бюджет и в любом случае составляет не более 16 кадров. Запрошенное ограничение применяется только после дедупликации; при окончательном прореживании сохраняются первый и последний выбранные кандидаты, если бюджет составляет не менее двух кадров. Версионированная политика
`grayscale-16x16-mean-cells-v2` использует большее из двух значений: средней разницы яркости и доли ячеек миниатюры, нормализованная разница которых составляет не менее 0,05. Порог дубликата задан константой 0,04, выбранной ради предсказуемости, а не предоставления настройки времени выполнения. Этот дополнительный высококонтрастный сигнал сохраняет небольшие движения и изменения видимого текста, которые может скрыть сравнение только по среднему значению. Ошибки средства сравнения или декодера приводят к безопасному продолжению работы с сохранением покрытия. В метаданных вывода отдельно указываются извлечённые кандидаты, успешно использованные кадры и отброшенные визуальные дубликаты.

Явно помеченная видеочасть может запрашивать контактный лист с временными метками. Мост создаёт JPEG-сетку не более чем из 4 столбцов и 16 кадров. В каждую 512-пиксельную ячейку временная метка исходного кадра впечатывается на высококонтрастной нижней полосе, а те же временные метки сохраняются в текстовых метаданных для последующего сопоставления и аудита. Размер полного JPEG остаётся ограниченным 32 МиБ. Если `sharp` не может декодировать или скомпоновать сетку, мост возвращается к отдельным JPEG-кадрам; прерывание со стороны клиента по-прежнему распространяется на операцию создания листа.

Данные для продвижения намеренно отделены от синтетического микротеста производительности компоновки. `scripts/perf/video-bridge-contact-sheet-eval.ts` определяет версионированный по схеме стенд A/B-тестирования для реальных моделей компьютерного зрения, совместимых с OpenAI. Он измеряет сообщаемое поставщиком количество токенов, сквозную фактическую задержку (включая компоновку листа), количество вызовов модели и сохранение фактов, определённых в манифесте. Необработанные ответы модели не записываются в отчёт; сохраняются только дайджесты SHA-256 и идентификаторы совпавших фактов. Тестовый стенд не выполняет сетевые или платные вызовы модели, если не передан параметр `--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и `OMNIROUTE_API_KEY`. Без такого явно запрошенного реального запуска его машиночитаемый вердикт остаётся `HOLD`; одни лишь синтетические измерения полезной нагрузки/количества вызовов не являются основанием для продвижения.

Вызывающие стороны могут прикрепить необязательный массив `transcript.cues` к поддерживаемой видеочасти, если у них уже есть синхронизированный текст. Каждая реплика должна содержать `text`, конечный интервал `start`/`end` в пределах определённой длительности и значение `source` из списка разрешённых (`client`, `embedded` или `audio-bridge`); значение `confidence` по умолчанию равно `1` и должно оставаться в диапазоне от `0` до `1`. Полностью совпадающие реплики объединяются. OmniRoute никогда не запускает транскрипцию на основе этих метаданных: проверенные реплики копируются в описанный результат вместе с источником, уверенностью и интервалом и отображаются как недоверенные наблюдения рядом с описаниями кадров. Недопустимый текст, текст вне допустимого диапазона или текст без сведений о происхождении отклоняется, а не смешивается с потоком описаний. Оба канала транскрипта в теле запроса нормализуют предоставленные сведения о происхождении до `client`, включая самозаявленные метки `embedded` или `audio-bridge`. Только адаптер под управлением сервера может назначать эти доверенные метки через доступный лишь из кода аргумент `trustedSource`; поле JSON запроса не может передать значение этому аргументу. Текст транскрипта остаётся недоверенным содержимым, полученным из медиа, независимо от его происхождения, и никогда не должен определять авторизацию.

Опытный вызывающий код может предоставить дорожку `audioTranscript` для того же видео;
она рассматривается как текст, предоставленный клиентом, а не как подтверждение серверной транскрибации.
Механизм объединения обрабатывает визуальные и аудионаблюдения в пределах
единого срока выполнения и сигнала прерывания, упорядочивает их на общей временной шкале, сворачивает
точные дубликаты и возвращает частичный результат, если успешно обработана только одна сторона.
Недопустимый `audioTranscript` приводит к такому частичному результату — визуальное
описание сохраняется, а аудиоветвь записывает очищенный код ошибки —
вместо сбоя обработки всего видео. Доступность каждой ветви, флаг частичного результата
и очищенные коды ошибок сохраняются в описанном результате, в
метаданных защитных механизмов (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), в метаданных кеша результатов и в счётчиках
объединения моста. Стандартный путь Video Bridge не вызывает преобразование речи в текст
и не загружает вторую копию медиафайла; без явно указанной дорожки он остаётся
только видеорежимом.

**Хранение транскриптов (#12150 P1).** Это применяется автоматически всякий раз, когда
Video Bridge (который сам требует явного включения) визуализирует реплику транскрипта — отдельного
флага хранения нет. Когда запрос визуализирует любую реплику транскрипта (объявленный вызывающей стороной
`transcript` или объединённый `audioTranscript`), защитный механизм помечает его как
`videoBridgeObserved` и создаёт отредактированную теневую копию описания видео —
идентичную визуализацию, в которой произвольный текст каждой реплики заменён на
`[redacted-video-transcript]`; она создаётся путём подстановки в структурированное поле реплики
до сборки строки (а не посредством разбора плоского текста, поэтому содержимое
реплики — вредоносное или обычное, включая текст с символом `]`, например
`[inaudible]`/`[music]`, — не может сохраниться). В теле запроса, сохраняемом в журнале вызовов,
каждая производная от видео текстовая часть заменяется этой отредактированной теневой копией,
сопоставленной по равенству содержимого; привязка `fullText` повторно считывается из завершённых
данных защитного механизма перед вызовом, поэтому сопоставление остаётся успешным после того, как
последующие защитные механизмы цепочки (маскировщики персональных данных и учётных данных
с приоритетами 10/95) изменят текст описания на месте, а внедрение системной
инструкции, передачи контекста и памяти преобразует массив сообщений. Тело, отправляемое
вышестоящей модели, не изменяется. Наблюдаемый запрос также не заполняет
постоянную Memory (извлечение как из запроса, так и из ответа пропускается),
поэтому собственный ответ модели не может скопировать текст транскрипта в Memory.

**Необработанные поля видео (#12430).** Когда мост включён, а встроенная поддержка видео неизвестна или отсутствует, определённые поля `transcript`/`audioTranscript` также активируют `videoBridgeObserved`, даже после сбоя описания или достижения лимита `maxVideos`. `null` и пустые строки учитываются; отсутствующие поля и метаданные, не относящиеся к видео, — нет. В сохраняемых копиях эти поля редактируются либо запрос полностью исключается, а кеши и Memory обходятся.

В этих резервных путях допустимые реплики, предоставленные вызывающей стороной, преобразуются в поддерживаемые
части `text`/`input_text`, а не в нестандартные поля провайдера. Обе предоставленные в запросе дорожки
остаются недоверенными наблюдениями `client` с явным предупреждением о том, что видео
не было описано, а временные метки не были сверены с медиафайлом. Существующие
ограничения в 256 реплик/64 КиБ суммарно и ограничения для каждой реплики применяются к двум дорожкам вместе;
временные метки должны укладываться в 600-секундный предел брокера и в любое указанное
окно фокусировки. Недопустимые дорожки отбрасываются, а не пересылаются как произвольный текст;
допустимая соседняя дорожка всё ещё может использоваться, если не превышен их общий лимит. Пустые поля
и поля со значением `null` не добавляют текст. Этот резервный механизм не добавляет ни загрузку медиафайла, ни транскрибацию.
Поля расширения транскрипта удаляются из резервного контейнера видео и его
объектов `video_url`/`source`. Список разрешённых полей OpenAI остаётся строгим; контейнеры видео
с неизвестной встроенной поддержкой остаются доступными, а известные цели, поддерживающие только текст, сохраняют безопасные маркеры.
Структурированные отредактированные теневые копии защищают добавленный текст транскрипта, тогда как
исходный запрос, принадлежащий вызывающей стороне, остаётся неизменным. Цели со встроенной поддержкой
и отключённые мосты сохраняют существующее поведение обхода.

Дополнительные сохраняемые копии используют тот же сигнал наблюдаемого запроса. Необработанный
снимок клиентского запроса до применения защитных механизмов, ожидающий запрос в памяти и журнал
рано отклонённых запросов структурно заменяют поля транскрипта в частях видео;
строковые инструкции, синтезированные этапами конвейера и при передаче контекста, редактируются
в точке сохранения тела запроса. Сохраняемый маркер `video_content_removed`
заставляет продолжение через `previous_response_id` завершаться безопасным отказом вместо восстановления
текста, который был намеренно удалён. Если наблюдаемый запрос теряет свою
теневую копию для редактирования отдельной части до журналирования или хотя бы одна из нескольких теневых копий видео
не сопоставляется после последующих изменений запроса, сохраняемое тело запроса
полностью исключается вместо сохранения частично отредактированного транскрипта.

В наблюдаемом запросе ответ модели может цитировать любую часть
транскрипта без структурированной границы реплики. Поэтому сохраняемое в журнале вызовов
поле `responseBody` заменяется маркером исключения; подробный
артефакт конвейера (который может содержать тела вышестоящих/клиентских сообщений и фрагменты потока)
не сохраняется. Семантический кеш, кеш идемпотентности и кеш воспроизведения рассуждений обходят
операции чтения и записи для такого запроса. Запрос провайдеру и видимый клиенту
ответ остаются неизменными. Ранние байты поддержания соединения удаляются из временного
буфера, когда подробный артефакт исключается. Предупреждение Kiro о некорректном EventStream
сообщает только количество байтов полезной нагрузки, но не её содержимое и не необработанную ошибку
парсера JSON.
Это не означает, что была проведена проверка всех несвязанных диагностических данных провайдеров/плагинов;
более широкий аудит точек сохранения отслеживается в #11658.

Внутренний жизненный цикл `/api/modality-bridge/video/drilldown` представляет собой отдельный кеширующий субстрат с доступом через loopback и аутентификацией по токену. Для каждой операции также требуется канонический непрозрачный идентификатор принципала. Прежде чем производственному вызывающему компоненту будет предоставлен доступ, он должен научиться получать этот идентификатор из данных аутентифицированного арендатора и ни в коем случае не передавать значение, выбранное клиентом. Ключи кеша связывают этого принципала с каноническими идентификаторами сессии и ссылки на видео, сохраняют только ключи, полученные из них с помощью SHA-256, и ограничивают как чтение, так и удаление областью того же принципала. В каждой записи кеша хранится не более 16 производных кадров JPEG, срок хранения которых истекает через десять минут; поддерживаются ограниченные чтения с параметрами `start`/`end` и явное удаление сессии.

Для каждого принципала установлено ограничение в 16 записей и 64 МиБ канонических данных JPEG. Эти ограничения не зависят от глобального предела в 64 записи/256 МиБ: при превышении квоты принципала сначала вытесняются только наименее недавно использованные записи этого принципала, и лишь затем рассматривается глобальное вытеснение по LRU. При активности кеша просроченные записи удаляются как из учёта принципала, так и из глобального учёта, а при отмене или ошибке валидации частичная замена не фиксируется.

Кеш отклоняет неканонический Base64, избыточное дополнение, данные не в формате JPEG, повреждённые или усечённые JPEG, а также JPEG, при ограниченном полном декодировании которых с помощью `sharp` возникает предупреждение. Каждое принятое изображение повторно кодируется как канонический JPEG; ширина и высота определяются по декодированным байтам без доверия к полям вызывающей стороны, а любые завершающие полиглотные байты отбрасываются, а не сохраняются. В обе квоты засчитывается только ограниченный канонический сжатый буфер. Ограничение формата JSON при передаче учитывает накладные расходы Base64 для предельного объёма декодированных входных данных в 32 МиБ. Для каждого сохранённого производного результата записываются его проверенные формат и разрешение JPEG, политика выборки, версия алгоритма получения производного результата, время создания, вычисленный сервером хеш содержимого, хешированная родительская ссылка и хеш родительского содержимого от доверенного вызывающего компонента. Отмена проверяется между асинхронными этапами декодирования и хеширования до атомарной фиксации в кеше.

Этот этап пока не подключает к маршруту производственный компонент-поставщик и не предоставляет выбор вариантов с несколькими разрешениями. Поэтому прозрачный путь запросов Video Bridge не несёт дополнительных затрат, а получение привязанного к арендатору принципала и полный жизненный цикл FU-08 с несколькими разрешениями остаются явно обозначенной последующей работой, а не документируются как уже реализованное поведение.

Для кадров последовательно формируются подписи с помощью настроенной модели Video. Пустое переопределение Video наследует настройку Vision; если обе настройки пусты, автоматический маршрутизатор Vision выбирает эффективную модель с поддержкой обработки изображений. Успешные подписи заменяют исходную часть текстом со стабильным префиксом `[Video description:`, который также помечает текст как ненадёжное наблюдение, полученное из медиаданных, и предписывает последующим моделям не выполнять инструкции, обнаруженные в этих медиаданных. Ключи кеша подписей кадров включают байты JPEG, запрос, временную метку и эффективную модель; кешируются только успешно созданные подписи. Записи кеша сохраняют фактическую модель, успешно создавшую результат, включая резервную модель; если разные кадры были обработаны разными моделями, мост сообщает `mixed`. При попадании в кеш повторно используется идентичность этой модели-производителя, а не метка запрошенного плана маршрутизации. Кеш результатов для всего видео индексируется по всем входным данным, влияющим на результат: запросу, эффективной модели, политике выборки, количеству кадров, режиму семантического анализа, отпечатку SHA-256 нормализованной подсказки фокуса, окну фокуса, `transcript`, `audioTranscript` и флагу контактного листа. Поэтому изменение любого из этих параметров приводит к промаху кеша, а не к повторному использованию устаревшего результата. Версия политики визуальной дедупликации, порог и ограниченное число кадров-кандидатов также явно включаются в ключ и метаданные кеша результатов; следовательно, изменение политики не может привести к повторному использованию устаревшего описания всего видео. Метаданные кеша результатов v4 сохраняют режим и отпечаток, но никогда не сохраняют необработанную пользовательскую задачу. Метаданные защитного механизма сообщают как запрошенный, так и эффективный режим анализа; запрошенный режим `focused` без пригодного пользовательского текста указывается как фактически работающий в режиме `full`.

Защитный механизм извлекает все поддерживаемые части видео, но описывает не более `modalityBridgeVideoMaxVideos`. Для целевого объекта, про который доказано, что `supportsVideo === false`, неудачно обработанные и превышающие лимит видео преобразуются в явные безопасные текстовые маркеры, чтобы необработанное видео нигде не сохранялось. Если возможности неизвестны, такие части сохраняют свой контейнер видео; любая резервная транскрипция проходит описанное выше ограниченное преобразование в текст. Целевые объекты с `supportsVideo === true` обходят мост. Сигнал отмены клиентского запроса распространяется на загрузку, очередь брокера, подпроцессы и вызовы формирования подписей; отмена останавливает обработку между видео и никогда не приводит к небезопасному пропуску необработанных медиаданных.

Параметры среды выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                                | Значение по умолчанию | Диапазон / поведение                                                                                                       |
| ----------------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`               | Необязательная среда выполнения, включаемая явно                                                                           |
| `modalityBridgeVideoAnalysisMode`   | `"full"`              | `full` сохраняет общие описания; `focused` использует ограниченный недоверенный контекст последнего сообщения пользователя |
| `modalityBridgeVideoModel`          | `""`                  | Наследует модель Vision Bridge                                                                                             |
| `modalityBridgeVideoFrameCount`     | `8`                   | 1–16                                                                                                                       |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`           | `uniform`, `scene_aware` или пропорциональный `segment_aware`; при сбое детектора используется `uniform`                   |
| `modalityBridgeVideoMaxVideos`      | `1`                   | 1–4                                                                                                                        |
| `modalityBridgeVideoTimeout`        | `120000`              | 1000–120000 мс                                                                                                             |

Сохранённые устаревшие значения тайм-аута Video свыше 120 секунд ограничиваются
предельным сроком брокера; новые настройки со значениями выше этого предела
отклоняются. `GET /api/modality-bridge/video/runtime` перед аутентификацией или
проверкой среды выполнения требует подтверждённой доверенной меткой локального
loopback-подключения, а затем — управленческой авторизации. Он возвращает только
`available`, очищенные версии FFmpeg/ffprobe и фиксированную причину
недоступности среды выполнения. Внутренняя конечная точка извлечения не является
публичным API для загрузки: переполнение очереди возвращает `503` вместе с
`Retry-After`, отключение вызывающей стороны — `499`, а истечение фиксированного
предельного срока брокера — `504`. Преобразованные ответы добавляют
`video->text;model=<visionModel>;parts=<videos>` в центральный заголовок
`x-omniroute-modality-bridge`, не удаляя сегменты Vision или Audio.

### Маскировщик PII (`piiMasker.ts`)

Выполняется на **обоих** этапах.

- **`preCall`** клонирует полезную нагрузку, обходит `system`, `messages`, `input`
  и `prompt` (включая элементы в виде простых строк) и применяет `processPII()`
  (из `@/shared/utils/inputSanitizer`) к строковым полям `content`/`text`. Когда
  `PII_REDACTION_ENABLED=true`, обнаруженные PII редактируются в исходящей
  полезной нагрузке. Это не зависит от `INPUT_SANITIZER_MODE` (который управляет
  только политикой в отношении инъекций в промпты). Когда редактирование
  отключено, вызов регистрирует количество обнаружений, не изменяя содержимое.
- **`postCall`** создаёт глубокую копию ответа, запускает `sanitizePIIResponse()`
  вместе с маскировщиком структуры Responses API (`maskResponsesOutput` —
  охватывает `output_text` и `output[].content[].text`). Если происходит
  какое-либо редактирование, изменённый ответ заменяет исходный.

Защитный механизм никогда не блокирует; он лишь добавляет аннотации
(`meta.detections`, `meta.redacted`) или изменяет данные.

### Инъекция в промпт (`promptInjection.ts`)

Обнаруживает вредоносные структуры в предоставленном пользователем содержимом и
применяет настроенную политику. Поведение определяется переменными окружения и
параметрами конструктора:

| Настройка        | Переменная окружения                                                                                        | По умолчанию | Эффект                                                                                                                                                                                                       |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Включено         | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`       | При значении `false` защитный механизм немедленно завершает работу.                                                                                                                                          |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`       | Политика обработки инъекций: `block`, `warn` или `log`. (`redact` поддерживается для обратной совместимости, но **не** удаляет текст инъекции; изменение PII в запросе управляется `PII_REDACTION_ENABLED`.) |
| Порог блокировки | параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдоним `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | Минимальная степень серьёзности, необходимая для блокировки. При значении по умолчанию средняя степень используется только для наблюдения.                                                                   |

**Приоритет режима** (`getMode`): `options.mode` вызывающей стороны →
**переопределение флага функции из БД** для `INJECTION_GUARD_MODE` (Dashboard →
Settings → Feature Flags) → переменная окружения `INJECTION_GUARD_MODE` →
переменная окружения `INPUT_SANITIZER_MODE` → `warn`. Таким образом,
переопределение через панель управления имеет приоритет над переменными
окружения, поэтому интерфейс Feature Flags управляет работающим защитным
механизмом в реальном времени (без перезапуска). Чтение из БД отказоустойчиво:
при ошибке защитный механизм возвращается к поведению на основе переменных
окружения, а если переопределение не задано, поведение идентично разрешению
только через переменные окружения.

Источники обнаружения:

1. `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий набор
   детекторов, используемый в других частях конвейера).
2. Встроенные `DEFAULT_GUARD_PATTERNS` (в настоящее время
   `system_override_inline` и `markdown_system_block`, оба со степенью
   серьёзности `high`).
3. Необязательные `customPatterns`, передаваемые через параметры конструктора
   (строки, регулярные выражения или записи
   `{ name, pattern, severity }`).

Когда `mode === "block"` **и** хотя бы одно обнаружение соответствует порогу
серьёзности, `preCall` возвращает `{ block: true, message: "Request rejected:
suspicious content detected" }`. В режимах `warn`/`log` защитный механизм
записывает событие в журнал, но разрешает вызов. Общий вспомогательный метод
`evaluatePromptInjection()` также экспортируется для вызывающего кода, которому
необходимо проверять промпты без использования реестра.

**Ограничение сканирования (v3.8.20):** детектор проверяет только **первые 16 КБ**
объединённого текста промпта — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384
байта) в `src/shared/utils/inputSanitizer.ts`. И `detectInjection()`, и
`evaluatePromptInjection()` вызывают `slice(0, MAX_INJECTION_SCAN_BYTES)` перед
запуском цикла проверки шаблонов. Директивы инъекций располагаются в начале
входных данных, поэтому такое ограничение снижает нагрузку регулярных выражений
на ЦП и сборщик мусора для полезных нагрузок размером в сотни КБ без ухудшения
обнаружения (см. #3932, #4041).

### Маскирование учётных данных (`credentialMasker.ts`)

Выполняется на **обоих** этапах и является последним в цепочке по умолчанию
(приоритет `95`). Маскирует известные шаблоны API-ключей и секретных токенов в
исходящей полезной нагрузке (содержимом сообщений, аргументах вызовов
инструментов, результатах работы инструментов), **а также** в ответе провайдера,
чтобы учётные данные, вставленные в промпт (или возвращённые в результате работы
инструмента), не передавались внешнему провайдеру или обратно клиенту.

- **Только явное включение**, по тому же принципу, что и редактирование
  персональных данных (смежно с жёстким правилом №20): отключено, если только
  `settings.credentialRedactionEnabled === true` **или**
  `CREDENTIAL_REDACTION_ENABLED=true`. Когда функция отключена, защитный
  механизм ничего не делает — он никогда не блокирует и не изменяет данные.
- `redactCredentials()` обходит всё дерево полезной нагрузки/ответа
  (`walkValue()`, с защитой от загрязнения прототипа и циклов посредством
  `WeakSet`) и заменяет совпадения заполнителем `[REDACTED:<type>]`, клонируя
  только те ветви, которые фактически изменились.
- `CREDENTIAL_PATTERNS` охватывает ключи провайдеров LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токены VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платёжные ключи (Stripe, Square),
  облачные ключи (ключ доступа AWS, Twilio, SendGrid, Mailgun), закрытые ключи /
  JWT, строки подключения, содержащие учётные данные
  (`mongodb://user:pass@...` и т. п.), а также универсальный шаблон значений
  заголовков `Authorization`/`x-api-key`/`api-key`/`apikey`. Ключи, имеющие
  форму заголовков (`authorization`, `x-api-key`, `api-key`, `apikey`),
  редактируются структурно (только значение, с сохранением префикса схемы,
  например `Bearer `/`Basic `), а не посредством универсального текстового
  регулярного выражения.
- Защитный механизм никогда не блокирует; он только изменяет данные
  (`modifiedPayload` / `modifiedResponse`) и добавляет аннотации
  (`meta.credentialsRedacted`, `meta.count`).

Защита от регрессий: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // значение true прерывает цепочку
  message?: string; // отображается при блокировке
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // возвращается методом preCall для изменения запроса
  modifiedResponse?: TValue; // возвращается методом postCall для изменения ответа
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Защитный механизм сообщает об отсутствии изменений, возвращая `void`, `{}` или
`{ block: false }`. Возврат `modifiedPayload`/`modifiedResponse` заменяет
значение, передаваемое по цепочке последующим защитным механизмам.
`signal?: AbortSignal` передаёт жизненный цикл вызывающей стороны защитным механизмам. Прерывание запроса является намеренным исключением из принципа fail-open: медиамосты прекращают работу и выполняют очистку, не восстанавливая необработанные медиаданные для целевой системы, которая заведомо их не поддерживает.

## Реестр (`registry.ts`)

Синглтон `guardrailRegistry` предоставляет:

- `register(guardrail)` — добавляет (или заменяет по нормализованному имени) защитный механизм и
  повторно сортирует по возрастанию `priority`.
- `clear()` / `list()` — вспомогательные функции администрирования.
- `runPreCallHooks(payload, context)` — итерирует активные защитные механизмы, пропускает
  полезную нагрузку через `modifiedPayload` и останавливается на первом `block: true`.
- `runPostCallHooks(response, context)` — тот же поток на стороне ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и опционально
  повторно регистрирует значения по умолчанию для чистой изоляции тестов.

Оба запускатора возвращают `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` — это массив записей `GuardrailExecutionResult`, которые включают
поля `blocked`, `skipped`, `modified`, `error` и `meta` для каждого защитного механизма,
полезные для трассировки.

### Отключение защитных механизмов для каждого запроса

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегирует
дедуплицированный список имен защитных механизмов, которые должны быть пропущены для текущего
запроса. Источники (все опциональные, все объединенные):

- `apiKeyInfo.disabledGuardrails`
- Тело запроса `disabledGuardrails` (верхний уровень)
- Тело запроса `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (или устаревший
  `x-disabled-guardrails`)

Значения могут быть массивами строк или строкой, разделенной запятыми; имена
нормализуются в нижний регистр kebab-case (`pii_masker` → `pii-masker`). Результат
передается через `context.disabledGuardrails` в реестр, который пропускает
соответствующие защитные механизмы (`skipped: true` в `results`).

## Порядок выполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` формирует список исключений из ключа API, тела запроса
    и заголовков.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускает защитные механизмы в порядке
    возрастания приоритета:
    - Отключенные защитные механизмы записываются как `skipped`.
    - Метод `preCall` каждого защитного механизма может переписывать полезную нагрузку через `modifiedPayload`.
    - Первый `block: true` прерывает цепочку, и обработчик возвращает
      ответ об отклонении защитным механизмом.
3.  (Потенциально переписанная) полезная нагрузка поступает в комбинированную маршрутизацию и
    диспетчеризацию вышестоящему сервису.
4.  После сборки ответа `guardrailRegistry.runPostCallHooks(...)`
    запускает ту же цепочку для ответа. `block: true` здесь отбрасывает
    ответ вышестоящего сервиса.

Защитные механизмы, которые выбрасывают исключения, записываются с `error: <message>` и
логируются через `logger.warn`, но цепочка продолжается — по замыслу, система
открыта к сбоям.

## Конфигурация

Переменные окружения, считываемые встроенными защитными механизмами:

| Переменная                            | Используется                  | Эффект                                                                                                                 |
| :------------------------------------ | :---------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`            | Установите `false`, чтобы полностью отключить обнаружение.                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`            | Политика инъекций: `warn`, `block` или `log`. Устаревшее значение `redact` не переписывает текст инъекции.             |
| `INJECTION_GUARD_MODE`                | `prompt-injection`            | Режим для защиты от инъекций; также флаг функции БД, который **переопределяет** переменные окружения (БД > ОКРУЖЕНИЕ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`            | Минимальная серьезность, при которой `MODE=block` отклоняет: `high` (по умолчанию), `medium` или `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`            | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`                  | Если `true`, PII запроса скрывается (независимо от режима инъекции).                                                   |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ниже по потоку) | Управляет поведением маскировщика на стороне ответа.                                                                   |

Защитные механизмы Modality Bridge считывают конфигурацию времени выполнения из хранилища настроек,
поддерживаемого БД (`getSettings()`), а не из переменных окружения. Основные ключи Vision:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и
`modalityBridgeCacheMaxEntries`. Устаревшие ключи
`visionBridge*` принимаются только в качестве документированного одноциклового
резервного чтения; записи с панели управления используют основные ключи. Значения по умолчанию и
резервный резолвер находятся в `src/shared/constants/modalityBridgeDefaults.ts`,
при этом устаревшие константы сохранены в `src/shared/constants/visionBridgeDefaults.ts`.

Аудио использует `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие
настройки `modalityBridgeCache*`. У Аудио нет резервного варианта для устаревших ключей,
поскольку эти ключи были введены со схемой Modality Bridge.

Видео использует `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` и
`modalityBridgeVideoTimeout`, а также общие настройки `modalityBridgeCache*`.
По умолчанию оно отключено, поскольку FFmpeg/ffprobe являются необязательными
операционными зависимостями, а создание подписей к кадрам увеличивает задержку и
стоимость модели.

## Пользовательские Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1.  Создайте `src/lib/guardrails/myGuardrail.ts`, расширяющий `BaseGuardrail`.
2.  Реализуйте `preCall` и/или `postCall`.
3.  Либо зарегистрируйте во время импорта (push из `registerDefaultGuardrails`), либо
    вызовите `guardrailRegistry.register(...)` во время выполнения — реестр заменяет
    любой предыдущий guardrail с тем же нормализованным именем.
4.  Добавьте тесты в `tests/unit/` (существующие примеры:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестирование

Используйте `resetGuardrailsForTests()` между тестами, чтобы начать с известного состояния.
Передайте `{ registerDefaults: false }`, чтобы начать с пустого реестра и
зарегистрировать только тестируемые guardrails. Vision Bridge принимает внедрение зависимостей
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge предоставляет эквивалентные точки расширения
для настроек, возможностей, выбора модели STT, проверки учетных данных и транскрипции.
Таким образом, тесты могут проверять оба потока без доступа к БД или сети.

## Покрытие маршрутов защитой от инъекций и red-team (Фаза 8 · Блок D)

Защита от инъекций (`createInjectionGuard` / `withInjectionGuard`) охватывает все маршруты,
которые принимают пользовательские промпты. Она учитывает `INJECTION_GUARD_MODE` (по умолчанию `warn` = только логирование;
`block` = возвращает HTTP 400 `SECURITY_001`).

| Тип                  | Маршруты                                                                                                                                             | Режим по умолчанию |
| :------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------- |
| Текст (существующий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративный         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные               | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) охватывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (ночной, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут блокирует
корпус OWASP-LLM в режиме `INJECTION_GUARD_MODE=block`; garak запускает зонды (пропускает без секрета).
`moderations` включен для согласованности — операторы в режиме блокировки могут исключить его через
`resolveDisabledGuardrails`.

Ночной рабочий процесс (`.github/workflows/nightly-llm-security.yml`, cron + ручной
запуск) состоит из двух задач:

- **`promptfoo-guard` (блокирующий)** — запускает `promptfoo eval -c promptfooconfig.yaml`
  с `INJECTION_GUARD_MODE=block`. Каждый adversarial-кейс (например, "игнорировать все
  предыдущие инструкции...", джейлбрейки в стиле DAN) подтверждает, что ответ содержит
  `error.code === "SECURITY_001"`, то есть защита фактически отклонила запрос.
- **`garak` (консультативный)** — запускает garak `--probes promptinject,dan,leakreplay`
  против локального экземпляра OmniRoute (`http://localhost:20128/v1`). Ограничен
  секретом провайдера (`PROMPTFOO_PROVIDER_KEY`); корректно пропускается и имеет суффикс
  `|| true`, поэтому он сообщает о результатах, не приводя к сбою CI.

Покрытие вспомогательной функции защиты (`createInjectionGuard` / `withInjectionGuard`)
охватывает каждый маршрут `/v1`, содержащий промпты; текст промпта извлекается из
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` с помощью
`extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
